## 1. 这个项目的 SFT 到底想让模型学会什么

TravelAgent 的核心训练任务不是背诵旅游攻略，也不是直接模仿一整篇漂亮行程。学生模型在统一 Agent Loop 中，需要根据当前状态选择下一步动作，并生成属于模型权限范围的参数。

可以把每个决策写成：

~~~text
输入 x：
用户目标与约束
+ 当前可见事实、证据和工具产物
+ 当前进度、失败反馈与剩余预算
+ 允许使用的动作及其 schema

目标 y：
一个经过审核的 assistant 工具调用
= 动作名称 + 模型拥有的参数 + 完整结束边界
~~~

例如，模型应学会：

- 缺少营业时间时去查事实，而不是编造。
- 候选已更新时补充新候选的详情和路线证据。
- 已有证据时避免重复执行同样查询。
- 证据充分后进入求解与验证。
- 需求缺失时问用户，事实证明不可行时合理停止。
- 从工具错误、空结果或预算接近耗尽的状态继续处理。

这些决策会改变随后模型看到的状态。因此单步工具名准确率不足以代表整个 Agent 成功率；最终仍要把学生放回同一执行环境里完整运行。

### 1.1 参数训练、工程约束和检索各管一部分

| 手段 | 在本项目中的职责 | 不应冒领的效果 |
|---|---|---|
| SFT | 提高正确动作在对应状态下被生成的概率 | 不直接修复数据库、队列或工具实现 |
| Harness | 约束权限、校验前置条件、管理预算和提交 | 不把代码替模型作出的决策记成模型能力 |
| 工具 / 检索 | 提供事实、候选、路线和外部结果 | 不保证模型一定知道何时调用 |
| 求解器 / Validator | 排程并检查约束 | 不等于模型理解了所有失败原因 |
| Prompt / 格式约束 | 定义输入和输出合同，减少格式错误 | 配置改动收益不能全部算到 SFT |

第四篇中“通知异常却提前发送 done”属于工程错误，再加一千条教师示范也不能从根本上修复。训练前先定位错误层次，是这套后训练路线的重要部分。

## 2. 先分清版本：仓库里不止一种训练历史

仓库保留旧阶段控制器、原生 ReAct、统一 Harness 等时期的代码与实验资料。它们可能使用不同动作、状态结构、模型起点和判分规则。

本篇以当前统一 Loop 的数据契约解释实现，并把历史结果按实验分开。不能把旧控制器时期的“只有一个合法工具”当成当前自主多工具决策，也不能把旧 GRPO 资产当作最新架构已完成的 RL 结果。

### 2.1 三种“基线模型”不能混称基模

| 名称 | 本篇含义 |
|---|---|
| Qwen3-4B 基础权重 | 预训练 / 指令模型的基础参数，具体版本由实验清单固定 |
| 早期初始学生适配器 | 正式教师示范与接续对照的共同起点；已经是带适配器的学生 |
| 后续保留原模型 repair_sft_lowlr | 经后续低学习率修复后保留的模型，是最新 SFT / DPO 对照的起点 |

早期 21.7% 是那轮初始学生适配器的结果，不能写成“裸 Qwen3-4B 的统一基线”。最新 95% 也不是同一批题上的同一模型。

同样，“从已有 Adapter 继续训练”意味着继承此前参数学习，不是把该轮新加入的 512 行当作模型全部训练经历。

### 2.2 当前训练入口也有不同用途

- ml/training 下有历史训练示例，不能当成当前 Agent Policy 主数据来源。
- ml/agentic/training/train_sft.py 是通用 TRL + PEFT 训练入口，默认参数也保留历史配置。
- train_matched_source_pilot.py 是为早期来源匹配试验写的专用训练器。
- 最新成功轨迹 / DPO 的云端实验有独立冻结 train.py 和 training-plan.json；本地全景说明记录了路径，但本次没有读取该云端脚本。

所以不能看到通用脚本默认模型是 Qwen2.5-3B，就推断最新训练也使用它；也不能把专用 BF16 LoRA 试验一律叫成 QLoRA。

## 3. 数据规模怎么数：任务、轨迹、动作、使用次数和 Token

“有多少数据”至少有五种答案。简历和面试中最容易犯的错误，就是用最大那个数字替代所有口径。

~~~text
来源组 / 模板族
    └─ 任务实例
         └─ 多个采样轨迹
              └─ 多个决策状态—动作
                   └─ 训练日程中的一次或多次使用
                        └─ 输入 Token 与监督 Token
~~~

一个任务运行 4 次，产生 4 条轨迹，但仍只对应一个任务实例；一条轨迹有 10 个动作，不能算成 10 条完整旅行任务；为了匹配训练预算重复某个动作，也不增加独立数据量。

### 3.2 这些数字怎样体现工程价值

价值主要来自来源可追溯、标签来自执行、状态隔离、监督预算匹配和失败保留，而不是把规模说成百万级。

原先 2,000—5,000 个独立 train 任务等规模目标是建设目标，不是已经完成的事实，也不是“大厂社招 80 分”的统一标准。当前应如实展示已有独立来源数、覆盖类型和验收范围。

## 4. 为什么六千多条旧数据不能直接拿来训练

2026-09-05 的审核结论是：原生 205 个动作可继续使用；六批旧 train 共 6,624 行，全部禁止原样混入 v9。保留旧文件作为迁移素材，并没有删除。

### 4.1 问题一：旧环境替模型做了太多选择

某些旧样本只暴露一个工具，模型只需填参数即可。“答案工具正确”可能主要由控制器事先决定。

当前统一 Loop 需要在多个动作中判断下一步。这两种学习问题不同，改字段名不会凭空补上缺失的决策过程。

### 4.2 问题二：目标包含当前不属于模型的权限

旧数据中有被移除的动作，以及让模型直接写 propose_tradeoff.options 的条目。当前权衡候选应由 Harness 按真实约束和授权生成，模型不能自行创造可选方案。

旧样本若直接混入，会教模型越过现在的权限边界。将旧动作简单改名也不能证明对应操作曾在新环境中正确执行。

### 4.3 问题三：跨版本来源重合

审核记录了跨版本 train 与 validation / test 提示重合，以及旧派生版本的拆分调整。它提示不能任意拼接各版本 train，再继续沿用其中某个旧 test 声称隔离。

这属于跨版本污染风险，不等于每个历史实验在各自定义的拆分内都一定泄漏。面试需要保持这个区分。

### 4.4 合理复用的是请求素材，不是未经核对的答案

处理流程应是：

~~~text
旧请求 / 约束 / 偏好
  → 来源和留出重合审核
  → 新环境重建事实、候选和工具状态
  → 预检任务是否可执行
  → 学生自主运行或教师示范 / 接续
  → 新协议下审核和导出
~~~

3,612 个迁移候选请求仍标记 training_ready=false，不能直接写成 3,612 条高质量 SFT。

这件事适合面试讲“为什么没有只追求数据量”：接收协议不兼容数据，可能比少训练一些更糟。

## 5. 场景环境：执行过工具，不等于使用了实时真实世界事实

当前研究数据包含可控制、可复现的旅行场景和工具 fixture。它们可以真实执行工具代码、求解器与验证器，同时使用冻结或合成的 POI、日期、预算和故障条件。

两个概念必须拆开：

- 执行真实性：动作实际经过执行器、产生观察与约束结果。
- 外部事实真实性：数据是否来自真实、及时、可授权使用的供应商信息。

一条合成场景经过真实 CP-SAT 求解，可以用于策略训练；但它不能被描述成真实用户在线旅行履约记录。

### 5.1 为什么先检查任务环境

若训练任务本身缺少必要事实、餐厅只是占位符、必须 POI 永远不可达，模型失败未必说明决策能力不足。

先做可行性和工具契约检查，可以区分：

- 环境本身不可满足。
- 环境可满足，但模型没有找到正确路线。
- 用户应当被追问或明确告知不可行。
- 基础设施出错，无法判断模型表现。

预检过程由脚本执行，不是学生模型自主决策，不应导出为学生能力标签。

### 5.2 质量门槛依任务类型而异

evaluate_harness_base.py 对 plan、clarify、grounded_stop 有不同判据。规划不仅要有行程，还要按合同提交并具备对应验证；澄清要问到缺失信息；停止需要有事实依据。

命名餐厅 curriculum 还增加软偏好和故障相关质量检查。不能把某个局部版本的 preference_match 阈值称为整个项目所有阶段的统一严格质量定义。当前基础判分对澄清使用缺失字段对应的词语匹配等规则，这也不是全面的自然语言语义理解；验收器的覆盖范围同样需要单列。

## 6. 三类监督来源：教师示范、教师接续与学生成功轨迹

| 来源 | 起始状态 | 标签提供者 | 主要覆盖 |
|---|---|---|---|
| 教师从头示范 | 新任务初始状态 | GLM-5.3-Flash | 理想规划路径、工具组织 |
| 教师在学生状态接续 | 学生实际达到的中间状态及 provider 快照 | GLM-5.3-Flash | 学生分布中的困难状态、恢复与续跑 |
| 学生成功轨迹筛选 | 学生自主 rollout 的各决策状态 | 学生自己，经过审核 | 已能成功执行的行为及稳定模式 |

三类来源都可以转成监督微调数据，只要最终训练目标是给定输入下拟合审核后的动作。

### 6.1 为什么教师从头生成可能不够

教师能力较强，可能很少进入“已经重复查了三次、预算不多、证据只补了一半”的状态。学生即使模仿教师理想轨迹，也可能在自主运行中偏离，从而面对训练数据里没有见过的状态。

让教师在学生实际状态下接续，直接针对这种状态分布差异补监督。这与 DAgger 在学习者访问状态上查询专家的动机相关，但本项目的有限批次接续不能自动等同于完整 DAgger 算法及其保证。[DAgger 原论文](https://proceedings.mlr.press/v15/ross11a.html)。

### 6.2 “接续”不必然是“纠错”

扩大配对阶段 252 个起点中，140 个断点步骤有记录错误或策略修复信号，112 个前缀没有这些记录。即便出现过错误，也还应区分是否已解决、当前是否仍需修复。

更准确的用词是“学生状态下的教师接续”，再按未解决错误、已恢复前缀、普通中途状态细分。不能把所有接续动作都宣传成针对失败的反事实纠错。

### 6.3 教师 Token、教师 reasoning 与监督 Token 不同

API 计费可能包含教师的输出或思考 Token，但训练并不因此把这些内容全部当标签。

本项目目标是完整模型动作，不是教师私有思考文本。教师付费成本、生成总量、审核后标签量和最终训练使用量要分别记账。

## 7. 教师怎样从学生状态接手

以 collect_paired_teacher.py 的小批配对实现为例：先要求学生采集完成且来源属于 train，再从真实 state-after 快照中挑非终止、仍有执行预算的起点。

选择规则会优先考虑重复无进展、部分错误或相关工具之后的状态，但这份脚本限定了特定 20 任务 pilot，不能当作所有后续批次完全相同的选择器。

### 7.1 恢复的不只是聊天文本

接续需要恢复：

- Ledger 与目标 / 计划版本。
- 已执行动作和剩余预算。
- 已有工具调用记录。
- Provider 内部状态与故障进度。
- 学生源轨迹和断点快照的哈希。

同一段用户消息，在不同工具缓存或故障状态下，正确下一步可能不同。只复制提示文本，无法证明教师接触到了学生真正面对的环境。

### 7.2 时间预算调整要公开记录

该脚本会调整接续的 timeout_ms，让教师获得新的执行时间窗口，同时记录 changed_initial_fields。审计时明确排除这一已声明变化，再核对其他初始状态和 provider 前缀。

因此不能把它称为“所有资源条件完全不变的原状态接手”。可以说业务状态和已执行工具前缀保留，时间预算调整被显式记录。

### 7.3 原始请求与导出输入如何对齐

audit_paired_teacher.py 会核对实际 API 请求、策略上下文、原始动作、模型参数和源快照。教师额外使用的固定单调用提醒也单独记录：它应只约束协议，不应包含下一步答案或隐藏事实。

自修复可能在同一动作尝试中加入 policy_feedback。若直接用修复后的答案配上修复前输入，就会形成错误的训练对。配对导出器因此排除 repair_attempts > 0 的相应目标；轨迹本身仍保留，供分析。

关键不是“答案看起来正确”，而是“这个答案确实是在这份可见输入下产生，并在这份环境里执行”。

源码：[教师配对采集](E:/A_Louis/TravelAgent2/scripts/collect_paired_teacher.py)、[配对审核](E:/A_Louis/TravelAgent2/scripts/audit_paired_teacher.py)。

## 8. 轨迹记录：从一个动作追溯到什么证据

AgentEpisode 记录环境版本、验证器版本、策略身份、初始状态、步骤、事件、最终状态、终止原因和内容哈希。TrajectoryStep 记录模型上下文、动作、观察、验证信息、前后状态哈希及时间。

动作结构还区分模型原始参数、执行时参数和控制器补全信息。这让数据审核能够回答：“这个 POI ID 是模型提出的，还是系统按当前状态补进去的？”

### 8.1 一份有用的训练证据包

~~~text
cases.json / manifest.json         任务与实验身份
episode.json                      执行轨迹
model-calls.jsonl                  模型实际请求与返回
tool-calls.json                    实际工具调用
state-after-xxx.json               中间状态与 provider 快照
summary.json                      该轨迹的任务及质量统计
provenance.json                    学生断点、教师模式与来源链
reviews.jsonl / audit.json         接受、拒绝和审核理由
train.jsonl                       最后导出的监督样本
~~~

这些文件不是越多越好，而是应能互相校验。某个目标要追溯到源轨迹、具体 step 和真实模型返回，不能仅有一张“审核通过”的汇总表。

### 8.2 哈希检查能证明什么

EpisodeReplayVerifier 会检查轨迹 ID、任务关联、动作是否属于允许集合、终态信息与内容哈希；在带计数合同的轨迹上，还会调用相应 accounting 校验。

它主要证明记录结构和完整性符合协议，**不等于重新执行了所有工具，也不等于证明事实正确**。如果最初记录的事实就是错的，哈希完全一致仍然是错的。

要证明训练价值，还要加原状态恢复、工具执行证据、任务验收和独立约束检查。面试时应避免把名字里的 Replay 解释成“所有步骤都已重新运行”。

源码：[轨迹模型与完整性校验](E:/A_Louis/TravelAgent2/backend/src/agentic/trajectory.py)。

## 9. 分层审核：任务成功后，为什么还有样本被拒绝

当前 SFTDatasetBuilder 的审核可以按三个层次理解：

| 层 | 代表性检查 | 目的 |
|---|---|---|
| L1 记录和来源 | 完结、内容哈希、步数、缺失状态、PII、生产授权 | 避免使用不完整、来源不明或不合规记录 |
| L2 动作和执行 | 动作合法、参数权限、grounding、工具观察、调用 ID、重试次数 | 确保学习的是有依据且实际可执行的动作 |
| L3 终态质量 | 可验证行程、必要澄清或合理终止 | 不把失败或无效终点当成好示范 |

专用导出器还会增加独立判分、原始目录约束检查、provider 错误、计数一致性和源调用核验。通用 Builder 的通过条件不能替代每批特定数据合同。

### 9.1 一条轨迹通过，是否所有动作都能训练

不能。_examples 还会逐步排除：

- decision_source=controller 的动作。
- 没有满足步骤成功判定的动作。
- 已经成功执行过的重复调用。
- 专用导出器禁止的修复尝试或其他不可信目标。

因此最新采集中 220 条严格质量通过，最终只有 174 条轨迹被导出器接受，并不必然矛盾。一个指标看最终任务，另一个还要求监督来源和动作结构可用。

本次没有重新取得该批逐条拒绝清单，因此不会替那 46 条差额编造具体原因。

### 9.2 工具前置拒绝不能伪装成工具执行成功

例如模型提前调用 solve_itinerary，但 Harness 因证据不足拒绝，根本没有调用 provider。轨迹应该保留这次尝试，帮助分析模型错误；但不应为了满足“每步都有 observation”给它伪造工具返回。

export_harness_sft.py 为明确记录的前置拒绝处理了结构例外，同时确保这类未执行步骤不进入目标集合，保留后续经过验证的恢复步骤。

例外必须精确限定，不能把所有缺失 observation 的步骤都放过。

### 9.3 去重需要看实际执行参数

某些动作的模型参数是空对象，系统会根据当前状态补入不同实体。仅按工具名 + {} 去重，可能错误地把两次不同来源的有效动作当成重复。

配对审核使用模型参数、目标 / 计划版本和 executed_arguments 组成执行签名，区分当前真实输入不同的调用。

另一方面，重复使用同一动作做匹配训练，并不新增数据；需要在训练日程里记录使用次数，不能偷偷复制后再报更大的唯一行数。

### 9.4 自动规则还有边界

PII 正则、grounding 检查和质量规则只能覆盖所实现的模式。它们不是“所有隐私已被完美识别”或“所有旅游事实都已逐条人工审核”的证明。

实际扩大到真实用户数据时，还应补来源授权、人工抽样、异常分层和规则外错误分析。这里是后续验收建议，本次没有导入真实用户数据。

## 10. 一行训练数据长什么样

当前导出的样本带 example_id、scenario_id、trajectory_id、step_index、split、quality_label、source、environment_version 和 policy_version 等元数据。

模型可见部分主要是系统提示、当前策略状态和动作 schema；最后一条 assistant 消息是一个原生工具调用。

下面是省略字段的示意，不是从某条训练样本复制的真实记录：

~~~json
{
  "example_id": "train-case:episode-hash:step",
  "split": "train",
  "source": "teacher",
  "messages": [
    {"role": "system", "content": "版本化 Agent 策略提示"},
    {"role": "user", "content": "当前可见状态的规范化 JSON"},
    {
      "role": "assistant",
      "tool_calls": [{
        "function": {
          "name": "search_pois",
          "arguments": {"keywords": "适合慢节奏游览的博物馆"}
        }
      }]
    }
  ],
  "tools": ["此处省略真实工具 schema"]
}
~~~

tools 在真实数据中是结构化 schema，上例字符串只是说明占位，不是可直接投入训练的合法完整样本。

### 10.1 目标只能包含模型拥有的参数

SFT 导出调用 project_model_owned_arguments，将模型决策与可信执行参数分开。POI 集、约束、距离矩阵、完整行程等系统持有字段，不应作为模型需要学着生成的答案。

例如 solve_itinerary 的执行器可能需要完整候选和矩阵，但模型目标不应因此把整张矩阵抄一遍。否则既扩大监督长度，也鼓励模型捏造本应由工具提供的数据。

### 10.2 空参数对象要保留

arguments: {} 可能是合法且有意义的目标。如果序列化时用 exclude_defaults=True 把它删掉，聊天模板可能无法正确处理该工具调用。

training.py 特别保留空参数对象。这个细节适合解释“数据不是 JSON 看起来能读就算通过”：还必须经过真实 tokenizer、模板和 parser。

### 10.3 当前状态快照不等于完整对话轨迹标签

一条样本通常监督一步，而不是把从头到尾所有消息全部作为待预测答案。历史动作、工具反馈和证据可能出现在状态投影中，提供条件，但不因此都成为监督目标。

这减少了不相关的模仿目标，也明确了模型要学的是当前状态下的下一步决策。

## 11. Chat Template 与 Mask：怎样保证训练没有学错位置

训练脚本先把 conversational 数据分成 prompt 和最后一个 assistant completion，再使用版本固定的模板分别渲染 prompt 与完整消息。

它要求：

~~~text
full_text 必须以 prompt_text 为前缀
completion_text = full_text 去掉 prompt_text 后的完整后缀
~~~

随后还要检查 Token 级前缀是否一致。字符前缀成立，不代表分词边界一定自动一致；实际 audit 会核对训练器预处理后的 input_ids。

### 11.1 为什么先渲染成字符串再交给 Dataset

不同工具的 arguments 字段结构不同。若直接让 Arrow 推断嵌套结构，可能把不同动作字段合并，为某些目标加入原本没有的 null 键。

training.py 先将 prompt / completion 渲染成标量字符串，以保留规范的工具调用形状，再进入后续训练预处理。这不是简单格式美化，而是防止存储层改变模型目标。

### 11.2 真正的标签掩码

简化例子：

~~~text
input_ids : [系统和状态……][工具调用答案……][EOS][PAD]
labels    : [-100……     ][答案 token……  ][EOS][-100]
attention : [1……        ][1……           ][1]  [0]
~~~

- prompt、工具观察和 padding 不参与目标损失。
- 完整工具调用参与监督，包括合法的动作名称、参数和结束符。
- 单个有效 EOS 被监督，避免模型只学会开始工具调用却不会完整结束。
- 教师私有 reasoning 不进入目标。
- 学生前缀用于提供接续环境，不作为教师监督答案。

### 11.3 不只检查配置开关，还检查真正的 Collator 输出

train_sft.py 的 audit_trainer_completion_masks 检查实际训练 / 验证 dataset 和 collator：

1. 渲染后的 token 与 TRL 预处理结果一致。
2. prompt 的 label 为 -100。
3. completion 的 label 与对应 token 一致。
4. padding 被屏蔽。
5. EOS 不丢失、不重复，后面没有实质目标文本。
6. 解码后的目标可被工具调用 parser 解析。

本次只是读取这些检查的实现，没有重新运行。历史报告中的标签验证通过属于对应历史环境的结果，不能代替未来升级依赖后的验证。

### 11.4 训练与服务必须使用同一个合同

chat_template_contract.py 固定模板文件哈希、渲染协议与 enable_thinking=False，并提供共享入口给本地策略和训练审计使用。

如果训练时有一个 assistant 前缀，服务时却换成另一种 thinking 模式、工具序列化或结束符，模型可能在训练损失很好看的同时在线输出错误。版本化模板与 Token 对齐，就是把这种差异纳入可核验对象。

源码：[数据渲染与预检](E:/A_Louis/TravelAgent2/backend/src/agentic/training.py)、[模板合同](E:/A_Louis/TravelAgent2/backend/src/agentic/chat_template_contract.py)。

## 12. 数据拆分：为什么不能把动作行随机打散

一份任务的多个动作高度相关。如果把同一轨迹前半段放 train、后半段放 test，测试中的目标和事实可能早已通过训练暴露。

同一个来源模板的城市、日期或人数变体，也不一定构成独立结构。需要同时看任务 ID、来源组、模板派生和用户分区。

### 12.1 通用构建器与正式试验拆分不同

通用 SFTDatasetBuilder 对非生产数据使用 template_family + city 形成组，再用稳定哈希分到 train / validation / test；生产数据使用用户分区标识。

这有助于避免同组随机散落，但不能证明不同城市的共享模板天然独立。专用 Harness 导出器使用预先定义的 source_group / lineage_group 与 explicit split，覆盖通用默认行为。

所以不能只看通用代码的 70/15/15，就声称所有正式实验都是随机按这个比例分割。

### 12.2 至少检查三层重合

- 精确内容：完整模型提示、工具 schema 与目标哈希。
- 来源关系：同一 source_state、scenario、episode 或派生模板。
- 语义结构：只是换了实体、日期或措辞的同构题。

当前代码中的模型可见 payload 去重能发现第一类，不会自动解决后两类所有问题。来源图与人工分层仍有价值。

### 12.3 Test 退役必须承认

后续一次新验收只通过 104/120，结果保留；这批验收后来退役为开发集。继续用它诊断和修复是可以解释的，但从那一刻起就不能再把它称为未见过的确认性测试。

修复后另用新的冻结验收 v2。这个过程需要公开记录，避免把反复使用的测试结果包装成一次盲测。

### 12.4 Split 隔离还不能证明基础权重从未见过类似题

领域 train / dev / test 隔离，证明的是该项目增量数据与选模流程中的隔离。它不自动证明基础大模型预训练语料中没有任何类似旅游资料。

当前基准以合成、预设槽位和相关来源结构为主，所以结论应限定在这些任务及协议，不宣称真实旅行用户总体泛化。

## 13. SFT 的训练目标：这个公式怎样对应到代码

给定输入 x 和审核后的 completion y，常见 SFT 使用因果语言模型交叉熵：

~~~text
L_token = - (1 / N) × Σ log πθ(y_t | x, y_<t)
~~~

N 是参与监督的目标 Token 数；prompt、padding 等 label=-100 的位置不计入该项。

“监督”指动作是已给定的学习目标。它不要求目标一定来自人类：教师生成、学生成功轨迹或经过执行审核的动作，都可以成为 SFT 数据。

### 13.1 Mask 掉 prompt，不代表 prompt 不参与计算

模型仍需要通过 prompt 理解状态，并计算后续目标的表示。屏蔽 label 只是不给 prompt 位置本身设置预测损失。

因此长状态输入仍影响训练耗时和显存；它也解释了为什么等监督 Token 的两组，可能有不同的计算量。

### 13.2 Teacher Forcing 与自主运行的差异

训练预测 y 的后续 Token 时，前缀使用目标中的正确 Token。在线运行时，模型要接收自己产生的动作和执行后的新状态。

单步 completion CE 降低，不保证多步 rollout 不偏离。训练数据需要覆盖学生实际状态，评测还必须放回完整 Agent Loop。

### 13.3 不同归一化方式是不同目标

两个样本的答案分别长 10 和 100 个 Token：

- token mean：总损失除以 110，长答案贡献更多权重。
- example mean：先各自平均，再取均值，两条样本权重相同。
- source mean：先在每个来源内部平均，再让不同来源等权。
- microbatch mean 的均值：由每个微批次内长度和组织方式决定实际权重。

这些都可以有明确用途，但不能互相冒充。变更梯度累积而未核对 loss 归一化，会悄悄改变训练目标。

### 13.4 动作 Token 加权是可选能力，不是所有实验都启用

通用训练器支持提高动作名称等目标片段的权重，也支持某些来源等权分支。相关开关存在，并不证明最新那轮 SFT 使用了这些设置。

更不能因为把 action 学得更准，就认为参数 grounding、后续证据收集和终态都已改善。动作加权应单独对照，并检查它是否挤压了参数学习。

## 14. LoRA、QLoRA 与继续训练：怎样讲得准确

LoRA 冻结原始权重，用低秩矩阵表示增量。对某个线性层可写成：

~~~text
W' = W + (alpha / r) × B × A
A: r × d_in
B: d_out × r
新增可训练参数约为 r × (d_in + d_out)
~~~

r 控制低秩适配的容量，alpha 参与增量缩放。具体默认初始化、目标层和缩放方式应以本次适配器配置为准，不用抽象公式替代真实参数文件。[LoRA 原论文](https://arxiv.org/abs/2106.09685)。

### 14.1 QLoRA 不是另一个损失函数

QLoRA 的关键是通过冻结的量化基础模型向低秩适配器反向传播；原论文使用 4-bit 基础权重，并引入 NF4、双重量化等设计。它主要改变训练资源需求，不改变“用审核动作做监督”的任务性质。[QLoRA 原论文](https://arxiv.org/abs/2305.14314)。

项目通用 train_sft.py 配置了 NF4、double quant、计算 dtype 和 LoRA；而早期 matched pilot 使用 BF16 基模加载、SDPA 和已有 Adapter 继续训练。后者不应因同样使用 LoRA 就被称为 4-bit QLoRA。

### 14.2 继续训练已有 Adapter 时，r 不一定由 CLI 新参数决定

通用入口检测到 adapter_config.json 后，会加载对应基础模型及现有 Adapter 并开启可训练；只有新建 Adapter 分支才创建新的 LoraConfig。

因此“命令行默认 lora-r=16”不等于每次继续训练都重新创建 rank16 适配器。实际身份应记录 adapter_config、初始权重哈希、可训练参数集合与模型版本。

最新分支按 2026-09-09 说明延续 rank16；历史正式记录约 3,303 万可训练参数。这里没有重新加载模型核数，不能据此宣称所有旧实验参数量完全相同。

### 14.3 为什么冻结基模仍可能训练很慢

虽然只更新少量参数，前向仍要经过大模型；为了计算 LoRA 梯度，相关计算图和反向传播仍有成本。长输入、梯度检查点重算、量化算子、设备吞吐和小微批次都影响速度。

LoRA 主要降低参数更新与优化器状态负担，不能简单把“可训练参数只有不到 1%”推导成“耗时也只有不到 1%”。

### 14.4 保存与回滚要保存哪些身份

至少保存基模标识 / revision、tokenizer 与模板、初始 Adapter、最终 Adapter、训练脚本、数据清单、超参数、随机种子和依赖版本。

只有 adapter_model.safetensors 不一定足够复现。错误基模、旧模板或不同工具 schema 都可能让同一个 Adapter 表现不同。

## 15. 来源与监督 Token 匹配：项目中最值得讲清的一项实验设计

早期实验想回答：

> 在共同来源、相同初始模型和监督预算下，加入学生状态接续，是否比仅使用教师从头示范更有效？

如果混合组只是多了更多数据、更多更新和更多 Token，即使结果更好，也很难判断增益来自接续状态还是训练量增加。

### 15.1 Pilot 怎样匹配

早期 pilot 有 14 个共同任务、13 个来源组、166 个唯一动作。两组都保留示范锚点；混合组再加入接续动作。

曾尝试同时匹配完整动作 Token 和样本行数，但无可行解。最终选择保留完整动作目标，通过有限重复使用匹配监督 Token，并公开两组行数不同。

每组每 epoch：

~~~text
13 个来源更新
7,053 个监督 Token

3 epochs：
39 次参数更新
21,159 个监督 Token
~~~

示范组每 epoch 167 行、456,281 prompt Token；混合组 191 行、587,927 prompt Token。两组输入量不相等。

来源：[匹配试验报告](E:/A_Louis/TravelAgent2/docs/MATCHED_SFT_EXPERIMENT_REPORT_20260906.md)。

### 15.2 来源更新的损失怎样累积

专用训练器以来源组作为一次 optimizer.step 的单位。设某来源组共同监督预算为 T_g，其中第 i 个动作的完整目标损失和为 S_i：

~~~text
L_g = (Σ_i S_i) / T_g

每个微批次：
(loss_sum_i / T_g).backward()

完成该来源所有动作后：
检查总目标 Token == T_g
梯度裁剪
optimizer.step()
~~~

分母在一次来源更新中固定，因此把微批次拆开计算，仍对应这份来源更新的 Token 总平均。不能直接把每个微批次自身的平均损失相加后称为同一个目标。

### 15.3 这和另一份 source_equal_sft.py 不是一回事

source_equal_sft.py 有面向历史 H006 的“来源平均—样本平均—目标 Token 平均”合同，并限制每来源的目标数量。通用训练器也声明了一种 microbatch mean 归一化合同。

它们不是上述 pilot 训练器的实现别名。一个严谨回答应指明当前实验实际使用哪份脚本、哪种归一化，不把仓库中所有 SFT 技术混成一次实验。

### 15.4 匹配到了什么，没有匹配到什么

匹配：共同来源、初始适配器、监督 Token、来源更新顺序与固定训练计划。

没有完全匹配：prompt Token、行数、序列长度分布、总 FLOPs、实际墙钟时间。

此外，混合组也改变了监督动作和状态覆盖；该实验检验的是这套接续数据组合的整体效果，不能把所有增益严格分离为某一种单独错误类型。

源码：[matched pilot](E:/A_Louis/TravelAgent2/ml/agentic/training/train_matched_source_pilot.py)、[另一种来源等权目标](E:/A_Louis/TravelAgent2/backend/src/agentic/source_equal_sft.py)。

## 16. 两轮教师示范／接续对照，结果并不完全相同

### 16.1 早期小试验：混合组没有胜出

早期 matched pilot 使用一个训练种子、三轮固定训练，在 12 个开发任务上比较：

| 模型 | 任务 / 质量通过 | 规划子集 / 8 | 约束终态 / 4 |
|---|---:|---:|---:|
| 原学生 | 6/12 | 2/8 | 4/4 |
| 仅示范 SFT | 11/12 | 7/8 | 4/4 |
| 示范＋接续 SFT | 10/12 | 6/8 | 4/4 |

混合组减少了部分原始策略参数错误，却仍在多日任务里缺少证据、重复无进展、未进入求解。不能因为理论上接续覆盖学生状态，就先验认定它在所有试验中一定更好。

该结果提示扩大独立规划来源与恢复类型，而不是根据 12 题立即宣布方法定论。报告没有按开发集成绩改题或直接替换原模型。

### 16.2 扩大正式对照：平均有效，但波动明显

根据 2026-09-09 全景说明，扩大阶段：

- 600 个学生来源候选中，审核获得 252 个配对任务，其中规划 204 个、约束 48 个。
- 匹配来源组 52 个；两组各三个预先固定训练种子，共六次训练。
- 每次 3 epochs、156 次更新、413,826 个监督 Token。
- 冻结七个模型，在 240 个锁定任务、60 个来源组上评测，共 1,680 次执行。

| 模型 / 组 | 该轮锁定测试严格质量通过率 |
|---|---:|
| 初始学生适配器 | 52/240，21.7% |
| 仅示范 SFT，三种子平均 | 57.1% |
| 示范＋接续 SFT，三种子平均 | 73.9% |

混合组比示范组平均高 16.8 个百分点。但三个混合种子分别约为 71.2%、88.3%、62.1%，波动明显；约束类平均从基线 97.5% 降到 96.7%，预设发布门未通过。

### 16.3 应怎样解释这次增益

可以说：

> 在这轮来源与监督 Token 匹配的合成锁定任务上，加入学生状态接续提高了三种子平均严格质量通过率，但种子波动和约束回退仍存在，未满足发布条件。

不应说：

- “所有教师纠错都比示范更强”。
- “稳定提高到 88.3%”——这只是最高混合种子。
- “相同计算量提高 16.8pp”——prompt 和总算力没有完全匹配。
- “真实用户准确率提升到 73.9%”——评测范围不同。
- “后面单种子 SFT 也有三种子验证”——那是另一轮实验。

### 16.4 怎样分析随机种子波动

训练种子影响初始化相关随机性、数据顺序、dropout 等；采样种子影响 rollout 的随机生成。二者不能互相替代。

三个训练种子已经比只报最佳一次更可解释，但仍不足以精确估计所有不确定性。相关来源组也会让样本间不独立，统计时宜按来源组配对或聚类处理。

没有原始逐题数据就不应临时编一个置信区间。后续应同时报告每个种子、来源组、任务族和失败类型，而不只留一个均值。

## 17. 训练前与训练后要核验什么

### 17.1 数据预检

通用 training.py 会检查 manifest、split 标签、来源组重合、模型可见 payload 重复、最小数量及依赖兼容性。它有默认最小 3,000 行门槛，也有专用内部试验配置。

这个门槛是脚本合同，不是 SFT 普遍必须达到的统计常数；专用 166 动作试验是否有效，应由它自己的目标、隔离与结果边界判断。

正式对照中的重复动作日程应与唯一数据池分开。不能一边用通用去重检查声明“零重复”，一边把重复使用次数当作新增唯一样本。

### 17.2 模型和输入预检

至少应核对：

- 基础模型与初始 Adapter 身份。
- 训练参数集合确实只有预期 LoRA 参数。
- tokenizer、工具 schema、模板与服务渲染合同一致。
- 完整输入未截掉任务约束，完整目标及 EOS 未截断。
- 模型输出目标能被实际策略 parser 解析。
- 梯度、损失和更新 Token 数有限且符合计划。

只看 loss 数字为有限值还不够：错误掩码也可能得到很正常的 loss。

### 17.3 训练后保存的证据

来源匹配训练器记录逐步来源、行数、监督 Token、损失和梯度范数，并核对初始 Adapter 文件未改变、训练结束后只保存新产物。

还应保留训练计划、环境版本、完成记录和可验证哈希。日志中的 step 到了 64，不能单独证明最终权重保存成功、评测正确加载了该权重。

### 17.4 Resume 要区分“验证完成”与“继续未完成优化”

早期 matched pilot 如果目录已存在且有完整 training-report，就核对已有产物后退出；若存在未完成目录则停止，不自动从头重复训练。

这是一种避免意外重跑的合同，不等于支持任意 step 断点继续。真正恢复优化还要保存 optimizer、scheduler、RNG 和数据位置；只重新加载 Adapter 再训练剩余行，不必然等价于不中断运行。

该区别与第四篇的 Job 恢复类似：保存了一部分状态，不等于保存了所有恢复语义。

## 18. 怎样加速而不改变要比较的问题

### 18.1 数据采集：不同任务并发，同一轨迹仍有依赖

独立任务可以同时请求教师或进入共享模型的动态批量队列；一条轨迹下一步依赖上一工具结果，不能把尚未知道输入的后续动作提前当成独立样本全部并发。

教师并发还受预算、服务限额和错误处理影响。把并发数调高，有可能增加 429、超时和重复付费。

项目的历史采集提速包括共享学生模型与批量推理；这些改变执行吞吐，不是参数训练收益。是否保持输入与采样合同，需要另外核对。

### 18.2 减少教师思考预算未必提高合格数据产出

2026-09-06 的教师 max / high 小批对照：两种设置各 4 条尝试，high 的请求中位延迟更短，但最终 SFT 审核接收轨迹为 1/4，max 为 3/4；共同可比较的合格起点不足。

当轮结论保留 max、等待更多证据，没有宣称 high 达到质量等价。速度应按“合格动作或独立任务 / 总成本或墙钟时间”衡量，不能只看最快请求，也不能把提前失败当作完成更快。

这只是当时两个任务上的小规模结果，不是当前教师 API 性能测评。来源：[教师速度试验](E:/A_Louis/TravelAgent2/docs/TEACHER_SPEED8_REPORT_20260906.md)。

### 18.3 训练加速：只对目标相关位置做输出投影

matched pilot 的输入可能很长，而答案较短。它仍让 Transformer 读取完整输入，但只计算监督答案预测所需的最后若干位置的词表 logits。

若答案有 n 个 Token，需要保留对应的 n 个预测位置；由于 causal shift，代码使用 logits_to_keep=n+1，再去掉最后一个不用于这些目标的 logits 位置。

这节省的是大词表输出层在无监督 prompt 位置的开销，**不是把 prompt 从模型计算中删掉**。

训练前该实现用实际 4B 模型比较完整序列 masked CE 与受限投影的损失，按容差验证一致。历史报告记录了验证；本次未运行该证明。

### 18.4 梯度检查点、长度与批量的取舍

- 梯度检查点降低激活保存需求，但会增加反向重算，不应简单称为提速开关。
- 长度分组可减少 padding，但来源匹配试验要保持预定来源和更新合同。
- 增大 microbatch 可能提高吞吐，但受显存、输入长度和模型算子影响。
- 梯度累积改变一次更新包含的样本量，必须同时检查 loss 归一化。
- 缩短输入只有在关键证据、错误状态和授权不被丢弃时才有意义。
- 改 epoch、学习率、更新数属于训练方案改变，应重新标记实验，而不是隐形加速。

当前通用入口 packing=False，不应把 packing 宣传成已经采用的提速措施。

### 18.5 加三张卡与四机联合训练不同

让不同机器分别跑两个实验组、三个种子或评测，是实验级并行；多进程共同同步梯度更新一个模型，才是联合训练的另一种配置。

已有全景说明明确不应写“四机 DDP 联合训练”。本篇不根据用户曾提供多台 GPU，就推断实际训练采用了 DDP。

如果今后确实做多机训练，需要保存 world_size、分布式启动参数、通信方式、全局 batch 和梯度同步证据。跨机器普通公网通信也不等于高带宽训练互联。

### 18.6 优化阶段耗时与全项目耗时

早期 pilot 记录仅示范训练保存约 805 秒，混合约 1,049 秒，加载与预检另计。最新成功 SFT 约 15.1 分钟，也只是对应优化阶段。

教师采集、失败调查、数据审核、参考计算、模型加载、逐题 rollout、验收和归档都可能比优化更久。不能用“15 分钟训练完成”回答整个后训练项目需要多久。

## 19. 定向修复 SFT：为什么强基线仍需要低学习率补课

扩大对照后，后续工作定位格式、证据覆盖、重复查询、预算和实体依据等问题。通过训练输入、执行轨迹与失败类型定位应该补什么状态，而不是继续无差别增加旅游文本。

根据 2026-09-09 说明，修复数据包含 439 个不同动作、601 次加权使用，两个学习率候选为 5e-6 与 1e-5，各 76 次更新，按开发集预定规则选择低学习率候选。

### 19.1 为什么混入保持样本

只用少量困难恢复动作继续训练，可能提高难题表现，却让原有简单任务或安全停止退步。加入已审核旧样本，相当于继续提醒模型保留已有行为。

它可以减轻遗忘风险，但不是保证不遗忘。比例、来源与任务族需记录，最终仍用旧能力回归验证。

### 19.2 32 个合成初始动作怎么描述

这批修复中存在 32 个合成初始动作：把已有教师通用动作放到新的 train 初始状态中实际执行验证，仅导出第一步。

它们不是教师实际在这 32 个状态下生成的响应，也不是 32 条完整教师成功轨迹。可称为“经执行验证的合成初始动作”，并保留模板来源及与真实教师数据的区分。

### 19.3 结果要分成开发诊断和新验收

在同机、同一 120 个开发任务、相同首轮输入且统一格式约束的对照中，三阶段通过数为 100 → 114 → 119。

另一次新验收是 104/120，随后明确退役为开发集；进一步修复后，另一套冻结新验收 v2 达到 119/120，成为后续保留模型。

不能将这几个阶段与早期 21.7% 连接成单条公平曲线；集合、模型身份和工程条件不同。格式约束带来的收益也应与权重学习分别归因。

## 20. 成功轨迹筛选 SFT：为什么它仍然是监督学习

当保留模型已经较强时，可以让它在新的 train 任务上多次运行，从完整成功轨迹中提取经过审核的动作。

最新阶段按归档说明使用 64 个任务、temperature=0.7、四个固定采样种子，得到 256 条轨迹。这里的四个种子是采样种子，不是四次训练。

流程是：

~~~text
冻结当前学生
  → 新 train 任务多次自主 rollout
  → 保留所有成功与失败记录
  → 完整任务 / 证据 / 参数 / 来源审核
  → 从接受轨迹中导出成功动作
  → 去重并构造训练日程
  → 用 completion CE 更新 LoRA
  → 独立完整运行评测
~~~

没有在训练中使用策略梯度，也没有根据组内相对奖励直接更新策略，因此它属于成功轨迹筛选后的 SFT，不应写成 GRPO。

### 20.1 为什么自己生成的数据可能帮助自己

采样时模型可能在同一个问题上产生不同策略，其中有的成功，有的失败。把经过执行验证的成功动作变成监督，可以提高这些行为被生成的概率。

但这不保证创造当前模型完全不会的新能力。若某类状态从未出现成功行为，纯成功筛选就没有正例可学；需要教师接续、修复数据或其他探索方式。

### 20.2 最大风险是只强化容易成功的分布

成功轨迹天然更容易来自简单任务或更顺利的工具结果。若不按来源、难度、故障阶段和动作类型审计，可能训练越多，模型越偏向简单路径。

保持样本与恢复状态覆盖需要一起设计。不要只按成功轨迹总数排序，也不要把失败轨迹从统计报告中删除。

### 20.3 最新 512 行由什么组成

归档说明记录：

- 128 个偏好正例动作。
- 256 个额外学生成功动作。
- 128 个历史教师保持样本。

SFT 分支只需要这些正向目标，做监督拟合。另一个 DPO＋SFT 保持分支还需要对应负例和参考概率；即使两组都说 512 行，计算量也不相同。

两个分支同起点、相同样本顺序、学习率 5e-6、64 次更新、seed=20260913、rank16、microbatch=1、累积=8。seed 是任意随机种子编号，不是执行日期证明。本轮只有一个训练种子。

DPO 的 128 对覆盖 41 个训练任务，不应与完整 64 任务采集池混称为同一个独立来源数。偏好对构造与 DPO 损失将在第六篇详细展开。

### 21.3 为什么不能用平均数盖过旧问题

旧问题暴露的是恢复路径是否被训练损害。新题全对并不会让已知回归消失，也不能证明长期运行稳定。

### 21.4 面试最值得讲的是发布判断

可以说：

> 成功轨迹 SFT 在冻结的新实例集合上达到 120/120，但已知复合故障复测仍从 6/6 降到 4/6，因此保留原模型，没有只因单一集合满分就上线。

这比把结果压成“训练到 100%”更能展示实验判断和产品责任。

## 22. 成本、云端执行和复现材料

### 22.1 教师账本与 GPU 成本分开

### 22.3 为什么保留失败、停止与重启记录

为了保持可复现性，应保留：

- 首次采集失败与 provider 错误。
- 已完成任务的哈希与恢复跳过记录。
- 未知用量请求的预留。
- 初版审核误判与最终修正规则。
- 训练启动失败、未完成目录和完成产物。
- 所有评测失败，不通过重抽只留下成功样本。

在云端暂停后继续，应从任务清单和产物确认工作状态，而不是重新运行整批以求“干净结果”。重试次数、是否重复优化与额外消费都需要可追溯。

## 23. 当前缺口与下一轮数据应该针对什么

这部分是依据现有结果提出的验证方向，本次没有启动新的采集或训练。

### 23.1 优先补“复合故障后的恢复状态”

成功筛选后，新实例提升而旧复合故障回退，说明不能只继续增加顺利规划轨迹。应先定位：

- 哪一次工具失败改变了候选、证据或预算。
- 学生实际看到什么，是否看见必要错误信息。
- 学生是否重复调用、过早求解或错误停止。
- 同状态下教师能否给出经过执行验证的恢复动作。
- 失败是否主要来自执行器缓存或状态丢失。

如果是工具实现导致有效产物丢失，应先做工程修复对照；如果模型在完整可见状态下仍选错，才把对应状态纳入 SFT。

### 23.2 防止把旧测试直接变成训练答案

旧故障可以用于识别“缺少哪类能力”，但确认集一旦用于选择和修复，就要如实降为开发材料。新的 train 状态应有明确来源与隔离规则，不能简单复制验收题换个城市名。

应保留独立新确认集，最终冻结候选后再运行。下一篇讨论偏好与 RL 时，也要遵守同样隔离。

### 23.3 扩大覆盖时优先看什么

比总行数更有信息的覆盖维度包括：

- 单日 / 多日与不同约束组合。
- 时间、预算、步行、同行人和餐饮偏好。
- 候选变化后的证据失效。
- 首次失败与连续失败后的恢复。
- 空结果、过期结果、超时和部分成功。
- 合理追问、明确不可行与允许权衡。
- 同一状态下多种可接受动作。
- 同一动作在不同 provider 状态下的后果。

这些维度可能共享基础模板，统计时仍要报告相关来源数，不能把组合数量自动当作完全独立任务数量。

### 23.4 何时继续 SFT，何时才考虑其他方法

如果主要问题是缺少某类状态下的正确动作，SFT 有直接监督信号，先补数据往往更容易归因。

如果同状态下已有多个合法动作，需要在质量相近时学习效率或选择偏好，可以考虑有执行证据的 DPO 对照。

如果瓶颈在长程探索与延迟回报，且可执行环境、奖励、采样概率和成本条件成熟，再评估 GRPO 等策略优化。并不是训练技术名字越多，项目就越高级。

本篇不展开 DPO / RL 的完整目标与历史裁决，留给第六篇。

## 24. 十二组面试追问与回答骨架

### Q1：你的 SFT 训练的是攻略生成还是 Agent 决策？

**回答主线：** 训练当前状态下的下一步动作。输入是目标、证据、进度、失败反馈、预算和工具 schema；目标是完整模型工具调用。事实由工具供给，约束由求解器和 Validator 检查。

**继续追问：为什么不直接训练最终行程？**  
项目希望模型学会补证据、选工具和恢复，而不是绕过执行生成表面合理的路线。最终行程仍可作为另一类任务，但不能替代当前策略训练。

**不要说：** “给它旅游知识，它就自然学会 Agent”。

### Q2：教师纠错属于 SFT 吗？和教师从头生成有什么区别？

**回答主线：** 是否是 SFT 取决于优化目标。把教师动作作为给定输入下的监督目标，用交叉熵训练，就是 SFT。区别主要在状态来源：从头示范覆盖教师路径，接续覆盖学生实际状态。

**继续追问：所有接续都是纠错吗？**  
不是。扩大阶段有 112 个前缀没有记录错误或修复信号，要区分普通续跑与未解决失败。接续起点及后续动作应保留来源标签。

**不要说：** “教师一出场就是 RLHF”或“所有接续都是失败修复”。

### Q3：你有六千多条旧数据，为什么不用？

**回答主线：** 数据协议已变化：旧控制器限制动作、旧参数有越权字段、工具已移除，还存在跨版本来源重合。直接混入会教错当前策略。

**继续追问：那旧数据完全没价值吗？**  
可以回收请求、约束和偏好，在当前环境重建并重新执行。3,612 个请求是待迁移候选，不能算合格标签。

**不要说：** “格式改一下就能兼容所有历史数据”。

### Q4：怎么证明教师没有看到学生看不到的答案？

**回答主线：** 保存实际 API 请求与模型状态、工具 schema、provider 快照和断点来源；审核它们与导出输入一致。教师协议提醒单独记录，不含隐藏任务答案。

**继续追问：自修复后答案还能直接配原输入吗？**  
不能默认可以。若原始调用多了 policy_feedback，就必须匹配真正输入；配对导出器排除相应 repair_attempts 目标，防止错配。

**不要说：** “教师回答正确，所以数据肯定可信”。

### Q5：你的数据量到底多大？

**回答主线：** 分任务、来源组、轨迹、唯一动作和训练使用次数回答。最新是 64 个任务四采样得到 256 条轨迹，导出 954 个去重动作候选，最终 SFT 使用 512 行混合日程；这些不是一个数字。

**继续追问：为什么 220 条质量通过只接受 174 条？**  
任务成功与训练来源审核是不同门槛。要看逐条审核理由，不能凭总数编造拒绝原因。

**不要说：** “954 条真实完整旅行任务”或“累计各批行数就是独立规模”。

### Q6：为什么只训练 assistant Token？Prompt 不训练是不是不读它？

**回答主线：** 模型要条件化于完整输入，但只对目标动作计算预测损失。prompt label=-100，不代表 prompt 被删掉；完整 Transformer 仍处理它。

**继续追问：怎么验证 Mask 真正确？**  
读取实际 TRL 预处理和 collator 输出，核对 token 前缀、label、padding、完整目标和单个 EOS，再用实际 parser 解码目标。不能只看 completion_only_loss=True。

**不要说：** “屏蔽 prompt，所以长上下文训练免费”。

### Q7：为什么要自己固定 Chat Template？

**回答主线：** 原生工具调用的边界与序列化影响监督。版本固定模板、共享渲染入口，并核对服务与训练 Token，减少前缀或 thinking 模式不一致。

**继续追问：数据 JSON 明明合法，为什么还会出错？**  
嵌套 schema 可能被 Arrow 合并并填 null，空 arguments 也可能被序列化删除。数据存储合法不代表模型合同没变。

**不要说：** “Tokenizer 只是把字变数字，对实验没影响”。

### Q8：LoRA 和 QLoRA 的区别？你到底用了哪一个？

**回答主线：** LoRA 冻结基模、训练低秩增量；QLoRA 进一步通过量化基础模型反传到 Adapter。当前通用脚本配置 4-bit NF4；早期匹配试验则是 BF16 基模上的 LoRA 继续训练。

**继续追问：最新 rank 和参数量怎么证明？**  
用对应 adapter_config、权重哈希和可训练参数记录。最新 rank16 及历史约 3,303 万参数来自归档说明，本次没有加载模型重新计数。

**不要说：** “仓库脚本默认值就是所有实验实际配置”。

### Q9：你说等 Token 对照，为什么还不是等算力？

**回答主线：** 匹配的是目标 Token 和来源更新，输入 Token 与行数不同。模型仍要读 prompt，所以输入更长的组可能花更多计算。

**继续追问：梯度累积怎么保证等价？**  
来源匹配训练器每个微批次贡献 loss_sum / 该来源共同 Token 预算，再执行一次更新。它对应来源更新的 Token 总平均，不是任意微批次均值平均。

**不要说：** “用了同一张卡、同样 epoch 就完全公平”。

### Q10：SFT 结果到底有多好？为什么前后数据不同？

**回答主线：** 分实验回答：小 pilot 为 11/12 对 10/12；扩大三种子对照为 57.1% 对 73.9%，但波动与约束回退存在；最新新验收 SFT 为 120/120，旧问题仍 4/6。

**继续追问：为什么不只报 88.3% 或 100%？**  
前者是最佳种子，后者是特定合成集合；都不能代替完整实验结论。发布还要看回归、独立性和预定门槛。

**不要说：** “一次训练把真实正确率从 21.7% 稳定提升到 100%”。

### Q11：学生成功轨迹再训练自己，不就是 RL 吗？

**回答主线：** 当前流程先离线筛选成功轨迹，再把动作作为固定标签做 CE，是监督学习。采样和成功筛选本身不意味着用了策略梯度。

**继续追问：这样有什么局限？**  
难以提供从未成功过的状态的正例，还可能偏向简单路径。要补教师恢复、任务覆盖和保持样本，并用完整 rollout 测试。

**不要说：** “多采样就是 GRPO”。

### Q12：如果面试官问项目还差什么，你怎么回答？

**回答主线：** 已有较完整的数据来源、动作审核、掩码验证和匹配实验，但最新仍是单训练种子、合成相关任务，且旧复合故障回归。应补恢复状态覆盖、独立确认和运行验证。

**继续追问：为什么不立刻换更高级 RL？**  
先判断失败来自状态、环境、模型选择还是验收器。基础信号没有校准，换算法可能把错误更强地优化。技术选择应由错误和可验证收益决定。

**不要说：** “大厂标准就是数据够多、算法名字够全”。

### 25.1 三分钟讲述稿

以下按项目视角写，改为第一人称前应核对个人真实职责。

> 这个项目的后训练对象是 Qwen3-4B 的 Agent 决策能力。每一步输入当前目标、证据、失败反馈、预算和允许工具，输出一个模型拥有参数的工具调用。求解器负责排程，Validator 检查结果，模型学习什么时候查证据、求解、恢复、追问或停止。
>
> 数据主要有教师从头示范、教师在学生真实状态下接续，以及学生成功轨迹筛选。接续的价值是覆盖学生实际会走到的困难状态，但并非每个接续起点都有未解决错误。采集会保存源轨迹、状态和 provider 快照、真实模型请求、工具执行与预算，审核后才导出动作。
>
> 我们没有把旧数据直接混进来。旧控制器状态、已移除工具和越权参数都与当前协议冲突，六千多条旧记录只作为场景迁移素材。训练标签也不包含工具观察、系统补全参数、学生前缀或教师私有思考，只监督完整动作和结束符，并检查实际 tokenizer 和 collator 的标签边界。
>
> 为判断接续数据是否有效，做过来源与监督 Token 匹配。扩大对照两组各三个训练种子，在 240 个合成锁定任务上，纯示范平均 57.1%，加入接续平均 73.9%。但种子波动较大，约束能力有回退，所以没有只选最佳种子发布。这个对照匹配了监督预算，未匹配全部输入计算量。
>
> 后续通过定向修复形成较强基线，再采集学生成功轨迹，做 SFT 与小规模 DPO 加保持项对照。最新 SFT 在 120 个新实例上全部通过，但旧故障复测仍从原模型 6/6 降到 4/6，因此保留原模型。下一步应针对复合故障恢复补数据，并用新的确认集验证，而不是把 100% 当成真实用户成功率。
