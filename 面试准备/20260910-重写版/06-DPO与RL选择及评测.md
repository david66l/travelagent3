## 1. 本篇最重要的问题：什么时候换训练方法才有意义

第五篇回答“怎样给模型正确示范”。本篇进一步回答：

- 模型能做出多个合法动作时，怎样让它更偏向有用的那个？
- 正例来自成功轨迹，负例究竟凭什么被判为更差？
- DPO preference accuracy 很高，为什么 Agent 仍会失败？
- 多次 rollout 有奖励后，是不是就可以直接做 GRPO？
- 怎样避免模型为了得分而跳过验证、缩短回答或迎合判分关键词？
- 新模型在一个集合全对，为什么还可能必须保留旧模型？

技术选择应由错误类型和可用信号决定。当前证据支持先做可信 SFT，再做有限偏好对照；是否进一步进入策略优化，取决于奖励、环境、探索与评测是否具备条件。

不能把 SFT → DPO → RLHF → GRPO 当成必须依次打卡的四级升级路线。

### 1.1 四个名称不在完全相同的分类维度

| 名称 | 主要指什么 | 典型信号 | 本项目应怎样表述 |
|---|---|---|---|
| SFT | 给定目标的监督优化 | 审核后的正确动作 | 教师示范、接续、成功轨迹都可用于 SFT |
| DPO | 基于成对偏好的直接优化目标 | 相同输入的 chosen / rejected | 最新是 DPO＋SFT 保持项对照 |
| RLHF | 由人类反馈驱动的对齐流程或方法族 | 人类偏好 / 评分 | 当前最新分支没有完成经校准人工偏好、独立奖励模型和 PPO 的完整流程 |
| GRPO | 使用分组相对奖励的策略优化方法 | 同任务多次 rollout 的可比较回报 | 仓库有历史训练及实现，不能推断最新统一 Loop 已完成有效 GRPO 验收 |

DPO 的标签可以来自人类、模型评审或程序验证；GRPO 的奖励也不一定来自人类。因此不能仅凭算法名称判断反馈来源。

## 3. 最新 DPO 想优化什么，而不是泛泛“让回答更好”

最新偏好主要针对同一可见状态下的工具信息价值与执行效率。

例如，当前缺少餐馆详情：

- chosen：获取尚未获得的必要详情，执行后产生新信息。
- rejected：再次获取已有且仍有效的同一份信息，或者执行满足对照规则但返回空结果的查询。

它不同于让人类比较两篇旅行攻略谁更生动，也不同于旧 H-004 对理由连接词的表面合同修复。

### 3.1 为什么强 SFT 后还要尝试 DPO

SFT 只告诉模型“这个动作值得模仿”。DPO 进一步给出“在同一个输入下，A 比 B 更值得选择”的相对信号。

当两个动作都能被 parser 接受、也都在权限范围内，区别在信息增益和重复消耗时，相对偏好可能比只增加 A 的正例更直接。但它仍需要高质量负例和独立评测。

### 3.2 偏好不等于绝对价值函数

一对 A > B 只描述一个比较关系，不能推出：

- A 是所有可能动作中最优。
- A 能保证整条轨迹成功。
- B 在任何其他状态下都不应使用。
- 用户总体更喜欢执行 A 的旅行方案。

项目的偏好标签是局部、条件化的。这个边界对 long-horizon Agent 尤其重要：一个立即产生信息的动作，未必是长期预算下最优的一步。

## 4. 同状态偏好对：为什么不能随便拼两条轨迹

一条标准偏好样本可以表示为：

~~~text
(x, y+, y-)

x  = 完全相同的模型可见输入
y+ = 更偏好的完整动作
y- = 较不偏好的完整动作
~~~

对状态化工具 Agent，还必须在 x 之外固定对应环境。两条文本提示相同，如果 provider 缓存、故障次数或已消耗预算不同，执行后果也可能不同。

根据最新归档说明，128 对偏好采用同一 Ledger 和 provider 快照分别执行正负动作，并保留提示、执行结果与快照哈希。

### 4.1 正确的比较顺序

~~~text
冻结状态 S 和 provider P
          │
          ├─ 独立副本 S+ / P+ ─► 执行 y+ ─► 观察 O+
          │
          └─ 独立副本 S- / P- ─► 执行 y- ─► 观察 O-

核对：输入相同、起点相同、权限合法
比较：哪些证据新增、哪些操作重复、哪些结果为空
保存：状态哈希、动作、执行参数、观察和偏好理由
~~~

不能先在同一可变 provider 上执行正例，再直接执行负例。正例可能已改变缓存、故障进度或可用资源，比较就不再来自相同起点。

### 4.2 最新正例来自哪里

正例来自完整任务成功、动作和输入经过审核的学生轨迹。它们不是教师根据验收答案直接写出的标签。

采集池为 64 个新 train 任务、四采样共 256 条轨迹；128 个偏好对覆盖其中 41 个训练任务。64 是采集任务数，41 是偏好对覆盖任务数，128 是对数，不能互换。

### 4.3 相同 prompt 应核验到 Token

JSON 语义看起来相同，仍可能因为字段排序、工具 schema、模板、thinking 模式或默认参数变化而产生不同输入 Token。

第五篇的模板和掩码检查在这里仍然适用。偏好训练必须把 y+ 和 y- 放在同一个渲染后的 prompt 后，并保留各自完整结束边界。

## 5. 负例审核：什么样的 rejected 才有训练价值

### 5.1 先排除不公平比较

不应把下列情况直接包装成有效偏好：

- 正例输入有答案提示，负例输入没有。
- 正例 provider 正常，负例恰好网络故障。
- 正例拥有更多剩余预算。
- 负例语法明显损坏，而目标却声称在优化工具效率。
- 正例只跑一步、负例被强制完整跑到失败。
- 为了凑负例，编造当时根本不在允许集合的动作。

这种数据可能容易让 DPO loss 下降，却没有教会所声称的能力。

### 5.2 重复调用必须依赖状态和时效

查天气不总是重复浪费。如果日期、目标城市或证据时效改变，再查可能必要。

同一个工具名与参数也可能由系统补全成不同实体输入。判定重复应核对目标版本、执行参数与证据有效性，不能简单按字符串相同决定。

因此负例标签应表述为“在此状态与有效证据下重复”，而不是“这个工具不好”。

### 5.3 空结果不一定是模型错误

一次合理探索可能得到空结果。只有明确控制环境并定义比较合同，空结果才可作为该对中较低信息价值的结果。

如果把任何空结果都惩罚，模型可能不再探索新候选。还要排查 fixture 对别名、餐馆全名和城市措辞的匹配是否过严，避免模型只是学会迎合测试数据接口。

### 5.4 局部反事实执行不是完整因果价值评估

从相同状态分别执行两个动作，可以更可信地比较它们的一步后果。但如果没有继续执行两条完整后续策略，就没有估计每个动作的真实长期 Q 值。

当前偏好不应被描述成“已证明全局最优轨迹”或“完整因果强化学习”。更准确的是“同状态、可执行的一步偏好审核”。

### 5.5 数据还应检查捷径

建议按动作、长度、来源、错误类型和重复模板检查正负分布。若 chosen 总是更短、固定带某个词或总用某个工具，模型可能学到标签捷径。

旧 H-004 曾报告长度 AUC=0.5 作为局部检查，但这不能证明不存在任何长度或词面捷径，更不能把这个旧结果移用到最新 128 对。最新偏好也需要自己的分布审核。

## 6. DPO 损失：从概率比到偏好分类

对同一个输入 x，定义完整 completion 的对数概率：

~~~text
sθ(y|x) = Σ_t log πθ(y_t | x, y_<t)

Δθ  = sθ(y+|x) - sθ(y-|x)
Δref = sref(y+|x) - sref(y-|x)

z = β × (Δθ - Δref)
L_DPO = -log σ(z)
~~~

θ 是正在更新的策略，ref 是冻结参考策略。目标推动 chosen 相对 rejected 的概率比，相比参考策略变得更大。DPO 不需要在这一步额外训练一个独立奖励模型。[DPO 原论文](https://arxiv.org/abs/2305.18290)。

本项目最新归档记录 β=0.1，参考策略是相同起始 Adapter，序列概率按完整 completion 求和。

### 6.1 用一个纯讲解例子看方向

下面的数字不是项目日志：

~~~text
参考策略：
sref(y+) = -20
sref(y-) = -22
Δref = 2

当前策略：
sθ(y+) = -18
sθ(y-) = -24
Δθ = 6

β = 0.1
z = 0.1 × (6 - 2) = 0.4
~~~

当前策略相对参考更偏向正例，z 为正，偏好损失低于初始相同策略时的 log(2)。

若当前与参考完全相同，Δθ=Δref，z=0，纯 DPO 项为约 0.693。归档说明记录过这个初始一致性检查；本次未重新运行。

### 6.2 为什么需要参考策略

没有参考校正的“正例概率比负例高”，会混入起始模型本来就有的偏好。DPO 的比较关注相对于参考的变化。

参考策略的基模、Adapter、模板、目标 Token 与计算 dtype 都应可追溯。缓存 reference logprob 时，键不能只用 pair_id 而忽略内容和模型版本，否则旧缓存可能悄悄污染训练。

缓存校验这一点是验证建议，不代表本次已检查最新云端实现具备所有字段。

### 6.3 β 不是学习率，也不是直接的采样温度

β 缩放偏好 logit；其理论来源与偏离参考策略的约束有关，但有限数据训练中的梯度、优化器与参考质量都会影响实际表现。

不能简单说“β 越大更新一定越小”或“β 越小模型一定更聪明”。它也不是生成时的 temperature。任何调整都应重做固定协议下的对照。

### 6.4 完整序列的梯度不会只落在不同的一个词上

虽然两个答案可能只差一个连接词，DPO 使用完整条件序列的概率和，梯度通过共享模型参数传播。后续 Token 的条件上下文也可能改变。

旧 H-004 假设卡曾预期梯度“几乎只落在连接词”，应当作待验证假设，不能当成 DPO 自动保证的属性。若真要限定训练位置，必须看到明确 mask 和相应审计。

## 7. 项目最新目标为什么叫“DPO＋SFT 保持项”

归档说明记录的目标有两种行：

~~~text
偏好行：
L_pair = -log σ(z) + 0.1 × CE(y+|x)

独立保持行：
L_keep = CE(y|x)
~~~

DPO 部分使用正负序列 logprob 的和；CE 按相应完整目标 Token 归一化。0.1 是偏好行中正例 CE 的系数，不等于全数据最终只有 10% SFT 贡献。

### 7.1 为什么增加正例 CE

相对差距变大可以通过提高 chosen，也可以通过更明显降低 rejected 实现；即使 chosen 的绝对概率下降，某些情况下偏好 margin 仍会上升。

正例 CE 直接鼓励保持 chosen 的概率，独立保持行则帮助保留已有能力。它们不能保证没有遗忘，但给出了区别于纯相对目标的信号。

### 7.2 为什么还要有成功 SFT 对照

如果 DPO 分支同时加入新成功动作和旧教师保持数据，模型改善可能来自这些正例，而不一定来自负例比较。

所以最新同时训练成功轨迹 SFT 分支：尽量匹配起点、数据日程和更新计划，让实验回答“加入偏好训练是否比这批正例 SFT 更有额外价值”。

这仍不是完美等算力消融，因为 DPO 要计算负例和参考项。

### 7.3 混合目标需要记录采样比例和归一化

全局优化受偏好行数量、保持行数量、目标长度、行顺序、微批次和梯度累积影响。不能只引用公式中的 0.1，就省略整个训练日程。

第五篇已经解释 Token mean 与 microbatch mean 的区别。最新云端 train.py 本次没有重读，因此本文不凭仓库通用脚本替它补写所有内部归一化细节。

## 8. Logprob 与 preference accuracy：同名指标可能不是同一个量

仓库的 evaluate_preference_logprobs.py 同时计算 completion 的平均 Token logprob 与整序列 logprob margin，并分别汇总正例被偏好的比例。

这份历史评分脚本不包含所有最新 DPO 训练逻辑，尤其不能把它的默认 preference_accuracy 直接等同于训练器中的参考校正偏好准确率。

### 8.1 至少区分三个 Margin

| 指标 | 定义 | 含义 |
|---|---|---|
| 原始序列差 | sθ(y+) − sθ(y−) | 当前模型对两个完整答案的概率比较 |
| 平均 Token 差 | sθ(y+)/长度+ − sθ(y−)/长度− | 长度归一化后的文本倾向 |
| 参考校正差 | β[(sθ+−sθ−)−(sref+−sref−)] | 相对参考策略的偏好变化 |

三者可能得出不同排序。目标长度不同时，平均 Token 与序列和尤其不能混算；改变成平均值也会改变原本的 DPO 目标，而不只是换一种显示单位。

### 8.2 高 Margin 不保证自主生成 chosen

评分是在给定两个固定答案时计算概率。在线生成要面对更大的候选空间，可能输出第三个动作、非法参数或在下一步走错。

因此应区分：

- pair scoring：给定正负答案，模型更偏向哪个。
- one-step generation：自主生成一步是否满足合同。
- full rollout：完整执行是否成功。
- reliability：多次运行是否稳定成功。
- deployment：是否通过发布、成本和回归门。

训练 margin 5.15 或偏好准确率 100% 只能证明相应偏好指标，不能跳过后四层。

### 8.3 对数概率怎样取正确位置

评分代码通过 causal shift，从 prompt_length−1 的 logits 位置开始对 completion Token 取 log probability，并排除 padding。目标应包括实际合同要求的结束符。

如果把 prompt 的概率也计入，长输入会污染比较；若截断 y−，又可能把不完整负例错当完整行为。Token 边界是实验定义的一部分。

源码：[偏好概率评分](E:/A_Louis/TravelAgent2/scripts/evaluate_preference_logprobs.py)。

### 10.3 旧 DPO 失败说明局部偏好没解决整段恢复

  → 求解

  → 在验证仍有效时提交
~~~

## 11. 当前奖励引擎：先保终态与约束，再看过程

reward.py 的默认 RewardConfig 为：

| 分量 | 默认权重 |
|---|---:|
| task | 0.40 |
| constraint | 0.40 |
| format | 0.04 |
| tool | 0.06 |
| grounding | 0.06 |
| efficiency | 0.04 |
| quality | 0.00，允许上限 0.10 |

当前默认过程权重合计 0.20，终态相关权重合计 0.80；配置还检查层级和总权重。quality 默认只记录、不影响训练总分，除非显式修改并校准。

这些是当前本地默认配置，不能认定每个历史实验都使用完全相同权重，也不能将旧假设卡的 reward 数字直接套到这套分解上。

### 11.1 层级门比单纯加权更重要

若出现非法环境修改、保护字段伪造或轨迹完整性问题，当前引擎可进入 unsafe 并给固定负分。错误提交、硬约束失败或终止合同不符，则让总分不超过对应负分上限。

这避免模型靠格式、少调用或流畅语言抵消关键失败：

~~~text
即使过程分不错，
如果提交不满足硬约束，
也不能因此变成正向成功。
~~~

### 11.2 为什么不能奖励“越短越好”

若奖励主要鼓励少工具、少 Token，模型可能直接 finish，省掉搜索、求解和验证。

当前效率分依赖终态是否成功，且属于较小的过程分量。实际发布还应在任务质量不回退的条件下看调用数，而不是让效率单独决定胜负。

### 11.3 奖励门与训练优化要分开

score 能给 episode 打分，说明有一个评分函数；它不证明这个分数已经在真实梯度更新中被消费，也不证明消费方向正确。

还需要验证：该 reward 与 rollout 对应、advantage 非零、模型 Token 对齐、优化器实际更新、最终权重被正确评测。

## 12. 奖励也会犯错：几个当前可见的边界

### 12.1 状态哈希变化不等于真正信息增益

_turn_rewards 里以 state_before_hash != state_after_hash，并结合 observation 成功等条件，判断 information_gain。

但是状态变化可能来自计数、时间或其他元数据，工具 ok 也可能返回空或重复信息。因此这是一种代理信号，不是语义信息增益的完整证明。

后续若将其用于更强 RL，应单独对比有效事实 / 产物的内容、来源、时效与是否填补缺口。不能用名称 information_gain 推导出已实现信息论度量。

### 12.2 重复判断与 SFT 去重合同未必一致

当前 reward 的步骤签名使用 action + arguments；第五篇的配对审核则把版本与 executed_arguments 纳入特定签名。

如果模型参数相同但系统补全实体不同，两套规则可能给出不同判断。这个差异应通过反例校准，不能让导出器认为是有效新动作、奖励却持续惩罚它。

本节是静态实现核对，不是本次新复现的训练故障。

### 12.3 Grounding 不是简单要求所有生成文本原样出现

当前 grounding 对 POI ID、日期和保护参数等检查较严格；对 search_pois.keywords、search_current_info.query 等生成式查询字段有区别处理，避免把合理改写一律当成伪造。

搜索短语是待查假设，工具返回才形成事实。另一方面，字符串出现在上下文中，也不自动证明它在当前版本、当前实体或当前时间有效。

因此 grounding 分数与最终研究证据门槛要配合，而不能互相替代。

### 12.4 环境失败和模型错误要分开

合理、合法的工具调用可能遇到真实超时或空结果。把所有外部失败都罚给模型，会教它回避有必要但不稳定的工具。

当前 TurnReward 与信用分配区分 invalid、external_failure、valid。区分依据仍需审查：接口 bug、输入不合理、供应商故障和 fixture 过严可能混在一起。

### 12.5 不要靠硬编码词面让分数变好

旧理由合同曾过于依赖某些连接词。模型改写了意思相近的句子，可能被严格词面判分误伤；反过来，固定插入关键词也可能掩盖错误理由。

更合理的拆分是：结构、动作和事实引用由确定性规则约束，理由是否与动作 / 证据一致另行检查。系统组装提高的分数应与 raw model 指标分列。

## 13. 传统 RLHF：如果真要做，还缺哪些东西

以经典人工反馈流程为例：

~~~text
监督示范训练初始策略
  → 收集同输入多候选的人类比较
  → 训练独立奖励模型
  → 用 PPO 等方法优化策略，并控制偏离参考
  → 独立评价与发布
~~~

这是一种代表性 RLHF 路线，不是 RLHF 唯一实现；人类偏好也可用于直接偏好优化。[InstructGPT 论文](https://arxiv.org/abs/2203.02155)。

### 13.1 当前为什么不必强行补一套奖励模型

当前很多旅行任务有可验证结构：预算、时间窗、证据、工具权限和任务终态。已有程序检查可以直接提供大量信号。

当前最新分支没有一份经过校准、覆盖充分且独立于训练选择的人类偏好集，也没有对应独立奖励模型验收。为了简历再加一个 Reward Model，反而会增加一个需要证明可靠的新模型。

### 13.2 真正需要人类评价的部分

可用于补充的方向包括：解释是否易懂、权衡是否体贴、推荐是否贴合真实偏好、澄清是否给用户增加不必要负担。

但这些偏好要有标注标准、多评审一致性、分歧处理和独立验证。由 GLM 纠错得到的工具调用，并不自动是人类反馈。

### 13.3 PPO 中参考策略与旧策略各是什么

参考策略 πref 用于控制对既有行为的偏离；旧策略 πold 是产生当前 rollout 的行为策略。二者可能在初期相同，但训练推进后职责不同。

PPO 的概率比比较当前策略与采样时旧策略，不应拿固定 reference 直接替代这个分母。Clipping 约束更新幅度，但不保证任何有限步更新都绝对安全。[PPO 原论文](https://arxiv.org/abs/1707.06347)。

## 14. GRPO：把同题多次尝试变成相对学习信号

对同一初始任务状态采样 G 条轨迹，得到回报 R₁…R_G。一个基本的组相对优势为：

~~~text
mean_R = mean(R₁…R_G)
std_R  = std(R₁…R_G)
A_i = (R_i - mean_R) / (std_R + ε)
~~~

高于组均值的样本得到正优势，低于均值的得到负优势。GRPO 用组内比较构造基线，避免单独训练同样用途的价值模型。[DeepSeekMath / GRPO 原论文](https://arxiv.org/abs/2402.03300)。

### 14.1 和成功轨迹 SFT 的根本区别

成功 SFT：把通过审核的动作当固定答案，用 CE 模仿。

GRPO：根据当前策略采样、执行与回报，对采样动作分配相对优势，再以策略优化目标改变概率。

两者都可能采集多条轨迹，但有没有策略概率比、优势和对应梯度更新，才是关键区别。

### 14.2 一个示意策略目标

用概念形式表示：

~~~text
ρ_i,t = πθ(token_i,t | history_i,t) / πold(token_i,t | history_i,t)

maximize:
aggregate_model_tokens(
    min(ρ_i,t × A_i,
        clip(ρ_i,t, 1-εclip, 1+εclip) × A_i)
)
- βKL × KL_regularization
~~~

此式用于解释组优势、策略比和参考约束的职责，不宣称当前脚本所有归一化细节都与原论文逐字相同。当前训练入口使用 loss_type="dapo"、scale_rewards="group" 等配置，具体聚合必须看真实实现。

### 14.3 工具 Agent 中的 history 包含环境反馈

后续动作依赖先前动作与工具观察。观察属于环境输入，不是模型生成动作，不应当作模型 Token 直接获得策略优势。

一个长轨迹的 completion 里可能穿插多段模型输出和工具结果。需要真实 mask 与边界对齐，不能把整个字符串都当作学生“说出来的答案”。

### 14.4 没有 Critic 不等于没有成本

GRPO 仍需多次生成、执行工具、记录旧策略概率、评分、计算新策略及参考项。对旅行 Agent，外部工具和长上下文成本可能比省掉价值模型更显著。

加大 G 可能增加发现成功的机会，也增加采集成本；它不是免费提高可靠性的参数。

## 15. 零方差与课程选择：为什么 rollout 很多仍可能没学到

GRPOGroupAuditor 会检查同组任务 ID、初始状态指纹、快照和环境版本、轨迹唯一性，再计算奖励均值、总体标准差和成功率。

当前默认最小组大小为 4，零方差阈值约 1e-8，优选成功率区间为 20%—80%。这些是当前代码默认，不是所有历史运行的实际参数。

### 15.1 全成功和全失败为什么都可能没有方向

~~~text
组 A：1, 1, 1, 1
组 B：0, 0, 0, 0
~~~

两组结果奖励都没有方差，组相对优势为零。A 说明该批太容易或采样太一致，B 可能太难或奖励太粗。

这不意味着任何优化器参数都绝对不变化：若同时有 KL、保持项或其他损失，仍可能更新。但这些更新不是来自新的结果奖励比较，不能据此宣称 RL 学会了任务。

当前组审核器会把零方差全成功组送往评测、其他零方差组送往 SFT 修复，避免把无信息组当作有效 GRPO 训练依据。

### 15.2 全失败不一定只能丢弃

若使用已验证的分解奖励，全失败轨迹也可能在合法动作、执行或证据方面有可比较差异。当前代码允许在明确 verified_partial_credit、非零方差等条件下，将某些低成功率组视为可学习。

但“有差异”不等于“差异正确”。如果只是某条轨迹多写了一个判分关键词，增加方差反而更危险。

### 15.3 前沿任务选择的代价

选取既可能成功又可能失败的任务，可以提高样本效率。但筛选后的难度分布已经变化：

- 不再代表原始用户任务分布。
- 容易题若完全移出，可能缺少保留能力的约束。
- 看到某组表现后再选择训练，会影响后续验证的独立性。
- 模型变强后，同一批前沿题可能变得过易，需要重新评估。

因此要保留原分布评测锚点，并区分用于课程选择的题和用于确认增益的新题。

### 15.4 为什么“给赢家奖励封顶”可能不起作用

考虑一组 G 条结果，其中一个赢家得 a，其余全为 b，a>b。忽略数值 ε，以总体标准差归一化：

~~~text
A_winner = sqrt(G - 1)
A_loser  = -1 / sqrt(G - 1)
~~~

在这个特殊组形中，只要封顶后赢家仍高于其他样本，改变 a−b 的绝对大小并不改变标准化优势。

这是可以从均值和方差直接推导的性质，不是所有奖励裁剪都无效。加入其他不同分数、ε、门控或 KL 后要重新分析；若裁剪让全部同分，学习信号反而消失。

旧 H-003 后续审查正是提醒：不能只看奖励数值变小，就假设策略梯度一定变小。

## 16. Long-Horizon 信用分配：最终成功该奖励哪些步骤

一个 Agent 可能先犯错，之后恢复并成功。如果把整条轨迹的正优势分给所有模型动作，早先错误也可能获得正向强化。

反过来，一条轨迹最终失败，前面合理获取证据的步骤未必都应该受相同惩罚。

### 16.1 仓库中的 B0 与 R1 研究分支

- B0：以整条轨迹的组相对优势为主要信号。
- R1：结合经过验证的逐轮信用，再投影到模型生成 Token。

当前代码中的 return_to_go_credit 被明确标为研究对照信号，不能因为它能计算一个数，就说 stock TRL 的 B0 已经使用了逐轮信用。

### 16.2 模型动作与环境失败的信用边界

policy_turn_credit_records 排除控制器来源步骤，并将模型动作分为：

| 类型 | 当前研究信用处理 |
|---|---|
| invalid | 固定负信用 |
| external_failure | 零信用 |
| valid | 本地过程分与折扣后的终态分混合 |

这种设计试图避免给无效动作分配最终成功的正信用，也避免把合法调用遇到的外部故障完全罚给策略。

但“external_failure 信用为零”不应说成“该位置在任何损失下都没有梯度”：独立 KL 或其他项仍需要检查。

### 16.3 从 turn 到 token 必须真的对齐

turn_credit.py 按 model token mask 的连续片段定位模型输出，排除工具结果，将逐轮信用映射到对应 Token。

如果片段数和信用记录对不上，代码会拒绝相关对齐，而不是猜测。工具返回后多出的最终 assistant 片段，如果不是部署策略动作，也不会自动获得终态正奖励。

训练器还检查有效非零逐轮信用、可比较轮次、错误动作是否拿到正信用、对齐拒绝和多余模型片段等统计。训练完成不代表候选可用，审计失败的结果可以标为 rejected。

源码：[逐轮记录](E:/A_Louis/TravelAgent2/backend/src/agentic/grpo.py)、[Token 投影](E:/A_Louis/TravelAgent2/backend/src/agentic/turn_credit.py)、[TRL 适配层](E:/A_Louis/TravelAgent2/ml/agentic/training/turn_credit_trainer.py)。

### 16.4 当前逐轮比较仍是近似

投影代码在组内按 turn_index 比较信用。但不同轨迹执行到第三轮，可能已经位于不同状态：一条正在补天气，另一条正在修路线。

相同初始任务、相同轮次，不等于当前业务状态相同。不能因此把所有逐轮比较称为严格同状态反事实，也不能自动视为无偏优势估计。

更强的后续研究应记录每个比较桶的状态、子目标或错误类型，并验证对齐规则是否改善完整任务。当前实现有工程防护，但效果仍需独立对照。

## 17. 采样分布与训练概率：格式约束可能改变什么

最新评测使用工具 schema 约束输出，这属于工程机制。若未来 RL rollout 也采用约束解码，需要核对实际采样分布与训练中计算的概率。

### 17.1 一个简化例子

假设基础模型对动作 A、B、C 的概率是：

~~~text
A: 0.2
B: 0.3
C: 0.5
~~~

当前状态禁止 C，生成端只在 A、B 中重新归一化：

~~~text
A: 0.4
B: 0.6
C: 0
~~~

若 rollout 从后一个分布采样，而训练却直接使用前一个分布的 logprob 作为采样概率，策略比的意义就变了。

这个例子用于说明问题，不是项目某次真实输出。

### 17.2 要核对哪些配置

- Temperature 与 top-p / top-k。
- 允许动作和 token grammar。
- Tokenizer、chat template、EOS 与工具返回后缀。
- 生成长度限制与截断。
- 采样时 Adapter 与旧策略版本。
- 多轮工具反馈实际如何加入下一轮输入。
- vLLM 与训练端的序列概率、mask 和数值差异。

不能只让最终 JSON 合法就视为 RL 概率合同已成立。

### 17.3 截断是一个策略事件

若截断 completion 被当作正常完整动作，奖励和概率都可能失真。当前 train_grpo.py 配置 mask_truncated_completions=True，并有 completion 长度和工具后缀相关预检。

这说明代码尝试处理边界，不表示所有在线超时、工具中断和 token 截断都已经被同一种规则正确覆盖。需要记录截断比例及其样本分布。

## 18. 当前 GRPO 入口具备什么，哪些不能据此宣称完成

代码中存在：

- task + snapshot 组成的语料格式。
- train / validation 任务 ID 与初始状态指纹隔离。
- 必要工具快照、不可行证据和数据合法性预检。
- completion 长度与工具调用轮数预算检查。
- rollout-only 诊断分支。
- B0 / R1 配置、模型 / 语料 / 输出产物来源记录。
- DAPO 风格 Token 聚合配置、组内 reward scaling 与截断 mask。

这是一套可审查的训练基础设施，而不是自动完成的训练结果。

### 18.1 Preflight 通过不等于已经更新参数

preflight-only 主要检查语料与配置。rollout-only 可以检验采样、奖励和方差，但不等于 optimizer.step 已执行。

即使实际训练完成，也要验证新权重哈希、有效更新、相同运行时下的完整任务，以及预定发布门。

### 18.2 部分历史语料已经被明确拒绝

grpo_training.py 中出现 LEGACY_DECISION_REPLAY_RETIRED 检查，拒绝某些旧决策回放标记。这与第五篇旧 SFT 数据不能直接迁移的原因一致：环境、状态和权限合同改变后，历史资产必须重新审核。

文件里的历史步数常量或工具路径，也不能当作当前统一 Agent 固定按某个轮数运行的证明。

## 19. 旧 H-003 / H-004：值得讲的是结果、勘误和边界

### 19.1 H-003 的前沿筛选与结果

旧 H-003 用学生多次采样寻找有组内差异的难题，再做 GRPO。报告记录第二轮在 hard 池中的 reward 与通过率提高，但 internal-dev 精确成功门未通过。

它展示“组内方差可以产生学习信号”，却没有证明可以无损提升所有任务，也没有完成最新架构的发布。

特别要注意：hard 池已被用于摸底和前沿选择，未训练的部分也不自动成为全新、未接触的确认集。不能仅凭其中对照部分涨幅更大，就宣布已排除所有记忆、选择和分布混杂。

### 19.2 使用统一四采样表，避免拿单采样混比

旧后续报告给出的可比表为：

| 旧模型 | internal-dev 四采样 full success | hard 平均 reward 相对 H-001 |
|---|---:|---:|
| H-001 h48 SFT | 0.869 | 基线 |
| H-003 r2 GRPO | 0.803 | +0.170 |
| H-004 r2＋DPO | 0.828 | +0.176 |

右列是旧 hard 指标中的 reward 差，不是 17.0 / 17.6 个百分点的任务成功提升。不能将 0.869 与旧单采样 0.887 随意替换。

H-004 相比 H-003 在该 internal-dev 指标提高约 2.5pp，但仍没有跨过当轮 0.85 门槛。

### 19.3 偏好目标拟合得很好，任务门依然没过

H-004 记录 DPO preference accuracy 为 100%、margin 约 5.15，固定 12 步停止。它主要修旧理由合同，结果仍只有 0.828。

这是一组很适合面试的反例：优化目标内部的成功，不能替代产品或完整任务成功。还要检查标签是否对准真实能力。

### 19.4 统计勘误不能省略

H-003 后续记录指出某个 McNemar 脚本有 off-by-one，相关 11 跌 / 3 涨比较的双侧 p 应为 0.057，而非早先 0.013。

所以不能继续把那一比较称为统计显著回退。与此同时，“没有达到显著”也不代表“证明没有退步”；未过预设性能门仍可构成不发布理由。

本篇引用的是已带勘误的历史报告，没有重新计算原始数据，更不将历史所有强结论照搬为当前已验证结论。

### 19.5 从词面合同转向职责拆分

H-004 的早期建议曾倾向强制理由形式；后续路线明确要求模型负责语义理由，系统负责确定性连接词，并分开 raw_model_contract_success 与 assembled_system_success。

这可以减少模型承担的无意义格式负担，但不意味着把判分关键词插进去就提升了模型推理。新旧模型必须在同一 parser、renderer 和工具环境下重评。

## 20. 当前为何优先补恢复 SFT，而不是立即加大 RL

最新归档指出成功动作池中缺少若干明确失败上下文后的成功恢复动作，包括 RESEARCH_EVIDENCE_INSUFFICIENT、VALIDATION_NOT_PASSED 等类型。

如果训练集里没有这些状态下可信的正向行为，先让教师在新的 train 实例恢复，再小步 SFT，通常比在尚未校准奖励上扩大昂贵 rollout 更容易验证原因。

### 20.1 进入新 GRPO 实验前，至少要满足什么

| 条件 | 需要的证据 |
|---|---|
| 环境可信 | 相同 snapshot 可恢复，工具真实执行，故障与状态可审计 |
| 奖励可信 | 对已知好坏反例方向正确，模型错误与外部失败区分 |
| 有效探索 | 不只是全同分；组内差异来源有意义 |
| 概率合同 | 采样、旧策略 logprob、mask 与约束解码一致 |
| 信用对齐 | 模型 Token 不混入工具观察，错误动作不吃正奖励 |
| 对照可比 | 同起点、同运行时、预算和种子预先定义 |
| 独立评测 | 调参与确认分开，保留旧能力回归 |
| 成本可控 | 计算采样、工具、参考与优化的总成本 |

这是下一轮实验门槛建议，不是宣称各项已全部完成。

### 20.2 技术选择表

| 剩余主要错误 | 优先调查或方法 |
|---|---|
| 提示看不到关键状态 | 先修上下文投影与状态传递 |
| 工具事实或执行器有 bug | 工程修复与同栈回归 |
| 正确动作缺少示范 | 教师接续 / 定向 SFT |
| 多个合法动作之间有可信偏好 | 小规模 DPO 与正例 SFT 对照 |
| 需要探索且有可信延迟回报 | 受控 GRPO / 策略优化 |
| 主观体验无法程序度量 | 人类评价协议，必要时考虑偏好模型 |

这个表是基于当前问题的方案选择框架，不是保证某方法一定有效。

## 21. 严格质量通过率与多采样指标

### 21.1 成功条件先由任务类型决定

可行规划要提交满足任务和约束的方案；信息缺失应提出必要澄清；不可行或需授权权衡时，应给出有证据的处理。

随后还要满足适用的证据、预算、参数、独立验收和故障触发要求。awaiting_user 并不必然失败，合法方案等待用户确认可以是正确终态。

反过来，JSON 合法、工具 ok、Job completed、reward 正值，都不能独立替代严格质量通过。

### 21.2 三种重复采样口径

本篇明确使用以下含义：

| 口径 | 问题 |
|---|---|
| 平均单次成功率 | 随机取一次执行，有多大比例成功？ |
| pass@k：至少一次成功 | 给 k 次尝试，有没有一条成功？ |
| pass^k：全部成功 | 同一任务重复 k 次，是否每次都成功？ |

若假设每次独立同分布、单次成功概率为 p，则讲解式为：

~~~text
至少一次成功：1 - (1-p)^k
全部成功：p^k
~~~

真实 Agent 的多次运行常共享环境和模板，独立性不能默认成立。报告应按实际运行记录计算，并声明具体定义；不能把 pass@4 和 pass^4 都缩写成“4 次成功率”。

### 21.3 多采样不增加同样数量的独立任务

80 个状态每个跑 4 次，得到 320 条执行结果，但独立业务状态仍是 80 个，甚至这些状态之间还有来源关系。

重复采样有助于观察不稳定性，却不能简单按 320 个独立任务算置信区间。最新 120 个实例也有 40 个相关来源组，需要考虑组内相关性。

### 21.4 100% 观察值不等于总体可靠性为 1

有限集合全部通过，只能说明这批输入和条件下未观察到失败。未覆盖的真实工具、多轮更改、长期记忆和复杂故障仍可能失败。

因此本项目保留旧问题复测，并拒绝把 120/120 写成真实服务总体正确率。

## 22. 配对统计：怎样判断增益，而不是只比较两个百分比

### 22.1 先看同题输赢

同一套题比较 A、B，至少记录：

| | B 成功 | B 失败 |
|---|---|---|
| A 成功 | 两者都成功 | A 独有成功 |
| A 失败 | B 独有成功 | 两者都失败 |

新增成功与新增失败比两个孤立均值更有信息。

最新归档中，SFT 在新实例上相对原模型修复 6 题且无新增失败；DPO 修复同样 6 题但新增 2 题失败。这是配对事实，不能只压缩成“100% 比 98.33% 高”。

### 22.2 McNemar 看的是不一致对

对二元、同题配对结果，McNemar 主要关注两模型结果不一致的样本。大量共同成功并不会自动让很少几个差异变得极其显著。

不过若实例共享来源、每题又重复采样，简单把每条执行当独立 pair 仍不合适。项目历史协议把 source_state_id 作为主要统计单位，并要求聚类 bootstrap 等处理。

不能看到“有 McNemar 脚本”就推断所有报告已经正确解决了相关性；H-003 的勘误本身说明统计代码也需要审核。

### 22.3 置信区间与发布门回答不同问题

- 点估计：这次观察到差多少。
- 置信区间：在声明的抽样假设下，不确定性有多大。
- 非劣门：某类旧能力最多允许退多少。
- 业务绝对门：总体最低成功标准是什么。

“p 大于 0.05”不证明两个模型等价；“平均显著提高”也不能覆盖关键安全子集退步。

本篇没有重算最新 120 题的 CI 或显著性，避免用归档汇总数伪造比原始证据更强的统计结论。

### 22.4 预先选指标，避免结果出来后挑赢的那个

如果同时比较多个模型、种子、checkpoint、子集和效率指标，总能找到某个更好看的数字。

应预先声明主要候选、主要指标、回归门、比较方法和多重比较处理。历史 promotion 协议包含 Holm 校正等要求，但那是该历史协议的规定，不代表最新实验已经照搬并执行了全部项目。

## 23. 发布协议：先冻结，再评测，失败后不能偷偷重开同一张卷

它说明另一个重要区别：写好了门槛，不等于已经有数据、跑完模型和通过发布。

哈希可以帮助发现已注册来源重叠，但前提是来源记录真实且完整。不能把字段都填上就等同于语义上绝无泄漏。

### 23.3 访问日志能说明什么

代码核对事件序号、前一事件哈希、当前事件哈希、campaign 开闭和访问预算。

这能使日志内的修改与断链更易察觉，却不自动防止有文件权限的人绕开工具读取题目。真正保护还需要访问控制与职责隔离，不能把哈希链说成绝对不可绕过。

最新三个模型已经在 120 题上产生结果，原先指定的主要候选是 DPO。看到 SFT 更好后，如果据此更换候选或继续修复，原集合便参与了选择。

合理做法是如实保留结果，明确其用途改变，并对最终冻结方案另作确认。不能不断换 checkpoint，直到同一集合全过，再说是一次未见测试。

## 24. 下一轮怎样设计，才能回答一个清楚的问题

以下是建议方案，没有新建云端任务、调用教师或训练模型。

### 24.1 先选一个错误假设

例如：

> 候选退步主要因为成功轨迹数据缺少“求解前置失败后重新补证据、重求解、重验证”的状态，而不是 Adapter 容量不足。

这个假设能指导数据采集与对照，比“再加一千条、再换 GRPO”更可检验。

### 24.2 冻结一个最小对照

| 分支 | 作用 |
|---|---|
| 保留模型 | 提供当前可用能力基线 |
| 恢复状态 SFT | 检验补充正向恢复监督是否足够 |
| 同正例、同保持数据的 DPO 对照 | 检验对应负例是否提供额外价值 |
| 条件成熟后的小型 GRPO | 检验剩余长程探索收益 |

不用一次同时运行所有分支。先确认数据和奖励，再按前一结果解锁后续，避免过多方法让归因更困难。

### 24.3 控制变量清单

应固定或明确记录：

- 相同初始模型和 Adapter。
- 相同环境、工具版本与判分器。
- 相同训练 / 开发来源规则。
- 完整动作目标与模板。
- 数据混合、更新次数与损失归一化。
- 采样 / 训练种子分别记录。
- 推理时同样的格式约束与超时。
- GPU、模型服务和并发条件。
- 总采样、工具、优化及评测成本。

若无法等计算量，应公开成本差异，并同时提供等质量成本或学习曲线等分析，不能把“同更新数”当完全公平。

### 24.4 先诊断，再冻结确认

开发阶段可以分析错误、调整数据和验证工程修复。确认阶段则应锁定候选和协议，禁止根据结果反复修同一模型后继续当盲测。

还应保留原能力、旧故障、未见组合与必要真实工具检查，分开报告，不用一个总体均值覆盖所有维度。

### 24.5 云端产物与发布条件

训练、采样和故障验证仍应在云端隔离运行，保存数据、概率、奖励、权重和运行环境身份。不要为写面试材料重新发起付费实验。

通过离线门之后，还应验证模型加载、失败回退、成本、时延与服务稳定性。模型实验通过只是产品发布的一部分，第四篇的可靠性条件仍然有效。

## 25. 一个完整失败案例：从“换算法”回到可验证假设

下面结合归档中的错误类型构造讲解过程，不是本次新增运行日志。

### 25.1 观察到的现象

DPO 候选在证据不足时先求解，得到拒绝；随后验证空行程；补充操作后得到新行程，却没有验证新版本就尝试 finish。

如果只看最终分数，它是一条失败；如果只看部分工具调用，可能有成功响应；如果只看偏好 accuracy，训练仍然可以是 100%。

### 25.2 分层定位

1. 输入层：模型是否看到缺失天气、验证对象为空、计划版本更新？
2. Harness：是否正确拒绝提前求解和过期验证提交？
3. 执行层：是否保存了求解结果、部分成功工具产物？
4. 策略层：模型是否理解补证据 → 求解 → 验证 → 提交顺序？
5. 数据层：训练是否覆盖这些失败后的真实状态？
6. 奖励层：是否把无效验证或普通状态变化误判为进展？
7. 评测层：是否要求故障实际触发，是否保留失败？

### 25.3 不同原因对应不同处理

- 模型没看见状态：修投影，再同栈比较。
- 状态正确但选错：在新 train 实例采集接续监督。
- 两个恢复动作都合理但预算差异可信：构建同状态偏好。
- 必须多步探索才能找到解：奖励与概率合同准备好后研究策略优化。
- 判分规则错误：先修评测并重跑所有基线，旧成绩保留。

这个思路可以解释“为什么没有机械地把 SFT 换成 GRPO”，也能展示 Agent 开发与后训练之间的联系。

## 26. 十二组高概率面试追问

### Q1：SFT、DPO、RLHF、GRPO 怎么选？

**回答主线：** SFT 学给定动作，DPO 学同状态相对偏好，RLHF 描述人类反馈驱动的流程，GRPO 是组相对奖励策略优化。先判断错误与信号，再选方法。

**继续追问：为什么没把四个都做一遍？**  
技术名称不是验收目标。当前恢复正例和奖励校准还有缺口，先做可信 SFT 和小规模偏好对照更容易归因。

**不要说：** “GRPO 比 DPO 更新，所以一定更适合”。

### Q2：你的 DPO 正负例怎么来的？

**回答主线：** 最新正例来自完整成功且经过动作审核的学生轨迹；在同一 Ledger / provider 快照的独立副本中执行正负动作，核对相同输入与权限，比较新信息、重复或合规空结果。

**继续追问：是不是把成功轨迹与失败轨迹拼起来？**  
不是任意拼。不同中间状态的动作不能直接组成同输入偏好。最新 128 对覆盖 41 个任务，详细构造依据归档说明，本次没有现场重跑。

**不要说：** “成功轨迹中的每一步一定优于失败轨迹的每一步”。

### Q3：写出 DPO 的核心公式，并解释 reference。

**回答主线：** z=β[(logπθ(y+)−logπθ(y−))−(logπref(y+)−logπref(y−))]，损失 −logσ(z)。reference 是冻结起点，用来衡量相对偏好变化。

**继续追问：初始策略与 reference 相同怎么办？**  
纯 DPO 项的 z=0、loss≈log2；这个检查能发现参考或 Token 不一致，但不代表全部训练实现都正确。

**不要说：** “reference 就是当前 rollout 的旧策略”——在 PPO / GRPO 中它们职责不同。

### Q4：为什么 DPO 还要加 SFT 保持项？

**回答主线：** 相对 margin 可以通过压低负例增大，并不保证正例绝对概率保持。正例 CE 和历史保持样本提供直接模仿信号。

**继续追问：那你证明是 DPO 的收益了吗？**  
必须与相同正例、保持数据和起点的 SFT 比。最新 DPO 没有在完整任务成功数上超过 SFT，且两者计算量不同。

**不要说：** “DPO 分支提高了，所以负例一定有效”。

### Q5：Preference accuracy 100% 为什么还失败？

**回答主线：** 它只在固定两个答案中比较概率，在线会生成更多其他动作，且后续状态与恢复仍可能出错。旧 H-004 就出现偏好全对而任务门未过。

**继续追问：Margin 大是否至少说明 chosen 常被生成？**  
也不一定。需区分原始序列、平均 Token 与参考校正 margin，再看自由生成与完整 rollout。

**不要说：** “训练 reward accuracy 就是业务正确率”。

### Q6：GRPO 为什么需要一组结果？全都失败怎么办？

**回答主线：** 同题多次采样形成组基线和相对优势。全同分没有结果比较方向；若全失败但存在可信分解奖励差异，可以研究部分信用，否则先补 SFT 或环境。

**继续追问：多采样几次就一定有方差？**  
不保证。确定性解码、任务过易 / 过难、奖励过粗都可能让结果相同。增加 G 还增加成本。

**不要说：** “advantage 全零仍然证明 RL 有效”。

### Q7：为什么奖励封顶可能没用？

**回答主线：** 在一个赢家、其他同分且忽略 ε 的组形中，标准化优势只依赖组大小；保持赢家领先而缩小差值，优势不变。

**继续追问：那所有 clipping 都没用吗？**  
不是。奖励裁剪、概率比 clipping、KL 和优势归一化是不同机制；多档分数、门控和 ε 都可能改变结果。

**不要说：** “奖励数值小了，梯度必然同比变小”。

### Q8：Agent 多轮信用怎么分到 Token？

**回答主线：** 轨迹级 B0 把终态优势给模型生成；R1 尝试结合逐轮信用，按工具结果 mask 分段映射。无效动作不给正信用，外部失败另行处理，对齐不明就拒绝。

**继续追问：同一轮次就是同一状态吗？**  
不是。当前逐轮比较按索引，是近似；分支状态可能不同，不能称严格同状态因果优势。需要状态或子目标级审计。

**不要说：** “有过程奖励就解决了 long-horizon credit assignment”。

### Q9：工具 schema 约束输出为什么会影响 RL？

**回答主线：** 约束改变允许 Token 和归一化后的采样概率。训练若使用未经同样处理的概率，旧策略比与实际采样不匹配。

**继续追问：但 SFT 时也约束输出啊？**  
两者都要合同一致；RL 额外依赖采样概率与策略比，所以不能只验证最终 JSON 合法。

**不要说：** “约束解码只影响显示格式，对训练没影响”。

### Q10：项目到底做过 GRPO 没有？

**回答主线：** 旧 H-003 有真实 GRPO 训练记录，hard 指标改善但整体门未过；当前统一 Loop 的最新主线是 SFT 和 DPO 对照，没有完成相应有效 GRPO 验收。

**继续追问：为什么不能把旧成绩写到当前 Agent？**  
模型、动作、环境与判分合同不同。只能按版本讲历史经验，不能跨版本归因。

**不要说：** “完全没做过”或“当前完整旅行 Agent 已通过 GRPO 达到 95%”。

### Q11：120/120 为什么还不发布？pass@4 和 pass^4 又有什么区别？

**回答主线：** 新集合满分不能覆盖旧故障回退，且来源相关、候选选择存在边界。pass@4 看至少一次成功，pass^4 看四次都成功，后者更关注稳定性。

**继续追问：重复四次是不是样本量乘四？**  
运行记录数量增加，独立任务量不按同倍增加，需要按来源或状态考虑相关性。

**不要说：** “一个集合全对就证明总体可靠性 100%”。

### Q12：你下一步怎么证明后训练有价值？

**回答主线：** 冻结错误假设，补新的恢复 train 状态，匹配 SFT / 偏好对照，校准奖励与概率合同；按旧能力、新组合、故障和成本分层评测，再用新确认集决定发布。

**继续追问：你现在能展示什么？**  
源码中的审核、奖励和信用分配实现，历史结果及勘误，最新归档的同机对照和回归失败；本篇没有新增现场训练证据。

**不要说：** “再多训一点肯定能过”。

### 27.1 三分钟讲述稿
