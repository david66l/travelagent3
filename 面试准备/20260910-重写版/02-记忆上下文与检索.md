## 阅读说明

本篇根据项目源码和实际调用关系整理。沿用上一篇的轻量文档工作方式，本次没有启动本地服务、训练、Embedding 推理或数据库实验，也没有重新探测云端连接。文档先保存于项目的面试准备目录，未声称已同步云端。

文中区分：

- **代码事实**：能在源码中定位的字段、调用和处理逻辑。
- **静态推导**：依据代码分析可能发生的行为，本次未运行复现。
- **改进建议**：未来可实施的设计，不是当前已有功能。
- **示意案例**：帮助理解的输入和状态，不是真实用户记录。

尤其注意：当前向量模型默认关闭、主 POI 工具优先结构化检索。仓库中“有向量字段”“有检索函数”和“当前主请求真的经过该函数”是不同证据。本篇不把旧面试材料中的三路检索与 RRF 直接复述为现状。

## 1. 先分清记忆、上下文、检索、缓存与模型参数

### 1.1 五个概念分别回答什么问题

| 概念 | 回答的问题 | 本项目中的例子 |
|---|---|---|
| 记忆 | 哪些信息跨步骤或跨会话保留下来？ | 用户画像、近期消息、Agent 失败历史 |
| 上下文 | 本轮调用模型时实际给它哪些信息？ | 当前目标、相关证据摘要、最近决策 |
| 检索 | 从较多信息里怎样找到本次需要的内容？ | 按城市筛景点、按向量找相似画像 |
| 缓存 | 怎样减少重复读取或计算？ | Redis 热会话、工具数据缓存 |
| 参数学习 | 怎样改变模型遇到某类状态时的行为倾向？ | 工具策略 SFT、DPO |

同一份数据可以同时参与多个机制。例如，用户画像长期存在数据库里，读取结果可能被缓存，部分字段随后被放进模型上下文。但保存画像不等于训练模型，检索画像也不等于查询整个聊天历史。

### 1.2 三种“模型好像记住了”的不同原因

1. 前一轮对话仍在本轮 prompt 中。
2. 应用从数据库召回事实并重新提供给模型。
3. 模型参数训练后形成了处理类似问题的能力。

例如用户说“还是按上次的预算”，可能需要第 1 或第 2 种机制。后训练提高工具策略正确率，不会自动让模型知道某位用户上次花了多少钱。

### 1.3 KV cache 不是什么

KV cache 属于模型推理中复用注意力中间计算的机制。它不提供用户画像 schema、永久保存承诺、跨用户权限或修改撤销语义。

因此，本项目的 Redis 会话状态、PostgreSQL 画像和 LangGraph 检查点不能统称为 KV cache。它们服务的是应用状态管理。

## 2. 全局数据地图：一次对话中的信息去哪里

~~~text
用户当前输入
   │
   ├── 最近消息窗口
   ├── 已累积的 personal / trip 画像
   └── 上一轮 slots 中仍适用的任务语义
   │
   ▼
需求解析 TravelSlots
   │
   ├── 本人长期画像 ─── PostgreSQL user_profile_vectors
   └── 相似画像线索 ─── 已有偏好向量查询（条件具备时）
   │
   ▼
冲突合并 + 画像更新 + 缺失/歧义/可行性检查
   │
   ├── 会话状态 → Redis 热/温快照、PlanningJob 状态
   └── GoalLedger → AgentLedgerState
                        │
                        ├── 工具读取城市 / POI / 实时资料
                        ├── Facts / Artifacts 保存来源和版本
                        └── PolicyContext 投影
                                 │
                                 ▼
                           本轮策略模型输入
~~~

这里存在两类检索：

- **用户记忆召回**：处理个人偏好与历史记录。
- **领域证据检索**：处理城市、景点、交通、营业与时效信息。

二者可以共同影响规划，但信任来源和更新策略不同。不能把“相似用户喜欢爬山”当成当前用户“必须安排爬山”的硬约束。

## 3. 会话状态：personal、trip 与 slots 的分工

### 3.1 默认会话结构

core/conversation_state.py 创建 schema_version=1 的状态，主要包含：

~~~json
{
  "recent_messages": [],
  "profile": {
    "personal": {
      "food_preferences": [],
      "interests": [],
      "pace": "moderate",
      "avoid": [],
      "accommodation_preference": null
    },
    "trip": {
      "origin": null,
      "destination": null,
      "travel_days": null,
      "travel_dates": null,
      "travelers_count": null,
      "travelers_type": null,
      "has_elderly": null,
      "has_children": null,
      "budget_range": null,
      "special_requests": []
    }
  },
  "phase": "gathering",
  "turn": 0,
  "last_intent": null,
  "missing_required": [],
  "revision": 1
}
~~~

示意省略了时间字段。recent_messages 最多保留最近 10 条，消息包含 role、content、timestamp。

### 3.2 为什么分 personal 与 trip

概念上，兴趣和住宿偏好可能跨旅行复用；目的地、日期、人数和同行人通常属于当前旅行。如果混在一起，新的一趟旅行可能错误继承上一趟的老人/儿童、必去项或预算。

但分了两个字典不等于完整生命周期已经做好：

- personal 中的字段不一定每轮都写入长期画像表。
- trip 字段是否在所有“新旅行”入口都正确清空，需要调用链和测试证明。
- 有些信息只在 slots 或 GoalLedger 中，不能仅靠 profile 重建当前任务。

### 3.3 slots 保存什么

TravelSlots 是解析和规划之间更具体的字段契约，包含旅行需求以及任务层的信息需要。例如：

- food_prefs、food_taboos。
- must_visit、must_not_visit。
- transport_preference、max_walk_minutes。
- intent_kind、information_needs、current_info_queries。
- transport_modes_requested、constraint_flexibility。

其中“需要查某活动”“需要城际车次”描述本次任务，不应自然转为长期用户偏好。

### 3.4 当前字段映射的真实细节

slots_to_patch 中可以看到：

| TravelSlots | 会话 profile 字段 |
|---|---|
| total_budget | trip.budget_range |
| travel_companion | trip.travelers_type |
| food_prefs | personal.food_preferences |
| food_taboos | personal.avoid |
| must_not_visit | personal.avoid |
| must_visit | 以“必去：名称”形式追加到 trip.special_requests |
| interests | personal.interests |

这里有一个值得面试讨论的边界：**食物禁忌和禁去景点进入同一个 avoid 列表**。这种宽泛存储便利，但会弱化类型和作用域；从 profile 逆向还原时不容易分辨某项是食物还是地点，也可能把本次禁去点误当成长期偏好。

本次确认的是映射本身，不是已经复现某次错误行程。理想改进是保留类型明确的字段、实体类型与旅行作用域，并做序列化往返测试。

## 4. 一轮输入怎样与已有记忆合并

### 4.1 process_user_turn 的实际顺序

~~~text
读取 recent_messages 最近 10 条
→ flatten_profile
→ DemandParserAgent.parse(当前文本、历史、已知画像)
→ 保留上一轮未被本轮显式修改的任务语义
→ ProfileRecallAgent.recall
→ MemoryConflictResolver.resolve
→ 歧义检查
→ slots_to_patch + merge_profile
→ 可行性和缺失字段检查
→ 更新 slots / inferred_slots / last_intent 等
→ 追加本轮用户消息，turn + 1
~~~

消息是在本轮解析完成后追加，解析输入还单独包含当前文本。不能假定 recent_messages 中已经有本轮消息，再在 prompt 中无条件重复添加。

### 4.2 “没说”“明确清空”和“False”为什么必须区分

示意：

- 没说交通方式：可以沿用之前仍有效的任务要求。
- 明确说“不用查高铁”：应撤销旧的城际交通信息需要。
- 说“这次不带老人”：False 是明确条件，不应当成缺失。

retain_agent_semantics_from_previous_turn 用 current.model_fields_set 区分模型 JSON 是否显式输出字段。对于它覆盖的任务语义字段：

- 本轮没有输出：可以继承前值。
- 本轮显式输出空列表：空列表有效，可以清除旧值。

这是精确的局部能力，不能推广为所有画像字段都具备同样的撤销语义。后面的冲突合并对布尔与列表使用了不同规则。

### 4.3 ProfilePatch 的四种操作

| 操作 | 当前作用 | 示例 |
|---|---|---|
| set | 覆盖受支持的标量或列表 | 将目的地设为上海 |
| add | 列表去重追加 | 增加博物馆兴趣 |
| remove | 移除列表中的匹配内容 | 删除某个 avoid 项 |
| clear | 列表清空或标量置 None | 清空旧日期 |

merge_profile 使用深拷贝避免直接修改原对象，只处理相应字段白名单。set 的标量值为 None 时不会作为清空执行，清空应走 clear。

**能力与接入要分开：** 通用函数支持 remove/clear，而本轮 slots_to_patch 主要生成 set/add；自然语言用户修改另有 RevisionOperation 路径。不能因为函数支持删除，就声称所有聊天说法都能完整删除长期偏好。

### 4.4 一个三轮示例

> 第一轮：“去上海三天。”  
> 第二轮：“带老人，走路不要超过半小时。”  
> 第三轮：“这次不查城际交通。”

期望是第二轮补充同行与步行限制，第三轮只撤销城际信息需求。目的地与天数继续有效。

检查代码时要逐层问：解析出来了吗？显式字段集合正确吗？画像映射保留了吗？slots 是否还在？GoalLedger 最终收到什么？面试不能只回答“把上下文传给 LLM 就能理解”。

## 5. 热、温、冷三级会话记忆（温层即 warm，也称暖层）

### 5.1 每层保存什么

| 层 | 位置 | 默认期限 | 作用 |
|---|---|---:|---|
| 热 | Redis session:{id}:state | 30 分钟 | 活跃会话快速访问 |
| 温 | Redis session:{id}:warm | 24 小时 | 热键失效后近期恢复 |
| 冷 | PostgreSQL Conversation.state_snapshot | 不按 Redis TTL 删除 | 长期归档恢复 |
| 定位指针 | Redis 中的 conversation_id 指针 | 90 天 | 从 session 定位冷记录 |

热和温是两个不同键及 TTL，不是自动建立了两套独立容灾系统。若它们位于同一 Redis 故障域，一次故障可能同时影响二者。

hot_set 依次写热键、刷新温快照。_compact_snapshot 主要是 deepcopy 和补充 updated_at，不做语义摘要；“compact”函数名不能当成压缩算法证据。

### 5.2 缓存未命中时怎样读取

MemoryManager.load_state：

~~~text
热键有值 → 返回
否则温键有值 → 返回，可选提升到热层
否则通过 Redis conversation_id 指针读 PG
否则 session_id 若是合法 UUID，尝试直接按会话 ID 读 PG
否则返回默认状态
~~~

chat_runtime.manager.load_state 在此基础上规范 schema；如果状态仍没有有效会话内容，再读最近 PlanningJob.user_feedback，并尝试重新写热状态。

### 5.3 缓存未命中与 Redis 故障不是同一路径

上述链路主要描述“get 成功但没有值”。如果热键读取直接抛连接异常，MemoryManager.load_state 没有在每层包独立容错继续向下查；调用方 chat_runtime 捕获后会走默认状态与 PlanningJob 回退。

因此不能简单说“Redis 挂掉就必然自动从 Conversation 冷快照完整恢复”。需要结合具体入口、异常处理和可用持久记录判断。

### 5.4 SessionManager 名称也可能误导

graph/session_manager.py 的 load 实际只读热→温，异常返回 None，没有直接走 MemoryManager 的完整冷恢复。is_expired 检查的是热键，而不是所有归档是否都不存在。

面试中如果说“所有入口统一热温冷恢复”，会与代码不符。更准确的是“有完整恢复管理器，但部分入口仍需要统一恢复语义”。

## 6. 归档、老化与删除

### 6.1 归档什么时候发生

Celery 配置声明：

| 任务 | 调度 |
|---|---|
| 活跃会话增量归档 | 每 5 分钟 |
| 断线归档登记 | 默认延迟 30 分钟 |
| 到期归档扫描 | 每分钟 |
| 温状态老化整理 | 每小时，处理超过 24 小时的记录 |
| 旧冷快照压缩 | 每天，处理超过 90 天的记录 |

这些是配置，不表示本次验证了 Beat/Worker 已部署运行。任务存在、派发成功、实际落库成功是不同状态。

断线后 30 秒的取消宽限属于另一个机制，不能与 30 分钟归档混淆。

### 6.2 为什么延迟归档用 Redis sorted set

schedule_delayed_archive 将 session_id 和到期时间写入有序集合，由定时扫描处理。这样避免把一个 30 分钟 countdown 消息长期放在 Worker/Broker 的待确认生命周期中。

这减少一类长延迟消息重复投递风险，但仍要验证任务失败重试、重新断线更新期限、扫描中途退出等情况。它不是“用了 sorted set 就绝不会重复或漏归档”。

### 6.3 archive_to_cold 做什么

1. guest 分支跳过冷归档，并删除温快照。
2. 尝试按 session 获取归档锁。
3. 在锁内读取温快照。
4. 校验 user_id 能否解析为 UUID。
5. 根据已有 conversation_id 更新会话行，否则创建。
6. 提交数据库事务。
7. 写回用于定位冷记录的指针。

锁后端异常时存在无锁继续的分支。新建会话时还会在数据库提交前把 conversation_id 写回温快照。因此这不是一个 Redis 与 PostgreSQL 的原子事务，失败边界值得专项验证。

### 6.4 90 天压缩保留什么

compress_snapshot 仅保留少量字段：last_intent、根级 destination/travel_days、身份信息、最近 5 条消息和压缩标记。

它没有保留完整嵌套 profile、AgentLedgerState 或全量事实；destination/travel_days 若只在 profile.trip，根字段读取也可能为空。message_count 是当前传入快照中 recent_messages 的长度，不是用户全部历史消息总数。

可以说“旧快照降级为有损摘要”，不能说“长期保存完整上下文且可无损恢复”。

### 6.5 缓存删除不是用户遗忘闭环

hot_delete 只删除热键；温键、PG 快照、画像向量、PlanningJob 或其他记录仍可能恢复内容。

如果未来要实现“忘记这项偏好/删除全部记忆”，应明确删除范围、缓存失效、向量更新、历史备份策略与再次召回规则。本次没有确认完整跨存储删除闭环，不能将 TTL 当成用户级遗忘证明。

## 7. 并发写入、一致性与用户隔离

### 7.1 会话锁解决什么

memory_manager.acquire_lock 使用 Redis 租约锁，默认 10 秒并尝试续期；chat_runtime 的 save_state 在锁内更新缓存和 PlanningJob，冲突会提示 session_conflict。

锁用于降低两个请求同时覆盖同一会话的风险。它不证明：

- Redis 与 PostgreSQL 同时原子提交。
- 租约失效后旧持有者不再写。
- 所有入口都采用相同锁。
- 数据库不会被较旧缓存覆盖。

“有分布式锁”应继续追问锁范围、租约、续期失败、写入顺序及数据库版本比较。

### 7.2 当前恢复不一定挑最新版本

恢复路径优先命中热/温状态，并不总是同时读取 PG 后比较 revision。因此“缓存能恢复”与“恢复的是最新权威状态”需要分别测试。

改进方向可以是明确单一权威记录、带版本的更新、失败补偿与缓存失效。但这些应按未来方案讲，不要写成已具备强一致性协议。

### 7.3 用户身份检查在哪里

底层 cold_get_by_conversation_id 按会话 ID 查询，函数参数没有 user_id。它依赖上层入口正确校验归属；不能把 UUID 难猜当授权措施。

ProfileRecallAgent 主要用 user_id 是否为空判断匿名，而冷归档还区分 user_role=guest。游客可能拥有非空身份标识，因此“游客不冷归档”不直接证明“游客从不触发长期召回”。

未来应做跨用户、游客和不同 API 入口的隔离测试。本文只陈述边界，没有宣称已发现或利用实际越权。

## 8. 长期画像的存储与回写

### 8.1 user_profile_vectors 的结构

字段包含：

- 用户主键与外键 user_id。
- profile_json。
- visited_cities、favorite_spots、avoid_spots。
- liked_foods、avoided_foods。
- avg_daily_budget、trip_count。
- preferred_transport、preferred_accommodation。
- preference_embedding，1024 维。
- updated_at。

结构化字段适合精确过滤和解释，JSON 提供扩展空间，向量用于相似性。向量不是权威画像的替代品：从一个向量不能可靠还原“用户明确禁食花生”等精确事实。

### 8.2 ProfileService 怎样更新

列表字段按传入内容与旧值合并；profile_updates 更新 JSON。传入 trip_budget 时维护平均值：

~~~text
新均值 = (旧均值 × 历史次数 + 本次日均预算) / (历史次数 + 1)
~~~

公式是否语义正确依赖调用方传入的单位。它不是自动识别“总预算/人均预算/日均预算”的算法。

更新不是严格只追加的事件日志，也没有天然提供撤销历史来源、相冲突事实版本等完整语义。列表集合合并还不保证保留偏好排序。

### 8.3 主链实际回写哪些内容

graph/node_impl.py 的 _user_memory_async 在 stage=completed 时尝试写：

- profile 根字段 destination 对应的 visited_cities。
- 行程 total_cost 总和除以天数得到的日均费用。

需要注意两点：

1. 如果此处收到嵌套 profile 而不是平铺结构，根级 destination 的读取需要适配。这是应验证的调用边界。
2. “规划确认完成”不等于“用户真的去过”。即便写入成功，也不应将计划行为宣传为真实旅行行为学习。

普通阶段则加载本人长期访问城市、喜爱地点、饮食和预算等缺失内容。

### 8.4 工具成功回执不等于长期落库

ToolExecutor._handle_update_user_profile 当前返回：

~~~json
{"updated": {"key": "value"}}
~~~

这是示意回执结构；处理器没有调用 ProfileService，也不代表当前 13 个策略动作中开放了该工具。

因此不能凭工具名和 updated 字段宣称 Agent 已实现自主长期记忆写入。应追到真实数据库写入调用与事务。

### 8.5 异步更新是不是完全无等待

ProfileService 在完成结构化写入后 await _update_embedding。BGE 的同步编码放到线程中，目的是避免堵塞事件循环，但当前调用仍等待这个异步函数返回。

“异步函数”“不阻塞事件循环”“后台任务不影响请求等待时间”是三种不同概念。本实现不能只看注释就声称画像向量更新完全没有请求时延。

## 9. 画像召回：优先级、推断与默认值

### 9.1 召回层次

ProfileRecallAgent.recall 按下列来源构造结果：

~~~text
相似用户画像线索
  被本人长期画像覆盖
  被本会话非空画像覆盖
  再与本轮解析槽位进行字段级冲突合并
~~~

这不是一句“最新信息优先”就能完整概括，后续不同字段有不同规则。

主 process_user_turn 传入 short_term_state，没有传 session_id；因此这条调用复用已经恢复的会话状态。recall 虽然支持额外读取 Redis，但该分支并不是主调用每次必走。

### 9.2 inferred_slots 的用途与边界

召回会生成缺失槽位的候选值，并记录推断字段。它会尽量不把 UserProfile 默认值当成真实记忆，例如默认 pace=moderate 与用户亲自选择的 moderate 难以仅凭值区分。

主流程将 inferred_slots 的键名标记到 resolved_slots，并保存该字典；但它不是直接把 inferred_slots 中每个数值无条件覆盖进最终槽位。最终结果仍经过 MemoryConflictResolver 和 profile 回填。

因此，看到 inferred_slots 中某项有值，不能直接断言该值已经用于 Solver。

### 9.3 两个值得检查的映射问题

**预算单位和字段名：** 召回可能将 budget_range 或 avg_daily_budget 映射为预算，再在推断时乘天数。冲突解析器读取 long_term.total_budget，而传入的 UserProfile 通常序列化为 budget_range。必须同时核对名称和单位，不能直接说“历史日均预算总会正确恢复为总预算”。

**默认值覆盖：** 短期 profile 默认 pace=moderate，_merge_layer 将非空短期值覆盖长期值。若没有显式来源标记，默认 moderate 可能压过真实长期 relaxed 偏好。是否在特定入口发生，需要测试完整调用链。

以上是静态推导的风险，本文未新建运行实验确认。

### 9.4 confidence 是否是可信概率

代码根据来源返回固定值：有长期或相似画像时 0.75，仅短期时 0.6，缺少数据时 0.25；匿名分支为 0。

这些是启发式标记，不是校准后的概率。0.75 不能解释为“这条用户偏好有 75% 概率正确”，也不能作为身体限制的唯一决策依据。

## 10. 冲突处理：为什么不能统一用“新值覆盖旧值”

### 10.1 当前代码按字段采用不同规则

| 字段类型 | 当前合并方式 | 容易误讲的地方 |
|---|---|---|
| 目的地、出发地、日期、天数、总预算、人数 | short.get(key) or long.get(key) | 判断的是真值，不是“用户是否明确说过” |
| 兴趣、喜欢的食物、忌口、必去与禁去地点 | 短期列表在前，合并长期列表，去重 | 合并支持增加，不等于支持撤销 |
| pace | 短期非空 → 长期非空 → moderate | 默认 moderate 也可能被当成显式偏好 |
| 交通偏好 | 短期有效且不是 any，否则长期 | any 在这里被当成未设置 |
| budget_per_person、include_restaurant 等 | 短期不为 None 时优先 | False 可以作为有效值保留 |
| 最大步行、交通时长 | 短期、长期、默认上限三者取最小值 | 默认 180/120 也参与取最小值 |
| 老人、儿童、孕妇、轮椅等布尔项 | 两边都有值时做 OR | 本次明确 False 未必能覆盖长期 True |
| 当前任务的六个语义字段 | 从短期直接传递 | 不应混入持久个人偏好 |

比如历史 max_walk_minutes=60，本轮说“今天最多走 120 分钟”，当前实现仍得到 60。即使短期与长期分别为 240 和 300，也会因为默认值参与计算而得到 180。代码体现了保守策略，但没有解释历史约束是否仍适用于当前同行人和当前行程。

更明显的例子是“上次带老人，这次一个人”。如果长期 has_elderly=True、短期=False，OR 合并仍为 True。它避免无意放松身体约束，却可能错误地把不同旅行的同行条件永久化。

这里应指出规则的适用边界，不要把 OR 和 min 直接叫作“智能冲突解决”。

### 10.2 “不再喜欢”和“这次不想去”是两类修改

假设长期兴趣是博物馆，本轮说“这次不安排博物馆”。正确的产品语义可能是：

- 个人兴趣依然保留博物馆。
- 当前行程增加不安排博物馆的条件。
- 本轮候选和已生成行程需要重新检查。

而“以后都不要推荐博物馆”才更接近长期偏好修改。

当前系统有 personal/trip 分层和 ProfilePatch 的 remove/clear 能力，但存在跨层映射损失，主 slots_to_patch 主要生成 set/add。不能据此宣称自然语言撤销已经覆盖到会话、长期数据库、向量和当前行程全部层次。

### 10.3 我会怎样改进——这是设计建议

建议给重要记忆保存以下元数据，而不是只存一个裸值：

~~~json
{
  "field": "max_walk_minutes",
  "value": 60,
  "unit": "minutes_per_day",
  "scope": "trip",
  "source": "explicit_user",
  "source_turn_id": "turn-example",
  "observed_at": "示意时间",
  "valid_until": null,
  "revision": 3
}
~~~

这个结构是建议，不是当前表结构。其价值在于让合并决策可解释：

1. 先比较适用范围：当前同行人、当前行程、长期本人偏好。
2. 再比较来源：明确表达、推断、相似用户先验。
3. 区分字段缺省、默认填充、明确 False、明确清空。
4. 最后处理版本与时效；保守限制需要放宽时，可按产品规则澄清。
5. 将撤销事件传到持久化和向量更新链路。

在面试里可以说“当前先用确定性字段规则控制风险，我识别到作用域和撤销语义是下一步”，不要说“已经实现完整的事件溯源记忆系统”。

## 11. 画像向量和相似用户：召回的是什么

### 11.1 BGE 在这里承担编码职责

代码中的模型是 BAAI/bge-large-zh-v1.5，维度 1024，编码时归一化。实现会优先加载本地缓存；缺失时可能尝试下载。异步接口通过线程执行同步编码，实例初始化有异步锁。

这里的“本地缓存”指运行该服务的机器，并不等于必须在用户电脑运行。当前文档工作没有加载模型。

画像向量由访问城市、喜爱地点、喜欢和避开的食物等文本拼接得到，各列表有截取上限。它不是所有画像字段的完整编码；预算、交通和身体限制不会因为结构化表里存在，就必然进入这一份向量文本。

因此两个用户向量接近，只能说明被编码的偏好文本相近，不能证明他们预算、同行人和身体限制相同。

### 11.2 pgvector 查询和结果解释

相似用户查询先取本人已有 preference_embedding，再查其他用户，以 <=> 距离排序并取最多 3 个结果。查询本身使用数据库里已有的向量，不必重新编码当前一句话。

面试可以用这段概念伪代码讲解：

~~~text
本人画像向量
  → 从其他用户中选择距离较近的少量候选
  → 读取候选的结构化画像
  → 作为缺失偏好的候选线索
  → 用本人画像和当前输入覆盖
~~~

不能把“按距离取前三”说成“只召回达到可信阈值的相似用户”。当前查询未体现距离阈值、按相似度加权融合等机制，后续字典覆盖也不是学习到的推荐排序。

此外，相似用户不是当前用户的事实来源。可以辅助提出“是否喜欢轻松一点的路线”，不宜把他人的忌口或身体限制直接认定为本人明确要求。若用于实际个性化，还需要评估用户授权、查询范围和输出最小化；不能把别人的原始画像直接展示给当前用户。

### 11.3 embedding_provider=disabled 的精确含义

当前配置默认禁用 Embedding 编码，相关 warmup 会跳过，编码入口也会受限制。它能避免无意加载 BGE 带来的显存、内存和下载开销。

但是，相似用户 SQL 直接使用数据库已有向量，没有在同一处检查这个编码开关。因此：

> 禁止生成新向量，不自动等于禁止查询旧向量。

面试被问“现在向量记忆是不是启用的”，应分别回答编码开关、表内向量覆盖率、召回入口是否执行、调用是否成功。本文未连接线上数据库，不能给出当前线上覆盖率或实时启用状态。

### 11.4 为什么还保留结构化画像

精确禁忌、数值预算、日期和轮椅需求适合以有类型的数据直接参与约束。向量适合模糊相似性，两者职责不同。

一个实际风险是文本向量没有及时更新：结构化画像已经删除某偏好，旧向量仍可能把用户召回到旧兴趣人群。对此应做版本一致性和删除传播测试，而不是仅检查向量列非空。

## 12. 旅游知识检索：当前主链和仓库能力要分开

### 12.1 当前 POI 获取链路

ToolExecutor._handle_search_pois 先尝试本地数据，之后根据缺失的指定 POI、类别等条件尝试高德等外部检索，并在需要时调用 POI 服务兜底，再合并和排序候选。

其中 _search_local_pois 对景点调用 RetrievalRepository.search_structured。结构化方法支持：

- 城市与未废弃状态过滤。
- 步行强度上限。
- 无障碍条件。
- 避开标签、适合人群。
- 按评分排序和数量限制。

但主调用传入的参数主要是 city、limit，没有在该调用处把以上全部用户条件都传入。方法“支持过滤”与请求“真的执行了过滤”必须分开。后续 Planner/Validator 的约束判断也不能自动证明检索阶段已完成过滤。

retrieve_city_knowledge 也优先使用结构化城市数据，失败或缺失时可能使用内置城市候选；无数据时会显式返回未索引的信息。返回中的 confidence 或 built_in 标签是实现提供的元数据，不能视为独立的事实正确率。

### 12.2 向量检索方法确实存在，但不应夸大接入程度

search_vector 会编码查询，在景点 description_vector 上排序，可限制城市。代码设置 hnsw.ef_search=128，但单凭这条设置不能证明实际数据库已建 HNSW 索引，也不能证明查询计划命中了索引。

本次对 backend/src 的调用检索未发现主业务调用 search_vector/search_bm25 的证据；看到的是方法定义。因此准确表述是：

> 仓库保留结构化与向量、词面检索能力；当前已核实的 POI 主链以结构化检索和外部数据补充为主，向量与词面方法不能按在线混合召回成果陈述。

这也修正了旧面试材料容易把“三路检索 + RRF”写成当前统一主链的表述。本文未找到足以证明该融合主链当前生效的调用证据。

### 12.3 search_bm25 的名字与实现不同

当前实现把查询按空白切成若干词，在名称、描述和标签文本中做 ILIKE 包含匹配，再按命中词数量排序。它没有实现标准 BM25 所需的词频饱和、逆文档频率和文档长度归一化。

所以“成都 熊猫”可以按两个词匹配；“成都适合带老人参观的博物馆”如果没有空白，可能作为一个长词进行包含匹配。它没有因为函数叫 BM25 就具备中文分词和成熟全文排序能力。

面试时可称“词面匹配兜底实现”，并主动解释命名与实现差异。不要背 BM25 公式后宣称这段代码实现了该公式。

### 12.4 RAG 的结果仍需证据校验

召回相关，不代表证据充分。至少要区分：

| 检查项 | 旅游场景示例 |
|---|---|
| 实体匹配 | 同名餐厅是否真的是目标城市、目标分店 |
| 时效 | 开放时间是否对应出行日期，临时闭馆是否已更新 |
| 字段完整性 | 有名称和地址，但没有可用时间窗 |
| 来源一致性 | 官网与聚合页面出现不同开放时间 |
| 约束适配 | “适合老人”的文本标签不能替代数值步行限制 |
| 是否兜底 | 内置候选可帮助继续检索，不是实时核验结果 |

结构化候选、外部证据、Solver 和 Validator 的关系将在第三篇展开。本篇需要记住：召回层负责找候选证据，不能独自签发“行程已满足全部要求”。

## 13. 通用对话压缩：窗口、摘要和中间截断

### 13.1 实际算法

core/prompt_compress.py 默认保留最近 12 条非 system 消息，单条处理阈值为 2000 字符。超出窗口的旧消息被折叠为摘要：

~~~text
提取全部 system 消息并保留
→ 把旧的非 system 消息逐条压成 role + 前约 120 字符
→ 拼接摘要并限制长度
→ 最近 12 条非 system 消息逐条保留首尾、截断中间
→ system + 旧摘要 + 最近窗口
~~~

默认摘要是离线字符串处理，没有调用大模型。接口可以注入 summarizer，但不能把这个扩展点当成已经部署了“LLM 多层递归摘要”。

2000 是字符阈值，不是 tokenizer 的 Token 数。截断符、摘要前缀和原样保留的 system 消息也使它不是严格的全请求字符上限，更不是端到端费用上限。

### 13.2 它与最近 10 条会话记录不是同一层

会话状态只保存有限近期消息；通用压缩器又对传给 LLM 的消息列表做限制。这两个上限来自不同模块，不能相加或直接解释为“模型总能看见最近 22 条”。

模型实际看到多少，取决于调用方怎样组装消息、是否已有历史被丢弃、是否经过压缩、以及任务类型。下游摘要器不能恢复上游已丢失且未写入结构化画像的内容。

### 13.3 信息损失的具体例子

以下是讲解示例，不是实测：

~~~text
旧消息：
“我们周六去杭州，……很长的背景……
但同行人对花生严重过敏，请不要推荐相关餐厅。”

只摘取旧消息开头 120 字符，可能留下城市，
却没有留下末尾的饮食限制。
~~~

因此长期有效、影响约束的事实应进入结构化状态。不能寄希望于“摘要大概会记住”。

首尾保留也不是对任意 JSON、工具结果或自然语言都安全：中间被删的可能是关键字段，拼接后的文本仍可能看起来连贯。这一策略适合控制输入体积，但需要围绕业务事实保真率评估。

### 13.4 两个值得面试展开的工程边界

**信任边界：** 当前代码把旧对话摘要包成 role=system。摘要可能来自用户或工具内容，即使加了来源前缀，也需要审查是否把低信任文本放入了高优先级通道。更稳妥的设计是将摘要明确作为历史数据，与真正系统指令隔离。这是本次静态审阅提出的改进点，并非已证明发生了注入事故。

**工具协议：** 最近消息被重建为 role/content，会丢失原消息可能携带的 tool_calls、tool_call_id 等其他字段。它不能未经适配就用于任意原生工具调用消息序列。当前 agent_policy 绕过该压缩器，与下一节的专用投影机制配合。

这两点比单纯回答“我们做了滑动窗口”更能体现你理解了压缩的代价。

## 14. Agent 策略上下文：从完整状态中选择每轮决策信息

### 14.1 为什么 agent_policy 不直接复用聊天摘要

core/llm_client.py 对 task=agent_policy 不执行通用 compress_message_history。策略模型需要的是当前目标、有效证据、失败原因、剩余预算和允许动作，而不是最近几条自然语言聊天的摘要。

这就是 Long-Horizon Agent Loop 的上下文设计重点：

> 执行记录可以长，单轮决策输入通过结构化选择保持有界。

“有界”在这里主要指条目数和摘要范围；原始请求、约束等其他字段仍可能影响整体长度，不能只凭 8 条上限宣称总 Token 数恒定。

### 14.2 _policy_context 的构造步骤

1. 只选 goal_version、plan_version 与当前一致，且未过期的 Fact 和 Artifact。
2. 对 Artifact 按类型保留迭代中最后覆盖的记录；current_info_search 额外按 query 区分，避免不同查询互相覆盖。
3. 根据任务所需事实、用户输入、固定事件、交通时间窗等排序。
4. 对 Artifact 优先保留任务要求的类型，以及事件、交通、求解、验证等关键结果。
5. 截取有限条目，加入历史动作、失败、动作累计次数和剩余预算。
6. 经 policy_prompt_payload 再投影为模型可见字段。

第 2 步依赖现有记录迭代顺序实现“最新覆盖”，并不是重新对每个分组做 created_at 最大值查询。第 4 步的任务必需类型来自 success_criteria；若当前任务没有设置该字段，就不会凭空获得这一级优先级。

### 14.3 模型可见窗口

| 内容 | 当前范围 | 为什么保留 |
|---|---|---|
| 有效 Fact 摘要 | 排序后最多 8 条 | 当前决策所需事实 |
| 有效 Artifact 摘要 | 排序后最多 8 条 | 数据获取、求解和验证进度 |
| 决策历史 | 最近 6 条 | 观察工具顺序与是否重复无效动作 |
| 失败摘要 | 先取全局最近 3 条，再过滤当前 task | 当前错误和可重试信息 |
| 动作累计次数 | 遍历当前保留历史，按 task 统计 | 可超过模型最近 6 条窗口，但不是无限全量历史 |
| 剩余预算 | 步数、工具、Solver、输出 Token、时延 | 决策必须面对真实资源约束 |
| 目标和能力 | 原请求、硬约束、软偏好、缺失信息、允许动作 | 保持任务语义与动作边界 |

“先全局取 3 条再按 task 过滤”与“当前 task 最近 3 条”不同。在多任务情况下，前者可能少于应有的当前任务失败记录。现阶段应按实际实现解释。

第三篇复核补充：_record_decision 将内存 decision_history 截断为最多 32 条，重复签名检测查看最近 8 条。因此这里的动作计数只覆盖保留窗口；完整 episode 审计需要核对外部轨迹记录。

### 14.4 摘要不是把大对象直接塞进去

不同 Artifact 有专门的可见表示：

- POI 候选：数量和前若干名称。
- POI 详情：总数、期望数量、最多 8 条详情、遗漏数量、外部不可信标记。
- 路线矩阵：行列数和 POI 标识，而非整张矩阵。
- Solver：状态、候选是否存在、求解耗时，按有限天数和活动数展示行程。
- Validator：硬约束是否通过、违规代码和信息、评分。
- 城市知识：城市、主题、记录数、最多 8 个名称、来源和是否兜底。
- 外部搜索：压缩后的来源域名等证据线索。

Solver 状态还标记为 solver_algorithm_only，提醒模型它只是求解算法的状态，不是最终业务验证结论。

完整数据留在执行侧，Harness 为后续工具补充可信记录与矩阵。模型负责选择工具、语义查询和下一步决策；它不需要在每轮原样复述整个矩阵。

### 14.5 第二次投影与后训练的一致性

policy_prompt_payload 会去掉控制器内部字段，归一化轨迹和证据标识，压缩来源 URL 等内容，并按动作契约处理可由控制器提供的信息。

这同时服务于在线输入和离线训练状态。若训练时给学生完整工具大对象，推理时只给摘要，学生学到的条件就不同；反过来，训练时暴露执行后的答案或内部完成标签，也可能让结果失真。

项目的这一设计可以这样讲：

> 我把执行账本和策略观察分开，并复用模型可见状态投影，让训练样本与实际决策输入尽量遵循同一契约。评估时还要检查具体导出器是否使用了同一版本，而不是只看函数存在。

不要把“有投影函数”扩大为“所有历史数据已自动满足无泄漏和完全同分布”。

### 14.6 8 条是否一定够

不一定。例如多城市、多天和多个固定事件可能同时需要超过 8 份证据。摘要存在 omitted_details 等字段，说明实现承认部分信息没有展开；并不证明所有关键条件都已保留。

改进时应先统计决策失败是否来自信息不可见，再考虑按任务自适应预算、显式展开证据动作或更细的选择策略。直接增加窗口可能增加 Token，却不解决错误来源、过期信息和低价值重复内容的问题。

## 15. 用户改需求后，旧记忆与旧证据如何区分

“用户喜欢博物馆”可能跨会话有效；“这份三日杭州路线通过验证”只对特定目标、计划版本、输入候选和时间信息成立。这两类数据不能用同一条 TTL 规则管理。

当前策略上下文检查 goal_version、plan_version 和 expires_at，能够阻止不匹配版本或过期记录进入该可见集合。但完整修改链还依赖上游正确更新版本、失效关联产物并重新执行相关步骤；一个过滤函数不能单独证明所有修改路径都正确。

示例：

~~~text
原需求：杭州三天，预算 3000 元
已有：候选、矩阵、求解结果、验证报告

用户改成：两天，必须加一个固定时段的活动

需重新判断：
旧候选是否仍适合
旧矩阵覆盖的节点是否发生变化
旧行程是否还能满足天数与固定事件
旧验证报告是否还对应新目标
~~~

这是审阅清单，不是“系统每次都会固定重跑全部步骤”的声明。是否复用要按依赖和事实变化决定，不能让模型看到旧 hard_pass=True 就沿用结论。

面试中可把记忆时间尺度分为：

- 长期个人偏好：适用范围、来源和用户更正优先。
- 会话工作状态：支持连续交互和恢复。
- 本次规划证据：有版本、来源和有效期。
- 单轮模型观察：从当前有效状态中挑选。
- 历史轨迹：用于追溯和训练，不默认重新成为当前事实。

## 16. 用一次完整对话串起这些机制

以下是用于面试演练的设计案例，未在本次实际运行。重点是区分预期行为与当前需验证之处。

### 第一步：“两个人去成都三天，预算 3000，不吃花生”

本轮解析产生目的地、天数、人数、预算和忌口。合并时需查本人历史偏好；当前明确要求应进入本次 Goal 和后续饮食约束。

需要追踪的不只是 profile 是否出现“花生”，还包括 food_taboos → avoid 映射后是否能在恢复时保持原类型，以及工具、候选和 Validator 是否接收到这个条件。

### 第二步：“不要太累，但想去熊猫基地”

pace 与 must_visit 同时改变。必须去的景点不应只降格为泛化兴趣；系统应保留指定实体约束。可从当前 resolved_slots 检查，再追到 Goal 和候选要求。

如果回写只把它转成 special_requests 字符串，需要检查跨会话恢复是否能重建同样的强约束，不能只看当前一轮成功。

### 第三步：关闭页面，稍后回来

先走热状态；热状态过期后可能走暖状态；更久之后依赖归档与冷状态恢复。需要分别测试恢复路径与 Redis 异常路径，二者不是同一个用例。

前端断连不应被解释为用户已撤销任务或要求删除记忆。当前归档与取消调度是运行管理，具体任务处理在第四篇展开。

### 第四步：“改成两天，这次不去熊猫基地”

这里同时涉及标量覆盖、显式撤销必去地点、可能新增禁去地点、计划证据失效。列表只做 union 容易残留旧 must_visit，因此需要验证自然语言否定有没有完整传递为 remove/clear，而非仅添加新字段。

若同时留下 must_visit 和 must_not_visit 指向同一地点，应显式处理冲突，不应让模型自行忽略其中一个。

### 第五步：“以后也别给我推荐花生相关餐厅”

这是长期偏好的写入意图。要检查是否落到本人结构化长期画像、是否更新向量、下一次新会话是否恢复、是否进入实际约束。工具回执 updated 本身不足以证明闭环。

这个案例能把“抽取—合并—缓存—持久化—召回—生效—修订”讲完整，比列 Redis、PostgreSQL、BGE 三个名字更有说服力。

## 17. 这部分能力应该怎样验证

本次仅做静态审阅和文档验证，没有启动服务、数据库、Embedding 或执行测试。下面是建议验收方案，不是新测结果。

### 17.1 已有测试入口

仓库存在会话状态、会话处理、记忆存储、画像召回、冲突解析、压缩、归档任务、检索仓库等单元测试文件。它们适合定位已有预期行为，但“文件存在”不代表当前全部通过，也不代表覆盖端到端业务语义。

尤其需要将“单个 merge 函数正确”与“用户说一句更正后，跨会话和 Solver 都生效”分开验收。

### 17.2 建议的核心用例

| 场景 | 操作 | 要观察的结果 |
|---|---|---|
| 默认值与明确输入 | 长期 relaxed，本轮未提节奏 | 默认 moderate 是否覆盖长期真实偏好 |
| 当前行程覆盖 | 上次带老人，本次明确不带 | 作用域是否正确，False 是否保留 |
| 撤销与清空 | 取消必去、删除忌口或兴趣 | 解析、patch、数据库、召回是否一致 |
| 单位一致 | 历史日均预算 + 新天数 | 总预算是否经过正确换算，仅换算一次 |
| 热暖冷往返 | 同一状态逐层恢复 | 硬约束、类型、来源与版本是否丢失 |
| 缓存异常 | Redis 缺失与连接失败分别注入 | 回退是否可用，是否读到旧快照 |
| 并发更新 | 两个请求修改不同字段 | 是否丢失修改，锁失效时如何处理 |
| 删除传播 | 删除个人偏好或会话 | 所有相关存储及索引是否按语义处理 |
| 用户隔离 | 不同账户请求同一会话标识 | API 到存储查询是否保持授权边界 |
| 证据变更 | 改日期、城市、必去地点 | 旧验证结论是否仍被错误采用 |
| 长历史压缩 | 把关键否定放在中间或早期 | 关键事实是否仍进入当前约束 |
| 对抗性外部文本 | 工具结果含指令式文字 | 是否作为数据而非系统命令处理 |
| 输入契约 | 同状态走训练导出和线上投影 | 模型可见字段、截断与动作定义是否匹配 |

应在云端隔离环境使用合成账户和固定样例执行，避免把真实用户数据当测试夹具。本次未安排或启动这些实验。

### 17.3 指标怎么定义

**明确事实保真率：**

~~~text
正确保留且类型、单位、作用域都一致的明确事实数
÷ 测试输入中应保留的明确事实总数
~~~

**更正生效率：**

~~~text
更正后在状态、恢复结果和下游约束中均正确生效的用例数
÷ 需要更正的有效测试用例数
~~~

**过期证据误用率：**

~~~text
实际决策采用了过期或旧版本证据的用例数
÷ 构造了过期或旧版本证据的测试用例数
~~~

**关键事实可见率：**

~~~text
本步决策所需且在模型可见输入中仍有足够信息的事实数
÷ 标注的本步必需事实数
~~~

**检索质量与系统结果：** POI 召回可看 Recall@K、指定实体覆盖率、硬条件违规率；端到端看行程验证结果。候选召回率不能替代最终约束通过率，端到端通过率也不能定位是哪一层出了问题。

**成本和延迟：** 记录请求输入/输出 Token、缓存命中 Token、画像读取耗时、压缩耗时、策略步数和全任务耗时，并按相同输入对比。不要把“摘要字数变少”直接换算成整任务费用下降。

### 17.4 如何设计消融

建议从相同会话集、相同模型、相同工具快照出发，比较：

1. 仅最近消息。
2. 最近消息 + 结构化当前画像。
3. 再增加本人长期画像。
4. 再增加相似用户候选线索。
5. 在固定状态下比较完整上下文与当前投影。

各组尽量只改变一个因素，单列匿名/新用户/老用户、有更正/无更正、短任务/长任务。相似用户组若只提升“看起来更个性化”而提高错误假设率，就不能算净收益。

## 18. 与 Token 优化和后训练结果如何衔接

第一篇已经讨论历史日志中的 Token 降幅及其统计边界。不能把那一项降幅直接归因于“记忆系统节省 Token”，也不能把历史请求口径移植成当前策略 Loop 的总体成本。

这里至少有三类不同干预：

- 结构化画像减少反复询问和重放历史，但可能增加每次召回成本。
- 上下文投影减少单轮输入冗余，但若丢关键信息导致多轮重试，全任务成本可能上升。
- SFT 改变模型动作选择质量，可能减少无效工具调用；它不直接修复画像字段映射或数据库一致性问题。

SFT 能学习在给定观察下选择检索、澄清、求解、验证、修订等动作。如果观察里已经丢掉了忌口，单靠训练不能可靠恢复用户没出现在输入中的个人事实。

DPO 可以比较两条可验证的决策偏好；RL 类方法可以优化带反馈的多步行为。但缺失的存储语义、错误预算单位和旧证据失效，应优先作为系统正确性问题修复。不要用“模型还不够强”解释所有跨层数据错误。

当前后训练评测也不能自动证明长期记忆优秀：若评测主要使用固定 profile 和单个 episode，它没有覆盖真实跨会话更正、冷热恢复、向量更新或用户隔离。面试时要主动交代测试覆盖的对象。

## 19. 高频面试追问与可使用的回答

下面是回答框架。涉及“我实现了”的部分要按真实个人职责调整，不要把阅读理解自动改写为独立完成。

### Q1：你这个 Agent 的记忆到底是什么？

**回答：** 我们把记忆拆成会话工作状态、个人长期画像和任务执行证据。会话状态通过 Redis 热暖层和 PostgreSQL 冷层恢复；长期画像保存结构化偏好与向量；规划证据进入 Ledger，并通过版本和时效筛选后提供给策略模型。它们的作用域和生命周期不同。

**继续追问：** 哪一层是事实来源？哪一层只是缓存？删除时覆盖哪些副本？

### Q2：为什么不把历史聊天全部塞进长上下文？

**回答：** 全历史会增加输入体积，也会把旧需求、重复工具结果和当前证据混在一起。我们用结构化状态保存约束，通用聊天做窗口和摘要，Agent 决策则看专用状态投影。但压缩有损，需要验证关键事实是否仍可见，不能只报告 Token 降幅。

**继续追问：** 为什么 8 条证据够？不够时模型如何获得更多信息？

### Q3：Redis 与 PostgreSQL 各做什么？

**回答：** Redis 支持近期会话快速恢复，热层约 30 分钟、暖层约 24 小时；PostgreSQL 存放归档会话和用户画像。主聊天恢复还有 PlanningJob 回退路径。缓存缺失与 Redis 故障必须分别处理，不能说有冷层就天然高可用。

**继续追问：** PostgreSQL 提交前写 Redis，失败会怎样？如何防止新缓存被旧库覆盖？

### Q4：你如何解决“用户改口”？

**回答：** 当前有字段级合并和 patch 能力，但不是统一的最新值覆盖。标量、列表、身体限制使用不同规则；列表合并和保守 OR/min 会让部分撤销难以生效。我会用显式来源、作用域和更正版本区分“本次不去”和“以后不喜欢”，并测试到数据库和下游约束。

**继续追问：** 这是现在已经完成的能力，还是你提出的改进？回答时必须分清。

### Q5：相似用户信息可靠吗？

**回答：** 它适合做缺失偏好的候选线索，不能视为本人事实。当前使用已有画像向量取少量近邻，未体现可信距离阈值和加权融合。我会把它作为低优先级先验，先验证是否增加错误假设，而不是仅看推荐更丰富。

**继续追问：** 长尾新用户没有向量怎么办？你怎样避免把别人的禁忌带给他？

### Q6：你们用了 BM25 和 RRF 吗？

**回答：** 当前核实的主链是结构化检索加外部补充。仓库有向量方法和名为 search_bm25 的词面方法，但后者实际按包含匹配词数排序，不能称为标准 BM25；我也没有把未确认接入的 RRF 当成当前线上成果。

**继续追问：** 如果真要接混合召回，如何对齐 POI ID、去重、过滤、融合和评测？这属于后续设计题。

### Q7：如何避免长期任务重复做无效工作？

**回答：** 策略观察保留近期动作和失败，同时提供当前保留历史内、按任务统计的动作次数及剩余预算。内存决策历史最多 32 条，模型直接看最近 6 条。有效证据按版本与时间过滤，重复类型结果做合并，减少旧结果挤占窗口。这些窗口都有边界，需用长轨迹测试验证。

**继续追问：** 最近 6 步之外的循环是否一定能发现？为什么累计计数不等于语义进展检测？

### Q8：为什么工具结果不原样给模型？

**回答：** 候选、矩阵和详细行程可能很大。策略需要看到证据是否足够、下一步该做什么，而完整参数可以由执行侧提供。我们按 Artifact 类型生成摘要，明确遗漏数量，并把 Solver 状态与 Validator 结论分开。模型仍负责语义查询与动作顺序。

**继续追问：** 摘要遗漏哪个字段会导致错误决策？如何定位和修复？

### Q9：你如何防止工具结果里的 Prompt Injection？

**回答：** 策略提示明确把工具、网页和记忆当作不可信数据，详情摘要也带信任标记。但提示和标签不是完整防护证明。通用摘要使用 system 角色这一点需要改进，测试还应验证外部文本不能改变动作授权和用户约束。

**继续追问：** 哪些控制由代码强制执行，哪些仍依赖模型遵循提示？

### Q10：你怎么证明记忆真的生效，而不是存在表里？

**回答：** 用多轮及跨会话用例，从原话、解析槽位、合并画像、持久化记录、召回结果一路追到 Goal 和最终约束验证。尤其测试更正、单位、否定和清空。数据库里存在一个字段只是链路中的一步。

**继续追问：** 最有代表性的失败案例是什么？如果没有实测，就明确是静态发现和待验证风险。

### Q11：后训练能解决记忆问题吗？

## 20. 三分钟讲述稿与自测

### 20.1 三分钟讲述稿

> TravelAgent2 的记忆不是只用向量库保存聊天。会话里把个人偏好和本次旅行需求分开，当前消息先解析成槽位，再与恢复的短期状态及本人长期画像合并。Redis 有热暖两层，PostgreSQL 存归档和用户画像，恢复时还要考虑缓存异常和任务记录回退。
>
> 字段冲突不是统一最新值覆盖。标量优先当前值，列表合并，身体限制取保守值。这种方案可解释、易测试，但我在链路审阅中也发现默认值覆盖、否定撤销、预算字段和作用域的问题，所以不会把它说成完全成熟的长期记忆闭环。
>
> 领域检索与用户画像召回分开。当前 POI 主链主要使用结构化数据和外部工具补充，向量和词面方法虽存在，接入程度要按调用证据讲。召回结果仍需检查实体、来源和时效，再交给约束求解与验证。
>
> 对长任务，我们将 Ledger 与每轮模型观察分开。模型只看当前版本的有限事实、工具摘要、近期动作与失败，以及剩余预算；完整矩阵和候选留给执行侧。通用聊天还有另一套窗口摘要，两者不能混为一个机制。
>
> 我会用跨会话恢复、用户更正、过期证据和上下文保真测试验证效果，再报告同口径的 Token 与任务成功指标。后训练则要复用模型可见输入契约，不能把数据库或映射错误归因于模型能力。
