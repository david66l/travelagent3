# 第三篇｜工具、证据与约束求解：从外部信息到可验证行程

> TravelAgent2 面试准备系列 · 2026-09-10 重写版  
> 前置阅读：第一篇的 Agent Loop 与 Harness，第二篇的记忆和上下文。  
> 本篇目标：能从一次模型工具调用讲到数据来源、约束建模、求解、验证、失败恢复和用户确认，并说清每层保证了什么。

## 阅读说明

本篇依据当前项目源码及调用链整理。没有启动本地训练、模型、求解服务、数据库或压测，也没有新运行云端实验；这里只做轻量阅读和文档写入。当前配置、代码能力与云端部署状态分别对待，本文不提供未经本次验证的实时性能或通过率。

文中使用四种证据口径：

- **当前实现**：能定位到代码的行为。
- **静态审阅发现**：代码中存在口径差异或覆盖缺口，本次未运行复现。
- **设计建议**：未来应做的修正或验证，不是已完成成果。
- **示意案例**：用于理解机制，不是线上日志。

本篇也不把源码里的注释直接当成事实。例如“最小化通勤”“全部真实地图时间”“四个搜索线程”“异步批量并发”都需要看最终表达式、参数和调用方式。

## 1. 这个系统到底在解决什么问题

用户通常不会提交一个完整的数学模型，而会说：

> “去一座城市玩两天，周六晚上要参加活动，必须去一个博物馆，带老人，别太赶，希望安排有名字的餐厅，预算不能超。”

这句话至少包含四类任务：

| 层次 | 需要解决的问题 | 主要负责方 |
|---|---|---|
| 理解 | 哪些是必须满足、哪些是偏好、哪些还不清楚 | 需求解析与用户交互 |
| 求证 | 活动何时开始、地点在哪、博物馆是否开放、有哪些餐厅 | 模型选择检索动作，工具返回证据 |
| 组合 | 哪天去哪里、怎样排序、何时抵达、成本如何分配 | 预处理与 Solver |
| 验收 | 结果有没有违反要求，引用的事实是否仍有效 | Validator 与 Harness |

LLM 擅长理解语义、选择下一步、构造检索词与解释。确定性代码负责状态权限、结构化校验和数学约束。两者协作的意义是把“写一段看起来合理的路线”变成一个可以追溯并检查的过程。

但要始终补上限定：可验证的是**已编码的约束、提供的事实和当前实现覆盖的范围**，不是现实世界的一切。

## 2. 四个执行角色分别做什么

### 2.1 策略模型：提出下一步

当前策略表面有 13 个动作。模型每轮选择一个动作，提交该动作允许它填写的参数。

| 动作 | 模型可填写的主要信息 | 用途 |
|---|---|---|
| search_pois | keywords | 获取地点候选 |
| retrieve_city_knowledge | topic | 查询稳定城市资料 |
| get_poi_detail | 空参数 | 获取执行侧选定候选的详情 |
| get_route_matrix | 空参数 | 为可信候选构建矩阵 |
| get_weather | date，可省略 | 天气证据 |
| search_current_info | query、info_type、date | 实时信息、活动、营业或闭馆 |
| search_transport | mode、date | 城际班次证据 |
| solve_itinerary | strategy | 提议进行行程求解 |
| validate_itinerary | 空参数 | 请求程序检查候选行程 |
| ask_user | question | 询问只有用户能提供的信息 |
| propose_tradeoff | reason、按状态提供的 evidence_ids | 提出有依据且获准的取舍 |
| abort | reason、按状态提供的 evidence_ids | 停止并解释原因 |
| finish | 空参数 | 提交已验证草案，等待确认 |

propose_tradeoff 并非所有状态都可见。只有能力记录包含合法授权选项时，控制器才暴露该动作。

### 2.2 Harness：决定这个提议现在是否允许执行

Harness 检查当前状态、前置证据、允许动作和终止条件。它可以返回“没有当前候选”“证据不够”“验证已过期”，但不会在拒绝后偷偷自动执行另一套检索工作流。

这一区别是 Long-Horizon 架构的关键：模型继续根据观察选择下一步，Harness 保持执行边界。

### 2.3 TravelActionExecutor：把模型动作翻译成真实工具请求

适配层会读取 Ledger 中的可信目标、候选、矩阵和事实，填入实际执行参数。它还负责把工具输出变成 Observation、Fact 和 Artifact。

“模型没填写 poi_ids”不意味着系统不知道查哪些地点；这些信息可以来自已获取的候选。反过来，“模型 query 写错”不能被适配层悄悄替换成一个正确语义查询。

### 2.4 ToolExecutor 与 Solver：提供具体能力

ToolExecutor 调用数据与搜索处理器、地图估算、求解器、验证器，并统一异常与结果契约。Solver 只在给定结构化输入下求解，不负责决定是否应该去查一场演出的地址，也不负责代替用户放宽预算。

面试时可以概括为：

> 模型决定做什么和查什么；Harness 判断是否允许；执行适配层提供可信参数；工具完成操作；验证器给出可检查的结果。

## 3. 一次动作从提出到提交的完整链路

~~~text
模型选择 action + arguments
      ↓
动作参数契约 / 当前允许动作
      ↓
Harness preflight
      ├── 拒绝 → 稳定错误码 → 返回同一策略模型
      ↓ 允许
资源预算准入
      ↓
TravelActionExecutor 填入可信城市、候选、约束等
      ↓
ToolExecutor → 具体处理器 / Solver / Validator
      ↓
ObservationEnvelope
      ↓
转换为 Fact / Artifact，记录版本、来源和有效期
      ↓
比较新旧证据 → 失效依赖结果 → 提交新结果
      ↓
策略模型观察更新后的状态，选择下一步
~~~

### 3.1 为什么先检查再扣工具预算

被 Harness 拒绝的提议已经花了模型推理的步数和 Token，但尚未调用真实工具。当前 Loop 在通过执行检查后、跨进执行器之前预扣工具次数与 Solver 次数，再按真实执行情况进行核算。

不能把“工具没执行”写成“这一轮没有成本”，也不能把所有模型提议都记为已完成工具调用。

### 3.2 提交顺序为什么重要

_commit_batch 先处理旧派生产物失效，再写入新 Fact/Artifact，随后刷新约束证据和能力记录。若新候选已经变化，旧矩阵、旧行程、旧验证结论就不能继续无条件成立。

这是一套输入与派生产物的依赖管理，不能误讲成 Harness 已替模型选好下一步工具。

## 4. 参数契约：限制模型能写什么

### 4.1 两套参数对象

以 solve_itinerary 为例，模型表面主要写 strategy；真正的 SolverRequest 还需要 pois、constraints、dist_matrix、tc_matrix 等内容。

这些来自执行侧，而不是让模型复述一个大型 JSON：

~~~text
模型：
{"strategy": "cpsat"}

执行侧补充：
pois          ← 当前候选与详情合并
constraints   ← 当前目标和有效事实
dist_matrix   ← 当前路线时间矩阵
tc_matrix     ← 当前路线费用矩阵
~~~

这样既减少复制错误和输入体积，也便于追溯事实来源。

动作记录保存 executed_arguments、argument_sources、controller_hydrated_fields，帮助区分模型原始输出与执行侧补充。离线训练时应投影回模型允许填写的字段，不能让模型学习伪造执行侧数据。

### 4.2 严格 schema 不能替代语义检查

策略参数模型使用 extra=forbid，额外业务字段原则上拒绝；代码也有少量兼容清理，用于删除复制进来的 schema 注释或明确由控制器负责的字段。

但 schema 只证明对象形状基本正确。一个格式合法的日期仍可能不在用户行程内；query 也可能搜索了错误实体。Harness 对部分日期与交通方式做检查，实体、来源与覆盖则还依赖证据处理。

### 4.3 ToolGuard 与 Harness 不是同一个开关

ToolGuard 支持 off、shadow、enforce；shadow 可以记录违规但放行。因此不能仅看有 Guard 类就声称所有入口都强制拦截。

项目 settings 的当前默认是 enforce，而 ToolGuard 类单独实例化时的默认是 shadow；ToolExecutor 使用 settings 配置。当前 Loop 自身还有动作授权和 preflight，不应把这些检查混为一个开关。云端最终启用什么配置，本次未连接验证。

## 5. 工具成功、证据有效与任务成功是三件事

### 5.1 ObservationEnvelope 保存什么

主要字段包括：

- ok、tool、data。
- source、confidence、is_fallback。
- latency_ms、cache_hit。
- error：code、retryable、message、details。
- tool_call_id、snapshot_version、environment_version。

from_tool_result 对成功的基础判断是来源不为 unavailable，且 data 不是 None。这不等于“数据非空”，更不等于“满足用户要求”。

一个搜索返回 results=[] 的字典，仍可表示调用正常完成；POI 动作会另外检查空候选，实时证据充分性也有另外的来源和覆盖检查。

### 5.2 为什么 fallback 可以 ok=True

某个详情工具找不到地点时，可能返回默认营业时间与建议时长，并标记 fallback。数据不是 None，所以 Observation 仍可能成功。

这要求后续层明确决定：哪种任务允许估算，哪种事实必须真实查证。不能统一把 ok=True 升级为“已核验”。

当前实时天气、活动、班次等充分性规则会拒绝特定 fallback，但 POI 详情充分性主要检查数量和部分字段，不能宣称所有默认详情都被拒绝。

### 5.3 错误分类如何帮助模型恢复

| 错误类别 | 当前常见分类 | 模型可能的下一步 |
|---|---|---|
| 超时 | TOOL_TIMEOUT，可重试 | 重试、缩小查询或改来源 |
| 408/429/5xx | TOOL_HTTP_TRANSIENT，可重试 | 在预算内重试或换方案 |
| 401/403 | TOOL_AUTH_ERROR，不可重试 | 停止无效重试，说明能力受限 |
| 其他 HTTP 永久错误 | TOOL_HTTP_PERMANENT | 修正输入或结束该路径 |
| 网络异常 | TOOL_NETWORK_ERROR，可重试 | 判断是否重试 |
| 结果类型/字段不合法 | TOOL_RESPONSE_INVALID | 识别契约问题，不能当正确证据使用 |

表中的下一步是解释可能性，不是代码固定执行的恢复流程。retryable=True 也不授权无限重试。

### 5.4 批量接口不代表并行

ToolExecutor.execute 接收调用列表，但当前内部使用 for 循环逐个 await handler。get_poi_detail 可以一次构造多个请求，在这一层仍按顺序执行。

这与后训练的数据采集批处理不是同一机制。面试说“详情批量并发”前，必须找到真正的并发调度，而非仅看到 list 参数。

## 6. 候选 POI：实体一致性比名称相似更重要

### 6.1 当前候选获取

POI 工具先读本地城市数据，再根据指定地点或类别缺口尝试外部搜索，最后合并与排序。详情、矩阵和求解依赖同一份候选序列。

执行层会合并城市知识、旧候选与新候选，按 ID 或规范化名称处理重复，然后过滤禁去项、把必去项放到前面。

这能减少“必去地点在截断之外”的问题，但启发式名称匹配仍不等于完整实体解析。不同分店同名、同一景点多个入口、简称与全称，都需要专门用例。

### 6.2 详情预算如何分配

默认 agentic_poi_detail_limit=8，另预留 3 次门槛工具预算。实际详情数量由候选数、上限和剩余预算共同限制。

必去项优先；要求具体餐厅时，候选排序还尝试在截断窗口内保留餐厅。不能把“最多 8 条详情”解释为完整城市候选都已调查，更不能保证任意多天行程都拥有足够餐厅覆盖。

### 6.3 为什么要严格检查详情实体

批量详情返回后，执行层逐项比较请求名称与返回名称的规范化形式，不一致时返回 POI_DETAIL_IDENTITY_MISMATCH。这样可以避免“想查博物馆 A，却把相似景点 B 的时间和票价拼进 A”。

但当前详情工具以名称和城市查询，严格规范化名称仍不是全球唯一实体键。将来源 ID、分店信息和坐标一起校验，是后续可以增强的方向。

### 6.4 字段格式必须跨层一致

当前详情处理器常返回 open_hours、suggested_hours；_poi_input 主要读取 open_time、close_time、recommended_hours、duration_minutes。候选与详情合并时，原候选字段仍可能成为实际求解输入。

因此“详情查到了新营业时间”并不必然意味着新值已被 Solver 使用。要逐层看映射，不能以 API 响应存在字段作为生效证据。

同样，_poi_input 没有透传所有原候选属性。例如 walk_intensity、is_peak 等字段的缺失会让 POIInput 使用默认值；这会影响对步行和高峰排队能力的描述。

## 7. 实时信息怎样变成可规划事实

### 7.1 搜索结果先作为不可信外部数据

搜索处理会规范化 Unicode、删除部分控制字符、限制标题与摘要长度，过滤非 HTTP(S) 或包含凭据的 URL，并标记指令式内容。

这些措施有助于隔离输入，但不证明网页事实真实，也不构成完整的注入防护。URL 存在、域名看似可靠与内容确实支持结论仍是不同检查。

### 7.2 营业时间和闭馆：当前使用规则抽取

当前实现从结果 title/snippet 中匹配候选名称、日期、时刻和“闭馆”等词，生成：

- closed_dates：特定日期关闭。
- closed_weekdays：周期性闭馆。
- date_opening_hours：某日期的特殊开放时间。
- availability_evidence_urls：相关来源。

这些字段随后进入同一候选集，再传给 Solver 和 Validator。

规则方法便宜、可检查，但存在明确边界：一个片段有多个实体、多个日期或多个时段时，简单匹配可能错误绑定；“不闭馆”“闭馆通知已取消”也不能仅凭闭馆关键词正确理解。本文将其列为应验证风险，没有宣称已复现错误。

### 7.3 覆盖要求不能只由模型搜索顺序决定

required_opening_targets 从用户必去项、候选实体、current_info_queries 与日期构造需要核实的目标，再检查搜索结果是否覆盖实体和日期。

这避免模型查到任意一个“营业时间”页面就宣布全部信息充分。但对于非营业时间类的一般信息，当前检查未必具有相同细粒度；不能把一个场景的严格度泛化到全部搜索类型。

### 7.4 活动搜索与固定时间

活动处理器从前几个搜索片段中抽取日期、开始/结束时间、场馆，并尝试通过高德获取场馆坐标。complete 主要看日期、开始时间、场馆；充分性检查还要求坐标和来源。

完整活动进入候选和 fixed_events，随后转为 Solver 的预约/固定活动约束。

这里采用的是跨片段正则抽取与场馆候选匹配，不是已经证明具备通用事件理解。第一场馆结果、时间片段归属和活动日期一致性，都需要端到端验证。

### 7.5 城际交通不是购票功能

search_transport 用搜索结果抽取车次或航班选项，当前 selected_option 取抽取列表首项。这不是按价格、时刻、换乘和余票联合优化后的全局最优班次。

已选入站班次的抵达时间加 60 分钟，收窄第一天起始时间；返程发车时间减 90 分钟，收窄最后一天结束时间。它使班次进入规划边界，而非只作为文本附件。

但只要部分有效 legs 形成可用窗口，applied 就可能为 True；不能据此断言去返程所有班次都已完整验证。当前时间字段也不等于实际余票、订单或购买授权。

## 8. ResearchSufficiencyVerifier：什么时候允许求解

### 8.1 基础要求

普通行程至少需要：

~~~text
poi_candidate_set
poi_detail_set
route_matrix
~~~

另按需求增加天气、活动、城际交通或实时信息。开始日期在当前日期后 0—10 天时，也会触发天气需求。城市知识不是所有请求都必需。

这说明系统有前置条件，但不意味着必须固定按“城市知识→天气→POI”的顺序执行。

### 8.2 检查不只是 Artifact 是否存在

当前包括候选数量、详情数量、具体餐厅必要字段、活动时间场馆与来源、交通时间窗能否应用、实时信息的来源与实体日期覆盖，以及矩阵维度。

最低候选数和详情数默认都是 1。它们是基础门槛，不是高质量多天行程的充分数量保证。

### 8.3 有效期有两层

| 类型 | 创建时 Artifact TTL | payload 时间戳的额外检查 |
|---|---:|---:|
| 城市知识 | 7 天 | 此验证器没有同类实时阈值 |
| POI 候选与详情 | 24 小时 | 基础检查为主 |
| 天气 | 1 小时 | queried_at / retrieved_at 约 3 小时 |
| 活动 | 6 小时 | 时间戳约 24 小时 |
| 城际交通 | 15 分钟 | 时间戳约 2 小时 |
| 当前搜索 | 6 小时 | 6 小时内，且不超过未来约 5 分钟 |
| 路线矩阵 | 30 分钟 | 矩阵形状检查 |

Artifact 先通过版本和 expires_at 过滤，再检查 payload 时间戳。因此不能只报“班次允许两小时”而忽略 15 分钟的产物有效期。

天气、活动、交通的 payload 新鲜度分支主要检查下界，与当前搜索的未来时间限制并不完全一致。边界、时区和时钟偏差应在测试中覆盖。

### 8.4 方阵正确不等于实体顺序正确

普通分支检查时间矩阵是期望大小的方阵；这可以抓住节点数量变化，但不能单靠形状证明第 i 行确实对应第 i 个 POI。

执行层尽量复用稳定候选顺序；具体餐厅分支还有来源矩阵扩展和 ID 校验。这些机制应共同说明，不要只说“有矩阵校验就不会错位”。

## 9. 路线矩阵：当前哪些是估算，哪些可以接真实地图

### 9.1 先看实际入口

get_route_matrix 调用 TransportSelector.build_matrices。它在候选前面加入虚拟酒店节点，返回 poi_ids、time_minutes、transport_cost。

TransportSelector 支持 amap_minutes 覆盖特定边的时间，但当前 Agent 的 _hydrate_arguments 没有在这个动作上主动获取并注入该映射。因此已核实的默认路径主要是距离估算，不能描述成“所有边都调用高德实时路网”。

仓库里的其他地图能力存在，不代表这个入口自动使用了那些能力。

### 9.2 估算公式与交通方式

当前先用经纬度计算球面距离，再乘 1.4 绕行系数，按交通方式速度估时间，加固定接驳开销；费用按配置的每公里成本与基础项计算。

交通方式主要由距离阈值及部分目的地类别选择：近距离步行，之后可能是地铁、出租车或驾车。函数接收 constraints，但当前选择逻辑没有据此完整落实用户交通偏好。

这是一组工程估算参数，不是从真实道路轨迹训练出的模型，也不是票价保证。

### 9.3 虚拟酒店是什么意思

酒店节点坐标为零，与其相连的边通常按零通勤处理。它是每日路线起终点的数学锚点，当前不能把它解释为“已选择真实酒店并核算酒店往返”。

同样，任一真实地点若缺坐标，也可能被矩阵构造逻辑当成零通勤对象。需要区分显式虚拟节点和缺失坐标的真实节点，不能用零同时代表两种语义。

### 9.4 可改进方向

建议逐边保存来源、查询时间、交通方式和估算标记；校验 ID 顺序而不仅是大小；把缺坐标视为数据缺口；通过真实地图边覆盖率和估算误差评估改进。

这些属于后续方案。本篇没有申请地图 API 配额或运行矩阵采集。

## 10. 求解前的五类预处理

TravelVRPSolver.solve 大致按以下顺序处理：

1. 预约实体对齐与提醒（该函数并未查询实时库存或实际删除候选）。
2. 游玩时长、部分营业时间和闭馆规则调整。
3. 普通用餐节点或具体餐厅备选节点注入。
4. 虚拟酒店节点注入与矩阵构造/扩展。
5. 疲劳预算、策略选择与求解参数设置。

### 10.1 时长调整有什么价值

数据源常给出过短的默认游玩时长。PlayTimeManager 按名称关键词、游玩模式和时段启发式调整，可避免大型主题公园只分配一两个小时。

但代码里的“真实时长”注释不能直接当成实时来源。部分主题公园规则会扩大营业窗口；部分博物馆规则会补充周闭馆日。它们属于领域假设，应保留来源层级并接受日期证据覆盖。

### 10.2 Solver 和 Validator 共享预处理的双刃剑

_effective_planning_facts 会为验证构造与求解相近的预处理事实，减少两边因窗口不同产生的误报。

收益是口径一致；风险是共享同一个错误默认值时，两边都可能通过。因此独立验证并不意味着独立获取了第二套真实来源。

### 10.3 步行与疲劳模型是什么

ConstraintsInput 可把 max_walk_minutes 按 4.5 km/h 转成公里预算。FatigueModel 根据同行人类型与假定每日用满预算，递推下一天的强度上限，并设置连续高强度后的恢复规则。

这不是用户实时运动传感器模型。CP-SAT 实际累加的是 POI walk_intensity，再与这些上限比较，公里、分钟和离散强度之间的语义需要统一。

当前 Agent 参数映射还未透传完整 travelers_type 和 POI walk_intensity 等信息，因此不能宣传所有用户类型都已精确个性化建模。

## 11. 怎样把旅行规划写成 CP-SAT 模型

### 11.1 为什么“VRP-TW”还不够精确

这里不仅是访问全部点并求最短路线，还涉及可选景点、跨天分配、偏好奖励、必须访问、固定活动、餐厅时段和费用约束。可称为带时间窗的多日选择与排程问题，借用了车辆路径问题的结构。

求解器使用 OR-Tools 的 CP-SAT，而不是直接调用 RoutingModel 的一个现成 VRP 示例。

### 11.2 主要决策变量

| 变量 | 代码名 | 含义 |
|---|---|---|
| V[d,i] | BoolVar | 第 d 天是否访问节点 i |
| X[d,i,j] | BoolVar | 第 d 天是否从 i 走到 j |
| A[d,i] | IntVar | 第 d 天节点 i 的到达时间，分钟 |
| DC[d] | IntVar | 第 d 天费用，随分支采用整数金额尺度 |
| DW[d] | IntVar | 第 d 天累积步行强度代理 |

普通用餐占位节点不进入路由弧集合；真实餐厅节点则参与路由。每天调用 AddCircuit，并通过访问变量与入出边联动。

### 11.3 时间窗约束

对被选中的节点：

~~~text
到达时间 >= 当天允许开始时间
到达时间 >= 场所开放时间
到达时间 + 游玩时长 <= 当天允许结束时间
到达时间 + 游玩时长 <= 场所关闭时间
~~~

对选中的 i→j：

~~~text
A[d,j] >= A[d,i] + duration[i] + travel[i,j] + buffer[i,j]
~~~

这里允许等待，因此不应同时强制等号。例如 09:30 到达附近，但场馆 10:00 才开门，等待是合法安排。

回到虚拟酒店的弧不传播到达时间，因为酒店时间锚定当天开始；否则会把“回程后时间”错误约束为“当天起点时间”，造成模型矛盾。

### 11.4 Big-M 为什么值得讲

未选中的边不应该约束时间。代码用 Big-M 使相关不等式在 X=0 时失效。

M 若过小，未选边仍会施加不可能的时间限制；若无必要地过大，也会让表达更难检查。当前 M_travel 根据日终、最长活动、最大旅行时间和缓冲计算，而非只取边长。

这是一个可讲清的建模问题；源码注释提到历史故障，但本次没有重新运行旧版本确认其影响规模。

### 11.5 其他约束

- 普通节点跨天最多访问一次。
- 找到匹配实体的必去项恰好访问一次。
- 固定活动限制日期、开始与结束时间。
- 临时关闭和周闭馆限制可访问日期。
- 每天总活动、通勤、缓冲与休息不能超过容量。
- OptionalInterval + AddNoOverlap 避免活动重叠。
- 每天景点数上限为 5，具体餐厅与普通餐饮占位不占同一景点计数。
- 跨远距离节点与远郊组合有同日排斥规则。
- 预算、步行代理、偏好下界与部分均衡指标有约束。

必去目标若没有匹配到候选，模型内部不会自动生成它；缺失实体必须通过证据检查、可行性诊断与最终 Validator 兜住。求解器不能凭空造一个地点满足约束。

## 12. 目标函数：不是“只优化最短路线”

当前代码的目标表达式可概括为：

~~~text
最大化：
  3000 × 访问数量
- 6000 × 重复功能景点惩罚
-  400 × 同日地理分散惩罚
-   80 × 总通勤时间
- spread_weight × 每日费用差
+   20 × 偏好得分
-   10 × 高峰得分
-    1 × 到达时间之和
~~~

这里的得分有各自整数缩放；金额分支也可能使用分为单位。不能把权重直接解释为人民币、分钟或经过用户实验学习到的效用。

### 12.1 为什么不单独最小化通勤

若可选节点没有访问奖励，最短路线可能是什么都不去。访问奖励和偏好项鼓励形成有内容的行程，通勤与重复功能惩罚帮助挑选和组合。

### 12.2 这是不是严格的多目标 Pareto 优化

代码有 EpsilonConfig，通过阈值限制若干指标，同时使用一个加权目标。但它没有在该入口循环扫描 epsilon 并输出一条 Pareto 前沿。

此外，名为 max_budget_mad 的参数实际约束 max_day_cost，不是按名称就实现了平均绝对偏差。描述算法必须跟最终表达式走。

### 12.3 固定权重是不是严格优先级

不是。注释中类似“这些惩罚只重排、绝不丢访问”的说法，不能作为严格证明。多个惩罚可以累积；加权目标通常仍允许取舍。

如果业务真的要求字典序优先，应显式做分阶段优化或给出足够严格的权重上界证明。当前可准确说“采用加权目标，并用硬约束保护必须满足的条件”。

### 12.4 OPTIMAL 的边界

OPTIMAL 表示对当前离散候选、当前约束和目标，求解器证明了最优；不表示所有真实景点、交通方式、酒店或未知营业信息都已穷尽。

FEASIBLE 表示找到可行解但未证明最优。对在线体验而言可用，但仍必须经过业务验证与证据门槛。

## 13. 普通用餐与具体餐厅：两个不同的问题

### 13.1 普通用餐占位

普通分支注入午餐、晚餐时间块。它们没有真实地点坐标，餐费由 food_day 统一表示，节点本身不再计门票费用。

这些时间块不会进入路线 Circuit。否则 A→午餐→B 两条零成本边可能绕过 A→B 的真实通勤，造成“通过吃饭瞬移”的建模漏洞。

用餐块使用 OptionalInterval 与其他活动做 NoOverlap，保证不与参观活动重叠。但当前普通分支没有为每段通勤建立同样的区间对象；因此不能仅凭 NoOverlap 证明吃饭绝不会与隐含的旅行时间冲突，需要专项测试活动间隙。

### 13.2 全天景点与用餐例外

普通分支对时长达到全天级阈值的节点，允许所在日不安排单独餐饮占位，假定在园内解决用餐。

代码还把达到 360 分钟阈值的这些节点强制访问。这是额外的业务规则，可能比用户明确 must_visit 更强。若候选里多个大型景点都被强制，可能压缩可行域；不能把全部约束都说成来自用户原话。

### 13.3 具体餐厅必须作为真实路线节点

require_named_restaurants=True 时，餐厅需要：

- 可识别的来源 ID 与名称。
- 坐标。
- 营业时间和用餐时长。
- average_cost。
- 与其他节点对应的时间和费用矩阵。

expand_dining_nodes 将每家来源餐厅展开为“第几天、哪一餐”的备选节点，保留 source_poi_id。模型约束每个用餐时段恰好选择一个备选。

同一家餐厅可以在不同天或不同餐次作为备选出现；当前不能据此声称有全程餐厅去重或多样性硬保证。

### 13.4 矩阵怎样随餐厅展开

expand_source_matrices 使用来源 POI ID 将展开节点映射回原矩阵。它会检查来源 ID 是否重复、矩阵大小是否与来源顺序一致，再扩展边。

输出行程恢复 source_poi_id，并将餐厅费用放进 meal_cost；named 分支按分缩放金额，避免直接截断小数金额。

这比给餐厅编一个名称更有含金量：实体、时间、成本、路线和输出必须贯通。

### 13.5 当前接入缺口必须说明

真实 ToolExecutor 的 get_poi_detail 目前主要按 attraction 获取详情，返回字段也没有完整提供 named 分支要求的 category、id、lat、lng、average_cost 等信息。而 ResearchSufficiencyVerifier 对具体餐厅详情确实要求这些字段。

因此，求解器与评测夹具支持具体餐厅，不自动证明真实工具链已经无缝支持。若数据源返回结构不匹配，任务会在详情或充分性阶段受阻。

本次没有运行真实请求；这是需要优先验证的接口差异，不能直接说线上全部失败，也不能跳过它宣称已完成端到端覆盖。

## 14. 预算、通勤与体力：最容易被追问的口径问题

### 14.1 预算是否涵盖整个旅行

当前求解主要统计景点、餐饮和市内交通相关费用。虚拟酒店不计真实住宿；班次搜索也不等于城际票价已经纳入总成本。

所以“总预算”在接口里是一个名字，产品上仍需明确覆盖范围。不能把一个不含酒店与往返交通的估计，宣传为全部旅行费用保证。

预算 0 在当前 Solver 中表示不限额，也不同于用户真的要求零预算。若用户允许输入 0，需要产品与解析层明确语义。

### 14.2 每日等额预算是额外限制

代码把总预算除以天数，再要求每一天费用不超过该日均额度。这比“整趟不超过总预算”更严格。

示意：两天总预算 1000，第一天 700、第二天 200，总计 900，本来满足总额；但每日 500 的限制可能拒绝它。

如果面试问“为什么有预算却排不进”，应检查是否误把均衡偏好做成了硬约束，而不是立即换一个更强模型。

### 14.3 普通分支可能重复计入交通费用

当前 CP-SAT 的每日 DC 已包含 day_tc。总预算约束在普通分支又对每日 DC 求和后加上 total_tc_expr；具体餐厅分支则不再额外加这一项。

这意味着普通分支在数学约束中可能对交通费计两次。它更可能过度收紧可行域，而不是直接让输出超预算。本文依据表达式提出该发现，没有运行复现，也没有在文档任务中改动业务代码。

面试可从这个例子说明：变量名称、单位、每日汇总与总计必须画成账目，不能只看最终 total_cost。

### 14.4 通勤上限在两层含义不同

Solver 在边上检查 travel[i,j] 是否超过 max_transit_minutes；Validator 却将每日通勤累加后与同一个字段比较。

这分别是“单次通勤上限”和“单日通勤总量上限”。即使每段 40 分钟合法，一天三段合计 120 分钟，也可能与字段原始意图不同。

此外，普通 CP-SAT 输出的 transit_from_prev 为空字典，而 Validator 依赖这些活动字段或日汇总计算通勤。因此，部分结果中它可能没有拿到真实通勤总量。

具体餐厅分支对源矩阵的逐边检查更严格，但不能用该分支的能力覆盖普通分支的缺口。

### 14.5 步行上限不是目前完整的独立验收项

当前主 Validator 没有一个与真实步行分钟数完全对应的硬违规检查；疲劳分数也主要依据活动时长等负载代理计算。

因此准确表述是“求解含体力代理与疲劳启发式”，而不是“已独立证明每天真实步行不超过 X 分钟”。

建议分别定义单次交通时间、单日交通时间、步行距离、步行时长和离散强度，再对各字段做从用户输入到求解和验证的一致性检查。

## 15. 求解速度、超时与降级策略

### 15.1 默认 Agent 并不是 auto

策略模型的 SolvePolicyArguments 默认 strategy=cpsat，执行侧也使用 cpsat 作为默认值。

SolverRequest 自身的默认却是 auto；auto 在真实节点不多于 15 且旅行不超过 3 天时选择贪心。两者是不同入口的默认值，不能说“所有小请求默认贪心”。

### 15.2 CP-SAT 的当前参数

调参函数按约 nodes² × days 的规模分档：

| 估算规模 | 时间上限 |
|---|---:|
| ≤ 900 | 4 秒 |
| ≤ 3600 | 10 秒 |
| ≤ 8000 | 18 秒 |
| 更大 | 25 秒 |

实际 num_search_workers=1。注释解释了某历史平台多线程挂起问题，但本次没有验证云端平台是否存在同样问题；也不能把注释中的历史问题当成所有版本的通用结论。

### 15.3 Warm start 是提示，不是预先确定答案

代码使用地理分组构造部分 V 变量提示，引导搜索更快找到紧凑候选。这是 AddHint 的用途；它不替代硬约束，也不意味着一定找到可行解或最优解。

节点数、天数、餐厅展开数量决定模型规模。将每家餐厅复制到每天两餐，会增加节点和弧，不能只根据原始 POI 数估算成本。

### 15.4 早停不等于质量不变

回调在达到最短搜索时间后，若新 incumbent 相对前一解改善低于阈值，则可能停止。当前调用使用约 45% 时间下限和 0.3% 改善阈值作为默认。

这是性能与解质量的取舍。一次小改进不能证明后面没有大改进；没有新解时回调也不会持续触发，因此还依赖 Solver 自己的时间上限。

本篇不复述注释中的“无质量损失”作为已测结论。

### 15.5 普通分支与具体餐厅分支的降级不同

| 情形 | 普通分支 | 具体餐厅分支 |
|---|---|---|
| 显式请求 greedy | 可使用贪心 | 强制转 CP-SAT |
| auto 的小问题 | 可选贪心 | 不使用旧贪心 |
| CP-SAT 未找到可用解 | 可返回贪心候选 | 保留 infeasible/error 等状态 |
| 求解异常 | 尝试贪心并给提醒 | 返回 error |

原因是旧贪心不能完整保障具体餐厅备选、来源路线和用餐时段约束。为获得一个“看起来成功”的输出而悄悄切到弱约束算法，会破坏验收意义。

### 15.6 asyncio.to_thread 的边界

求解处理器通过 asyncio.to_thread 运行同步 Solver，避免阻塞事件循环。但取消等待不必然终止已经在底层线程里运行的求解；外层工具超时与 Solver 内部时间上限需要共同设计。

ToolExecutor 当前单工具超时默认 30 秒。不能把 25 秒 Solver 限制、30 秒工具超时和整个 Agent 任务时长当成同一指标。

本次未运行速度实验，也未修改线程数或启动新的云资源。

## 16. Validator：独立检查输出，但不创造真实事实

### 16.1 输入和输出

ItineraryValidator.validate 接收 itinerary、constraints 和 facts。输出包括：

- validator_version，当前为 travel-validator.v3-named-dining。
- hard_pass。
- hard_violations，带稳定代码与相关实体。
- soft_scores。
- metrics。
- feasibility。
- evaluation_scope。

它不接受模型一句“已经检查过了”作为通过条件，hard_pass 由违规集合是否为空计算。

### 16.2 当前主要硬检查

| 类别 | 示例 |
|---|---|
| 基本形状 | 空行程、旅行天数不匹配、无效起止时间 |
| 排程 | 活动重叠、超出每日可活动边界 |
| 开放性 | 营业时间外参观、周闭馆、特定日期闭馆 |
| 指定要求 | 必去缺失、禁去出现、固定活动日期时间改变 |
| 重复与餐饮 | 普通 POI 重复、多余或紧接的用餐活动 |
| 成本 | 总预算超限 |
| 具体餐厅 | 餐数与时段、实体、餐费、时长、逐边路线、日费用一致性 |

预约检查依赖事实提供 reservation_required 与 reservation_available=False 等信息。若字段未被数据链透传，验证器不能凭空推断预约不可用。

### 16.3 具体餐厅为什么检查得更多

validate_named_dining 会：

1. 检查午晚餐各自窗口中是否恰好一餐。
2. 根据来源 ID 检查餐厅名称、类别、坐标。
3. 校对餐费和最短用餐时间。
4. 读取来源路线矩阵。
5. 将活动按时间排序，检查上一节点 ID、通勤时长与费用。
6. 验证两项活动之间留出了足够旅行时间。
7. 在主验证器核对每日费用合计。

它检查的是给定源目录和矩阵的一致性。若源矩阵本身是估算，验证通过仍只是与该估算一致，不能自动升级为真实路况保证。

### 16.4 hard_pass=True 没覆盖什么

至少不能自动证明：

- 全部外部信息来自可信且最新的官方来源。
- 酒店、车票、门票已经可购买或已预订。
- 未提供的营业、预约、步行数据都正确。
- 路线费用包括全部旅行支出。
- 普通分支的每段交通与输入矩阵逐边一致。
- 行程对用户主观体验达到某个固定分数。
- 用户已经确认最终方案。

例如空列表会被拒绝，但一个包含若干天对象、每一天 activities 都为空的行程，并不等同于 itinerary=[]。是否被其他约束挡住需要结合必去项、餐饮模式和上层门槛，不能把“非空行程检查”说成“每天都有充分活动检查”。

### 16.5 为什么共享事实可能产生共同盲点

Solver 和 Validator 分开实现是有价值的，可以抓出输出格式、排程、费用与证据不一致。但它们使用同一批输入事实，甚至共享部分预处理。

因此建议增加第三类检查：对来源事实本身进行审计，或用锁定的独立数据样例验证。不要用同一条错误默认营业时间同时生成和验收，然后宣称事实已交叉验证。

## 17. “方案失败”与“任务不可行”必须分开

### 17.1 三种不同结论

| 观察 | 能推出什么 | 不能推出什么 |
|---|---|---|
| 某条行程违反约束 | 这条候选不能提交 | 所有可能行程都不行 |
| CP-SAT 超时或未得到解 | 当前搜索没有给出可用方案 | 现实任务必然无解 |
| 必去费用下界已超预算 | 在这些可信事实和边界下存在不可行证据 | 可以擅自提高预算 |

同样，模型反复查不到结果，可能是查询差、工具故障或数据缺失，不能直接等同于事实不存在。

### 17.2 当前不可行证据的范围

assess_required_facts 当前主要生成两类充分条件：

- 必去场馆在全部可用日期都有明确的特定日期关闭记录，且没有相应开放覆盖信息。
- 已知必去项的票价下界合计已经超过预算。

它先对实体和重复别名进行处理。冲突结构化记录不能直接用来建立硬终止证明；未知成本不会被当作一个正的费用下界。

特别地，它不使用预处理推测出的“博物馆通常周一闭馆”作为硬终止证据。领域假设和明确日期事实的来源强度不同。

### 17.3 没找到 witness 就是 undetermined

该函数不是另一个完整求解器，也不会因没有发现矛盾就返回“可行”。可能存在复杂的时间窗冲突、交通不可达或数据缺失，只是当前检查没有覆盖。

这是一种保守设计：只在能够指出具体事实依据时宣布某类不可行，其他情形继续保持未定。

### 17.4 为什么不强迫模型先跑一次无意义 Solver

refresh_constraint_evidence 在详情足以证明矛盾时就可以生成 constraint_evidence、更新 capability。比如明确必去门票下界超过总预算，不必为了遵守固定流程先浪费一次求解。

但该函数只提供证据和能力状态，不替模型选择 abort 或 propose_tradeoff。这保留了模型的决策职责，也避免把“必须先求解再停止”硬编码为隐藏工作流。

## 18. 放宽约束与用户授权

### 18.1 ConstraintFlexibilityContract 表达什么

约束维度被分为：

- locked_constraints：不能放宽。
- solver_adjustable_constraints：可在现有用户边界内重排。
- relaxable_constraints：用户明确允许放宽的维度。
- relaxation_options：该维度获准的具体选项。

三组必须互斥，选项只能属于可放宽维度。重排活动顺序不等于可以多加一天；在已有预算内换餐厅不等于可以提高预算。

### 18.2 取舍选项谁写

模型写原因及当前状态要求的证据引用；控制器提供合法选项。controller_tradeoff_options 要求状态与选项有效，最多保留符合契约的一小组选择。

多个 witness 出现时，当前 capability 构造对相关维度的授权选项取交集。这是保守的字符串选项处理，可能导致没有共同选项；不是自动生成并验证一个复杂组合修改方案。

### 18.3 旧证据不能支持新的终止理由

abort/propose_tradeoff 在存在证据要求时，会检查当前 witness、capability.evidence_ids 与提交的 evidence_ids 是否匹配，并拒绝过期证明。

一个新的搜索结果若改变了场馆开放信息，旧“全部日期闭馆”证明就可能失效。模型必须面对更新后的状态，不能继续复用旧理由。

### 18.4 finish 的准确含义

finish 要求当前 Solver 结果、hard_pass=True 的当前验证报告，验证时间不能早于最新求解结果，而且研究证据仍需充分。

实际结果是 awaiting_user，并生成已验证草案相关产物。它代表“可提交用户确认”，不代表“用户已经确认”，更不代表执行了购票、预订或支付。

## 19. 证据变化、重试与无进展检测

### 19.1 当前失效规则

| 新动作或新证据 | 主要失效对象 |
|---|---|
| 研究证据发生变化 | 旧 Solver、验证、草案、接受标记、约束证明等 |
| 候选集合变化 | 还会失效详情与矩阵 |
| 详情变化 | 还会失效矩阵 |
| 重新求解 | 旧验证、草案与完成相关产物 |
| 重新验证 | 旧验证及依赖其通过结论的产物 |

代码比较 payload、事实值、来源、置信度和某些有效期变化，尽量避免只因 ID 或更新时间变化就认为取得了新业务证据。

但 payload 里若仍包含动态字段，不同路径的比较可能有差异。不能把“做了比较”说成所有语义等价数据都已规范化。

### 19.2 重复无进展怎么识别

_record_decision 对事实、Artifact 和 Observation 内容生成签名；相同 task、action、规范化参数和签名，在最近 8 条记录中重复时，标记无进展。

对 Solver 数据，它会排除 solve_time_ms，避免“耗时变了”被当成新的求解事实。无进展会形成 REPEATED_NO_PROGRESS_ACTION 反馈，模型应调整查询或换下一步。

### 19.3 记录并非无限保存

当前内存中的 decision_history 最多保留 32 条；模型可见投影又只取最近 6 条。所谓“累计动作次数”遍历的是当前保留的记录，不能无条件说是无限完整 episode 历史。

这也细化了第二篇的表述：Ledger 的工作记录、模型观察窗口和外部轨迹审计文件是不同对象。长任务要审计全部行为，应核对 Recorder/sidecar，而不是只依赖内存列表。

### 19.4 重试预算不是语义正确性的替代

改一个 query 可能拿到同样证据，也可能只是随机换词。反过来，同一个工具在外部状态更新后重试，可能有实际价值。

因此重试质量要同时看新事实、前置问题是否解除、预算消耗和最终结果。不能以“工具调用成功次数”替代有效进展。

## 20. 用一个完整案例串起 Agent、Solver 和 Validator

以下所有地点与数值都是教学示例，不是外部旅游建议或本次运行结果。

### 20.1 用户目标

~~~text
A 城两天。
第一天晚上 19:30 必须参加固定活动。
必须参观博物馆 M。
每日午晚餐要给出真实餐厅。
总预算 800 元，只计本地活动、用餐和市内交通。
不允许增加天数，允许在原预算内更换非必去景点。
~~~

先明确预算范围，使“800 元”在求解与解释中具有一致含义。

### 20.2 研究阶段

模型可以先检索活动，也可以先搜 POI。执行侧把城市等可信参数填入工具。

活动证据需要时间、场馆、坐标、来源；博物馆如果存在闭馆信息需要绑定具体日期；餐厅要有来源实体、消费、时长和营业窗口。

若模型提前调用 solve_itinerary，Harness 返回缺失项。它不会替模型调用详情、天气和路线后假装这是一次成功求解。

### 20.3 矩阵阶段

候选与详情形成稳定序列，加入虚拟酒店；对具体餐厅保留来源节点与边。之后餐厅按天和餐次展开，矩阵按 source_poi_id 扩展。

如果只检查 N×N，仍可能将 M→餐厅 R 的时间错用成 M→活动场馆的时间，所以应检查实体顺序。

### 20.4 求解阶段

模型选 cpsat。求解器决定：

- M 安排在哪一天。
- 固定活动在哪个日期、何时开始。
- 每个餐次选择哪个真实餐厅。
- 景点与餐厅的顺序和到达时间。
- 在预算与时间窗内怎样取舍非必去候选。

模型不直接生成整张“已经满足约束”的时间表来绕过工具。

### 20.5 验证阶段

拿到 FEASIBLE 后，模型仍需调用 validate_itinerary。验证可以发现：

- 餐厅费用与来源不一致。
- 晚餐和活动之间没有足够通勤时间。
- M 在安排日期闭馆。
- 固定活动开始时间被改变。
- 日费用合计与活动和交通合计不一致。

此时失败是这条候选不合格，不能自动解释为用户任务无解。

### 20.6 恢复阶段

若是候选餐厅覆盖不足，可以扩大检索；若是重复求解同样输入且没有进展，继续调用同一 Solver 不一定有价值。

若明确证据证明 M 两天都关闭，形成不可行 witness。用户不允许删必去或加天数，则不能随意提出这两项修改；可解释冲突并按当前授权选择合适的交互。

### 20.7 提交阶段

当前行程通过验证，证据仍有效，模型调用 finish。用户看到的是待确认草案及依据，而不是已执行的真实订单。

面试时把这个案例讲透，比一次罗列 LangGraph、RAG、OR-Tools、Redis、SFT 更能展示系统理解。

## 21. 怎样验证这条链路，避免“训练分数很好但真实运行不通”

本次没有执行以下实验。它们是基于当前源码提出的验收方案。

已有 test_named_dining.py 使用手工构造的 POIInput、餐厅均价与坐标来检查求解和验证；test_harness_loop.py 包含 SequencePolicy 等受控策略。这类测试适合验证局部契约，但并未自动经过真实搜索和详情处理器。当前文件存在并不代表本次已执行通过。

### 21.1 分层检查

| 层 | 建议检查 | 不能替代的上一层问题 |
|---|---|---|
| 工具契约 | 参数形状、异常分类、空数据、fallback | 外部事实是否真实 |
| 实体与证据 | 名称/ID/坐标、来源、时效、日期绑定 | 行程能否排得下 |
| 参数映射 | 字段、单位、来源顺序、餐厅结构 | 求解逻辑是否正确 |
| Solver | 小实例、边界约束、状态与降级 | 真实工具能否提供输入 |
| Validator | 对故意篡改的行程能否报错 | 源事实本身是否有误 |
| Agent Loop | 选择、恢复、合理终止、预算 | 用户主观满意度 |
| 真实工具集成 | 使用真实适配器跑可复核样例 | 大规模稳定性和全部场景 |

### 21.2 应优先做的反例

1. **同维度错顺序矩阵**：交换两个 POI，方阵形状仍正确。
2. **两段分别合法、总和超限**：区分单次和单日通勤。
3. **每日费用不均、总额合法**：检查额外日均预算约束。
4. **普通分支交通费非零**：检查是否重复计入。
5. **地点没有坐标**：不能变成免费零通勤。
6. **详情只有 open_hours**：验证新时段能否真正进入求解。
7. **餐厅详情经过真实处理器**：核对 named 所需字段是否完整。
8. **活动搜索含多场演出**：防止跨片段拼错时间与场馆。
9. **“闭馆已取消”**：检查否定语义。
10. **天气时间戳位于未来**：检查时钟边界。
11. **全日景点与两餐**：分别检查普通占位与具体餐厅规则。
12. **同样 Solver 结果只改变耗时**：不应算有效进展。
13. **新证据使旧闭馆结论失效**：旧终止引用必须拒绝。
14. **所有天对象都有、活动全部为空**：检查是否出现伪通过。
15. **将餐费、来源 ID、通勤边轻微改坏**：验证器应定位具体违规。

这些用例更有价值的地方在于跨层，而不是只给一个函数输入然后断言它照原实现返回。

### 21.3 正确率应该怎样拆

建议至少分开报告：

- 工具执行成功率：正常完成的实际调用 / 实际调用数。
- 证据充分率：通过当前研究门槛的样例 / 进入该检查的样例。
- 行程 hard pass：通过指定版本 Validator 的行程样例 / 被评估行程样例。
- 正确终止率：按独立任务标签判断 finish、ask、tradeoff、abort 是否合适。
- 严格任务成功率：同时满足结果、证据、终止与预算条件的任务 / 固定任务集。
- 恢复成功率：遭遇指定故障或需求变更后仍正确完成的任务 / 对应恢复场景。

分母、数据集、工具环境、验证器版本和是否允许 fallback 必须随指标一起记录。

“合理停止不可行任务”可能是策略正确，但不是成功生成一条可行行程。二者不要混在一个无解释的 95% 中。

### 21.4 性能应该怎样拆

记录模型推理、搜索、详情、矩阵、Solver、Validator 和重试各自耗时，以及端到端 p50/p95/p99。Solver 4 秒不等于整个 Agent 4 秒。

优化顺序应由测量决定。例如详情当前顺序执行，多请求延迟可能占主导；具体餐厅展开可能增大 CP-SAT；模型无效循环也可能比一次求解更慢。

本篇不提供新的速度倍数、节省比例或成功率。

## 22. 与 SFT、DPO 和 RL 的联系

### 22.1 后训练主要学哪一部分

后训练可以学习在当前状态下：

- 何时补充资料，何时已有足够证据。
- 怎样选择更相关的 query。
- 何时求解、验证、修订。
- 如何响应工具失败。
- 什么时候应该问用户、提出获准取舍或停止。

它并不替代 CP-SAT 的搜索，也不自动修复工具接口、错误单位或缺失真实数据。

### 22.2 成功轨迹为什么必须同时看结果和过程

如果一条轨迹靠估算默认值绕过证据门槛，或者 Validator 本身遗漏关键约束，即便最终 hard_pass=True，也可能不适合直接作为高质量教师数据。

应把工具来源、fallback、证据覆盖、参数权限、终止语义和环境版本一起审阅，再筛成功轨迹。

### 22.3 DPO 的偏好对应该怎样构造

可比较同一状态下两种有清楚差异的下一步：一方补齐具体实体的证据，另一方重复无关查询；或者一方引用当前不可行 witness，另一方凭旧证据停止。

但不能简单把“更短轨迹”都标为 chosen；省略必要工具也会更短。不能把“用了更多工具”当成更严谨；重复无效检索也会更多。

### 22.4 RL 的奖励可能被怎样钻空子

若只奖励 hard_pass 或工具成功，策略可能利用空数据、默认费用、未覆盖约束或错误终止统计获得高分。

奖励前先固定契约、补齐验证盲点，并用独立任务集和真实适配器做验证。否则训练只是更快地利用系统漏洞，而非更可靠地规划旅行。

这一点是面试中连接“Agent 工程”和“后训练方法”的核心，后续第五、六篇会展开具体数据与实验。

## 23. 高频面试追问：从回答到继续追问

以下是讲解框架，涉及个人完成范围时应按真实职责调整。

### Q1：为什么不让大模型直接生成完整行程？

**回答：** 自然语言生成可以给出漂亮路线，但难以可靠维护时间窗、指定地点、成本和固定活动等多约束。我让模型选择工具和下一步，结构化求解器生成候选，验证器再检查输出。可靠性仍依赖事实质量与已实现约束，不能说完全消除了错误。

**追问：** Solver 和 Validator 共用错误事实时怎么办？

### Q2：你这个系统是真 Agent，还是固定工作流？

**回答：** 当前模型掌握工具顺序、语义查询、何时澄清、求解、修订和提交；Harness 检查合法性和前置证据。被拒绝后返回同一模型，没有隐藏流程代替它执行下一步。外层状态机负责生命周期，内层模型负责逐步决策。

**追问：** 哪些决定仍由工具实现固定？可以举出班次首项选择和交通估算等局部规则。

### Q3：为什么工具参数不全部让模型填写？

**回答：** 城市、矩阵、已验证候选等已有可信来源，让模型复制会增加错误和输入体积。模型保留语义查询与策略选择，执行侧补充数据，并记录字段来源。这样训练也能区分模型责任与控制器责任。

**追问：** query 写错会不会被代码偷偷修正？当前不应替换其语义选择。

### Q4：用了 OR-Tools 就能保证行程正确吗？

**回答：** 它只能对输入模型求解。候选缺失、营业数据错误、矩阵估算偏差都会影响结果；目标最优也不等于全部业务要求已覆盖。因此还需要证据检查与输出验证，并说明未覆盖的范围。

**追问：** 举一个当前项目的真实口径差异：单次与单日通勤上限、普通预算交通重复计入。

### Q5：CP-SAT 具体怎么建模？

**回答：** 按天定义访问变量 V、边变量 X、到达时间 A，以及每日费用与强度。Circuit 和入出边建立路线，条件时间窗、边时间传播、NoOverlap 保证排程；再加入必去、闭馆、固定活动、餐次和预算等约束。目标是访问和偏好奖励减去通勤、重复与分散惩罚。

**追问：** 为什么时间传播只能给下界？为什么回到酒店不传播？

### Q6：你说多目标优化，真的输出了 Pareto 前沿吗？

**回答：** 当前是阈值约束加加权目标，没有扫描多组阈值输出前沿。我会按最终表达式描述，不把 EpsilonConfig 的名字当成完整多目标优化实验。

**追问：** 固定权重如何校准？当前没有新实验就不要给出最优权重结论。

### Q7：餐厅为什么难？

**回答：** 真实餐厅是带地点、费用、时长和营业窗口的路线节点，不只是“午餐一小时”。我们有按天餐次展开备选、保留来源 ID、复用来源矩阵和独立餐饮检查的实现。但真实详情接口与该分支要求仍需核对，不能用夹具成功代替真实集成。

**追问：** 为什么普通午餐不能当零费用路由节点？会出现绕过真实交通的捷径。

### Q8：什么时候可以说任务不可行？

**回答：** 一条候选失败不足以证明全局无解。当前用少量保守证据，例如必去项明确全部日期关闭、必去票价下界超过预算。没有这类证明就保持未定，而非凭超时直接说用户需求不可能。

**追问：** 有不可行证据，是否就能删景点或加预算？不能，仍取决于授权范围。

### Q9：怎么保证用户改了要求后不会提交旧结果？

**回答：** 证据绑定目标和计划版本，研究输入变化会使派生矩阵、求解、验证和草案失效；finish 再检查当前报告与新鲜度。代码只负责失效，不替模型安排后续工具。

**追问：** 同版本内的证据变化怎么办？需要内容比较，不能只靠版本号。

### Q10：为什么不用更多线程把 Solver 跑快？

**回答：** 当前参数是单 worker，并有历史平台限制的注释。是否增加线程要在目标云环境测，并同时观察可行率、解质量、并发请求数和资源成本。候选裁剪、餐厅展开规模、重复动作与详情串行也可能是更主要的瓶颈。

**追问：** 外层 asyncio 超时是否能杀掉求解线程？不能直接这样保证。

### Q11：你怎么证明没有幻觉？

**回答：** 我不会承诺“没有幻觉”。模型不能直接写通过结论，证据与输出有程序检查，但规则抽取、默认详情和估算矩阵仍有边界。更准确的是减少可识别的错误，并用固定反例与端到端证据说明覆盖范围。

**追问：** 你当前最担心的盲点是什么？选一个讲到源码与验证方案。

### Q12：后训练成绩很好，为什么还要测真实工具？

**回答：** 固定环境可能提供了完整、干净的餐厅和营业字段，真实适配器未必如此。训练成绩主要衡量那个输入契约下的策略行为；还必须测真实来源、字段映射、错误恢复和证据时效，才能说明系统整体可用。

**追问：** 你如何锁定训练与评估环境、避免验证器漏洞成为奖励捷径？

## 24. 三分钟讲述稿与自测

### 24.1 三分钟讲述稿

> 这个项目把旅行规划拆成语义决策、证据获取、约束求解和结果验证。当前模型通过 13 个动作决定查什么、何时求解和如何恢复，Harness 检查前置条件、权限和预算，执行适配层从账本补充可信候选、约束与矩阵。
>
> 外部工具结果先进入统一 Observation，再形成带版本、来源和有效期的事实与产物。求解前不仅检查有没有结果，也检查实体、日期、来源和矩阵等条件。不过当前真实入口仍有估算地图、字段映射和具体餐厅详情的接入边界，我会按源码说明，不把测试夹具能力直接当成线上全覆盖。
>
> 行程求解使用 CP-SAT，按天建立访问、路线与到达时间变量，加入开放时间、固定活动、必去、餐次与预算等约束，再通过加权目标兼顾偏好和通勤。普通用餐是时间占位，具体餐厅则是有来源 ID 和真实边的路线节点，二者降级策略不同。
>
> 求解成功后还要验证。验证器检查输出及源数据一致性，finish 只能提交当前通过的草案等待用户确认。某条方案失败不代表任务无解；只有足够明确的约束事实，才支持不可行诊断和授权范围内的取舍。
>
> 我也会说明工程盲点，例如预算和通勤口径、默认事实与验证覆盖。后训练主要改善模型决策，不能代替修正这些数据与系统问题。验收时把策略正确率、行程通过率、证据覆盖和真实工具集成分别报告。
