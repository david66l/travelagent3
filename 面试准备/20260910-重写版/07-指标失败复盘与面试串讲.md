## 1. 这一篇要帮你完成什么

面试官听到一个项目，通常需要确认四件事：

1. 你解决的具体问题是什么，为什么现成调用还不够。
2. 你能否沿真实数据流解释实现，并指出关键不变量。
3. 改动到底有效到什么程度，数字有没有合适的比较对象。
4. 你实际参与了哪些工作，遇到反例后怎样判断和调整。

这里的“通常”是组织材料的经验框架，不是某家公司的固定评分标准。没有一个可核验的“大厂社招 80 分”统一量表。能展示规模、方法、结果和边界，比自评项目已经达到某个分数更有说服力。

本篇的最终练习是：不看文档，讲清一个完整用户案例、一组可信实验、一个失败复盘和一项亲自完成的贡献；每个关键数字都能指出来源。

### 1.1 建议阅读顺序

- 第 2—9 节：统一数字与证据口径。
- 第 10—15 节：把架构、记忆、求解和服务串成可解释案例。
- 第 16—19 节：准备职责、取舍与不同长度的讲述。
- 第 20—24 节：综合追问、白板、复习安排与来源查证。

前六篇负责深入机制，本篇负责选择重点和检验能否连贯讲清。

## 2. 每项简历主张都应有一张“证据卡”

不要先记住百分比，再临时寻找解释。先填以下字段：

| 字段 | 要回答的问题 |
|---|---|
| 问题 | 改进前用户或系统受到什么影响？ |
| 主张 | 你究竟说哪个能力或指标改善？ |
| 版本 | 哪个代码、模型、Adapter、工具和判分器？ |
| 统计单位 | 请求、任务、轨迹、动作、连接还是来源组？ |
| 分母 | 总共多少，失败、超时和重试如何计入？ |
| 比较对象 | 与哪个基线相比，哪些条件相同？ |
| 结果 | 原始数量、比例、离散程度与子集表现？ |
| 证据 | 报告、逐条记录、配置和身份校验在哪里？ |
| 限制 | 什么没有匹配，哪些场景没有覆盖？ |
| 职责 | 哪些决策、实现、验证由你实际完成？ |

“用了 LangGraph、Redis 和 LoRA”是一份组件清单。补上这些字段，才能变成能被追问的工程经历。

### 2.1 四种证据强度不要混写

**实现存在：** 找到真实调用与状态更新代码。它不自动证明运行正确。

**静态风险：** 从分支、字段或合同推导可能的反例。它不自动等于发生过生产事故。

**实验观察：** 固定条件下有运行记录和统计。它不自动代表线上总体表现。

**发布与用户效果：** 还需要真实运行、监控、回滚和用户场景证据。当前材料不能支撑“大规模生产用户已经验证”的说法。

在讲述中直接使用“代码实现了”“历史实验观察到”“静态审查发现风险”“下一步拟验证”等词，能减少不必要的歧义。

### 2.2 哈希能提供什么

哈希帮助确认你读到的文件是否还是同一份。它不能单独证明数据真实、没有泄漏、指标设计合理，也不能证明个人作者身份。

最新云端结果在本文中来自归档说明；对说明做哈希校验，只能确认说明文件身份，不能替代重新读取原始云端日志。

## 4. Token 降幅：最值得准备的一张完整证据卡

### 4.1 实验身份

历史实验名称为 stage40-policy-driven-runtime-vs-pure-react-v1，报告模型是 deepseek-v4-flash，运行模式为当时的 policy_driven。

两组按相同 case_id、input_hash 和模型配对，共 30 个信息完整的可规划任务，覆盖 2—4 天。纯 ReAct 使用冻结工具夹具，历史运行时使用当时仓库工具栈与 PostgreSQL。

这不是当前统一 Harness 的最新复测，也不是 Qwen3-4B LoRA 训练的独立消融。

### 4.2 原始聚合与计算

| 项目 | 纯 ReAct 参考 | 历史运行时 |
|---|---:|---:|
| 任务数 | 30 | 30 |
| 总 Token | 856,564 | 175,519 |
| 平均 Token / 任务 | 28,552.13 | 5,850.63 |
| 平均模型调用 | 5.50 | 8.70 |
| 平均工具调用 | 6.83 | 12.57 |
| Verifier 硬通过 | 1/30 | 29/30 |
| 平均端到端时间 | 58.66 秒 | 17.03 秒 |

~~~text
按总量计算降幅：
1 - 175519 / 856564 = 79.508945...%

同样本量下，均值之比给出相同降幅。
平均每任务减少：
(856564 - 175519) / 30 = 22701.5 Token
~~~

本次从本地 report.json 重新计算聚合比值，得到 79.508945%。没有重新跑模型，也没有在本次重新逐行审核两组原始轨迹。

报告还给出配对 Token 差的 bootstrap 区间；本文没有重算原始样本分布，不将该区间升级成“排除了工具环境混杂”的证明。

### 4.3 为什么调用次数更多，Token 反而更少

调用数只是一项乘数。每次输入有多长、输出是什么、是否反复生成整份行程、是否携带冗余观察，都影响总 Token。

可用讲解式：

~~~text
总 Token = Σ每次模型调用的输入与输出 Token
~~~

更多短动作，可能比更少的长篇推演便宜。但这只是机制解释；要证明每个组件贡献多少，需要同工具、同计量、同模型下的逐项消融。

不能从这张总表直接推出“上下文压缩贡献了全部 79.51%”，也不能把节省全部归给 CP-SAT。

### 4.4 三个重要限制

第一，工具环境不同。即使用户输入相同，工具给出的观察、可用候选和成本也不完全相同。

第二，计量入口不同。参考组累计 provider 的 prompt + completion；历史运行时记录 Ledger used_tokens，无法完整拆出 prompt / completion。总量相符不自动意味着所有计费类别一致。

第三，成功分布差异很大。全样本效率包含失败；它不是相同质量、共同成功任务上的纯效率比较。也不能把两组各自成功子集的均值直接相除，因为子集大小和组成不同。

### 4.5 求解与时延也要保留状态

29 个硬通过任务的求解状态包括 13 个 optimal、16 个 fallback。不能说 29 个都由 CP-SAT 证明最优。

报告 P95 延迟约为 124.06 → 23.25 秒，但新运行时最大值约 124.35 秒。均值改善不代表没有长尾，30 个样本也不足以拿来宣称稳定的生产 P99。

### 4.6 面试可用表达

> 历史同模型 30 对任务中，记录的平均 Token 从约 2.86 万降至 0.59 万，降幅 79.5%，当轮硬约束通过数从 1 提至 29。我把它作为架构组合的历史证据；工具环境和计量入口有差异，所以没有把全部收益归因给记忆压缩或最新后训练。

这段保留了成绩，也提前给出准确的归因范围。

## 5. 后训练结果：必须讲清的三代基线

### 5.1 初始学生不是最新保留模型

| 身份 | 所属阶段 | 可以连接的比较 |
|---|---|---|
| 早期初始学生 Adapter | 示范 / 接续实验 | 240 题上的 21.7% |
| 修复后的 repair_sft_lowlr | 后续强基线 | 最新 120 新实例的 114/120 |
| 成功 SFT 与 DPO 候选 | 强基线继续训练 | 同一新集合的 120/120、118/120 |

“基线”是相对实验而言的。不能把早期初始 Adapter、裸基础模型和后续保留模型都简称为一个“原模型”。

### 5.2 早期对照：接续有平均收益，但并不稳定

归档记录：

- 252 个配对任务，52 个匹配来源组，3,960 个唯一教师动作。
- 纯示范与示范加接续各 3 个训练种子，共 6 次训练。
- 每次 3 epochs、156 次更新、413,826 个监督 Token。
- 240 个锁定合成测试任务，60 个来源组。
- 冻结初始模型及 6 个候选，总计 1,680 次执行。

三种子均值从纯示范 57.1% 提升至混合 73.9%，差为约 16.8 个百分点。它不是“提高 16.8%”的相对比率，也不是某一次运行的精确分数。

混合种子分别约 71.2%、88.3%、62.1%；约束类平均从初始基线 97.5% 降至 96.7%。因此不能用最高种子代表稳定能力，也不能把规划提升解释为所有子任务都提升。

匹配了来源和监督 Token，不代表匹配了 prompt 长度、总 FLOPs 或墙钟时间。详细机制见[第五篇](E:/A_Louis/TravelAgent2/面试准备/20260910-重写版/05-数据工程与SFT.md)。

### 5.3 修复阶段：开发提升与新验收分开

同机、相同首轮输入、统一格式约束的 120 题开发比较，归档记录 100 → 114 → 119。

第一次新验收为 104/120，失败保留，该集合随后退役为开发。继续修复后，另一个冻结验收 v2 为 119/120，低学习率修复模型成为后续保留模型。

它说明开发集提升不保证立刻迁移到新验收。不能把这些不同集合的分数接成一次干预的学习曲线。

### 5.4 最新继续训练：新集合提升，旧故障退步

| 模型 | 新实例 120 题 | 其中复合故障 15 题 | 另列旧故障 2 题 × 3 次 |
|---|---:|---:|---:|
| 保留模型 | 114/120 | 15/15 | 6/6 |
| 成功 SFT | 120/120 | 15/15 | 4/6 |
| DPO＋SFT 保持项 | 118/120 | 14/15 | 4/6 |

新实例有 40 个相关来源组；旧故障复测不是额外 6 个独立任务，也没有合进新实例分母。

SFT 在新实例修复 6 个原失败且没有新增失败；DPO 修复同样 6 个，但新增 2 个。候选都在旧问题上出现回归，归档的决定是保留原模型。

本文没有连接模型服务确认当前线上加载哪个 Adapter，因此“保留”指该轮实验决定，不是当前线上服务状态的实时报告。

### 5.5 新实例满分为什么不能直接写成“准确率 100%”

至少还有以下边界：

- 有限合成集合与真实旅行需求的分布不同。
- 同一来源的实例相关，不能当 120 个完全独立来源。
- 旧故障仍失败。
- 三个模型的结果已打开，后续再据此选模需要新的确认。
- 本轮只有一个训练种子，不能借用早期三种子条件。

最合适的讲法是“该轮冻结新实例验收中达到 120/120，同时公开旧故障回归并未晋升”。它比一个无分母的百分比更能体现工程判断。

## 6. 数据规模：怎样避免把 64 条说成 954 条

最新链路可以记成：

~~~text
64 个训练任务 × 4 个采样种子
  → 256 条执行轨迹
  → 220 条严格质量通过
  → 导出审核接受 174 条轨迹
  → 954 个去重成功动作候选

从中构造：
128 个偏好对，覆盖 41 个任务

训练使用：
128 个正例 + 256 个额外成功动作 + 128 个历史保持样本
  = 512 行
~~~

### 6.1 每一层对应不同问题

任务数反映业务覆盖；轨迹数反映多次尝试；动作数反映监督决策；训练使用次数还包含重复与权重。

严格质量通过后仍可能因重复动作、输入不一致、权限或来源要求被拒绝导出。因此 220 和 174 不矛盾，也不能把差值直接叫作“46 条错误答案”，需要查看拒绝原因。

954 个动作不是 954 条完整旅行成功轨迹。512 行也不能在没有去重身份检查的情况下叫 512 个独立任务。

### 6.2 历史阶段不能直接求和

早期教师、后续保持样本、修复数据和最新偏好正例可能有复用。把所有行数相加，会混入重复样本、派生动作、加权使用和同源任务。

面试如果被问“到底多少数据”，先回答正在讲的阶段，再解释统计单位；不要用最大的总行数掩盖实际场景覆盖。

### 6.3 为什么规模不只取决于条数

对 Agent，关键还包括：

- 任务类型与约束组合是否覆盖。
- 正常状态与失败恢复状态是否都出现。
- 工具参数、观察、证据和权限是否可回放。
- 同来源是否隔离，教师是否看到了学生不可见信息。
- 动作目标、Token Mask、模型输入是否真实一致。

当前主要缺口之一正是失败后恢复覆盖，而不是简单缺少更多顺利成功的重复动作。

## 7. 训练速度、调用效率和费用是三本账

### 7.1 优化用时不等于完成整个实验

早期完整实验约 34.13 GPU 小时，调度至收齐约 12.03 小时；最新 SFT 15.1 分钟、DPO 19.4 分钟，属于较小的 64 步继续训练。

两者的数据、更新计划和样本长度不同。不能声称把同一个完整实验仅靠底层优化压缩了几十倍。

阶段应拆成：

~~~text
准备数据 → 采样 / 教师 → 审核 → 参考概率
→ 参数优化 → 保存与部署 → 多模型评测 → 归档
~~~

每个阶段可能使用不同硬件并行。GPU 小时是设备时间累加；墙钟是用户等待，二者不能相互替换。

### 7.2 做过的并行是什么

归档记录多台云机分担独立任务采样、候选训练与评测准备；关键对照回到同一台 GPU 依次评测。

这属于多机任务并行，不是多机器共同 all-reduce 一个模型的 DDP。用户最初设想的跨机器联合训练，不能在简历中被当成已经完成的实施结果。

### 7.3 可描述的优化机制

归档记录了 BF16、SDPA、LoRA、梯度检查点、仅在必要 completion 范围计算词表输出投影、vLLM 与缓存等措施。

其中输出投影优化不代表跳过 prompt 的 Transformer 前向；格式约束也属于推理工程，不是参数学习的成绩。不同措施的单独速度收益仍需对应对照，本文不补造倍数。

### 7.4 工具调用下降不等于全面效率提升

64 题开发集上，三个模型共同成功的 60 题平均工具调用为：

| 模型 | 平均调用 |
|---|---:|
| 保留模型 | 11.95 |
| 成功 SFT | 11.37 |
| DPO | 11.15 |

按报告四舍五入均值计算，相对下降约 4.85% 和 6.69%。这只是共同成功子集、工具次数的描述性比较；不能推断全体任务总时延、Token 或费用同比下降。

共同成功子集可以辅助比较质量相近的运行，但它本身经过结果选择。仍应同时报告全体任务成功、失败开销与重试。

### 7.5 教师 API 费用

2026-09-09 归档保守记账为 93.429114 元，最新成功 SFT / DPO 及其复测新增教师调用为 0。

这是历史教师账本，不是现在的账户余额或供应商最终扣费；GPU 租赁、存储和其他 API 另计。不能写“全部后训练成本不到 100 元”。

本篇没有调用教师、核实当前价格或购买算力，也未消耗新的实验预算。

## 8. 服务性能：先说测了什么，再说有多快

### 8.1 性能目标确实存在，但目标不是成绩

docs/PERFORMANCE.md 明确使用“PRD 目标”标题，列出：

- HTTP 202 首响应 < 100ms。
- 缓存命中草稿 < 500ms。
- 完整行程 P99 < 8s。
- SSE 首事件 P99 < 500ms。
- 每实例并发 SSE ≥ 1000。
- Celery ≥ 50 task/s/worker。

本次没有核实与这些条件配套的达标报告。应表述为目标或验收要求，不能直接移入简历成果栏。

### 8.2 k6_sse.js 的文件名不能替代代码语义

本次读取该脚本，实际路径为：

创建游客身份

当前阈值是 chat_acceptance 的 P95 < 600ms、P99 < 1000ms，以及请求失败率和 checks 门槛。这既不是“SSE 首事件 P99 < 500ms”，也不是“完整行程 P99 < 8s”。

constant-vus 设置的是同时运行的虚拟用户数量；每个用户还执行鉴权、建会话和等待。VUS 不能直接等同于规划吞吐或活跃 SSE 连接。

### 8.4 六种时间戳应分别报告

| 指标 | 起点与终点 |
|---|---|
| 受理延迟 | 客户端发送请求 → 收到持久受理响应 |
| 队列等待 | 任务受理 → Worker 实际认领 |
| 首有效事件 | 任务受理 → 客户端收到第一个业务事件 |
| 首文本 Token | 声明的请求起点 → 首个用户可见文本 Token |
| 业务完成 | 任务受理 → 通过验收的结果可见 |
| SSE 寿命 | 建连 → 断连 |

快返回响应头，并不意味着模型已生成内容；Job completed 也不自动代表用户得到完整可用行程。

跨机器时间差需要时钟同步或可关联的单端计时。本文只给测量设计，没有现场采集新的时延。

### 8.5 真正要证明容量，需要一份怎样的报告

SSE 专项还应包括连接建立、事件大小与频率、断连重连、游标回放、慢客户端、最大持续时间和终态交付。

不能只截取最好看的一段成功请求 P99，排除超时和拒绝后宣称全部服务达标。

## 9. 统一指标字典：减少“正确率”歧义

### 9.1 模型、行程与任务指标

| 名称 | 一种清楚的统计口径 | 不能代替 |
|---|---|---|
| 原始策略格式合法率 | 未经修复的模型输出满足动作格式的次数 / 模型输出次数 | 动作有用 |
| 工具参数合法率 | 通过相应参数与权限检查的调用 / 请求调用 | 工具返回真实事实 |
| 工具执行成功率 | 按工具类型定义的成功调用 / 已执行调用 | 任务成功 |
| 行程硬约束通过率 | 通过指定 Verifier 的行程 / 明确的候选集合 | 所有研究证据充分 |
| 严格任务质量 | 满足任务类型及所有适用门槛的执行 / 固定任务集 | 真实用户总体满意度 |
| 恢复成功率 | 指定故障实际触发后成功的执行 / 已触发故障执行 | 普通无故障成功率 |

这些是报告应明确的定义框架；实际实验应以冻结协议为准，不能借本表悄悄更改旧分母。

例如“工具执行成功率”必须决定空结果、部分成功和合法否定结果如何记账；任务要求正确澄清时，不能因为没有行程就统一判失败。

### 9.2 记忆指标

建议单列：

- 当前明确偏好与历史画像冲突时的正确采用率。
- 用户否定或撤销后的错误保留率。
- 跨会话恢复后关键字段的保真率。
- 不同用户之间的错误召回或泄漏事件。
- 过期证据被继续用于求解 / 提交的比例。
- 同质量条件下上下文长度、模型成本与任务表现。

这些专项本次没有新测量。固定 profile 的单 episode 后训练成绩，不能证明长期画像写回和冷热恢复都正确。

### 9.3 可靠性指标

恢复应分别测客户端重连、任务派发失败、Worker 中断、模型超时与外部工具失败。每一种都有不同触发点和恢复完成定义。

任务最终完成但重复付费调用三次，不能只报最终成功率；还应报告重复执行、副作用、额外成本和恢复时延。

### 9.4 比率以外，保存失败与配对关系

对同任务比较，保留：

~~~text
双方成功 / 仅基线成功 / 仅候选成功 / 双方失败
~~~

对长任务，还应保存首次错误动作、最后有效状态、预算消耗、工具观察与终止依据。一个最终 0/1 不足以定位哪个环节需要改进。

统计与多采样口径见[第六篇](E:/A_Louis/TravelAgent2/面试准备/20260910-重写版/06-DPO与RL选择及评测.md)。本文不根据汇总比例新造置信区间或显著性结论。

## 10. 用一个用户场景串起整套架构

以下是教学场景，不是本次新运行的日志：

> 用户计划杭州三日游，要求总预算受限、必须去一个指定景点、每天不要太累；历史画像里曾记录同行老人，但用户本次明确说“这次自己去”。生成草稿后，用户把日期推迟一天；客户端中途断开，外部详情接口又有部分超时。

不要先背组件，先讲系统需要维护哪些不变量：

1. 当前明确需求不能被旧旅行的同行条件悄悄覆盖。
2. 模型看到的日期、候选、矩阵与当前任务版本一致。
3. 无效或过期验证不能授权提交新行程。
4. 网络断开不能让同一逻辑请求无意创建多个任务。
5. 合法外部失败需要可见反馈，模型不能伪造补齐事实。

### 10.1 接收和恢复

API 校验归属与幂等请求，持久保存消息和任务，再派发 job_id。客户端用 SSE 查看进度；断线后根据任务与游标恢复。

这里需要区分“设计目的”和“保证范围”：数据库任务、SSE 事件和图 Checkpoint 各有作用，不能只说“用了 Redis，所以不会丢”。

### 10.2 记忆合并与目标

先处理当前消息与已有会话状态，再召回长期画像。日期、人数、预算和必去项进入当前旅行目标；旧偏好只能在合适作用域内补缺。

第二篇已经指出布尔 OR、列表合并、预算单位等静态边界。这个场景中的“这次自己去”恰好适合验证长期同行人条件是否错误保留，不能直接保证现有所有字段都已正确覆盖。

### 10.3 决策与工具

LangGraph 组织会话阶段；内部模型基于 PolicyContext 选择下一动作。Harness 校验权限、前置证据和预算，工具执行结果写入 Ledger，再投影给下一步。

模型可以选择补天气、搜地点、补详情、求矩阵、求解、验证、澄清或提交。求解和验证不是每个工具执行后都会自动完成的固定后缀。

### 10.4 用户改日期

目标版本变化后，应重新判断营业时间、天气、固定活动、矩阵和验证结论是否适用；能复用的稳定事实不必全部丢掉。

改日期本身不会把数据库中的所有画像删除，也不该继续拿旧行程验证结论提交新计划。这里要讲清 goal_version、plan_version 与证据依赖。

### 10.5 工具部分失败

已有成功详情应保持来源和状态，失败项带上可重试信息。模型根据缺口与预算决定补查、换候选或澄清。

如果整体重试反复消耗已成功部分的预算，就要同时检查工具适配和策略训练；不能把所有耗时归因于模型慢。

### 10.6 完成门

Solver 基于已获取的数据生成候选，Verifier 检查适用约束；Harness 还要确认研究证据、计划版本和终止条件。

合法草稿等待确认可能是任务规定的正确终态。JSON 完整或 finish 字符串出现，则不足以证明成功。

实现细节与来源入口见[第一篇](E:/A_Louis/TravelAgent2/面试准备/20260910-重写版/01-项目全貌与Long-Horizon-Agent架构.md)、[第二篇](E:/A_Louis/TravelAgent2/面试准备/20260910-重写版/02-记忆上下文与检索.md)、[第三篇](E:/A_Louis/TravelAgent2/面试准备/20260910-重写版/03-工具证据与约束求解.md)、[第四篇](E:/A_Louis/TravelAgent2/面试准备/20260910-重写版/04-后端可靠性与部署.md)。

## 11. 失败复盘一：DPO 学会偏好，仍不会恢复顺序

### 11.1 已观察到什么

2026-09-09 归档中，DPO 的旧案例 stress64-017 三次仅通过一次。失败类型描述为：

~~~text
缺天气 → 提前求解被拒
→ 验证空行程
→ 后续求解得到行程
→ 未重新验证该行程
→ 连续 finish 被拒
~~~

这是归档复盘，不是本次重新执行的轨迹。

### 11.2 哪一层实际发挥了作用

Harness 拒绝了前置不足、空计划或未验证计划的提交。系统守住部分完成门，并不意味着策略已经学会正确恢复。

模型失败与防护有效可以同时成立。不能因为最后没有错误放行，就把这条任务算成功。

### 11.3 为什么 DPO 可能没有覆盖它

最新偏好主要围绕同状态下的信息增益、重复调用和合规空结果；这些局部比较不一定覆盖“发生错误后，重新求解导致验证失效”的多步状态链。

归档还指出成功动作池缺少 RESEARCH_EVIDENCE_INSUFFICIENT、VALIDATION_NOT_PASSED 等失败上下文后的成功恢复动作。

这是有证据支持的缺口假设，但并未单独证明它是全部回归的唯一原因。还应检查上下文可见性、执行器、模板、保留数据和随机性。

### 11.4 下一步怎样验证因果

建议在新的 train 实例触发同类状态，保存真实快照，采集正确接续；固定初始权重和运行时，做小步恢复 SFT 及匹配对照。

开发时检查是否学会完整顺序，而不是看到错误码就固定输出 validate。重新求解前后、计划为空与非空、有效验证与过期验证，必须有对应区分。

最后用旧故障观察恢复是否稳定，并对最终冻结候选安排新确认集。本文没有执行这一方案。

### 11.5 面试复盘表达

> 这轮 DPO 的局部偏好没有转化成全部恢复能力。旧案例中模型在求解受阻后验证空计划，之后又漏验新计划。系统没有放行，但任务仍失败。我会先审查状态是否可见，再补充新的恢复接续数据，用同栈对照验证；不会只增加训练步数或放松 finish 判定。

## 12. 失败复盘二：成功轨迹筛选的选择偏差

### 12.1 已观察到什么

成功 SFT 的旧案例 stress64-023 三次只通过一次。归档描述：前期优先搜景点，餐馆补充较晚，详情批量重试已消耗较多预算，后续餐馆证据无法补齐。

新集合 SFT 120/120，旧故障却仍退步。两个数字共同揭示覆盖边界，而不是互相矛盾。

### 12.2 为什么筛选成功还不够

成功筛选只保留当前模型能够完成的路径。模型最不擅长的状态可能因为从未恢复成功而被持续排除；反复训练容易进一步偏向“顺利输入下的典型路线”。

动作级去重能减少重复文本，但无法自动补齐未出现的策略状态。

### 12.3 模型和工具分别可能有什么问题

| 层次 | 需要核对的假设 |
|---|---|
| 目标投影 | 是否提前显示餐饮要求和当前缺口 |
| 查询策略 | 是否过晚获取必要类别 |
| 工具批处理 | 已成功详情是否被重复请求 |
| 预算 | 失败重试怎样计费、怎样扣工具次数 |
| 训练分布 | 是否有部分失败后的成功接续 |
| fixture | 餐馆全名、别名或城市匹配是否过严 |

归档提示过 fixture 匹配边界。若修复接口，应在所有模型使用同一新运行时后重评，不能只给候选更宽松的工具。

### 12.4 可验证的修复方向

先保留失败轨迹，找首次偏离必要证据收集的位置。补充新状态中的正确查询和部分失败恢复，再测旧能力是否保留。

不建议直接在控制器里写死“第 3 步必须搜餐馆”，因为不同用户要求不同。更合适的是让必要类别成为可见缺口，并用数据和门槛约束需求完成。

这段是方案取舍，不是本次已经改过源码的结果。

## 13. 失败复盘三：记忆错误不应全部交给训练解决

### 13.1 一个静态反例

第二篇指出部分合并规则对布尔条件使用 OR。若长期画像“带老人”为 True，本次“自己去”为 False，直接 OR 会继续保留 True。

这可以保护某些身体约束，却可能把一次旅行的同行状态错误长期化。该例是静态风险推演，本次没有复现真实用户事故。

### 13.2 为什么加大模型不一定解决

如果模型输入已经被合并器改成“带老人”，更强模型仍可能忠实执行错误状态。训练不能自动恢复上游丢失的否定含义。

应先定义字段的类型、时间和作用域：

- 用户自身长期事实。
- 本次旅行条件。
- 可撤销偏好。
- 暂时推断与默认值。

然后验证写入、读取、更新和删除的往返语义。仅在最终 prompt 中加一句“以用户最新需求为准”不能替代整条数据链正确性。

### 13.3 与 Token 优化的关系

减少输入之前，需要知道哪些信息不能丢。预算单位、日期版本、禁止事项和证据来源，比完整重复的工具原文更需要准确保留。

压缩后的长度下降应和关键事实保真、任务成功一起测。历史 79.51% Token 对照没有单独验证这些长期记忆语义，因此不能借用它证明画像质量。

## 14. 失败复盘四：任务恢复不是一个“重试开关”

### 14.1 用故障时刻划分问题

| 中断时刻 | 需要恢复或处理的状态 |
|---|---|
| 数据库提交前 | 请求是否成功受理 |
| 已提交、尚未派发 | 持久任务如何补偿派发 |
| Worker 已认领 | 执行归属、租约和心跳 |
| 工具已执行、状态未持久化 | 重复调用及外部副作用 |
| 状态已保存、事件尚未交付 | 事件补发与游标 |
| 客户端刚重连 | 回放、重复消费、终态一致性 |

这是一张故障演练设计表，不是本次全部通过的测试清单。

### 14.2 当前审阅中值得讲的边界

第四篇记录：某些状态写入、回收条件与租约归属之间仍有静态风险；并非每条路径都有完整 fencing。SSE 也不能把“保存最大事件 ID”直接等同于所有追加事件都幂等消费。

这些风险应说明代码位置和触发条件，但不能编造成“线上事故后把故障率降低多少”。

### 14.3 面试官问 Exactly-once 时

先问保证对象：数据库结果、任务执行、事件交付还是外部操作？

本项目可以讲幂等键、持久任务、条件认领、状态恢复和事件游标的组合。对外部工具已执行但确认丢失的情况，仍需要供应商幂等、查询补偿或业务约束，不能统一承诺只执行一次。

具体实现与风险见[第四篇](E:/A_Louis/TravelAgent2/面试准备/20260910-重写版/04-后端可靠性与部署.md)。

## 15. 求解器案例：数学可行不等于真实世界正确

### 15.1 沿一条证据链追问

~~~text
用户要求
→ 结构化约束
→ 真实候选与营业、价格
→ ID 对齐的交通矩阵
→ CP-SAT / 回退求解
→ 独立验证
→ 与当前版本一致的提交
~~~

任何一层出错，都可能让最终行程不合用。最优解只相对于给定候选、模型、约束和目标成立。

### 15.2 三个适合白板讲的反例

**营业时间失真：** 输入告诉求解器全天营业，现实却已闭馆。数学模型正确执行了错误事实，不能靠多训练几个 epoch 修复。

**交通矩阵错位：** 矩阵顺序和地点 ID 不一致，路线时间传播会引用错误边。需要数据合同与验证，不是让模型给更长解释。

**普通用餐与指定餐厅混淆：** 一段午餐时间占位，不等于已经安排有地点、费用和营业窗口的餐厅。不能用普通占位满足用户指定餐馆要求。

以上用于机制讲解，不作为本次新发现事故。具体源码与已有静态边界见第三篇。

### 15.3 超时、fallback 与无解不同

超时可能只是没有在预算内完成搜索；fallback 是另外生成候选的策略；不可行结论则需要适当证据。

历史 stage40 的 16 个 fallback 硬通过说明回退可以生成可验收结果，也说明不能把总通过数写成 CP-SAT 最优解数。

## 16. 个人职责：把项目事实变成自己的经历

文档能够证明项目里有什么，不能替你证明全部工作都是独立完成。本系列不自动代填“主导”“独立设计”“线上负责”等职责。

### 16.1 按具体产物填写

| 工作项 | 你需要准备的个人证据 | 当前填写 |
|---|---|---|
| 架构拆分 | 当时方案、取舍记录、关键实现与评审 | 待按真实经历填写 |
| 记忆与上下文 | 映射规则、修复、测试、具体反例 | 待填写 |
| 工具与求解 | 适配、约束建模、验证或优化修改 | 待填写 |
| 服务可靠性 | 幂等、派发、事件、故障演练产物 | 待填写 |
| 数据审核 | 规则、拒绝案例、来源与版本记录 | 待填写 |
| 训练与速度优化 | 脚本修改、配置、诊断与等价验证 | 待填写 |
| 评测与发布判断 | 冻结记录、失败分析、最终决定 | 待填写 |

对每一项再问自己：

- 哪个难点需要你做判断？
- 你提出过什么替代方案，为什么没选？
- 你亲自验证了什么？
- 如果删掉某项检查，会发生哪个反例？
- 哪些实现来自工具生成、他人工作或现有库，你怎样审核？

代码提交记录是辅助证据，不是作者身份的唯一证明。生成代码可以是开发方式的一部分，但应如实说明需求拆分、修改、审查和验收由谁完成。

### 16.2 动词应和证据匹配

“实现”需要具体改动；“设计”需要模型与取舍；“优化”需要基线与结果；“验证”需要实际执行；“主导”还需要职责范围与决策权。

只阅读并理解某段代码，可以说“梳理了”或在面试中解释它，不能自然升格成当时亲自完成的生产改造。

### 16.3 不用虚构用户数来证明规模

可展示的规模包括真实任务来源、训练 / 评测次数、工具合同复杂度、失败覆盖、版本身份和计算预算。

若当前没有真实活跃用户、商业收入或生产部署证据，就不要填一个看起来像大厂的数。工程深度可以通过完整实验和准确复盘体现。

## 17. 面向 Agent 开发岗位，应该突出哪四条主线

以下是内容组织，不是自动代填个人职责后的最终简历。

### 17.1 主线一：模型决策和系统约束的分工

**问题：** 自由生成无法可靠维护多约束、版本和证据。

**机制：** LangGraph 会话编排，内部统一 Agent Loop；模型选择动作，Harness 约束权限与预算，Ledger 保存事实、产物和失败，Solver / Verifier 承担求解与验收。

**证据：** 第一、三篇的实际链路；历史架构 Token 对照。

**追问准备：** 模型还有哪些自主权？为什么系统不能直接 finish？用户改日期后哪些对象失效？

### 17.2 主线二：记忆与上下文工程

**问题：** 多轮需求、长期画像与大量工具观察容易相互覆盖或挤占窗口。

**机制：** 会话状态、热温冷存储、画像召回，以及面向当前任务的版本与时效过滤、产物摘要和失败投影。

**证据：** 第二篇字段流和代码路径。

**追问准备：** 显式 False 怎么处理？历史兴趣和本次必去项一样吗？摘要保留什么？当前真实 POI 路径是否使用所宣称的向量链路？

不要写成“RAG 记住用户所有历史，彻底消除幻觉”。

### 17.3 主线三：数据与后训练实验

**问题：** 教师从头示范和学生实际遇到的中间状态不同。

**机制：** 教师接续、成功轨迹审核、来源与监督 Token 匹配、LoRA 微调、同状态偏好对照。

**证据：** 240 题多种子实验、最新 120 题与旧故障结果、数据来源和拒绝记录。

**追问准备：** 同源泄漏如何控制？为什么匹配 Token 不等于等算力？为什么选 SFT、DPO，为什么当前没有扩大 GRPO？

### 17.4 主线四：长期执行与可验证发布

**问题：** 规划是长任务，网络、Worker、模型和供应商都可能中断。

**机制：** 持久任务、幂等受理、恢复检查点、事件回放、成本与轨迹记录；候选通过回归和确认门后再晋升。

**证据：** 第四篇实现、归档失败保留与不发布决定。

**追问准备：** 一次外部调用成功但本地保存失败怎么办？P99 测的是哪条链？为什么 120/120 仍保留原模型？

### 17.5 版面不足时怎样取舍

优先保留一条架构主线、一条记忆 / 工具深度、一条有明确对照的训练结果，以及一条可靠性或发布判断。

不要同时塞进所有组件、全部历史百分比和未核实容量目标。面试中能展开的两三个数字，比一行十个指标更有价值。

## 18. 三种长度的项目讲述稿

以下讲述以“项目”为主体。改为第一人称前，按第 16 节确认职责；不要机械声称每项都是独立完成。

### 18.1 三十秒：只建立结构

> TravelAgent2 是一个可验证的旅行规划 Agent。外层 LangGraph 管会话和恢复，内层模型根据结构化状态持续选择工具；Harness 管权限、证据和预算，CP-SAT 与独立验证器负责行程求解和验收。项目还包含多轮记忆、上下文投影、异步长任务，以及围绕真实决策状态的 SFT 和 DPO 对照。重点是让模型在错误和需求变更后仍能按证据完成任务。

这里不急着报所有数字。让面试官先知道你做的系统由哪些责任边界组成。

### 18.2 两分钟：加入一组实验与一个边界

> 项目解决的是旅行规划中信息不完整、约束多、执行时间长的问题。模型负责选择工具、补充证据和处理错误；系统负责把事实、行程和验证状态绑定到当前版本，防止模型直接声明完成。
>
> 外层 LangGraph 管理需求收集、确认和恢复，内层统一 Loop 每步读取 Ledger 的当前投影，包括目标、有效证据、失败与预算。会话记忆和长期画像分开保存，策略输入也不直接拼全部聊天历史。用户改日期时，系统要重新判断旧证据和旧验证是否有效。
>
> 后训练重点是工具动作决策。早期比较纯教师示范和加入学生状态接续，匹配来源与监督 Token，各训练三个种子。在 240 个锁定合成任务上，均值从 57.1% 提到 73.9%，但约束类和种子波动仍有问题。
>
> 后续做定向修复，再从成功轨迹提取监督并构造 128 个同状态偏好对。最新 120 个新实例中，保留模型、成功 SFT、DPO 分别通过 114、120、118；但两个候选在旧故障复测只有 4/6，所以实验决定保留原模型。这个项目让我更关注错误状态覆盖和发布证据，而不只是某一张表的最高分。

### 18.3 五分钟：按问题、机制、证据、反例展开

**第一段，约 40 秒：业务问题。**  
解释为什么查到地点和生成自然语言不等于可执行行程。日期、营业时间、预算、必去点、交通和用户修改会相互影响。

**第二段，约 70 秒：一次执行。**  
画外层会话与内层 Loop。挑一个动作从 PolicyContext、Harness、工具、Ledger、下一轮走一遍。解释求解器和验证器各管什么。

**第三段，约 45 秒：记忆和长程状态。**  
区分画像、会话快照、Ledger 和 Checkpoint。用用户改日期或撤销同行条件说明作用域和失效，而不是背热温冷术语。

**第四段，约 65 秒：实验。**  
选早期接续 SFT 作为主要对照，讲来源匹配、监督 Token、三种子和分布。对方偏系统效率时，可换讲历史 Token 对照，但保留工具与计量差异。

**第五段，约 50 秒：失败与判断。**  
讲 DPO 漏掉新计划重验的案例，说明系统拒绝并不等于任务成功，恢复正例缺口和局部偏好为什么不同。解释保留原模型。

**第六段，约 30 秒：个人贡献和下一步。**  
选择实际参与最深的一项，说清判断、实现和验证；提出一个具体未完成实验，不讲“继续扩大规模”这种空泛计划。

以上时间只是练习分配，真实面试应跟随追问，允许在任何一段深入。

### 18.4 被打断时怎样接回主线

面试官问记忆，就停在状态流；问公式，就切到第五、六篇；问容量，就先澄清统计单位。

回答完可以用一句连接：“这解释了该环节如何保证输入，接下来失败轨迹正是用同一份状态来做接续训练。”不要从头重背五分钟稿。

## 19. 六个设计取舍：避免只会说“因为它强”

| 选择 | 解决的问题 | 代价 / 边界 | 替代方案何时合适 |
|---|---|---|---|
| 模型逐步决策＋Harness | 动态补证据与恢复，同时限制权限 | 更多状态、门槛与数据合同 | 流程稳定且分支少时固定工作流更简单 |
| 结构化 Ledger | 证据来源、版本、失败、预算可查 | 结构和投影可能遗漏信息 | 短对话、无工具时简单上下文即可 |
| Solver＋Verifier | 约束排程与输出独立检查 | 依赖输入事实与覆盖，需维护双层规则 | 仅需开放式建议时不必引入复杂求解 |
| 接续 SFT | 覆盖学生实际遇到的中间状态 | 教师可见性、快照恢复和采集成本 | 简单固定输出任务可先做普通示范 |
| 有限 DPO 对照 | 学习同状态可比较的相对动作偏好 | 局部标签不保证长程最优 | 缺少正向恢复时先补示范更直接 |
| 异步任务＋SSE | 让长任务独立于前台连接持续运行 | 租约、补偿、回放和重复消费复杂 | 极短请求可采用同步接口 |

每次回答取舍，最好补一个该方案不适合的条件。这不削弱项目，反而说明你知道复杂度为什么值得支付。

### 19.1 什么才构成可复用贡献

可复用的部分不是“旅游”两个字，而是状态—动作—观察合同、权限与证据边界、恢复数据构造和评测身份管理。

迁移到其他领域时，工具、约束、奖励和用户授权必须重新定义。不能声称换个 prompt 就能无成本覆盖医疗、金融或交易等高风险任务。

## 20. 十二组综合面试追问

### Q1：你的项目最有技术含量的部分是什么？

**回答主线：** 是把模型决策、证据状态、执行权限和训练评测连在一起。选一个真实动作说明，它如何被约束、怎样产生证据、怎样成为训练样本，最后怎样验收。

**继续追问：别人也会接工具，有什么区别？**  
展开版本失效、前置拒绝、恢复轨迹和对照实验，不靠增加组件数量回答。

**准备产物：** 一张执行链图、一条实际样本结构、一个失败复盘。

### Q2：你说 long-horizon，和普通 while 循环有什么区别？

**回答主线：** while 是控制结构；这里需要在多次工具交互、失败和需求变化中保持目标、证据、预算与恢复状态。重点是状态合同和终止依据。

**继续追问：模型最多看六条历史，怎么长期决策？**  
近期历史之外还有结构化目标、有效产物、失败摘要与预算。内存决策历史也有上限，不能承诺无限完整记忆；应测试长轨迹中的信息丢失。

**准备产物：** 第一、二篇中的完整状态与模型投影对照。

### Q3：记忆到底带来了多少收益？

**回答主线：** 有明确的存储、召回和投影实现，但目前没有一组独立的长期记忆消融足以给出净收益百分比。历史 Token 降幅也不是记忆单组件消融。

**继续追问：那怎么证明值得做？**  
先定义跨会话恢复、用户更正、过期证据和上下文保真测试，再固定模型与工具比较。本文提出方案，没有伪造已测成绩。

**准备产物：** 第二篇专项测试矩阵。

### Q4：79.5% Token 降幅怎么来的？你敢复算吗？

**回答主线：** 历史 30 对任务总 Token 856,564 与 175,519，1−后者/前者约 79.51%。本次已核对聚合计算。

**继续追问：是上下文压缩的收益吗？**  
不能全部归因。两组工具环境和计量入口不同，且通过率差异大；需要同条件消融才能拆分组件贡献。

**准备产物：** stage40 REPORT.md 与 report.json。

### Q5：有没有把测试集训练进去？

**回答主线：** 区分来源、模板、状态和动作哈希；不同阶段数据有复用，不能只按行随机拆分。已经用于诊断的验收集要如实退役，不能继续当未见题。

**继续追问：有 split 检查就证明绝无泄漏了吗？**  
不能。哈希和来源审核有覆盖边界，基模预训练与语义近重复也不能仅凭这些检查排除。

**准备产物：** 第五篇来源审核与第六篇确认集协议；不展示受保护题目。

### Q6：你为什么用教师接续？怎么证明不是多喂数据？

**回答主线：** 学生会进入教师从头示范较少覆盖的状态。正式实验匹配来源和监督 Token，各三个种子，比较加入接续后的效果。

**继续追问：那是完全公平实验吗？**  
控制了重要因素，但 prompt 和总计算量不同。报告平均增益、种子波动与约束回退，不能声称等算力稳定全面提升。

**准备产物：** 252 配对任务、52 来源组、240 题对照的证据卡。

### Q7：为什么不用 GRPO 一次解决这些错误？

**回答主线：** 需要先确认错误来自策略而不是输入合同或工具 bug。当前恢复监督和奖励校准仍有缺口，扩大采样未必提供可靠相对优势。

**继续追问：项目做过 GRPO 吗？**  
旧 H-003 有历史训练及未过门的结果；当前统一 Loop 最新主线没有完成对应有效 GRPO 验收。不能把两个版本混在一起。

**准备产物：** 第六篇历史分层与奖励、信用分配说明。

### Q8：新 SFT 满分但不发布，是不是失败？

**回答主线：** 新集合有改善，是有价值的实验；旧故障回归说明候选不满足完整晋升条件。两者应同时报告，保留模型是依据门槛作出的决定。

**继续追问：6 次旧复测样本太小怎么办？**  
它适合定位已知复合故障，不估计全部线上回归率。扩大诊断和新确认都需要预先计划；不能因为样本小就隐藏已观察失败。

**准备产物：** 新实例与旧故障分表，以及失败轨迹摘要。

### Q9：你是不是改了格式约束，才让模型分数变高？

**回答主线：** 格式约束确实可能影响结果，所以同一比较应统一推理合同，原始模型格式和系统组装结果分开。不同阶段不应串成单次训练增益。

**继续追问：约束输出不合理吗？**  
它是合理的系统手段，但应公开归因；RL 中还涉及采样概率与训练概率匹配。不能把工程约束冒充权重学习。

**准备产物：** 第五篇输入模板与第六篇概率合同。

### Q10：千连接、P99 500ms 你怎么测的？

**回答主线：** 当前读到的是 PRD 目标，不能当已测结果；k6_sse.js 实际覆盖受理链路，没有测 SSE 事件交付。本次没有对应容量验收报告。

**继续追问：那下一步如何测？**  
分别做受理、SSE 长连和完整规划负载，冻结硬件、流量、缓存、模型和超时条件，保留所有失败及资源曲线。

**准备产物：** 第 8 节的脚本审阅和测量字典。

### Q11：几台机器做了什么？为什么训练一度很慢？

**回答主线：** 实际是独立任务并行，关键对照同机评测。早期六次完整训练与最新 64 步继续训练规模不同；长 prompt 前向、采样、工具和评测也是成本。

**继续追问：是不是你做了 DDP？**  
没有证据就明确说明没有。用户最初期望的联合训练与实际方案要区分；不能用“多机”模糊替代实现。

**准备产物：** 阶段耗时账、任务分工、环境与 Adapter 身份。

### Q12：你个人做了什么，AI 工具做了什么？

**回答主线：** 按真实职责说明需求分析、设计、代码修改、审核、实验和结果判断的分工。拿一项自己掌握的改动，从动机讲到反例和验证。

**继续追问：不用工具，你还能解释或修复吗？**  
现场解释状态合同、关键函数和一个故障路径。不会的部分明确说明，不临时编造。

**准备产物：** 第 16 节补全后的职责证据表，而不是整个仓库的总提交数。

## 21. 五道白板练习：从背答案到能推演

### 21.1 练习一：七分钟画完整系统

要求只画两层：

~~~text
外层：用户 → API / Job → Worker → LangGraph → SSE / 确认
内层：PolicyContext → 模型动作 → Harness → 工具 → Ledger → 下一步
~~~

然后分别标出：画像存在哪里、哪份是 Checkpoint、哪个节点求解、哪个节点验证、用户改日期后谁失效。

自查：有没有把 SSE 当任务队列、把画像当 Ledger、把 Solver 当自动跟随每个工具的阶段？能否指出模型还保留哪些决策权？

### 21.2 练习二：五分钟复算两个指标

题目 A：

~~~text
参考组 30 题，总 Token 856564
候选组 30 题，总 Token 175519
~~~

写出平均数、降幅、平均差。解释为什么不能据此得到缓存命中率、API 费用降幅或最新 SFT 收益。

题目 B：

~~~text
新实例：原模型 114/120，SFT 120/120
旧故障：原模型 6/6，SFT 4/6
~~~

分别报告结果，不把旧 6 次说成 6 个独立任务，不擅自混出一个“综合准确率”。若想构造总体指标，先定义权重和目标分布。

### 21.3 练习三：八分钟诊断一个失败

给定：

~~~text
goal_version=2
plan_version=4
last_validation.plan_version=3
模型请求 finish
~~~

回答：

1. 哪个合同不满足？
2. 应拒绝什么，保存什么原因？
3. 模型下一步是否一定只能 validate？
4. 如果计划也不满足当前目标，是否需要先改计划？
5. 这条状态怎样成为可信训练样本？

第三问不能机械回答“永远 validate”。需要判断已有计划和证据是否仍适用；版本只是入口，不替代完整有效性判断。

### 21.4 练习四：设计最小记忆实验

构造四种情况：

- 老画像有“带老人”，当前明确“自己去”。
- 当前预算明确为 0 或 False 类字段有显式值，不能按 truthy 当缺失。
- 冷恢复后出现新日期，与旧证据冲突。
- 两个用户具有相似兴趣，但禁止把彼此的私有历史当本人事实。

写出预期状态、真实读取位置和失败条件。无需先训练模型，先验证字段链和隔离；涉及实际运行时应在云端隔离环境执行。

### 21.5 练习五：设计一轮公平的修复验证

限定问题：补充恢复状态能否降低旧故障回归？

至少说明：

- 训练实例与开发、确认来源怎样分离。
- 正确接续如何从真实状态产生。
- 与什么基线比较，如何控制模型与工具。
- 成功率、旧能力、失败预算和成本如何报告。
- 怎样处理候选选择、失败验收和后续新确认。

如果答案只剩“增加数据、增大 batch、换 GRPO”，说明还没有把实验问题定义清楚。

### 22.1 每次练习用同一种检查法

先不看资料讲一遍，记录停顿或含混词；再只查对应证据入口；最后用一个新反例再讲一次。

“看过答案觉得懂”与“能独立解释错误为什么发生”不是同一能力。可以把以下内容作为未掌握标记：

- 只会说“框架自动处理”。
- 数字没有分母和模型身份。
- 所有风险都回答“加 prompt”或“多训练”。
- 不能区分静态风险与已发生故障。
- 需要删掉限制才能讲出好结果。

### 22.2 临近面试优先记什么

优先记住：

1. 两层架构和四个状态对象。
2. 一个用户修改导致证据失效的案例。
3. Token 对照的总量与归因边界。
4. 三种子 SFT 的均值、波动与匹配条件。
5. 最新新实例和旧故障的两张表。
6. 一条自己真正完成的贡献。
7. 当前最需要补的一个验证。

不必背完整 Adapter 哈希，但应知道在哪里查，以及为什么评测需要它。
