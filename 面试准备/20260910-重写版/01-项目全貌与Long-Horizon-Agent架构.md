## 1. 先把项目讲成一个完整问题

### 1.1 用户到底想完成什么

用户输入的往往不是一份完整表单，而是：

> “从济南去上海玩三天，带老人，预算有限，想去某个博物馆，行程不要太赶。”

系统需要把这句话变成一个可检查的旅行方案：

1. 确认日期、人数、预算口径、必去和禁去等必要条件。
2. 区分用户本次要求与以前保存的偏好。
3. 找到真实可用的景点、餐饮和交通信息。
4. 判断营业时间、通勤、预约、天气或活动是否产生冲突。
5. 生成具体的每日安排。
6. 检查方案是否满足硬约束。
7. 接受用户修改，再生成对应的新版本。
8. 保存任务状态与结果，支持过程查看和中断后的恢复。

因此，项目需要同时解决**语义理解、连续决策、数据可信、组合约束和长任务工程**。

### 1.2 为什么旅行场景适合展示 Agent 能力

旅行问题的可变部分多：不同目的地、同行人、实时事件、用户临时修改，会导致不同工具需求。它又不是完全不可验证的开放聊天：时间窗、预算、必去项、交通间隔等可以被程序检查。

这使项目具备两个面试价值：

- 能展示模型如何根据观察改变下一步行动。
- 能用明确约束和轨迹证明动作与结果是否合格。

代价是领域数据的真实性与覆盖会影响效果。工具返回错误地点时，模型可能选对了动作但仍无法得到有效方案；求解失败也可能来自候选不足，而不是数学算法不够强。必须能拆开归因。

### 1.3 推荐的一句话定位

> TravelAgent2 是一个面向多约束旅行规划的 Agent 系统：模型负责工具决策和错误恢复，Harness 管理执行权限、证据与预算，求解器和独立验证器负责方案计算与验收，外层会话和任务系统支持多轮交互与恢复。

这句话已经包含业务、智能决策、可靠执行和工程边界。介绍开头不必先列十几个框架名。

## 2. 项目有三条主线，分别回答三个问题

| 主线 | 核心问题 | 主要实现 |
|---|---|---|
| 产品和服务 | 用户怎样发起、查看、修改、恢复一个规划任务？ | 前端、Gateway、FastAPI、PlanningJob、Celery、SSE、PostgreSQL |
| Agent 执行 | 下一步做什么，怎样保证不会越权、失控或虚报完成？ | BoundedAgentLoop、Ledger、Policy、Harness、工具、Solver、Verifier |
| 后训练和评测 | 怎样让小模型在真实执行状态下做出更好的下一步决策？ | 教师示范/接续、成功轨迹筛选、SFT、DPO、回放、冻结评测 |

面试中最容易混淆的是把三条主线的结果互相替代：

- SSE 响应很快，只证明消息接入或推送，不证明整次规划很快。
- Agent 框架测试通过，只证明框架规则，不证明模型能选对工具。
- SFT 测试通过率高，不证明用户画像召回或数据库恢复正确。
- 生成了一个行程，不证明满足约束，更不证明完成了真实预订。

## 3. 从外到内看系统结构

### 3.1 服务结构

~~~text
用户浏览器
  │
  ├── POST：发送消息 / 修改 / 确认
  └── SSE：接收进度和结果，携带事件游标恢复
  │
Go / Echo Gateway
  └── JWT、限流、熔断、请求追踪、反向代理
  │
FastAPI
  └── 校验请求和归属 → 事务保存 Message + PlanningJob
  │
  ├── PostgreSQL：任务、消息、事件、最终结果
  └── Celery / Redis：派发 job_id
         │
      PlanningWorker
         └── 认领任务、心跳、执行图、记录事件、处理取消
                │
             LangGraph
                └── 需求收集、Agent Loop、输出、用户确认、检查点
~~~

这是代码和部署配置所表达的组件关系。本篇不据此声称 Kubernetes 集群当前已经运行，也不把部署副本数量当成通过压测的容量。

### 3.2 Agent 内部结构

~~~text
当前用户目标 + Ledger
        │
        ▼
  PolicyContext 构造
  版本 / 时效 / 相关证据 / 失败 / 剩余预算
        │
        ▼
  Policy 模型提出一个动作
        │
        ▼
  Harness / 执行边界
  动作授权、schema、可信参数、前置证据、预算
        │
        ├── 不允许：记录原因 → 下一轮模型继续决定
        │
        └── 允许：调用工具
                   │
             Observation / ActionOutcome
                   │
             更新 Facts / Artifacts
             记录 Failures / Decisions / Budget
                   │
             提交当前状态和轨迹
                   │
        ┌──────────┴────────────┐
        │                       │
     继续循环              澄清 / 提交草稿 / 停止
~~~

solve_itinerary 和 validate_itinerary 是模型可以选择的动作。不能把上图误读为“每次普通工具调用后都自动重新求解和验证整个行程”。

### 3.3 技术名词如何对应业务职责

| 名词 | 在项目里的具体含义 |
|---|---|
| LangGraph | 保存和调度会话节点，处理中断与恢复；不是直接替模型决定查哪个工具 |
| Policy | 从当前模型可见状态选择下一动作 |
| Harness | 执行约束、状态与证据处理的整体边界，不只是一个 prompt |
| Ledger | 目标、证据、历史与预算的结构化状态 |
| Tool Executor | 将动作转换成真实工具调用，装配可信参数、规范化结果 |
| Solver | 对已经取得的数据进行约束排程 |
| Verifier | 检查证据或方案是否满足要求；不同验证器负责不同层 |
| Episode / Trajectory | 一次执行的状态、动作、观察及计量记录 |
| Checkpoint | 图执行保存点，用于恢复；不等于模型 KV cache |
| SSE | 将进度和结果推送到浏览器的传输机制 |

## 4. 一条消息真正经过哪些代码

### 4.1 前端与 API：先保存任务，再开始执行

主要聊天入口是 POST /api/v1/chat/message。前端 useChat 与 useSSE 协同，保存 job_id、当前会话与最近事件游标。

后端关键行为：

- 校验用户、会话及消息。
- 读取幂等键和请求指纹。
- 相同幂等键重复提交时复用已有任务；内容不一致时不能无条件当成相同请求。
- 创建消息和 PlanningJob。
- 事务提交之后才派发任务，避免 Worker 先收到消息却查不到数据库行。
- 返回 202 及任务信息，含义是“任务已接收”，不是“行程已完成”。

**面试追问：提交成功后 Broker 发布失败怎么办？**

项目利用 PlanningJob 的持久状态提供轻量 Outbox 语义，定时重新派发符合条件的 pending/retrying 任务。Worker 通过数据库原子认领与租约减少重复执行。这里是“可恢复派发 + 幂等认领”，不应直接承诺所有外部工具 exactly-once。

代码入口：api/v1/chat.py、api/chat_runtime.py、repositories/planning_job.py、worker/planning_tasks.py。

### 4.2 Worker：执行任务与发送进度分开

PlanningWorker 从任务记录恢复输入、近期消息、画像及控制动作，调用 stream_graph_events。它维护心跳、取消检查和会话执行锁，并记录公开任务事件。

事件先保存到 PostgreSQL，Redis Pub/Sub 用于通知在线连接拉取。客户端断线后可依据 job_id + last_event_id 读取持久化事件。

这解决了一个常见问题：如果进度只存在 API 进程内队列或 Redis 临时通知中，切换 API 副本后可能丢失历史进度。持久化事件可以重放，但仍要处理游标、重复事件和客户端渲染幂等。

代码入口：worker/planning_worker.py、api/chat_runtime.py、api/v1/chat.py。

### 4.3 gathering：把自然语言变成当前任务事实

graph/gathering.py 复用 process_user_turn：

~~~text
当前输入 + 最近对话 + 已知画像
→ DemandParserAgent 解析 TravelSlots
→ 会话/长期画像召回
→ 冲突合并
→ 歧义与缺失字段判断
→ 可行性检查
→ 更新会话状态
~~~

已知“上海、三天”后，用户下一句只说“带老人”，系统应更新同行条件并保留此前信息，而不是把上一轮要求清空。

需求收集也有两种来源：外层 gathering 处理初始槽位，内层 Agent 在工具执行中发现必要信息缺失时还能主动 ask_user。不能把“进入 Loop 前收集过一次”理解为之后不再允许澄清。

### 4.4 profile_recall：把用户需求投影成 Agent 目标

该节点读取或更新适用的画像信息，再调用 initialize_agent_ledger。GoalLedger 保存原始请求、硬约束、软偏好、用户授权和缺失信息。

结构化约束是控制器与工具之间的契约。例如，用户说的禁去地点应进入明确字段，不能只藏在一大段历史聊天中。否则模型生成工具参数时容易遗漏，求解器也无从检查。

### 4.5 agent_loop：执行一个可保存的决策批次

真实调用链：

~~~text
graph/nodes.py: agent_loop_node
  → agentic/integration.py: run_agent_branch(single_step=True)
  → 恢复 AgentLedgerState 与 EpisodeRecorder
  → 选择策略后端，包装有限格式修复
  → BoundedAgentLoop.run(max_batches=1)
  → 返回更新后的 ledger、episode、status
  → LangGraph 保存检查点
  → router 判断继续 agent_loop，还是进入 output
~~~

这里的 single_step 指一次执行批次返回图层，不保证只消耗一次模型请求或一次底层 HTTP 调用。格式修复可能多请求模型，批量 POI 详情可能调用多个底层接口；因此要分别记录模型调用、Agent 步数和工具调用。

### 4.6 output 与 confirm_gate：可展示和已确认分开

模型提出 finish 后，必须具备当前有效方案和通过的验证。通过后输出草稿，进入 confirm_gate 的 interrupt。

用户可以：

- 确认：核对当前草稿与验证依据，记录用户确认事实。
- 修改：解析修改操作，生成新 Goal/Plan 版本，回到同一 Loop。
- 继续补充：在对应阻塞状态中结合待回答问题解释用户答案。

booking 节点目前是 MVP 预订信息聚合，不是可据此证明的真实支付、出票和履约闭环。

## 5. 外层 LangGraph 与内层 Agent Loop 为什么要分开

### 5.1 两层处理的是不同的不确定性

外层处理产品流程：收集需求、等待用户、保存检查点、展示结果。内层处理策略选择：先查什么、资料不足怎么办、是否重试、何时求解或结束。

如果把所有细节都写成图边，新增一种证据需求就容易变成新增节点和分支。反过来，若把用户确认、持久化和预算全部交给模型，又难以可靠执行权限与一致性规则。

因此本项目让确定的业务边界留在外层，让需要观察后决定的动作留在内层。

### 5.2 当前的 task_graph 不是旧版阶段 DAG

ReactTaskGraphPlanner 当前创建：

~~~text
TaskGraph
  goal_version = 当前目标版本
  plan_version = 当前计划版本
  tasks = [
    TaskNode(
      task_id = "travel_agent",
      depends_on = (),
      allowed_actions = 当前动作集合,
      max_attempts = 24
    )
  ]
~~~

assert_session_contract 会检查只有这一个任务、名称一致且没有依赖。旧 DAG checkpoint 不能直接当成当前会话继续运行。

对象还叫 TaskGraph，是为了保留状态协议和生命周期管理等结构；名字保留并不说明当前仍运行多阶段任务图。TaskScheduler 在这条路径里主要维护会话任务状态，不自动安排搜索、求解、校验的顺序。

### 5.3 这也不是多个大模型专家协作

DemandParserAgent、ProfileRecallAgent 等命名表示职责模块，不等于每个模块都是自主规划的 LLM Agent。当前核心策略是一条统一循环；教师模型参与离线数据生成，也不代表在线总有一位“教师 Agent”接管学生任务。

可以讨论未来多 Agent 的候选评估或分工，但简历中的已实现架构应按现在的调用链描述。

## 6. Long-Horizon 在本项目中具体意味着什么

### 6.1 长程来自跨步骤依赖

“旅行三天”是业务时间长度；“模型推理九步”是执行长度；“用户今天回来继续修改”是会话生命周期。三者不能混为一个指标。

这里的 Long-Horizon 核心是：**早期动作会改变后续可用证据、剩余预算和可行方案，模型需要跨步骤维持目标并恢复错误。**

例如：

1. 首次搜索没有包含餐馆。
2. 后续详情与矩阵只覆盖景点。
3. 求解时无法满足具名用餐要求。
4. 已消耗的工具预算限制了补救机会。
5. 即使最后补到了餐馆，也必须重建相应证据并重新验证。

错误不是孤立的一次回答错误，而是沿状态和资源传播。

### 6.2 支撑长程执行的六个机制

| 机制 | 具体作用 | 不具备时的后果 |
|---|---|---|
| 结构化目标和约束 | 持续携带用户任务定义 | 后续步骤忘记禁去、预算或同行条件 |
| Facts / Artifacts | 保存工具证据与中间产物 | 重复查询，或凭记忆编造资料 |
| 失败与决策历史 | 让下一步看到已尝试内容和错误原因 | 在相同空结果上反复重试 |
| 预算账本 | 限制步数、调用、Token、时延 | 无限工具循环或成本失控 |
| 版本与有效期 | 区分新旧目标及过期证据 | 用旧矩阵、旧验证提交新方案 |
| 检查点与用户中断 | 保存执行状态，跨请求继续 | 断线、进程退出或用户补充后从头开始 |

这六项是工程能力。它们为后训练提供明确的状态语义，但不自动证明模型已经掌握长程决策。

### 6.3 当前规模怎么讲

BudgetLedger 源码默认包含 24 步、24 次工具、3 次求解、32,000 Token 账本上限和 120 秒执行时间预算。实际运行配置、后端计量和实验协议可能覆盖这些默认值。

准确的表述是“有预算约束、可保存和恢复的多步工具决策循环”。目前没有证据支持“数百步稳定自主执行”“无限时长自主任务”或“解决了长程信用分配”。

特别要区分：某些历史成功任务平均约 9 次模型调用，是历史模型与环境的测量；不能直接当成当前 Qwen3-4B 的固定调用数。

## 7. Ledger：让事实、历史与控制权有明确位置

### 7.1 主要对象

| 对象 | 保存内容 | 举例 |
|---|---|---|
| GoalLedger | 用户原始需求、硬约束、软偏好、授权、缺失信息 | 必去博物馆、最多步行 30 分钟 |
| FactRecord | 单项事实及来源、版本、时间 | 用户确认的出发地 |
| ArtifactRecord | 成组结果或派生产物 | 候选 POI 集、详情集、矩阵、行程、验证报告 |
| FailureRecord | 错误码、失败动作、参数、是否可重试 | RESEARCH_EVIDENCE_INSUFFICIENT |
| DecisionRecord | 动作、结果、观察签名、有无进展 | 搜索后结果与上次完全相同 |
| BudgetLedger | 资源上限与已使用量 | 还剩 4 次工具调用 |
| PlanVersion | 修改触发原因、变化约束和失效记录 | 用户删去某景点后产生新版 |
| AgentEpisode | 更完整的运行审计记录 | 输入、模型动作、执行参数、观察与状态快照 |

### 7.2 为什么不只保存聊天历史

聊天历史适合解释语义，但不适合独自承担以下判断：

- 这条天气对应哪一天，是否过期？
- 当前验证是在最新一次求解前还是后完成？
- 预算剩余是 3 次还是 5 次？
- 候选 ID 是工具给的还是模型编的？
- 用户是否已明确确认这一版方案？

结构化记录让这些问题能由代码检查。模型仍可以通过历史理解上下文，但最终权威应来自有字段、有来源、有版本的状态。

### 7.3 为什么分别记模型参数与执行参数

例子：模型只决定调用 get_route_matrix，矩阵对应的候选实体由执行器从可信状态提取。

如果只保存最终调用，外部观察者可能误认为模型准确生成了所有候选 ID；如果只保存模型输出，又无法回放真实执行。

所以轨迹区分 model_arguments、executed_arguments、argument_sources。它既是可靠性设计，也是训练归因设计：哪些能力来自模型，哪些来自工程装配，需要能被证明。

## 8. Policy 与 Harness 的边界

### 8.1 Policy 真正拥有的决策

模型可以选择：

- 下一项工具及其合法语义查询。
- 在结果为空、不相关或失败后，改查询、重试或继续取证。
- 必要时询问用户。
- 何时尝试求解、何时验证、是否提交。
- 在具备依据时停止或提出受授权约束的折中方案。

模型不能直接将任务状态改成 succeeded，不能自报 hard_pass，也不能通过工具参数偷偷放宽用户硬约束。

### 8.2 Harness 不是另一个隐藏 Planner

Harness 负责判断“提案是否可执行”，而不是决定“下一步最佳动作是什么”。

例如模型在没有候选时调用 get_poi_detail，系统返回 CANDIDATES_REQUIRED。模型随后可能调用 search_pois，也可能发现用户需求不完整先提问；Harness 不替它生成一串正确工具调用。

preflight_action 中可以有业务规则，例如求解必须具备必要证据。这是执行前置条件，不等于把完整策略序列写死。能否解决任务，仍依赖模型自行补足条件并选择后续动作。

### 8.3 当前 13 个动作

| 类别 | 动作 |
|---|---|
| 稳定知识与 POI | retrieve_city_knowledge、search_pois、get_poi_detail |
| 时效信息 | get_weather、search_current_info、search_transport |
| 路线与方案 | get_route_matrix、solve_itinerary、validate_itinerary |
| 用户交互和结束 | ask_user、propose_tradeoff、abort、finish |

这里说的是策略动作集合。ToolExecutor 可能还有更底层工具处理器，但它们不一定全部作为模型动作开放。比如存在 update_user_profile 处理器，不代表它是当前 13 个策略动作之一。

### 8.4 一个工具调用的分层检查

1. 能否解析成声明过的动作和参数类型？
2. 当前状态是否允许该动作？
3. 参数是否与用户事实冲突？
4. 工具和求解预算是否足够？
5. 必要证据是否存在、对应实体正确、版本与时效有效？
6. 执行后的结果如何进入状态和预算？
7. 动作是否造成有效进展，是否满足对应状态转换？

这几层检查解决不同问题。JSON 正确不代表实体正确，实体正确不代表证据充分，工具执行成功不代表行程合格。

### 8.5 概念伪代码

~~~python
# 用于解释职责，不是可替代项目实现的源码。
while session_can_continue:
    context = project_current_ledger(ledger)
    proposal = model.choose_action(context)

    charge_decision_and_model_usage(proposal)
    rejection = check_authority_arguments_budget_and_evidence(proposal, ledger)

    if rejection:
        record_failure_and_feedback(rejection)
    else:
        outcome = executor.execute(proposal, trusted_state=ledger)
        commit_observations_facts_artifacts_and_usage(outcome)
        record_decision_and_progress(outcome)

    save_trace_and_return_checkpointable_state()

    if needs_user or verified_draft_submitted or terminal_stop:
        break
~~~

真实实现还包含超时、取消、批次未提交审计、格式修复、状态转换验证等。伪代码中的提交不意味着外部 HTTP 副作用与数据库写入处于一个原子事务。

## 9. 一条成功路径与三条异常路径

### 9.1 成功路径：信息完整的多日规划

下面是示意路径，顺序由任务和模型决定：

| 步骤 | 模型/系统行为 | 状态变化 |
|---|---|---|
| 1 | 理解自然语言、合并画像 | 形成当前 Goal 与约束 |
| 2 | 查候选景点与餐馆 | 保存 poi_candidate_set |
| 3 | 获取候选详情 | 保存开放时间、价格、时长等证据 |
| 4 | 按需求查天气/活动/交通 | 保存来源与时效信息 |
| 5 | 获取路线矩阵 | 建立候选之间的时间/距离关系 |
| 6 | 模型提出 solve_itinerary | 先检查研究证据；通过才求解 |
| 7 | 模型提出 validate_itinerary | 独立检查日程与约束 |
| 8 | 模型提出 finish | 检查最新方案、验证与证据状态 |
| 9 | 系统展示草稿并暂停 | 等待用户确认 |
| 10 | 用户确认 | 记录确认事实，进入后续产品流程 |

城市知识检索不要求每次固定先调用；天气也不是所有任务都必须查询。当前研究门槛按实际需求检查。

### 9.2 异常一：搜索返回空结果

需要先区分：

- 结果为空：这个查询没有找到合适内容。
- 服务不可用：当前无法取得结果。
- 已有证据证明不存在/闭馆：更强的事实判断。

空搜索结果不足以证明“该景点不存在”。模型可以改关键词、换来源或进一步澄清；不能直接把网络错误解释成用户任务不可行。

如果换一个查询字符串却仍返回完全相同的证据，也不必然代表取得进展。DecisionRecord 的观察签名与进展标记用于识别这类循环。

### 9.3 异常二：证据不足就求解

假设模型已经取得景点详情，却遗漏必要天气或餐馆信息。它提出 solve_itinerary 后，ResearchSufficiencyVerifier 返回缺口，Harness 拒绝本次求解。

后续应由模型补齐缺失证据，再重新选择求解。这里尤其容易发生两种错误：

- 不看缺口，原样重复求解，浪费决策步和 Token。
- 调用一个无关工具后，以为所有前置条件已经满足。

当前 Harness 会重新检查历史失败对应动作的真实前置条件。只有条件确实满足，旧前置失败才不应继续阻止合法重试；这一内部判断不替模型选动作，也不改写历史失败记录。

### 9.4 异常三：求解后漏验证直接 finish

finish 的检查包括：

- 当前有效 solver_result 存在。
- 当前有效 validation_report 存在且 hard_pass=True。
- 验证时间不能早于当前求解结果。
- 当前所需研究证据仍充分有效。

因此“先验证空行程→求解新行程→直接 finish”会被拒绝。验证是针对某个方案和证据状态的，不能当成一次执行里永久有效的许可证。

### 9.5 已经发生过的两个策略回归

2026-09-09 的后训练复测中：

**成功轨迹 SFT 候选的旧故障：** 初期只搜景点，补餐馆太晚；详情失败后的重复调用消耗预算，后续无法完成具名餐饮证据覆盖，最终预算耗尽。

**DPO 候选的旧故障：** 缺天气时提前求解被拒，后续验证空行程，重新求解后又没有重新验证，连续 finish 被拒绝。

这两条失败能解释为什么项目需要状态、失败反馈、预算和独立验证。它们也说明框架拦住错误不等于策略已经学会恢复；最新模型仍有需要补训练的状态覆盖。

## 10. 求解与验证：为什么把这部分交给程序

### 10.1 模型擅长的部分与求解器擅长的部分

模型适合处理语义和不固定的信息获取：理解“不要太赶”、选择查询词、识别当前缺什么。求解器适合在结构化数据和约束下安排访问顺序与时间。

可以把排程理解为：

- 输入：候选点、游玩时长、营业时间、费用、交通时间、必去/禁去、天数等。
- 决策变量：某天是否访问某点、访问顺序、开始/结束时间等。
- 硬约束：必须满足的预算、时间和用户条件。
- 目标/软偏好：在可行范围内考虑体验、紧凑程度等。
- 输出：具体日程，或者没有找到可行方案的状态。

本篇只建立职责概念。具体 CP-SAT 变量、约束表达与回退策略在第三篇逐段展开，不用“VRP-TW”一个术语掩盖真实代码实现。

### 10.2 为什么 Solver 后还要 Verifier

即使求解算法没错，也可能发生：

- 解析器没把用户限制传到约束对象。
- 候选资料错误或时间字段转换出错。
- 预处理丢掉禁去项、交通窗口等语义。
- 求解的回退策略没有覆盖全部要求。
- 后续文案或用户修改导致方案与验证对象不一致。

因此 Verifier 用于再次检查。它不是万能事实核验器：若 Solver 与 Verifier 同时使用错误供应商数据，仍可能一起通过。真实工具数据质量和独立来源检查仍然重要。

### 10.3 求解失败不等于任务无解

求解超时、模型规模过大、候选不足，都可能导致当前尝试没有可行方案。不能据此宣称用户需求在现实世界中不可能完成。

更有说服力的不可行证据包括：

- 已确认的必去场馆在所有旅行日期闭馆。
- 必付成本下界已经超过不可放宽预算。

当前 Harness 对适用证据形成 constraint_evidence，模型可以据此选择停止或询问。它不会为了“走完流程”强制模型先运行一次已知无意义的求解，也不会自动替用户放宽条件。

### 10.4 回退的三种含义

| 回退 | 当前应如何理解 |
|---|---|
| 工具回退 | 外部 API 不可用，使用另一来源或内置数据，并保留回退标记 |
| 求解回退 | CP-SAT 没有给出可用结果，采用明确记录的启发式结果，仍需验证 |
| Agent 安全停止 | 记录失败/预算耗尽，返回错误或澄清；不是暗中切换旧 Planner 生成答案 |

integration.py 的 _fallback 将 agent_status 设为 failed、next_action 设为 agent_error。仅凭函数名 fallback 不能推断系统存在一个会自动救场的第二规划器。

## 11. 记忆与上下文在整体架构中的位置

### 11.1 三种记忆、两类模型输入

整体上先区分：

- 会话记忆：最近消息、累积槽位和阶段，支持一轮一轮补充需求。
- 长期画像：跨会话复用本人偏好和记录。
- Agent 工作状态：当前执行的事实、产物、失败和预算。

通用需求解析输入是近期对话与结构化画像；Agent 策略输入是从 Ledger 投影出的当前状态。模型参数里的知识和用户数据库记忆不是同一件事。

### 11.2 为什么不能每轮拼上所有历史

输入越来越长会带来成本、延迟和证据混淆。项目采用结构化状态，并在策略输入中：

- 按目标/计划版本和有效期过滤证据。
- 去除重复产物，优先保留求解和验证等重要结果。
- 展示有限事实、产物摘要、最近决策和失败。
- 显式给出剩余预算和当前允许动作。
- 对内部 ID 与控制器字段做受控投影。

当前实现展示最多 8 个事实、8 个产物摘要、最近 6 条决策；失败从全局最后 3 条中筛出当前任务相关项。完整历史不因此从审计记录中消失。

### 11.3 通用压缩与策略投影分开

普通聊天压缩保留 system 消息，对旧消息做抽取式折叠，并截取过长消息。它主要按字符控制长度。

agent_policy 路径跳过通用中间截取，因为那可能破坏 JSON 结构和关键证据，导致训练与服务输入不一致。策略用专门的投影和长度检查。

这里的取舍是：压缩降低成本，但窗口和摘要可能漏掉重要细节。需专门测试长行程、旧失败和约束保留，不能声称“摘要不会丢信息”。

### 11.4 当前检索不要讲错

当前主 POI 工具优先使用结构化 PostgreSQL 数据，必要时外部查询。仓库有向量检索封装，但 embedding 默认关闭；search_bm25 当前实现是词法匹配计数。

旧面试材料中的“三路并行＋BM25＋向量＋RRF”不应继续作为当前主链路介绍。第二篇会详细讲哪些召回能力接入、哪些只是可用模块，以及画像回写和冲突合并的实际边界。

## 12. 版本化修改与断点恢复

### 12.1 用户修改需要改变什么

用户说“第二天不去那个博物馆，预算再低一点”，不是简单让模型重新润色：

1. 解析为受控 RevisionOperation。
2. 检查字段、类型、数值范围及授权。
3. 更新硬约束或软偏好。
4. 增加 goal_version、plan_version。
5. 新建当前会话任务的生命周期状态。
6. 旧事实和产物保留供审计，但旧版本不能冒充当前证据。
7. 由模型重新取证、求解、验证和提交。

当前 revise_agent_ledger 的 preserved_task_ids=[]，实现偏向保守重建。不能沿用旧文档的“依赖图级精准增量重规划”作为已验证现状。

### 12.2 为什么分别有 goal_version 与 plan_version

概念上，目标变化与执行计划变化并非同一事：用户改预算改变目标；同一目标下重新组织方案也可能需要区分计划。

当前用户修订函数会同时增加两个版本。不要把概念上的灵活性直接当成已经覆盖所有单独更新场景的实现。应以具体函数和运行记录解释实际变化。

### 12.3 澄清回答怎样接回原任务

resume_agent_conversation 检查会话处于 blocked，并查找当前版本的 user_question 或 propose_tradeoff。解析回答时附带原问题，避免把“济南”随意填入第一个空字段。

它调用修订流程后复制原预算账本，保留同一执行的资源约束。普通修订会创建新预算，因此要区分“回答当前问题”和“发起一版新修改”。

### 12.4 三种恢复不是一回事

| 恢复 | 依据 | 目的 |
|---|---|---|
| 前端进度恢复 | PlanningJobEvent + last_event_id | 补看遗漏事件 |
| 会话内容恢复 | Redis 热/温状态、PG 快照/任务状态 | 找回画像、消息与当前状态 |
| 图执行恢复 | LangGraph Checkpoint | 从持久化执行位置继续 |

SSE 连上不代表模型已恢复；缓存中有聊天历史不代表知道执行到了哪个图节点；保存了图检查点也不代表外部 HTTP 工具不会重试。

### 12.5 Exactly-once 的边界

如果外部工具已调用成功，但进程在提交检查点前退出，恢复后可能再次调用。检查点只能缩小重跑范围，不能凭空让外部系统与数据库形成一个事务。

读取型工具可以结合请求缓存、观察记录和幂等处理减少代价。真实预订/支付则需要供应商支持的幂等键、操作状态查询及补偿机制。目前 booking MVP 不能作为这些能力已经完成的证据。

## 13. 数据、训练和线上为什么要共享同一循环

### 13.1 后训练优化的对象

当前学生是工具策略模型。输入是状态、可用动作和工具 schema；目标是合格的下一步动作及模型拥有的参数。

训练不直接更新 CP-SAT，不会自动修复缺失的数据库写入，也不会因为 loss 下降就让外部天气 API 更准确。

### 13.2 共享 Runtime 的作用

线上通过 integration.py 驱动 BoundedAgentLoop；离线评测用相同 Loop 和接口，但工具可能由冻结快照提供；交互式训练环境也复用这套执行语义。

这样有助于避免：训练时一条动作合法，上线后 schema 不同；训练时忽略预算，上线后频繁超限；训练时让控制器替模型跑完前几步，评测却声称模型会完整规划。

共享代码不是充分条件。模型模板、工具 schema、提示投影、错误契约、依赖版本和实际 provider 仍需核对一致。

### 13.3 为什么接续数据有价值

从头教师示范常处在比较整洁的状态。学生执行后可能走到不完整、冗余或失败状态，下一步正确动作与“理想轨迹的下一步”不同。

从学生实际状态让教师接续，可以更直接覆盖这些输入分布。接续仍然可以训练为 SFT，因为监督目标还是给定状态下的正确动作；它不是仅因包含失败前缀就变成 RL。

所有接续也不一定都是纠错：之前审计中有些断点没有记录明确错误信号。讲数据时要区分接续来源与真实纠错来源。

### 13.4 为什么成功轨迹筛选还会漏能力

模型能成功的轨迹更容易被筛选进训练。如果某类严重失败状态下模型从未恢复成功，成功筛选池里就缺少对应正确动作。

最新分析正好发现研究证据不足、验证未通过等恢复上下文覆盖不足。这说明需要定向采集新训练实例的成功接续，而不是无限重复已有成功样本。

第五、六篇会分别展开数据审核、SFT 目标、DPO 偏好构造与为何暂不直接扩大 RL。

## 14. 架构演进：面试时怎么解释为什么改

### 14.1 可以确认的演进方向

| 阶段 | 主要特征 | 面试如何定位 |
|---|---|---|
| 早期业务工作流 | 将需求理解、检索、排程、展示拆成固定节点；部分检索/天气并行 | 历史设计，适合解释起点 |
| 中间可验证策略架构 | 加入任务 DAG、模型逐步策略、Solver/Verifier；部分阶段由控制器推进 | 历史 Token 架构对照所在阶段 |
| 研究段 ReAct | 研究阶段动态取证，保留阶段边界和部分唯一动作控制 | 过渡设计，旧文档常描述这一版 |
| 当前统一 Harness | 单一 travel_agent 会话任务；模型选择取证、求解、验证和提交 | 本篇主讲的当前架构 |

阶段不是线性的“每版所有指标都更好”。增加模型自由度可能暴露原来被控制器代办的决策错误，需要重新测量，而不能直接继承旧版成绩。

### 14.2 这次拆掉固定规划阶段的理由

从代码和文档能够支持的理由是：

- 不同用户需求需要不同信息，固定顺序容易做多余查询。
- 控制器替模型选择动作，会掩盖真实策略能力。
- 训练环境如果与线上流程不同，数据监督容易失真。
- 多套执行路径会增加调试和维护成本。
- 统一循环便于让模型在同一状态中处理失败、澄清和用户修改。

这些是工程设计依据；如果面试官问“是谁提出并主导了这次改造”，你需要补充真实个人职责，不能由项目代码自动推出。

### 14.3 代价是什么

让模型拥有更多决策权，需要承担更难的策略训练和验证：

- 工具顺序可能不合理。
- 需要学习何时验证和提交。
- 失败状态覆盖要求更高。
- 模型调用次数不一定更少。
- 通用 Loop 与领域约束之间需要清楚的接口边界。

当前项目的做法是保留确定性的权限、状态与结果验证，将语义策略交给模型，并通过轨迹和后训练提升策略质量。

## 15. 结果证据：数字该怎样讲才完整

### 15.1 79.51% Token 降幅来自哪里

历史实验 stage40-policy-driven-runtime-vs-pure-react-v1：

- 模型：deepseek-v4-flash。
- 30 对任务，case_id、input_hash 和模型匹配。
- 范围：信息完整的可规划任务，覆盖 2—4 天。
- 纯 ReAct 参考使用冻结工具夹具；新架构使用当时仓库工具栈和 PostgreSQL。
- 新架构采用当时的 policy_driven 模式，不是本次最新统一 Harness 的重新测试。

| 指标 | 纯 ReAct 参考 | 历史可验证运行时 |
|---|---:|---:|
| 总 Token | 856,564 | 175,519 |
| 平均 Token/任务 | 28,552.13 | 5,850.63 |
| Verifier 硬通过 | 1/30 | 29/30 |
| 平均模型调用 | 5.50 | 8.70 |
| 平均端到端时间 | 58.66 秒 | 17.03 秒 |

计算为：

~~~text
降幅 = 1 - 175519 / 856564
     = 79.508945...%
~~~

2026-09-09 已根据两组原始 runs.jsonl 在云端复算，结果与报告一致。它证明记录的总量及配对关系吻合；不等于新增运行了一轮公平性更强的对照。

**必须知道的限制：**

- 两组工具观察不是逐字节一致，存在工具环境混杂。
- 参考组按 provider 的 prompt + completion 记录；运行时按 Ledger used_tokens 计量，prompt/completion 拆分不可用。
- 全样本包含失败任务，并非等质量共同成功样本的效率对照。
- 模型调用变多而 Token 减少并不矛盾：总成本还取决于每次输入/输出长度与各轮预算。
- 29 个通过中当时 solver 状态包括 13 个 optimal 和 16 个 fallback，不能说“29 个都由 CP-SAT 最优求解”。
- 原简历“7 分钟降至 30 秒”不是这组报告的均值，不应套用。

准确讲法：

> 在历史同模型 30 对任务的架构对照中，记录的平均 Token 降低 79.5%，硬约束通过数由 1/30 提升到 29/30。由于工具环境和计量入口有差异，这组结果用于说明历史架构组合的效果，不当成最新模型训练的独立收益。

### 15.2 三随机种子 SFT 对照证明什么

早期正式实验使用 252 个配对任务、3,960 个唯一教师动作，两组分别为纯示范与示范加学生状态接续。两组匹配来源和监督 Token，各训练 3 个种子。

在 240 个锁定合成任务上：

| 方案 | 严格质量通过率 |
|---|---:|
| 更早的初始学生适配器 | 21.7% |
| 纯示范 SFT，三种子平均 | 57.1% |
| 示范＋接续 SFT，三种子平均 | 73.9% |

混合组相对纯示范增加 16.8 个百分点。prompt Token 和总算力并未匹配，且存在种子波动及约束类退步，因此不能写成“等算力下稳定全面提升”。

### 15.3 最新 SFT / DPO 结果说明什么

新训练阶段从 64 个任务、4 个采样种子得到 256 条轨迹；建立 128 个同状态可验证偏好对，再做成功轨迹 SFT 与 DPO＋SFT 保持项对照。

后续新实例验收：

| 模型 | 新的 120 题验收 | 旧故障 6 次复测 |
|---|---:|---:|
| 保留模型 | 114/120 | 6/6 |
| 成功轨迹 SFT | 120/120 | 4/6 |
| DPO＋保持项 | 118/120 | 4/6 |

结论是候选对新实例有改善，但旧复合故障仍回归，因此保留原模型。120 题包含相关来源组和共享模板，不能写成真实用户总体准确率 100%。

当轮预先指定的主要候选是 DPO。看到结果后优先考虑 SFT 属于后验选择，若继续修复或选模，需要新的确认性测试。

### 15.4 三组数字分别归属什么

| 数字 | 所证明的对象 |
|---|---|
| 79.51% Token 降幅 | 历史架构与工具环境组合的记录对照 |
| 57.1% → 73.9% | 早期纯示范与加入接续 SFT 的多种子实验 |
| 114/120、120/120、118/120 | 最新冻结模型在新实例集合上的对照 |
| 原模型 6/6，新模型 4/6 | 旧故障恢复稳定性诊断 |

不可拼成“通过同一次优化，将 Token 降 79.5%，准确率从 21.7% 提到 100%”。它们不共享模型身份、集合和实验条件。

## 16. 关键设计取舍：要讲得出替代方案

以下是由项目实现支持的技术解释，个人是否参与当时决策需要按真实经历说明。

### 16.1 为什么不让 LLM 直接生成最终行程

直接生成实现简单、响应形式灵活。但多约束一致性、实体和时间计算难以稳定验证。项目采用模型做语义与工具决策，Solver/Verifier 做结构化计算与检查。

代价是更复杂的数据适配和工具依赖；当前效果也受候选质量和约束建模范围限制。

### 16.2 为什么不是全部写死成工作流

固定流程便于预测和测试，适合需求稳定的任务。但可变的信息需求和失败恢复会造成分支膨胀。当前把策略选择放进 Loop，同时用 Harness 保留不能越过的边界。

代价是需要更强策略模型和覆盖失败状态的数据。固定工作流不是普遍错误方案，应根据任务变化程度选型。

### 16.3 为什么使用结构化 Ledger

它使预算、版本、授权与证据可被程序判定，也便于回放。代价是 schema 维护、兼容迁移和投影逻辑更复杂。当前显式拒绝旧 DAG checkpoint，是避免错误兼容的一种取舍。

### 16.4 为什么每步返回检查点

降低进程退出后的重跑范围，并把用户确认和后续修改接回持久状态。代价是状态序列化、数据库写入和恢复协调成本。

如果每一步包含大产物，应避免把全部原始正文重复塞进公开事件；完整产物、执行检查点和客户端展示摘要要分工。

### 16.5 为什么用异步任务加 SSE

规划比普通 CRUD 请求长，且需要展示中间进度。持久任务让执行独立于一次 HTTP 请求，SSE 适合服务端持续发送事件。

代价是需要处理 Broker 派发失败、任务租约、幂等、事件重放、取消和前端状态同步。仅“用了 Celery”不足以解决这些问题。

### 16.6 为什么保留失败而不自动调用另一个模型救场

若评测失败被隐藏接管，难以知道学生真实能力，也无法判断后训练是否有效。当前统一 Loop 的失败需要显式记录。

实际产品可以设计升级模型或人工介入，但必须明确触发条件、成本和统计口径，不能将接管成功混入学生原生成功率。

### 17.2 当前主要风险在哪里

- 模型对严重失败状态的恢复覆盖不足。
- 部分工具批量失败后重复消耗资源。
- 画像撤销和字段映射可能不完整。
- 多个 API/会话恢复入口的语义不完全统一。
- 长期快照压缩是有损的，不能保证完整恢复旧执行状态。
- 真正的数据隔离、真实工具一致性和长时间稳定运行仍需专项验收。

这些问题可以成为面试中的工程讨论：先明确错误发生在哪一层，再决定改代码、补数据、改评测还是换训练方法。

### 17.3 “大厂级”怎么回答

不要只说“技术栈齐全”或“有很多代码”。可以按下面的证据组织：

1. 业务目标和完成标准是否明确。
2. 架构职责与权限是否可解释。
3. 正常和异常路径是否能追踪。
4. 数据/训练/评测是否可复现且口径合理。
5. 新模型出现退步时是否有发布规则。
6. 真实部署和容量有哪些已验证与未验证边界。

当前项目在策略执行和后训练审计上已有较完整材料，但没有因此自动获得真实大流量生产证明。

## 19. 本篇的高概率追问与回答要点

### Q1：这到底是一个工作流还是 Agent？

考察：是否真的存在模型根据观察改变后续动作。

回答应覆盖：外层业务流程固定，内层统一策略循环开放工具选择；用工具失败后改查询、补证据后再求解的例子说明。再指出当前单任务会话封装，不按旧阶段 DAG 讲。

继续追问：哪些决策来自模型，哪些来自程序？能否指出一次模型参数与执行参数的区别？

### Q2：Long-Horizon 比普通 while 循环多了什么？

考察：状态、资源、时效、恢复和多步错误传播。

回答应覆盖：目标/证据/失败/预算 Ledger、版本失效、检查点、用户中断；解释早期候选不足怎样影响后续餐饮与求解。不要用“工具调用多”作唯一论据。

继续追问：最长实际测过多少步？哪个集合与什么协议？不要把 24 步预算当成所有任务都完成了 24 步。

### Q3：Harness 检查这么多，还算模型自主吗？

考察：前置条件与策略代办的边界。

回答应覆盖：模型选动作；Harness 拒绝非法提案并提供反馈。预算、授权和实体来源属于工程约束。需要补哪条证据、怎样查询和何时再试仍由模型决定。

继续追问：如果只有一个动作可行，会不会暗中自动完成？应按当前调用链解释，不能沿用历史控制器推进设计。

### Q4：为什么用 LangGraph？自己写循环不行吗？

考察：框架承担的具体价值。

回答应覆盖：内层循环本身可写；项目将 LangGraph 用于会话节点、持久检查点、中断与恢复。它不是模型效果来源，也不是用了框架就天然 exactly-once。

继续追问：一次进程退出发生在工具执行后、checkpoint 前，会怎么样？

### Q5：模型直接 finish，你怎么知道它没撒谎？

考察：完成标准是否由模型控制。

回答应覆盖：当前 Solver/Verifier 产物、hard_pass、创建时间、新鲜证据、用户确认。finish 只提交草稿，用户确认是下一道产品边界。

继续追问：旧版 hard_pass 能不能确认新版方案？为什么？

### Q6：查不到信息与任务无解怎么区分？

考察：不确定性处理和事实依据。

回答应覆盖：空查询、供应商不可用和明确不可行证据是不同观察；只有闭馆覆盖全部日期或必付费用下界等可靠证据才能支持对应不可行判断。

继续追问：一次求解超时能不能给用户说“无解”？不能把算法停止当成现实证明。

### Q7：为什么既有 Solver 又有 Verifier？

考察：独立检查的范围及局限。

回答应覆盖：防止需求投影、数据适配、回退和版本变化造成错误；它不保证外部数据真实，二者也可能共享错误输入。

继续追问：什么情况下两个都通过，最终行程仍有问题？

### Q8：Token 降了 79.5%，具体怎么算？

考察：基线、统计单位、Token 范围和归因。

回答应覆盖：30 对、同模型与输入、856564 对 175519、全样本平均；历史 policy_driven 架构、工具环境与计量差异、包含失败样本。

继续追问：为什么模型调用更多而 Token 更少？能否按相同质量、同工具快照再测一次？

### Q9：为什么不用纯 SFT 一次训练到位？

考察：输入状态分布和错误覆盖。

回答应覆盖：理想教师示范与学生实际失败状态不同；成功筛选可能遗漏难恢复状态；需要状态接续、保持样本和旧问题回归。

继续追问：你如何证明数据来自训练实例，没有把验收答案混进去？

### Q10：新 SFT 120/120 为什么还不发布？

考察：指标选择与发布判断。

回答应覆盖：新实例集合与旧复测不同，旧故障候选仅 4/6；新测试模板相关，不能外推生产；当轮主要候选预先是 DPO，后验选 SFT 需新确认。

继续追问：如果只优化平均成功率，会隐藏什么风险？

### Q11：用户取消或改需求，旧工具结果怎么办？

考察：并发执行与版本一致性。

回答应覆盖：任务取消、Goal/Plan 更新、版本/时效过滤和派生产物失效；当前修订偏保守重建。外部调用是否可取消与供应商接口有关。

继续追问：已有结果可以复用哪些？目前实现是否真有精准依赖级复用？

### Q12：系统能承受多少并发？

考察：有没有把架构配置当性能数据。

回答应覆盖：接入、SSE、Worker、模型推理、工具供应商和数据库容量分别测；本篇没有重新验证生产并发，旧压测也不能直接继承到新版本。

继续追问：增加 FastAPI 副本能不能加快 GPU 上的模型推理？

## 21. 当前最需要避免的旧说法

| 旧说法或过强说法 | 当前更准确的表达 |
|---|---|
| LLM 只做理解与文案 | 模型还负责整个 Loop 的工具顺序、恢复与提交时机 |
| 每次都先 RAG 与天气并行 | 当前工具顺序由模型根据任务和证据选择 |
| 主链路是多阶段 DAG 自动推进 | 当前内部只有一个 travel_agent 会话任务 |
| 三路混合检索＋RRF 已默认生效 | 当前 POI 优先结构化检索；向量与词法能力需按接入情况说明 |
| 一次 finish 就表示完成订单 | finish 提交经过检查的草稿；后续用户确认，booking 仍为 MVP |
| 有 checkpoint 就是 exactly-once | 可恢复执行位置，外部副作用仍需独立幂等 |
| 求解失败证明任务无解 | 需要区分超时、当前方案失败与事实不可行证明 |
| 所有后训练数据都是失败纠错 | 示范、状态接续、失败纠错、学生成功动作要分清 |
| 95%/100% 是真实用户准确率 | 对应具体合成集合和任务成功契约 |
| 四卡就是跨机 DDP | 此前实际是多机分担独立任务 |
| 当前已完成 GRPO 并优于 SFT | 历史资产与当前架构实验分开；当前最新对照是 SFT/DPO |
