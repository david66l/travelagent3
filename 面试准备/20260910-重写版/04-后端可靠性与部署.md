## 1. 先明确：这一篇解决什么问题

前三篇主要回答 Agent 怎么理解需求、管理上下文、使用工具和验证行程。本篇回答另一组问题：

- 用户点击发送后，HTTP 请求断了，这次规划到底有没有被受理？
- 同一个请求重发两次，会不会产生两份任务、两次模型费用？
- Worker 执行到一半退出，怎样知道还有工作没做完？
- 页面刷新、切换网络或 API 滚动更新，用户怎样看到已有进度？
- 用户取消后，界面停止、数据库终止和 GPU 停止计算是不是同一时刻？
- 增加 API 副本、Worker 或 GPU，哪个环节会先变成瓶颈？
- 如何证明部署能恢复、能承载，而不是只证明配置文件写得完整？

TravelAgent 的一次交互可能涉及多轮模型决策、外部查询、路线矩阵、约束求解、人工确认和结果输出。这样的任务会跨越单次 HTTP 请求的生命周期。把全部工作塞进请求处理函数，会把浏览器连接、服务进程和业务执行强耦合。

当前主聊天链路的设计是：**先把任务存下来，再通知 Worker 执行；执行进度写入数据库，浏览器通过 SSE 获取；图的恢复状态另由 Checkpointer 保存。**

这套分工已经有具体代码，但若干故障分支尚不能支持“任何故障都能自动恢复”的结论。面试时应同时讲清楚已实现机制、保证范围和未完成的验证。

### 1.1 至少区分四种“成功”

| 层次 | 含义 | 不能推出什么 |
|---|---|---|
| 请求受理成功 | 消息、任务等必要记录已经提交，接口返回任务标识 | 不代表 Worker 已开始，也不代表路线可行 |
| 任务执行完成 | 本轮执行到合法终点，例如完成回答、提出澄清或等待用户确认 | 不代表已经生成最终行程 |
| 行程质量通过 | 工具证据、约束、业务规则满足对应评测口径 | 不代表服务没有重复计费、超时或事件丢失 |
| 服务可靠性达标 | 在明确负载和故障条件下，受理、恢复、交付达到预设指标 | 不代表所有输入都有高质量答案 |

项目中，澄清轮和等待确认轮也可能被映射为本次 Job 完成。不能直接拿 jobs_completed / jobs_created 当“旅行规划正确率”，更不能把它与后训练的严格通过率混用。

## 2. 当前实际链路：前台连接、后台任务和持久状态

主前端通过 postChatMessage 调用 POST /api/v1/chat/message。其核心调用链可以按下面的顺序讲述：

~~~text
浏览器 useChat / useSSE
    │ POST 消息 + 身份信息 + Idempotency-Key
    ▼
Go / Echo 网关
    │ JWT、IP / 用户限流、熔断、反向代理
    ▼
FastAPI 主聊天入口
    │ 归属校验、重复请求检查、输入处理
    │ PostgreSQL 事务提交消息与 PlanningJob
    ├───────────────► HTTP 202 + job_id
    │
    └─ Celery 派发 ─► Redis Broker ─► Planning Worker
                                      │ 数据库任务租约
                                      │ 同一会话的执行锁
                                      ▼
                               LangGraph + Agent Loop
                                      │
                 ┌────────────────────┼───────────────────┐
                 ▼                    ▼                   ▼
        PostgreSQL Checkpoint  Job / JobEvent       会话状态存储
                 │                    │
                 │                    ├─ Redis 通知、Token
                 │                    ▼
                 └─────────── FastAPI SSE 推送层
                                      │ 事件回放 + 状态恢复
                                      ▼
                                    浏览器

Celery Beat ──► 扫描长时间未派发的 pending / retrying 任务并补发
~~~

这里不是每个箭头都属于一个事务。数据库提交与 Broker 发布之间有失败窗口，数据库事件与 Redis 通知之间也有失败窗口。系统的可靠性来自对这些窗口的识别和补偿。

### 2.1 四类持久或临时数据不要混为一谈

| 载体 | 主要职责 | 当前边界 |
|---|---|---|
| PlanningJob | 本轮任务身份、状态、尝试次数、执行归属、结果投影 | 不等同于完整图执行历史 |
| PlanningJobEvent | 阶段事件及恢复游标 | 不包含全部实时 Token |
| PostgreSQL Checkpointer | LangGraph 状态与执行恢复所需信息 | 不自动让外部 API 具备幂等副作用 |
| Redis / 进程内连接队列 | 调度、锁、缓存、低延迟通知与连接交付 | 不能统一当成永久业务事实 |

第二篇解释的用户记忆也不等于执行日志。画像可以长期保留偏好，却不能替代“哪个 Worker 正在执行哪个 Job、已经消费哪些事件”的运行状态。

### 2.2 仓库还保留另一条执行路径

api/v1/agent_chat.py 中存在通过 asyncio.create_task 启动后台工作的路径，且该 Router 仍在 v1 Router 中注册。它与主前端使用的持久 PlanningJob 派发链路不能视为完全相同。

面试可以说：“当前主聊天入口已经采用持久任务执行链路；仓库还保留另一条进程内后台执行接口，需要继续统一可靠性语义。”不要说“所有入口都天然经过同一套任务恢复机制”。

## 3. HTTP 202：怎样把“已受理”做成可解释的承诺

主聊天入口先验证 conversation 是否属于当前用户，再进行请求校验、幂等判断和输入处理。普通消息会写入用户消息并创建规划任务，事务提交后才调用 enqueue_planning_job。

confirm、modify、reject、trip_event 等控制动作也会形成 Job，并将动作上下文放入任务相关状态。这样，用户确认不是只存在于某个 API 进程的局部变量里。

源码锚点：[主聊天入口](E:/A_Louis/TravelAgent2/backend/src/api/v1/chat.py)、[任务创建与派发辅助逻辑](E:/A_Louis/TravelAgent2/backend/src/api/chat_runtime.py)。

### 3.1 为什么要先 commit 再派发

假设先把 Celery 消息发出去，再提交数据库：

1. Worker 可能很快消费消息。
2. 此时它按 job_id 查不到尚未提交的记录。
3. 或者 API 随后回滚，但 Worker 已经开始执行一个没有正式受理的任务。

当前顺序避免了这个特定窗口。数据库事务一旦提交，就有一个可以检查、补发和解释的任务实体。

但这不等于消除了所有双写问题：提交后 API 仍可能在发送 Celery 消息之前退出。下一节会讲补偿。

### 3.2 202 的延迟应怎样测量

不能把 202 受理延迟简化成“往 Redis 放一条消息”的时间。真实入口还包含认证、会话归属、输入校验、附件解析、幂等锁等待、数据库提交等步骤。

应分别观测：

- submit_latency：浏览器发起 POST 到得到受理响应。
- queue_wait：任务创建到 Worker 真正获得执行权。
- first_progress_latency：受理到浏览器收到第一条有效业务进度。
- end_to_end_latency：提交到满足所定义业务终点。

第一个指标快，后面三个仍可能很慢。例如任务在队列里等了两分钟，但 POST 只用了 100 ms，不能据此声称用户两分钟的等待问题已经解决。

## 4. 幂等：同一个请求、同一份任务，以及它的边界

主接口支持 Idempotency-Key，请求头要求长度为 8—128 且满足限定字符格式。接口根据规范化后的请求内容计算 SHA-256 指纹，并按 user_uuid 与 key 查找既有任务。

相同用户、相同 key、相同请求内容，复用已有任务；相同 key 对应不同请求内容，则返回冲突。key 是可选的，因此不带 key 的调用不能被描述为具有同样的重复提交保护。

### 4.1 为什么不能只在插入前 SELECT 一次

两个请求可能同时执行：

~~~text
请求 A：查不到 key ──► 准备插入
请求 B：查不到 key ──► 准备插入
~~~

“先查后写”本身无法排除竞态。当前实现叠加了：

1. 基于用户和 key 计算的 PostgreSQL transaction advisory lock。
2. 持锁后再次查询已有任务。
3. 数据库中 user_uuid + idempotency_key 的唯一约束。
4. IntegrityError 后回滚，再检查已有记录的兼容性。

事务级锁解决常见并发窗口，唯一约束作为最终数据库约束。不同用户可以使用相同 key；同一用户不能把一个 key 当成多个不同请求的编号。

源码锚点：[任务模型](E:/A_Louis/TravelAgent2/backend/src/models/planning_job.py)、[任务仓储](E:/A_Louis/TravelAgent2/backend/src/repositories/planning_job.py)。

### 4.2 客户端必须保留“一次逻辑操作”的 key

前端发送消息时使用 crypto.randomUUID 产生 key。这个行为保证新操作有独立标识，但不能单凭它证明“用户失败后手动重发仍复用原任务”。

如果第一次 POST 已提交，响应恰好丢失，而前端重试时生成新 key，后端有权把它当作新任务。因此，完整设计还应让同一次逻辑提交的网络重试复用 key，直到得到确定结果；用户明确编辑内容重新提交时，再生成新 key。

当前文档没有把这项客户端重试协议认定为已完整落地。

### 4.3 三种幂等必须分开

- API 幂等：重复请求是否创建重复 Job。
- 执行幂等：消息重复投递是否让同一个 Job 同时执行两次。
- 外部副作用幂等：重放某一步是否重复下单、扣费或写入外部系统。

本项目的请求 key、数据库租约、Checkpoint 分别参与前两类保护。它们不会自动赋予第三方系统幂等性。未来如果接真实预订，必须在工具层单独处理业务操作标识和外部确认结果。

“支持请求幂等”和“端到端恰好执行一次”之间，还有很长一段需要证明的链路。

## 5. 数据库提交了，队列消息没发出去怎么办

enqueue_planning_job 在数据库提交之后尝试派发任务。派发失败会记录日志，任务仍以持久记录保留。Celery Beat 每 30 秒调度一次补发扫描，查找更新时间早于约 15 秒前的 pending / retrying 记录，每批最多 100 条，再向队列投递。

这是一种数据库记录驱动的补偿派发。它利用“受理事实已在数据库”这一点，补上部分提交后未成功入队的任务。

### 5.1 它和事务 Outbox 的区别

当前做法不是“在同一个事务里同时提交数据库和 Celery”，也没有在本文审查的主链路中看到独立 Outbox 事件表的完整确认协议。

可这样解释：

> 数据库中的任务记录是受理事实，Broker 消息是执行通知。通知发送失败时，定时扫描尚未执行的任务进行补发；Worker 再通过原子认领避免普通重复投递导致重复并发执行。

这个表述准确，也能体现理解，不需要把它升级成未实现的分布式事务。

### 5.2 补发时间不是绝对 SLA

“每 30 秒扫一次、超过 15 秒才扫描”意味着理想情况下还要等待相应调度窗口，但实际延迟受 Beat 存活、扫描成功、100 条批量上限、Broker 恢复和 Worker 容量影响。不能承诺所有丢派发任务都在固定 30 秒内启动。

例如积压 10,000 条符合条件记录时，每轮只处理 100 条，即使没有新流入，也不能忽略扫描吞吐本身。

### 5.3 补发不等于崩溃恢复全覆盖

扫描针对 pending / retrying。已进入执行阶段、状态变成 planning 或 tools_executed 的任务，并不在这个扫描条件中。

应分别设计并验证：

- 已受理但未调度：补发扫描。
- 已调度但无 Worker：队列监控与消费能力。
- 已被认领但 Worker 崩溃：过期租约回收。
- 已执行外部操作但未记录结果：操作幂等与结果核对。
- 已完成但用户没收到：事件回放与结果查询。

五种情况不是一个 retry 就能解决的。

## 6. 数据库租约：谁有资格执行这份 Job

PlanningJob 保存 locked_by、lock_expires_at、heartbeat_at、attempt_count、max_attempts。Worker 获取任务时原子更新执行归属和租约，同时增加 attempt_count。

有两条认领方式：

| 方式 | 关键实现 | 用途 |
|---|---|---|
| 扫描认领 | UPDATE…RETURNING，子查询按创建时间选择，并用 FOR UPDATE SKIP LOCKED | 嵌入式 Worker 轮询获取任务 |
| 按 ID 认领 | 带状态、过期时间和次数条件的 UPDATE…RETURNING | Celery 消息指定 job_id |

按 ID 的方式没有必要描述为也执行了 SKIP LOCKED；它依赖条件更新的原子性。两种方式都只认领 pending、retrying，或租约已过期的 running，且 attempt_count < max_attempts。

当前 Worker 心跳间隔约 10 秒、租约约 60 秒。心跳更新和部分写入带 worker_id 归属条件，以降低旧执行者继续覆盖新执行者结果的风险。

### 6.1 租约表达的是执行资格，不是杀死旧进程

某个 Worker 网络暂停 70 秒后，另一个 Worker 可能取得资格；旧 Worker 恢复时，旧进程仍然存在。租约不会让操作系统自动终止旧进程，也不会撤销它已经发出的工具调用。

因此还需要 fencing：重要写入只有当前执行代次或当前所有者可以提交。现有代码中，心跳、release 和部分阶段更新有归属条件，但结果或反馈相关写入并未全部采用同样条件，不能声称已经完成端到端 fencing。

改进时可以让每次认领增加单调执行代次，把 job_id + execution_epoch 贯穿结果、阶段和副作用提交。这里是建议，不是现有字段功能的描述。

### 6.2 状态字段复用带来的静态风险

当前 status 同时承担任务生命周期与业务阶段，例如从 running 改成 planning、tools_executed 等。租约回收查询却只匹配过期的 running。

于是存在一个需要故障测试验证的窗口：

~~~text
Worker 认领 → status=running
写入规划进度 → status=planning
Worker 退出 → 心跳停止、租约过期
回收条件只识别 running → 这条记录可能无法被正常重新认领
~~~

这是从状态写入和认领条件交叉检查得到的静态风险，不是本次观测到的云端事故。

更清晰的后续设计是拆成 lifecycle_status 与 current_stage：前者描述 pending / running / succeeded / failed / cancelled，后者描述 perception / tools / solve 等执行进度。这样，UI 展示不会意外改变调度可恢复性。

## 7. 会话锁：为什么 Job 锁之外还要再加一把锁

任务锁防止多个 Worker 同时认领同一个 Job。但同一会话可以先后创建多个 Job：用户补充预算、修改天数、确认方案。如果两个不同 Job 并发修改同一个会话 Checkpoint，仍可能相互覆盖。

Worker 在执行前还会获取 agent-run:{session_id} 对应的会话执行锁，当前 TTL 约 60 秒，并在执行期间续租。等待时也检查取消信号。

源码锚点：[Planning Worker](E:/A_Louis/TravelAgent2/backend/src/worker/planning_worker.py)。

### 7.1 两层锁分别保护什么

- Job 租约：一个任务的执行归属。
- Session 执行锁：不同任务对同一个会话状态的并发修改。

不同会话仍可并行，同一会话则在进入图执行前串行。这是用一定的等待成本，换取状态更新更容易推理。

例如：

~~~text
会话 A：Job 1 正在规划 ── Job 2 等待会话锁
会话 B：Job 3 正在规划
会话 C：Job 4 正在规划
~~~

这个结构适合避免多轮对话中“旧回答覆盖新约束”，但不代表已经保证严格业务顺序。

### 7.2 互斥不是 FIFO，也不是最新请求优先

锁保证互斥，但不自动保证 Job 2 一定先于 Job 3 抢到锁。多个任务同时等待时，具体顺序还依赖调度和竞争。

如果产品要求“用户最后一次修改优先”，还需要明确：

1. 是否取消旧任务。
2. 是否合并排队中的多次修改。
3. 是否按会话 revision 拒绝过时结果。
4. 旧任务已经生成的可复用证据怎样保留。

不能只用一句“Redis 锁保证一致性”回答这些问题。

### 7.3 等锁也会占用 Worker 资源

当前 Worker 认领任务后再等待会话锁。过多同会话请求可能占据多个执行槽，却只有一个任务真正前进。

因此扩容前应区分 queue_wait 与 session_lock_wait。若主要耗时来自同会话互斥，增加 Worker 可能只会增加等待者。

可考虑按会话分区调度或在进入执行槽之前做串行化，但这是后续方案；不能当作目前已有的队列能力。

### 7.4 心跳后台任务也需要被监督

当前心跳循环发现归属不再有效时，会设置取消事件。可是数据库心跳调用若直接抛出异常，后台任务可能退出；异常退出和“明确发现租约已丢失”不是完全一样的路径。

可靠性审查还要问：后台监督任务停止后，业务执行是否会停止、报警或降级？仅在 finally 中收集异常，不等于执行过程中已经及时处理失去监督的问题。

## 8. Checkpoint 恢复：保存了什么，仍可能重做什么

API 与 Celery Worker 各自建立长期存活的 PostgreSQL Checkpointer 上下文，并将其交给图实例。图执行以 session_id 作为 thread_id。恢复信息属于持久图状态，不只存在于 Web 进程内存。

graph/runner.py 会检查恢复快照，并根据当前 Job、已有消息、图的等待状态和终点决定恢复、重放可见结果或处理新动作。代码对同 Job 重入、澄清和等待确认等场景有专门分支。

源码锚点：[图运行入口](E:/A_Louis/TravelAgent2/backend/src/graph/runner.py)、[Worker 图初始化](E:/A_Louis/TravelAgent2/backend/src/worker/planning_tasks.py)、[API 生命周期](E:/A_Louis/TravelAgent2/backend/src/api/main.py)。

### 8.1 Checkpoint、JobEvent 和用户记忆是三个视图

| 视图 | 服务对象 | 典型问题 |
|---|---|---|
| Checkpoint | 图执行器 | 从哪个状态继续？是否等待人工输入？ |
| JobEvent | 浏览器和任务观察者 | 用户错过了哪些阶段变化？ |
| 用户记忆 / 会话快照 | 对话恢复和个性化 | 用户偏好是什么？最近有什么消息和行程？ |

这三个视图各有用途。不能用用户消息列表重建全部图内部状态，也不能直接把完整 Checkpoint 当成对前端公开的事件。

Worker 对结果做公开投影，测试中也有不把完整 agent checkpoint 塞进进度载荷的检查定义。这减少不必要的数据暴露和传输膨胀，但本次没有运行对应测试。

### 8.2 从断点继续不等于从任意机器指令继续

假设工具调用已经返回，但下一次持久状态写入前进程退出。恢复时可能再次调用同一工具。Checkpoint 能恢复已提交状态，无法凭空知道尚未记录的外部结果。

对查询类工具，可以通过缓存键、请求指纹和可复用产物降低重复成本。对写操作，需要独立的业务幂等和确认机制。后训练能改善模型选择动作的质量，不能替代这种存储协议。

### 8.3 快照读取异常也值得单独分析

runner 的恢复读取存在异常后按没有快照继续处理的路径。它有助于避免整个入口因读取失败立即退出，但也意味着某些情况下可能重新开始一部分工作。

这不是“恢复失败完全无影响”。需要结合日志、执行代次、外部调用账单和状态一致性验证。面试可以强调：“我会把无快照和读取快照失败分开，避免把基础设施故障误判成真正的新会话。”

## 9. 重试、退避和死信：哪些失败值得再试

Celery 规划任务设置了延迟确认，并对异常分类。重试判断会检查异常及其原因链：超时、网络或部分数据库瞬时故障被视为可重试；参数、类型、权限等明确错误通常不重试。

实际执行函数会把应重试的失败向 Celery 包装层传播。否则，内部吞掉异常并返回成功，Celery 就不会知道需要重新执行。

源码锚点：[任务包装与补发](E:/A_Louis/TravelAgent2/backend/src/worker/planning_tasks.py)、[异常分类与退避](E:/A_Louis/TravelAgent2/backend/src/core/task_retry.py)、[死信存储](E:/A_Louis/TravelAgent2/backend/src/core/dead_letter.py)。

### 9.1 基础设施重试与 Agent 修复不是一回事

第三篇的 Agent 修复可能是：换候选 POI、补充营业时间、重新求解。这里的基础设施重试可能是：数据库连接暂时不可用、Broker 连接中断、服务请求超时。

前者改变解决问题的策略，后者再次尝试执行工作。对确定的约束不可行反复重启整份 Job，会浪费资源；对临时网络断开直接让模型“重新想办法”，也可能制造无意义推理。

正确做法是保留失败类型、原因和已完成产物，在相应层处理。

### 9.2 退避公式要读到 jitter 之后

当前退避使用指数增长，并先对基础延迟做上限限制，再乘以随机抖动因子。默认基础量级为 2 秒，上限基数为 30 秒，随机因子约在 0.5—1.5。

因此可解释为：

~~~text
base_delay = min(2 × 2^(attempt - 1), 30)
actual_delay = base_delay × random_factor
~~~

这意味着配置中的 30 秒不是最终严格上限；加上抖动后，实际等待可接近 45 秒。加入 jitter 的作用是降低许多失败任务在同一时刻重新冲击依赖的概率。

描述退避时要区分“基础上限”和“实际最大等待”。

### 9.3 当前有三套次数上限，需要统一核对

| 层次 | 当前默认或声明 | 统计对象 |
|---|---|---|
| Job 数据库 | max_attempts 默认 3 | 成功认领并进入一次执行资格的次数 |
| 包装层重试计数 | 配置默认重试上限 3，计数保存在 Redis | 异常处理分支中的重试次数 |
| Celery 装饰器 | max_retries=10 | Celery 自身允许的重调度次数 |

三者并不是同一个计数器。不能只看 Celery 的 10 次，就说一个 Job 一定重试 10 次。

一个静态边界是：数据库已经达到认领上限，但包装层仍安排下一次重试；下一次拿不到执行权，函数返回 False，被当成任务调用正常返回。这种路径不天然等于“成功完成死信收口”。

需要测试第三次失败到最终收口的完整序列，而不是仅测试单次异常能调用 self.retry。

### 9.4 死信保存和人工处理

当前死信主要先存入 Redis 列表，包含任务、Job、异常和参数等诊断信息，后续可归档到 PostgreSQL。归档不是重新执行，存在死信接口也不等于所有失败会自动修复。

另一个顺序风险是：最终失败处理先写 Redis 死信，再标记数据库 Job 失败。若 Redis 本身不可用，最终数据库状态的更新可能受前一步失败影响。

改进目标应是：任务的确定终态不能长期依赖故障中的通知或诊断通道；死信诊断可以补偿，业务状态需要可收敛。本文只记录这个边界，没有修改实现。

### 9.5 延迟确认不等于任何进程退出都会自动重投

acks_late 表明确认时机延后，但实际 Worker 丢失、Broker visibility、任务拒收和进程终止的组合还受 Celery 配置影响。本次没有看到一份足以证明所有 Worker 丢失情况均自动重投的完整运行证据。

面试应把“配置了延迟确认”与“验证了进程崩溃后的恢复结果”分开叙述。

## 10. 阶段事件为什么先写 PostgreSQL，再发 Redis 通知

Worker 的 record_stage 将 Job 阶段变化与 JobEvent 写入数据库事务。事务提交后，再更新 Redis 的状态缓存并发布通知。Redis 通知失败会计数和记录日志，不应因此把已经成功提交的业务进度当成整份任务失败。

这体现了一个明确选择：数据库负责持久事实，Redis 通知负责让观察者更快发现事实。

### 10.1 事件游标不是数组下标

PlanningJobEvent 的 ID 是数据库中的递增标识。恢复查询使用 job_id + id > last_event_id，再按 ID 排序。

不同 Job 的事件共享 ID 分配空间，所以某个任务的相邻事件不一定编号连续。客户端应理解为“已消费到哪个事件标识”，不能用缺少一个整数判断必然丢了一条本任务事件。

### 10.2 事件表不等于完整 Event Sourcing

当前既有 Job 当前状态，也有图 Checkpoint、会话状态和事件记录。事件主要用于进度与恢复，并没有在本次审查中证明所有状态都能仅靠事件序列从零重建。

可以说“持久进度日志与事件回放”，不宜直接说“整套系统采用完整事件溯源”。

### 10.3 一个容易误读的耗时字段

仓储更新 stage_timings 时，记录的是从 Job 创建到该阶段写入的累计时间，不能未经转换就视为该阶段独占耗时。

例如：

~~~text
进入 tools_executed：从创建起已过去 10 秒
进入 solving：从创建起已过去 18 秒
~~~

这不等于工具阶段用了 18 秒。即使用相邻值相减，也要考虑重复进入同一阶段、覆盖写入和异步分支。要做准确的阶段分布，应单独记录阶段进入、退出和执行代次。

## 11. SSE 的恢复语义：哪些能补，哪些只能恢复最终状态

前端使用 fetch 读取流，以便携带 Authorization 等请求头。服务端返回 SSE 格式的 data 消息，浏览器解析 JSON 中的业务字段。

流接口接受 conversation_id、可选 job_id 和 last_event_id。前端把事件载荷中的 event_id 维护为恢复游标，重连时通过查询参数传回。

这套协议基于自定义 JSON 游标，不是依赖浏览器原生 EventSource 自动维护 Last-Event-ID 的全部行为。

源码锚点：[SSE Hook](E:/A_Louis/TravelAgent2/frontend/src/hooks/useSSE.ts)、[前端事件处理](E:/A_Louis/TravelAgent2/frontend/src/lib/chatEvents.ts)、[流接口](E:/A_Louis/TravelAgent2/backend/src/api/v1/chat.py)。

### 11.1 三类数据的恢复能力

| 类型 | 实际通路 | 断线后的能力 |
|---|---|---|
| 持久阶段事件 | PostgreSQL JobEvent，经通知或轮询发现 | 可按游标查询后续事件 |
| 实时 Token | Redis token:{job_id}，转发至连接队列 | 没有同等的逐 Token 持久回放保证 |
| 当前会话结果 | restore_session_state 读取会话状态 | 可恢复已有消息、行程、阶段、确认信息等投影 |

因此“支持断线重连”可以成立，但应补全对象：支持持久阶段事件续接和会话状态恢复；实时逐字文本主要通过临时通知传递。

如果用户离线期间错过了一段 Token，系统可以通过最终消息恢复可见结果，并不一定按原速度、原分片补齐当时所有字符。

### 11.2 前端自动重连的具体边界

当前 Hook 对异常断开采用指数退避加 jitter。基础等待约从 1 秒开始，上限基数 30 秒，乘以 0.75—1.25，所以最终等待也不是严格最多 30 秒。

401 / 403 会停止自动重试；429 会使用 Retry-After 或响应中的 retry_after 等信息。这样的分类有意义：认证失败不能靠无限快速重连解决，限流也不应被重连放大。

但 reader 正常返回 done、即流以 EOF 正常结束时，代码退出读取循环，并没有在这一路自动安排重连。若业务 done 尚未收到，干净的连接结束和业务完成仍可能混淆，需要单独覆盖。

### 11.3 有游标不等于前端完整去重

chatEvents 会把 event_id 更新为已见最大值，但没有在入口统一拒绝 event_id 小于等于当前游标的事件。保存最大游标与忽略重复事件，是两件事。

服务端多个推送任务向同一会话广播、重连交叠或重复回放，都可能要求事件处理本身具有幂等性。对阶段覆盖赋值，重复执行影响较小；对追加消息、弹出确认、增加统计等动作，则需要明确去重。

当前 Hook 中的游标也不能自动等同于跨浏览器重启的永久恢复记录。

### 11.4 SSE 的正常保持与资源占用

服务端等待队列期间约每 30 秒发一次 keepalive，流超时参数默认 1,800 秒，允许范围约 60—3,600 秒。响应包含 no-cache 与关闭代理缓冲提示。

这些是连接行为参数，不是高并发结果。长连接仍占用文件描述符、内存、连接状态和代理资源；每条连接背后的数据库轮询也有成本。

## 12. “Redis 失败就用数据库兜底”当前不能说得过满

push_job_status 同时启动 Redis 订阅与数据库轮询。数据库轮询约每 2 秒读取新事件和终态，这能在通知遗漏时发现持久进度。

但它使用 FIRST_COMPLETED 等待两个后台任务：其中一个结束，就取消另一个。两个任务内部发生异常时，都有捕获、记录并返回的分支。

于是“有两种数据来源”不等于“任意一种失败，另一种一定独立继续”。

### 12.1 一个需要优先验证的故障序列

~~~text
Job 仍在运行
    ↓
Redis 订阅异常，被捕获后函数返回
    ↓
FIRST_COMPLETED 认为一个任务已结束
    ↓
数据库轮询任务被取消
    ↓
最后再读一次事件
    ↓
后续路径可能把 planning 会话设为 completed，并发送 done
~~~

最后一段没有在所有出口重新要求数据库中的 Job 处于真实终态，因此存在“观察通道退出被当作业务完成”的静态风险。

这不是本次复现结果。它说明面试回答应该是：“实现了持久事件和轮询机制，但通道监督及终态判定还需要故障注入验证和修正”，不能说“Redis 掉线时绝对无感”。

### 12.2 正确的后续修正方向

应区分三类退出原因：

1. 数据库明确记录了 Job 终态：可以发送相应业务结束。
2. 某个通知通道暂时失败：重建该通道，或继续其他可用通道。
3. 整个观察端无法继续：告诉客户端连接异常，不伪造业务完成。

重新发送最终结果也要以持久业务事实为依据，不能用“当前推送任务不再运行”替代“业务已成功”。

### 12.3 连接队列的上限和丢弃行为

ConnectionManager 的单连接队列与无连接暂存队列都有 4,096 条的局部上限。队列满时主要是记录告警并丢弃相应入队事件，不能理解为已经实现了无损背压。

此外，局部队列有界不意味着会话字典或整个进程总内存天然有一个固定总上限。慢客户端数量、事件大小、会话数量仍影响内存。

更完整的策略可以包括：持久事件用游标补回、Token 分片合并、低优先级进度合并、过慢连接主动断开并恢复快照。这些属于建议，当前没有验证统一落地。

### 12.4 游标推进和批量读取也有边界

服务端读取事件后先推进内部游标，再交给连接队列；它没有等待浏览器确认消费。队列满或连接中断时，服务端“读过”与用户“看到”可能不同。

恢复查询当前也没有 LIMIT。大量历史事件一次性回放可能形成内存与数据库压力。后续应明确分页、最大回放窗口以及从快照恢复的策略，而不是让事件日志无限制地成为单次响应负载。

## 13. 取消需要三个时钟：请求、状态和计算停止

取消不是一个布尔字段就能完整表达的能力。至少要区分：

- 用户请求取消的时间。
- 数据库进入 cancelling / cancelled / force_cancelled 的时间。
- 模型、求解器或外部请求实际停止消耗资源的时间。

当前有显式取消、断线宽限后的取消通知，以及超时强制标记等机制，但它们没有共同保证底层计算即时停止。

### 13.1 Worker 主要在图事件边界观察取消

Worker 有 Redis Pub/Sub 取消监听，收到 job:cancel 通知后设置 asyncio.Event。执行图事件循环时检查该事件，并处理取消。

如果底层正在等待一个很慢的模型调用，且迟迟没有产出新的图事件，这个检查可能暂时得不到执行机会。仓库中虽有查询数据库取消状态的 check_cancelled 方法，但本次未在这条执行链中找到对应主动调用，不能据此声称已经有可靠的数据库轮询取消兜底。

### 13.2 force_cancelled 不等于 SIGKILL

超时处理会把仍在 cancelling 的任务标为 force_cancelled，清除相应执行归属并写入事件。它是持久状态收口，不是对模型服务或求解进程发出操作系统终止信号。

因此不能把“30 秒后强制取消”直接翻译成“30 秒后绝对不再产生模型费用”。

后续可以在模型客户端、工具执行器和独立求解服务中传递取消信号、配置超时，并让迟到结果无法覆盖取消后的状态。对已经送达外部平台的请求，还需要认识到远端计算未必可撤回。

### 13.3 断线取消是另一条有宽限的策略

SSE 断开后会安排约 30 秒的延迟处理，检查当前会话是否已重连，再尝试请求取消。延迟逻辑本身通过 API 进程内 asyncio.create_task 启动，进程重启可能使计时丢失。

取消状态检查还存在与阶段状态复用有关的范围问题：某些入口只接受 pending / running / cancelling 等生命周期值，业务阶段写入后未必仍匹配。

所以短暂断线、主动取消、API 进程退出、远端计算停止应分别测试，不能用一个“断开 SSE”的测试代替。

### 13.4 怎样衡量取消能力

建议按不同任务阶段记录：

~~~text
cancel_state_latency = terminal_cancel_state_at - cancel_requested_at
cancel_compute_latency = last_actual_compute_at - cancel_requested_at
post_cancel_cost = 取消请求后仍产生的可归属调用成本
~~~

并区分等待队列、等待会话锁、模型生成、外部查询、求解执行和输出阶段。这里给出的是指标定义，没有声称已采集结果。

## 14. 鉴权和限流：网关做什么，应用还要做什么

默认网关实现是 Go / Echo。它对受保护的 /api/v1 路径串接认证、限流、熔断与代理，同时保留公共认证及健康等路径。

后端仍有自己的用户依赖、会话归属和任务归属检查。仅仅经过网关验证了 JWT，不足以说明用户有权读某个 conversation_id 或 job_id。

源码锚点：[网关入口](E:/A_Louis/TravelAgent2/gateway/cmd/gateway/main.go)、[网关认证](E:/A_Louis/TravelAgent2/gateway/internal/middleware/auth.go)、[后端用户依赖](E:/A_Louis/TravelAgent2/backend/src/api/deps.py)。

### 14.1 身份校验和对象授权必须分开

JWT 解决“调用者是谁”；conversation / job 的用户归属解决“调用者能看或改哪份数据”。主聊天及指定 Job 的流接口有相应归属检查。

仓库还存在独立规划任务接口和另一条 Agent 入口。它们不能因为“用了同一个 APIRouter”就被假设拥有完全相同的授权逻辑。

例如，有状态修改接口的注释称面向 admin / worker，但实际依赖与归属校验不等同于管理员角色校验。这类接口需要单独审视权限矩阵。本文不把注释当作已实现的权限保证，也没有进行越权运行测试。

### 14.2 网关与 Python 的限流算法并不相同

Go 限流器使用 Redis Sorted Set 与 Lua：清理窗口外请求、统计数量、决定是否加入本次请求，在脚本内完成。它对应真正按时间窗口滑动的计数。

Python RateLimitController 中的请求计数主要按分钟桶 INCR，是固定窗口实现，不能照着注释把它称为同一种滑动窗口。

| 层 | 主要用途 | 当前需要理解的取舍 |
|---|---|---|
| Go IP 限流 | 入口级流量保护 | 共用出口 IP 的用户可能相互影响 |
| Go 用户限流 | 对同一用户限制访问频率 | 多 API 类别是否共用额度要明确 |
| Go SSE 并发 | 限制用户同时占用连接 | 计数失效、断开释放和错误路径需要核对 |
| Python 请求 / 成本控制 | 应用侧补充规则 | 固定窗口与入口滑动窗口并存 |
| 应用 SSE 会话槽 | 按用户及会话记录活跃连接 | 扫描再设置不是完整原子协议 |

双层限流不是自动“双倍可靠”。用户可能在不同层收到不同错误，监控也应区分命中位置和规则，避免难以解释的 429。

### 14.3 Redis 故障时，当前若干规则选择 fail-open

部分限流逻辑在 Redis 错误时记录日志并允许请求继续。网关中的黑名单或封禁 Redis 查询错误处理，也不能简单理解为“依赖故障时全部拒绝”。

fail-open 保持一部分可用性，但会弱化相应保护。fail-closed 则更严格，但依赖短暂故障可能扩大成入口不可用。应按认证、撤销状态、计费上限和普通频率限制分别决定，不能全局只背一种答案。

### 14.4 SSE 计数需要明确所有权

Go 并发限制使用计数增减和过期；应用侧又使用 sse:session:{user}:{session} 一类键表示连接占用。同一会话重连可以刷新键，避免把每次重连都简单当成新的长期槽位。

但扫描后设置存在竞态；旧连接退出时删除共享会话键，也可能影响新连接。计数在 TTL 后归零再执行释放，则需要防止负数等错误。更完整的设计可以为连接分配独立 token，用原子脚本或带所有权的释放协议。

这些是当前静态边界，不是已经完成改造的能力。

### 14.5 请求频率限制不等于模型费用封顶

主聊天入口调用应用限流时 estimated_tokens=0，因此这一入口的预估 Token 扣减分支不会按正数预扣。不能据此说系统完全没有成本控制，因为模型路由、执行预算和其他层另有机制；同样也不能说该入口已经对每次实际费用做了完整预留与结算。

真正的硬预算需要定义额度预留、实际结算、失败释放、重试累计和并发超卖处理。第五、六篇讨论后训练成本时，也要与在线请求预算区分。

## 15. 熔断：HTTP 服务健康与 Agent 业务健康

Go 网关熔断器在进程内维护 closed、open、half-open 状态，基于观察窗口中的失败数量与比例控制放行。当前参数包括约 10 秒观察窗口、20 次失败门槛、50% 失败比例和约 30 秒打开时间。

这些参数描述一个网关实例的状态；多个副本并不会自动共享同一份熔断器历史。

源码锚点：[熔断器实现](E:/A_Louis/TravelAgent2/gateway/internal/breaker/breaker.go)。

### 15.1 异步系统中的特殊问题

POST 返回 202 后，Worker 可能在三分钟后模型超时；SSE 也可能保持 HTTP 200，却在业务事件中携带任务失败。

如果网关主要观察 HTTP 5xx，它不一定能看到这些业务失败。网关熔断保护的是特定 HTTP 访问层面的故障，不自动等于模型供应商熔断或 Agent 质量控制。

因此需要分别观察：

- HTTP 错误和代理失败。
- Job 失败及超时。
- 模型供应商错误与限额。
- 工具失败和求解不可行。
- 最终质量门槛未通过。

### 15.2 Half-open 也要看放行策略

当前半开状态没有完整的少量探测配额控制，成功响应可以让状态恢复。若大量请求在半开时同时涌入，依赖仍可能受到集中冲击。

面试可以讲清楚后续方向：限制半开探测数量、区分依赖、设置最小样本与恢复门槛，并验证故障恢复期间的流量。不要仅用三个状态名称证明熔断设计已经完整。

## 16. 容量分析：为什么加 API 副本或加卡不一定更快

一次行程规划的时间可以拆成：

~~~text
总等待 = 受理 + 队列等待 + 会话锁等待
       + 模型调用 + 外部工具 + 求解 + 状态持久化 + 输出交付
~~~

扩大其中一层，只对那一层的瓶颈有效。训练多卡与在线规划服务扩容也是不同问题；本篇讨论的是在线长任务可靠性，不把训练吞吐结果直接拿来证明接口容量。

### 16.1 Worker 并发不等于模型并发能力

增加 planning Worker 可以让更多独立任务同时进入执行，但后面可能共享：

- 同一个模型服务或教师 API 的并发、RPM / TPM 配额。
- 路线与搜索供应商限额。
- 同一个数据库连接池。
- 同一个求解服务的 CPU / 内存。
- 同一会话执行锁。

如果后端瓶颈是模型服务，每个 Worker 都更快地发出请求，可能只会增加服务端排队、429 与重试成本。

### 16.2 一个只用于理解的容量算例

假设每份任务占用一个执行槽，平均占槽 30 秒，共有 10 个可用槽。忽略所有其他瓶颈，理想完成吞吐约为：

~~~text
10 / 30 ≈ 0.33 份任务每秒
~~~

这不是本项目实测数据。它说明不能拿“API 每秒受理多少请求”直接替换成“每秒完成多少次规划”。

同理，平均有 300 个正在等待或执行的任务、平均完成时间 60 秒，在稳定且统计口径匹配的观察区间，平均完成速率量级约为 5 份每秒。这只是 Little's Law 的讲解算例，不是生产容量结论。

### 16.3 数据库连接预算按进程计算

数据库配置中，单进程连接池大小 20，额外 overflow 10。实际连接按需建立，但最大潜在连接数会随着 API 进程、Celery 子进程和其他服务累计。

不能只看 backend replicas=3 就得出总共最多 30 条连接。Worker 使用数据库时，也可能在各自进程里建立池；Checkpointer 还需要单独核对其连接生命周期。

建议按以下口径审查，而不是直接改大所有池：

~~~text
潜在连接需求
≈ 各类实际进程数 × 各自池上限
  + Checkpointer / 运维 / 迁移 / 备份等额外连接
~~~

过多连接并不保证更高吞吐，反而可能让数据库更忙。应把池等待、连接数、事务时长和查询耗时一起看。

### 16.4 SSE 的数据库轮询成本

一条活跃 Job 推送任务约每 2 秒轮询数据库。连接或重复推送任务增加时，数据库查询量也会增加。

即使每次查询很小，也要考虑活跃任务数、连接重叠、索引和事务开销。可评估集中通知、按 Job 共享观察者、批量扫描等方案，但不应在没有负载证据时随意替换当前结构。

### 16.5 不同队列扩容应依据不同指标

- planning：队列等待、执行槽占用、模型等待和完成时延。
- memory：归档积压、最老任务年龄和数据库写入压力。
- default：实际路由到该队列的任务类型与延迟。
- poi：必须先确认真实任务路由和消费者，不能只看 Deployment 名称。

当前 K8s HPA 主要依据 CPU，队列自定义指标 / KEDA 相关说明属于注释或方案。不能说现在已经按队列积压自动扩缩容。

## 17. 可观测性：把用户、任务、模型和结果串起来

仓库包含 Prometheus 指标、网关 HTTP 指标、可选 OpenTelemetry 配置和 LangSmith 接入。关键不是组件数量，而是能否回答一次失败发生在哪里、花了多久、成本多少、是否重复执行。

建议统一关联字段：

~~~text
request_id → user_id / conversation_id → job_id
           → worker_id / execution_attempt → graph thread_id
           → model / tool call → terminal outcome
~~~

当前代码已使用其中多种标识，但本次没有证明网关、API、Celery、图和模型服务已经共享一条完整父子 Trace。存在 OTel 初始化和 LangSmith 配置，不等于跨进程链路传播已经验收。

源码锚点：[业务指标](E:/A_Louis/TravelAgent2/backend/src/core/metrics.py)、[HTTP 指标中间件](E:/A_Louis/TravelAgent2/backend/src/middleware/metrics_middleware.py)、[Tracing 初始化](E:/A_Louis/TravelAgent2/backend/src/core/tracing.py)。

### 17.1 已有指标能说明什么

源码中有任务创建、完成、失败、强制取消、死信、重试结果、会话锁等待、模型 Token、模型耗时、工具调用、缓存与 Agent 终态等指标定义。

定义存在不等于所有路径都有正确上报，也不等于当前云端仪表盘已接入。需要在运行验证时检查：关键异常分支是否计数、标签是否稳定、指标是否跨进程汇总、是否出现重复累计。

特别是 task completed 与 Agent 业务终态应配合解读，避免澄清轮被算作最终行程成功。

### 17.2 API 与网关的“耗时”未必是同一口径

FastAPI 的 HTTP 中间件围绕 call_next 计时，对流式响应通常不能直接解释为整个业务流的完成耗时。Go 网关处理代理请求的耗时又可能覆盖更长的连接生命周期。

因此应明确：

| 指标 | 应取的时间点 |
|---|---|
| HTTP 受理延迟 | POST 发出到 202 返回 |
| 首业务事件延迟 | Job 创建到第一个有效阶段事件被交付 |
| TTFT | 对所定义模型或用户可见文本的首 Token 时间 |
| Job 完成延迟 | Job 创建到持久终态 |
| SSE 连接寿命 | 建连到连接关闭 |
| 行程完成延迟 | 提交到通过业务验收的结果可见 |

SSE 连接持续 10 分钟，不等于后端单次请求处理慢了 10 分钟；很快得到响应头，也不等于模型已经吐出第一个 Token。

### 17.3 多进程指标不能只设置一个目录

部署清单有 PROMETHEUS_MULTIPROC_DIR，指标端点当前使用默认 generate_latest()。本次审查没有看到完整的 multiprocess collector 聚合与进程退出清理闭环。

环境变量存在，只能说明配置意图；还需要检查 Celery 多进程指标如何暴露、旧进程文件如何处理、Gauge 类型是否合适，以及抓取端是否真的获取到所有 Worker 数据。

### 17.4 标签不要带来新的容量问题

job_id 适合日志和 Trace 检索，却通常不适合直接作为每个 Prometheus Counter 的无限标签。任务量增长后，会产生高基数时间序列。

网关对 UUID、数字路径做归一化有助于控制 HTTP 指标标签。对模型、动作、终态等业务标签，也应采用有限集合；详细任务上下文留在日志或 Trace。

## 18. 健康检查、优雅退出和数据库迁移

后端提供不同健康接口：存活检查表示进程能响应；就绪检查进一步访问 Redis 与数据库。K8s 使用 /api/ready 做 readiness，并把 /api/health 用于 liveness / startup。

源码锚点：[健康接口](E:/A_Louis/TravelAgent2/backend/src/api/health.py)、[后端 Deployment](E:/A_Louis/TravelAgent2/k8s/backend-deployment.yaml)。

### 18.1 Ready 不是整个业务链路健康

Redis PING 和数据库 SELECT 1 成功，并不代表：

- Celery 队列有人消费。
- 模型端点可用且未限流。
- 求解服务能完成请求。
- 外部地图 API 有剩余额度。
- SSE 的通知、回放和终态判断正确。

应分层设置探针与业务合成检查。不要让一次外部供应商短暂故障导致所有 API Pod 不停重启；同时也不能把进程活着当成业务可用。

### 18.2 优雅退出需要给长连接和任务安排去处

后端 Deployment 有 preStop 等待和 termination grace，网关也有关闭超时。Worker 配置有自己的退出等待。

这些配置为连接迁移或任务结束提供时间，但若任务本身可能运行几分钟，60 秒终止宽限不能保证每个任务都自然完成。仍然需要停止接新任务、保存状态、租约回收和客户端恢复配合。

SSE 用户在滚动升级期间可能连接断开。浏览器重连、跨副本状态读取与持久事件回放必须一起验证，不能只看 Pod 是否成功 Ready。

### 18.3 create_all 不能代替版本迁移

API 启动包含数据库初始化与 Checkpointer setup。业务模型的 create_all 不等于能够正确变更所有既有表结构。

K8s 中另有 Alembic migration Job，并通过 ArgoCD 同步阶段安排在应用更新之前执行。这比让每个 API 副本启动时各自迁移更容易避免并发争抢。

但声明 migration Job 不是迁移已经在当前云端执行。面试应知道实际发布还需确认迁移版本、失败处理和新旧服务兼容。

### 18.4 版本回滚与数据回滚是两件事

回滚镜像只能回到旧代码。如果迁移已经删除列、改变数据含义或写入新格式，旧代码未必还能正常工作。

改进和发布方案宜采用兼容迁移：先新增结构，让新旧版本共同运行；切换读写后再清理旧字段。本文说明原则，没有对数据库执行任何迁移。

## 19. 部署清单提供了什么，不能证明什么

仓库有 Dockerfile、基础 / 生产 Compose、K8s 资源、CI 和 Deploy 流水线。它们提供了可复用的交付骨架，但不能仅凭这些文件断言系统已经在生产环境承载了某种规模。

### 19.1 容器和运行环境

当前后端 Dockerfile 使用 Python 3.13 系列镜像、固定 uv 工具版本与 frozen 依赖安装，并使用非 root 运行。网关 Dockerfile 编译 Go 程序，最终运行网关二进制。

这也解释了为什么不能把 gateway/nginx.conf 的所有配置都当作当前默认网关行为。Nginx 文件可以作为另一种入口方案或历史配置存在，但默认 Go 镜像并不会自动执行其中的全部规则。

本篇不据此推断云端训练环境的 PyTorch 版本；后端服务镜像、在线模型服务、训练环境可能不同。

### 19.2 K8s 清单中的工程能力

后端 Deployment 声明了副本、资源请求和限制、探针、非 root、只读根文件系统、临时目录、退出宽限及反亲和偏好。Worker 按队列分开部署；还包含 HPA、PDB、网络策略、备份与迁移等文件。

其中 backend 声明 3 副本，HPA 的后端范围为 3—20，planning 为 2—30 等。它们是允许的扩缩范围，不是已运行副本数量或已验证承载能力。

镜像字段中的 git-sha-required 也是待发布流水线替换的占位，不能直接视为可运行的正式版本。

### 19.3 CI / Deploy 的实际定位

CI 文件包含后端格式、静态检查、测试、迁移校验、安全扫描，以及前端检查构建等步骤。Deploy 文件按源代码 SHA 生成镜像版本，构建并扫描镜像，再衔接部署流程。

这是“仓库定义了哪些门槛”的证据。没有查看某次云端流水线运行结果，就不能说这些门槛当前全绿，更不能拿脚本里的命令替代验收日志。

面试可以使用“配置了 CI 检查和基于版本的部署流程”，若要说“已稳定自动发布”，应再补最近成功运行链接、镜像 digest、环境与回滚记录。

这一节集中列出静态审查发现的配套问题，目的是准备追问与后续验证，不是宣称本次已经修复或线上必然故障。

| 项目 | 当前证据 | 为什么需要核对 |
|---|---|---|
| Redis Cluster | K8s 声明集群；应用客户端仍以普通 from_url 建立连接，配置保留多个逻辑 DB | 没有看到完整 Cluster 适配，不能仅凭 StatefulSet 声称应用已支持集群 |

| 默认不带 job_id 的流恢复 | 最新活动任务查找只覆盖部分生命周期状态 | 业务阶段被写入 status 后，可能无法正确附着当前任务 |

### 20.1 为什么这里没有直接把 Redis 改成集群

集群不是“多写几个副本”的问题。客户端类型、数据库选择、Lua / 多 key 操作、锁、Pub/Sub、Broker 以及故障恢复都要一起验证。

当前优先事项应是选择一套明确支持的运行形态，并把配置、客户端和测试对齐。对于面试项目，能解释当前边界、给出可复现验证，比同时罗列多种尚未接通的部署模式更有价值。

### 20.2 Beat 的单副本不等于单活协议

replicas=1 表示期望副本数量，但默认滚动更新策略可能有短暂新旧实例重叠。要严格保证定时任务只有一个调度者，还要考虑更新策略、领导者选举或任务本身的去重。

此外，celery inspect ping 是面向 Worker 控制面的检查；拿它直接验证 Beat 自己是否健康，需要核对目标和运行方式。不能用一个命令名字证明它适合所有 Celery 进程。

### 21.1 需要回答 RPO 与 RTO

- RPO：最多能够接受丢失多少时间内的数据。
- RTO：发生故障后，多久能恢复到所定义的可用状态。

每日一次备份不自动给出可靠 RPO：备份可能失败，PVC 可能与主库共享故障域，也可能缺少最近一次可验证备份。恢复时间则受数据量、环境重建、索引、模型服务和业务校验影响。

可以说“定义了每日备份任务”，不能说“已证明分钟级恢复、零数据丢失”。

### 21.2 恢复演练应该包含业务检查

建议在云端隔离环境恢复一份备份，至少验证：

1. 数据库能启动、版本与扩展匹配。
2. 会话和任务记录可以读取，用户归属仍正确。
3. Checkpoint 能被当前版本解析。
4. 事件游标与结果投影没有明显错位。
5. 旧的 running / cancelling 记录按规则收敛，而不是永久挂起。
6. 下载和导出文件若存于其他介质，有对应恢复路径。

这些是待执行的验证方案，本次没有创建数据库或恢复任何数据。

## 22. 云端交付与故障演练：下一次实际验证该怎么做

这一节是一份可执行的验证设计，不是本次已执行的操作。遵循项目既有约束，模型加载、服务部署、压测、故障注入和数据库恢复均应在云端隔离环境进行，不在用户本机启动。

### 22.1 先固定环境，再谈结果

每次验收至少保存：

- 代码 commit、镜像 digest、迁移版本。
- API / Worker / 模型服务的实际实例数与资源配置。
- Redis 运行形态、数据库版本、队列路由与消费者列表。
- 模型和 Adapter 版本、上下文上限、并发、超时与重试参数。
- 测试输入集、随机种子（适用时）、负载模型、开始结束时间。
- 日志与报告位置，以及哪些测试使用真实供应商、哪些使用故障桩。

配置固定后，才有资格比较“扩容前后快了多少”“哪个重试策略更稳”。

### 22.2 建议验收顺序

| 顺序 | 范围 | 通过条件示例 |
|---|---|---|
| 1 | 镜像、迁移、路由、队列配套 | 一个请求能经过真实网关进入正确 Worker，memory 队列也有消费者 |
| 2 | 单任务正常链路 | 202、Job、Checkpoint、事件、最终结果可关联 |
| 3 | 幂等与授权 | 同 key 同内容复用；不同内容冲突；其他用户不能读取对应会话 |
| 4 | 连接恢复 | 断网、EOF、API 重启后，最终状态与数据库一致 |
| 5 | Worker 恢复 | 在不同阶段退出后，任务在预期时间内恢复或明确失败 |
| 6 | 取消与迟到结果 | 状态收敛，取消后结果不能覆盖，资源停止时间可测 |
| 7 | 依赖故障 | Redis / DB / 模型部分故障不会制造虚假成功 |
| 8 | 负载与扩容 | 完成吞吐、队列年龄、成本、尾延迟在目标范围 |
| 9 | 发布与备份恢复 | 滚动升级和恢复后业务对象可读取，版本一致 |

“通过条件示例”必须在实际验收前量化。这里没有擅自给项目填入未测量的 SLA。

### 22.3 应优先补的故障矩阵

| 注入位置 | 观察问题 | 应保留的证据 |
|---|---|---|
| DB 提交后、Celery 发布前退出 API | 任务是否补发，是否重复创建 | Job、原始 key、补发时间和认领记录 |
| 同 key 并发提交 | 是否只有一个逻辑任务 | 两个响应、唯一约束结果、实际 Job 数 |
| 写入 planning / tools_executed 后杀死 Worker | 阶段状态是否阻碍租约回收 | status、lease、attempt 变化 |
| 心跳查询抛错 | 执行是否失去监督仍继续 | 心跳异常、执行代次、迟到写入 |
| Redis 订阅断开而 DB 正常 | SSE 是否错误发送 done | SSE 原始事件与同时刻 Job 状态 |
| 正常 EOF 但没有业务 done | 前端是否恢复或提示连接中断 | 网络记录和 Hook 状态 |
| 慢客户端撑满队列 | 是否可恢复最终状态 | 队列丢弃指标、事件游标、结果对比 |
| 长模型调用期间取消 | 状态与实际计算多久停止 | 请求时间、终态时间、调用结束和费用 |
| 达到第三次失败 | 重试是否正确收口到明确终态 | 三套计数、最终状态、死信记录 |
| Beat 更新或异常重启 | 是否重复调度、是否停止补发 | Beat 实例时间线、派发与消费记录 |
| API 多副本重连交叠 | 旧连接释放是否影响新连接槽 | 连接标识、Redis 键和网关计数 |
| 发布后执行数据库恢复 | 是否能够恢复可用业务状态 | 恢复日志、版本、对象抽查和耗时 |

这张表的价值在于把“我考虑过高可用”落成明确可观察的实验。只讲组件名字，面试官无法判断是否真正理解故障。

## 23. 可靠性指标、现有测试与证据等级

### 23.1 指标分母必须固定

建议把同一批被受理任务按明确业务终态分类，观察窗口结束时单独列出仍未收口的任务，不能悄悄丢弃。

~~~text
受理成功率 = 得到确定受理结果的合法提交 / 合法提交总数

观察窗口内任务收口率
= 已进入明确终态的受理任务 / 观察窗口覆盖的受理任务

最终行程质量通过率
= 满足指定质量门槛的最终行程 / 对应评测协议要求产出行程的样本

持久事件恢复完整率
= 故障后正确恢复的应恢复事件 / 故障期间应恢复的持久事件
~~~

最终行程的质量率应由明确样本集、失败处理规则和验收器定义。不能只用“成功生成的样本”作分母，把超时、格式错误或任务丢失排除后再汇报高通过率。

事件恢复指标也必须限定“持久事件”，不能把它扩大为所有临时 Token。

### 23.2 时延与成本应一起呈现

至少列出：

- 提交 P50 / P95 / P99。
- 排队等待与最老任务年龄。
- 任务完成时延和失败 / 超时占比。
- 首进度与首 Token 时延。
- 取消状态时延与取消计算时延。
- 每个已受理任务、每个最终成功任务的模型与工具成本。
- 重试额外消耗，以及重复调用占比。
- 故障后的恢复时间和人工处理量。

若只提高成功率却让每个请求重试十次，吞吐和成本可能不可接受；若只压低延迟却提前发送 done，也没有完成产品目标。

### 23.3 仓库已经有相关测试定义

本次确认了以下测试文件或测试名称，**没有运行它们，也没有据此声明当前全部通过**：

| test_planning_tasks.py | 调用 Worker、无法认领、重试、死信、pending 补发、Checkpointer 清理 |
| test_planning_worker.py | 阶段映射、取消、同会话锁、通知失败不破坏已提交进度、异常传播 |

## 24. 用一个完整场景串起所有机制

下面是讲解案例，不是云端运行日志。

用户提交“杭州三天，预算有限，带老人，少走路”，浏览器为本次逻辑请求分配 key=K1。

### 24.1 受理阶段

网关验证身份并检查流量规则；FastAPI 验证会话归属与请求内容。后端在事务中写入消息和 Job J1，提交后派发 Celery，返回 J1。

如果响应丢失，同一次网络重试应继续用 K1，才能复用 J1；若生成 K2，服务器不能凭自然语言相似就断定它一定是重复操作。

### 24.2 开始执行

Worker 通过条件更新认领 J1，取得租约，再获得当前会话锁。它加载图 Checkpoint 并运行 Agent Loop。

Job 锁保护 J1 的执行归属，会话锁保护同一个 conversation 的图状态。两者都不能替代工具内部的副作用幂等。

### 24.3 用户看到进展

Worker 写入阶段和 JobEvent，再发布通知。SSE 读取事件，通过 JSON 载荷携带 event_id。实时文本通过另一条 Token 通道到达。

如果浏览器短暂离线，之后带着游标重连，阶段事件可以回放；若错过临时 Token，则依靠当前消息或最终结果恢复，而不是假设所有字符都能逐个补发。

### 24.4 Worker 在工具阶段退出

此时理想目标是新 Worker 取得过期租约，从持久状态继续。但当前 status 被写入业务阶段后可能不匹配 running 回收条件，所以不能直接说这个例子在现状下一定自动成功。

这是应该通过云端故障注入优先确认的点：先证明状态能收敛，再测恢复需要多少秒。

### 24.5 用户又说“改成四天”

新请求形成 J2；同一会话执行锁防止两份 Job 同时修改图。但应明确旧任务要继续、取消还是被新 revision 替代，锁本身不会替产品决定。

第三篇的约束与证据失效处理发生在图内；本篇的排队、互斥、取消与迟到写入发生在执行基础设施层。两层配合，才能避免旧约束生成的结果覆盖新需求。

### 24.6 最终输出并验收

某轮 Job 可能只完成澄清或等待确认。只有最终行程满足约束和证据门槛，才能计为对应业务成功。

最后复盘同时看：是否只创建一个逻辑任务、是否重复付费、是否正确恢复、是否错误提前 done、行程是否通过验证，以及用户总共等了多久。

## 25. 十二组高概率面试追问

### Q1：为什么不用一个 async HTTP 接口直接完成规划？

**回答主线：** 长任务生命周期超过单次连接和 API 进程。主入口先持久化任务并快速返回标识，Worker 负责执行，浏览器通过独立流观察，降低连接断开对执行的耦合。

**继续追问：async 本来就不阻塞线程，为什么还需要 Celery？**  
异步解决等待时的调度效率，不能自动提供持久任务、跨进程消费、重试和进程退出后的恢复。进程内 create_task 仍可能随进程消失。仓库另一条 Agent 入口正好说明两种方式可靠性语义不同。

**不要说：** “用了异步就不会丢任务”或“用了 Celery 就绝不丢任务”。

### Q2：你怎样实现幂等？为什么既用锁又用唯一约束？

**回答主线：** 用用户与 Idempotency-Key 标识逻辑请求，用规范化内容指纹防止同 key 被复用于不同内容；事务级 advisory lock 缩小并发竞态，唯一约束兜底，冲突后回滚并查询。

**继续追问：HTTP 响应丢了怎么办？**  
同一逻辑操作的网络重试必须复用原 key。当前前端新提交会生成 UUID，持久重试协议还需专门核对。

**不要说：** “文本一样就不创建新任务”或“API 幂等已经保证所有外部操作只执行一次”。

### Q3：数据库和 Redis 双写怎样保持一致？

**回答主线：** 主链路先提交数据库，再发送执行通知。提交后消息丢失，用定时扫描 pending / retrying 补发；Worker 原子认领抵御普通重复投递。

**继续追问：这是事务 Outbox 吗？**  
当前更准确的是任务表驱动补偿派发，没有把它描述为完整 Outbox 协议或跨系统原子事务。还需监控补发积压与扫描吞吐。

**不要说：** “commit 后发消息所以没有双写窗口”。

### Q4：Worker 崩溃后怎么恢复？两个 Worker 会不会同时跑？

**回答主线：** 数据库保存执行归属、租约、心跳与尝试次数，认领通过原子条件更新；Checkpoint 保存图状态。租约过期后理论上允许其他 Worker 接手。

**继续追问：旧 Worker 又恢复了呢？**  
必须有归属或执行代次控制迟到写入。当前部分写入有 owner 条件，但未全链路 fencing；业务阶段覆盖 status 也可能让回收查询漏掉任务，需要修正和故障验证。

**不要说：** “租约过期会自动杀死旧 Worker”。

### Q5：既然一个 Job 有锁，为什么还需要 Session 锁？

**回答主线：** 两个不同 Job 可能属于同一会话，同时写同一个 Checkpoint。Job 锁管一份工作，Session 锁管会话状态的并发修改。

**继续追问：加锁后请求就按顺序执行了吗？**  
互斥不等于 FIFO。最新修改、取消旧轮和 revision 校验需要独立定义。等待会话锁也可能占用 Worker 执行槽。

**不要说：** “Redis 锁解决了所有多轮一致性问题”。

### Q6：你的 SSE 是否支持断点续传？

**回答主线：** 持久阶段事件保存到 PostgreSQL，客户端携带 JSON event_id 游标重连；会话恢复返回已有消息、行程与确认状态。实时 Token 主要走 Redis 通知，不具备相同逐 Token 回放保证。

**继续追问：客户端怎样去重？**  
当前保存最大事件 ID，但未在统一入口完全过滤重复事件。后续要让追加型事件有明确幂等消费规则，并验证跨连接重叠。

**不要说：** “SSE 协议天然保证消息不丢不重”。

### Q7：Redis 掉了，数据库轮询不是还能兜底吗？

**回答主线：** 有持久事件与两秒轮询，但还要检查监督方式。当前 FIRST_COMPLETED 会在某个后台任务结束时取消另一个，异常返回可能让轮询也停止，后续还有过早发送 done 的风险。

**继续追问：你会怎么改？**  
区分通知通道失败、业务终态和观察端退出；通知失败不能转成业务成功，数据库确认终态才结束。先写针对这一窗口的故障测试，再修改监督与重连逻辑。

**不要说：** “有 Redis 和数据库两份数据，所以天然高可用”。

### Q8：用户点取消后，为什么还会产生费用？

**回答主线：** 状态取消与计算停止不同。当前主要在图事件边界检查取消，底层模型等待可能尚未结束；force_cancelled 也是持久状态，不是终止远端计算。

**继续追问：怎样证明取消有效？**  
分阶段测量请求到状态收口、请求到实际计算停止、取消后新增费用，并验证迟到结果不能覆盖取消状态。

**不要说：** “前端停止流式输出就代表模型停止生成”。

### Q9：为什么重试不能统一设得越多越好？

**回答主线：** 参数错误与业务不可行不会因重试自动变好；瞬时故障需要退避和抖动，重试次数还受成本和整体时间预算约束。

**继续追问：这个项目最多重试几次？**  
不能只给一个数字：数据库认领次数、Redis 包装层计数和 Celery max_retries 有不同语义，当前存在默认 3 / 3 / 10 的组合，需要测试达到边界后的收口。

**不要说：** “Celery 写 10 就一定重试 10 次”。

### Q10：你做了 K8s，为什么还不能直接说高可用？

**回答主线：** 清单具备副本、探针、资源、迁移、备份和扩缩容等部署结构，但应用协议与运行验证决定真实恢复能力。

**继续追问：具体还有什么没对齐？**  
例如 Redis Cluster 与普通客户端、多逻辑 DB；基础 Compose 的 memory 消费者；Beat 探针与调度存储；API 前缀；租约回收与事件终态。应选择一套实际环境验证，而不是堆配置名词。

**不要说：** “有三个副本就不会中断”。

### Q11：系统慢了，你第一反应是加卡还是加 Worker？

**回答主线：** 先分解受理、排队、锁等待、模型、工具、求解、持久化和输出。模型计算占主导才评估模型服务扩容；队列执行槽紧张才评估 Worker；锁等待或供应商限流则需其他措施。

**继续追问：HPA 现在按什么扩？**  
当前清单主要按 CPU，队列指标方案并未被当作已启用配置。长任务等待可能 CPU 不高，所以不能假设 CPU HPA 能解决队列拥塞。

**不要说：** “加卡能等比例提升整条 Agent 链路”。

### Q12：怎样证明这不是玩具项目？

**回答主线：** 不靠组件清单或一个漂亮平均值。展示从受理到恢复的协议、失败窗口、明确指标分母、可复现环境和云端故障演练记录；能解释当前不足及修正顺序。

**继续追问：你现在已经有什么证据？**  
已有具体实现、部署定义与相应测试代码；本篇是静态审查，没有新增线上运行结果。后续用固定版本的验收报告补足恢复、容量与回滚证据。

**不要说：** “我觉得达到大厂标准了”代替可核验事实。

## 26. 三分钟讲述稿与自测

### 26.1 三分钟讲述稿

下面以项目视角写。面试中改成第一人称前，需要确认相应设计和实现确实属于自己的工作范围。

> TravelAgent 的规划会跨越模型决策、外部工具、约束求解和人工确认，所以后端把请求受理、后台执行和前端观察分开。主聊天入口先把消息与 PlanningJob 提交到 PostgreSQL，再派发 Celery，返回 202 和 job_id；浏览器通过独立 SSE 连接观察进度。
>
> 为避免重复提交，接口用用户加 Idempotency-Key 标识逻辑请求，校验内容指纹，并结合事务 advisory lock 和数据库唯一约束处理并发。数据库提交后消息仍可能没发出去，所以有定时扫描 pending / retrying 的补发机制，Worker 再原子认领任务。这里提供的是持久受理加补偿，不把它说成跨数据库和队列的原子事务。
>
> 执行层用了两层控制：任务租约与心跳管理 Job 的执行归属，会话锁避免不同 Job 同时修改一个会话的图状态。LangGraph 的 Checkpointer 保存恢复信息，但外部调用的副作用仍要自己做幂等，不能靠 Checkpoint 解决所有重复执行。
>
> 进度先写数据库事件，再发 Redis 通知。SSE 重连可以按事件游标回放阶段，并恢复当前行程与消息；实时 Token 主要是临时流，恢复能力与持久事件不同。取消也分成请求、数据库终态和底层计算停止，界面停止输出不意味着模型立刻停止计费。
>
> 工程上有容器、按队列部署、探针、迁移、指标和流水线配置，但我会把配置与验证结果分开。当前审查仍发现业务阶段与生命周期状态复用影响租约回收，以及 SSE 通道异常可能过早触发结束等边界。下一步应固定云端环境，围绕这些窗口做故障注入，同时记录任务收口、恢复时间、尾延迟和额外成本。这样才能用证据说明系统的可靠性，而不是只列组件名称。
