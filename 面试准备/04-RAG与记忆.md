涉及简历写的「pgvector 检索 / 画像召回 / 事实校验 / 幻觉检测」,都是会被深挖的点。

---

## A. 先补地基:embedding 和向量检索是什么

**embedding(向量化)大白话**:把一段文字变成一串数字(一个向量)。关键性质——**意思相近的文字,向量也相近**。「博物馆」和「美术馆」的向量距离近,和「火锅店」的远。

**你项目用的模型**:`BAAI/bge-large-zh-v1.5`(BGE 中文向量模型),**1024 维**,本地用 sentence-transformers 跑(不调外部 API)。`normalize_embeddings=True` 把向量归一化,方便算余弦相似度。

**工程细节(能讲出就显专业)**:模型 1.3GB,做了 ① 单例懒加载 + asyncio.Lock 防并发重复加载 ② 用 `asyncio.to_thread` 把推理放线程,不阻塞事件循环 ③ 启动时 warmup 预热 ④ `local_files_only` 强制走本地缓存(否则每次冷启会联网检查元数据,卡 ~45s 然后失败)。

**向量检索**:把用户查询也变成向量,在库里找**向量距离最近的几个** = 语义最相关的结果。哪怕用词不同(查「适合带老人」能召回「无障碍、坡度缓」),也能命中——这是它比关键词搜索强的地方。

**相似度怎么算**:**余弦相似度**(看两个向量方向夹角)。pgvector 里 `<=>` 算子是余弦距离,`1 - 距离 = 相似度`,`ORDER BY 距离 LIMIT k` 就是取最近的 k 个。

## B. 什么是 RAG,为什么需要

**RAG = Retrieval-Augmented Generation(检索增强生成)**:先从外部知识库**检索**相关资料,再把资料塞进 prompt 喂给 LLM,让它**基于资料**回答。

**为什么需要**:LLM 的知识是训练时固化的——① 会过时 ② 不知道你的私有数据(景点库)③ 容易胡说。RAG 让回答**知识可更新、可溯源、少幻觉**。

> 💡 在你这里 RAG 的作用:从景点知识库检索出**真实的 POI**(名字、营业时间、票价、坐标)喂给后续流程,LLM 和求解器都基于真实数据,不凭空编景点。

---

## C. pgvector:在 PostgreSQL 里做向量检索

**pgvector** 是 PostgreSQL 的**扩展**,让 PG 能存向量字段、建向量索引(HNSW / IVFFlat)、做近邻检索。检索就是一句 SQL:`ORDER BY description_vector <=> 查询向量 LIMIT k`。

> 💡 **追问「为什么用 pgvector 不用 Milvus(专门向量库)」**:本项目 POI 数据量不大,用 pgvector ① 少维护一个组件 ② POI 的结构化字段和向量**在同一个库**,可以一条 SQL 同时按向量相似度 + 结构化条件(预算/城市)过滤,事务一致 ③ 不用做两套数据同步。**而 PaperRAG 用 Milvus,是因为 30 万文献规模大、需要专门向量库的性能**——这俩对比一讲,说明你是按场景选型,不是无脑套。

📖 八股:向量索引是 **ANN(近似最近邻)**——HNSW(图索引,快、内存大)、IVFFlat(倒排+聚类,省内存)。精确最近邻太慢,生产用近似换速度。

## D. 你项目的检索:其实是 hybrid(混合检索)

`retrieve` 节点不是只做向量检索,而是**三路并行 + 融合**(和 PaperRAG 同一套思路):

```
查询 → 并行三路:
        ├ 结构化检索(按城市/预算/标签精确过滤)
        ├ 向量检索(pgvector 语义召回)
        └ BM25 检索(关键词召回)
       → RRF 融合 → top_k → (空了走 fallback) → 实时信息增强
```

- **为什么混合**:向量擅长语义(「带老人」→「无障碍」),BM25 擅长精确关键词(「迪士尼」),结构化擅长硬过滤(预算≤500)。三者互补,召回更全。
- **RRF(Reciprocal Rank Fusion,倒数排名融合)**:把三路各自的排名按 `1/(k+rank)` 加权相加再排序,不依赖各路分数的绝对值,简单又稳。

> 💡 **能把「我在 TravelAgent 和 PaperRAG 都用了混合检索 + RRF」串起来讲**,面试官会觉得你 RAG 是真懂,不是调个 API。

## E. 画像召回(profile_recall)

把用户偏好存成向量(`preference_embedding`),新会话时用**向量检索召回历史相似偏好**,填补当前对话缺失的槽位(slot)。例:用户这次没说预算,从历史画像召回他一贯的预算档位,少问一句。

- SQL:`ORDER BY preference_embedding <=> 当前偏好向量` 取最相似的历史偏好。
- **memory_conflict_resolver**:处理记忆冲突(历史"喜欢安静",这次说"要热闹")——以本次为准或提示用户。

---

## F. 记忆体系:hot / warm / cold 三层

| 层 | 存哪 | 放什么 |
|---|---|---|
| **hot** | Redis | 当前会话热状态,读写最快 |
| **warm** | Redis/中间层 | 较近期状态 |
| **cold** | PostgreSQL | 持久化:用户画像、历史会话、历史行程 |

- **会话写锁(acquire_lock)**:防止用户多设备同时改同一会话造成冲突;抢不到锁就回 `session_conflict` 让前端重试。
- 断线后延迟归档(archive):把会话从热层沉淀到冷层。

## G. 事实防护:两道防线(★ 简历写的「事实校验 + 幻觉检测」)

**关键认知:这两道都是「确定性规则校验」,不是「用 LLM 判 LLM」**——便宜、可靠、不引入新幻觉。这是强设计点。

**防线 1 — fact_guard(内部一致性)**:
求解器算出的行程是**真 facts**(时间、票价、坐标)。LLM 只负责给行程**润色文案**。fact_guard **逐字段比对**润色前后的受保护字段(`poi_name / start_time / end_time / duration_min / ticket_price / location`),确保 LLM 润色时**没偷偷改掉事实**。改了就报出哪个字段变了,可回退原值。

**防线 2 — hallucination_detector(对齐真实数据)**:
把生成的行程和**真实工具数据**交叉核验,逐项打分 + 列问题:
- POI 是否真实存在(在检索结果里)
- 活动时间是否落在该 POI 的**真实营业时间**内
- 标注票价是否和工具票价一致(算**偏差比例**,超阈值报警)
- 路线/通勤是否可行、预约标注是否正确

> 💡 **追问「怎么防止 LLM 幻觉」**(标准答法):「两道防线,而且都是**确定性校验**:① fact_guard 保证 LLM 润色不篡改求解器算出的时间/票价/坐标;② hallucination_detector 把生成内容和真实工具数据逐字段交叉核验(营业时间、票价偏差、POI 存在性)。我故意没用『LLM 判 LLM』,因为那会引入新幻觉、还费 token——确定性规则又快又稳。」

## H. 必背 + 追问 + 八股

**必背**:
1. embedding 把文字变向量,意思近向量近;BGE 中文 1024 维本地跑。
2. 检索是 **hybrid**:结构化 + 向量(pgvector)+ BM25 → RRF 融合。
3. 事实防护**两道确定性防线**:fact_guard(防 LLM 篡改)+ hallucination_detector(对齐真实数据)。

**高频追问**:
- *为什么 pgvector 不用 Milvus?* → 数据量小、同库事务一致、少维护;PaperRAG 大规模才上 Milvus(按场景选型)。
- *向量检索原理?* → 查询向量化 → ANN 找最近邻(HNSW/IVFFlat)→ 余弦相似度排序。
- *RRF 是什么?* → 多路召回按倒数排名融合,不依赖绝对分数。
- *怎么防幻觉?* → 两道确定性防线,不用 LLM 判 LLM。

> 📖 **八股底**:RAG 流程(chunk → embed → 存 → 检索 → 重排 → 拼 prompt)、ANN(HNSW/IVFFlat)、余弦相似度、RRF、向量维度与召回质量权衡。
