## 一、先有一个画面（这项目到底干嘛）

**一句话**：用户用大白话说旅行需求，系统自动吐出一份**能照着走的多天行程**。

想象一个真实场景：

> 用户打字：「我想带爸妈去上海玩 3 天，预算 2000，他们喜欢历史景点，走不了太多路。」
> 几十秒后，屏幕上一边滚动着「正在找景点…正在排路线…」，一边出来一份行程：
> 「Day1：上午 9:00 豫园（票价 40，玩 2 小时）→ 步行 10 分钟 城隍庙吃午饭 → 下午外滩…」每天去哪、几点、怎么走、花多少，全排好，还能下载 PDF。

**记住这个画面。后面所有技术，都是为了把这个画面变成现实而被迫加进来的。**

## 二、核心洞察（整个项目就靠这一句话立住）

如果面试官只让你说一句话，说这句：

> **「这个项目最关键的设计，是把『排行程』这件事从 LLM 手里拿走，交给数学求解器。LLM 只负责听懂需求和润色文案，真正排行程用的是 OR-Tools 的约束求解器。」**

**为什么这是核心？** 因为 99% 的人做「AI 旅行助手」就是写个 prompt 让 GPT 列行程。但 LLM 是「语言概率模型」，它会给你一份**看起来很顺、其实经不起推敲**的行程：时间对不上、超预算、把周一闭馆的景点排周一、把城东城西两个景点挤一天来回 3 小时。

因为排行程**本质是个数学难题**（专业叫 VRP-TW，带时间窗的车辆路径问题，NP-hard），要同时满足十几条互相打架的硬规则。这种问题**只有数学求解器能保证算对**，LLM 天生算不准。

> 💡 这一刀（LLM 管语言、求解器管数学）是你和「调个 API 的玩具项目」的根本区别。**面试时把这句话当锚点，所有展开都从它出发。**

## 三、从零搭一遍：6 个问题逼出整个架构（★★ 全文最重要）

**别去记「这个项目有哪些组件」。记不住，也不理解。**

正确的方式：假装你从一张白纸开始做这个项目，每解决一个问题，就「被迫」加一个零件。这样你记住的不是一堆名词，而是一条**因果链**——面试时你能顺着链条自己讲出来。

---

### 问题 ①：用户说的话很模糊，怎么听懂？

用户说「带爸妈去上海玩几天」——没说几月、没说预算、没说住哪。

**自然的解法**：用 **LLM** 把这句话拆成结构化的字段（目的地=上海、天数=3、预算=2000、偏好=历史、人群=老人）；缺的关键信息就**反问用户**（「请问大概几月出发？」）。

→ 这就是流程图里第一个节点 **`gathering`（理解需求 + 追问）**。

> 术语：把一句话拆成一个个字段，每个字段叫一个 **slot（槽位）**。填槽位的过程叫「**意图识别 / 需求解析**」。

---

### 问题 ②：信息齐了，让 LLM 直接排行程行不行？

**不行。** 这就是上面「核心洞察」说的——排行程是数学难题，LLM 算不准。

**自然的解法**：把行程问题翻译成一道**标准的运筹学题目（VRP-TW）**，丢给专业的**约束求解器 OR-Tools CP-SAT** 去算。

- 你只告诉求解器「**有哪些规则**（营业时间、预算、必去点…）」和「**要优化什么**（去的景点尽量多、走的路尽量少）」；
- 求解器自动在天文数字种排法里，找出**满足全部规则、且最优**的那一种。

→ 这就是节点 **`plan`**，它调用一个**独立的求解微服务**。

> 💡 **为什么求解要单独拆成一个微服务？** 因为求解是「**CPU 密集**」的重计算（占满 CPU 算几十秒），如果塞在主程序里，会把其他用户的请求全卡死。所以隔离出去单独跑、单独扩容。（这点和「FastAPI 异步只救 I/O、不救 CPU」是同一个道理，面试常连起来问。）

---

### 问题 ③：求解器需要「真实的景点数据」，从哪来？

求解器要算「9 点到豫园、票价 40、玩 2 小时」，它得先知道**上海有哪些景点、营业时间、票价、坐标**。这些数据哪来？

**自然的解法**：建一个**景点知识库**，用户一说需求，就从库里**检索**出相关的真实景点喂给求解器。

但怎么检索？用户说「适合带老人」，库里景点描述写的是「无障碍设施、坡度平缓」——**字面对不上，但意思一样**。普通关键词搜索搜不到。

→ 所以用 **RAG（检索增强）+ 向量检索**：把文字变成「向量」（一串数字，意思相近的向量也相近），用「带老人」的向量去找最接近的景点向量。这就是节点 **`retrieve`**。

> 实际做得更细：**三路一起搜**——向量搜（管语义）、关键词搜 BM25（管「迪士尼」这种精确词）、结构化搜（管「预算≤500」这种硬过滤），再融合。叫 **hybrid（混合检索）**。细节看 `04-RAG与记忆`。

---

### 问题 ④：行程排好了，但 LLM 润色文案时会乱改、会胡说，怎么办？

求解器算出的是**铁打的事实**（豫园票价 40、9 点到）。但行程要给用户看，得有人写成通顺的话——这步还是 LLM 干。问题是 **LLM 润色时可能偷偷把「票价 40」写成「票价 60」，或者编一个不存在的景点。**

**自然的解法**：加**两道检查岗**，而且故意**不用 LLM 检查 LLM**（那会引入新的胡说，还费钱），用**写死的规则逐字段比对**：

- **第一道 `fact_guard`**：润色前后，把「票价、时间、坐标」这些字段**逐个对比**，LLM 敢改就报警、回退原值。
- **第二道 `hallucination_detector`（幻觉检测）**：把成品和真实数据交叉核对——这景点真实存在吗？营业时间对吗？票价偏差超过阈值吗？

→ 对应节点 **`factcheck` 和 `hallucination`**。

> 💡「**用确定性规则、而不是用 LLM 判 LLM**」是个有水平的设计选择，面试官爱听。

---

### 问题 ⑤：从理解到出行程要几十秒，用户不能盯着空屏干等，怎么办？

整套流程跑完要几十秒。如果用户发个请求就在那转圈等 30 秒，体验极差，还容易超时。

**自然的解法（两条通道）**：

- 用户**发消息的请求**（POST）：后端**不干活，立刻回一句「收到了，在处理」（202）**，秒回。
- 真正的处理**丢到后台异步跑**；同时前端另开一条**长连接（SSE）**，后端把进度**一段段实时推**过去——「正在找景点…正在排路线…」，像直播一样。

→ 这就是「**202 异步 + SSE 流式**」，是整个「响应快」体验的来源。

> 术语：**SSE** = 服务器主动往浏览器单向推消息的长连接（基于普通 HTTP）。为什么不用 WebSocket？因为推进度是**单向**的（服务器→用户），SSE 更简单、还能自动重连。细节看 `02`。

---

### 问题 ⑥：很多人同时用会崩、LLM 调用很烧钱，怎么扛？

到这里功能全了。但**上线**还有两个现实问题：① 一堆人同时用，系统会被打垮；② 每次调 LLM 都花钱，不控制账单会爆。

**自然的解法（这就是简历上「高并发」那一坨的来由）**：

- **最前面放一个 Go 网关**当「保安」：所有请求先过它，做**鉴权**（你是谁）、**限流**（防狂刷）、**熔断**（后端挂了就快速拒绝，别拖死）。Go 写是因为它扛高并发网络快。
- **重活交给 Celery**（后台任务队列）：把「生成行程」丢给独立的 worker 进程去跑，崩了能重试、不丢任务。
- **缓存**：查过的景点/天气结果存起来，下次直接用，不重复花钱调。
- **成本治理**：简单任务走小模型、长对话压缩、**全局成本熔断**（今天花超预算就强制降级），见 `05`。

→ 这一层不改变功能，只保证**又快、又稳、又不烧钱**。

### 把六步连起来（这就是你要画在白纸上的东西）

```
用户一句话
  ① gathering   听懂需求、缺啥问啥         （LLM）
  ② retrieve    从知识库捞真实景点         （RAG / 向量检索）   ←┐ 这两步
     weather     顺手查天气                                      ├ 互不依赖，
                                                              ←┘ 并行跑
  ③ plan        把景点排成最优多天行程     （CP-SAT 求解器）★核心
  —— 先出「草稿行程」给用户看 ——
  ④ confirm_gate 暂停，等用户点「确认」      （人在环路 / 断点续跑）
  —— 用户确认后继续 ——
  ⑤ tool_call   查真实票价/酒店
  ⑥ factcheck + hallucination  两道事实防线 （写死规则，不用 LLM 判 LLM）
  ⑦ output      生成最终行程 + PDF/Excel

全程：POST 秒回 202，进度走 SSE 实时推；外面包 Go 网关 + Celery + 缓存 + 成本治理
```

**这张图你能默写出来、并说清每一步「为什么存在」，项目就算看懂了。** 上面这条链就是「数据流」，开场问「介绍一下项目 / 一个请求怎么走」时，照着 ①→⑦ 讲。

> 💡 两个最容易被夸的亮点，单独记住：
> - **并行**：②检索景点 和 查天气 互不依赖，LangGraph 让它们**同时跑**省时间。
> - **人在环路 + 断点续跑**：③出草稿后**暂停**等用户确认（`confirm_gate`），这个暂停状态**存进数据库**，所以用户关了页面再回来、或服务重启，都能**从暂停处接着跑**，不用重来。这靠 LangGraph 的 `checkpoint` 机制。

## 四、那 LangGraph 是什么？（把上面那张图变成代码的工具）

你可能会问：上面这条「①→⑦、还能并行、还能暂停」的流程，代码里怎么组织？

如果用一堆 `if-else` 手写，会乱成一团、暂停续跑要自己造轮子。

**LangGraph 就是专门干这个的编排框架**：它让你把流程画成一张**状态图**——每一步是一个**节点**，节点之间用**边**连接（还能按情况分支、并行、回退、暂停）。所有节点共享一个 **State（状态字典）**，数据在里面流动。

一句话：**LangGraph = 把「问题三」那张流程图，变成可控、可暂停、可恢复的代码。** 细节看 `02` 第 5 节。

> 💡 诚实加分点：如果被问「这算真 Agent 吗」，答「**结构化的 Agent workflow**——整体流程图是我设计死的（可控），但每个节点内部由 LLM 决策（听需求、判断要不要追问、核验事实）。没做成完全自主的 ReAct，是因为旅行规划要可控可降级」。这个「知道边界」的回答面试官很吃。

## 五、面试会顺着这条线问你（★ 追问地图）

你说「不知道会被问什么」——其实面试的提问是**有套路、有树状结构**的。几乎一定是这样走：

```
开场：「介绍一下你这个项目」
  └─ 你答「核心洞察」那句 + ①→⑦ 数据流（30秒~2分钟）
        │
        │  面试官会从你的回答里挑一个点往下钻，主要四个方向：
        │
  ├─【方向 A · 最高频】「为什么不用 LLM 排行程？求解器怎么做的？」
  │     → 这是项目最硬核的卖点，必被深挖。准备：VRP-TW 建模、约束、
  │       多目标加权、超时三层兜底（热启动/早停/贪心）。→ 看 03
  │
  ├─【方向 B】「RAG / 防幻觉怎么做的？」
  │     → 混合检索 + RRF 融合；两道确定性事实防线。→ 看 04
  │
  ├─【方向 C】「高并发 / 成本 / 可观测怎么搞的？」
  │     → 202+SSE、Celery、限流熔断、成本治理五招、缓存三连、
  │       可观测三支柱。→ 看 05
  │
  └─【方向 D · 压力题】「这是你一个人做的吗 / 这算 Agent 吗 /
        压测是真调 LLM 吗 / Redis 一鱼多吃有隐患吗」
        → 考诚实和边界感，别吹。标准答法 → 看 06 第六轮 + 红线清单
```

还有一类是 **「传统后端转 AI 你踩过什么坑」**（方向 E），如果你简历写了后端背景，大概率会问 → 看 `07`。

> 💡 用法：**开场答完，面试官钻哪个方向，你就调用对应那份文件的内容。** 你不需要一次背完所有，你需要的是「开场讲清主线 + 知道每个追问去哪取答案」。**06 是模拟考场，先盖住答案自己说，再对照。**

## 六、术语速查（卡壳时翻这里，一行大白话）

| 术语 | 一句话人话 |
|---|---|
| **LLM** | 大语言模型（如 DeepSeek/GPT），管「听懂人话、写通顺文案」，但**不擅长精确计算** |
| **Agent / 智能体** | 能自己分步骤、调工具、做决策来完成任务的 AI，不只是聊天 |
| **LangGraph** | 把 AI 工作流画成「状态图」的框架，支持并行/分支/暂停/续跑 |
| **节点 / State** | 流程图里的一步 = 节点；贯穿全程、各步共享的数据字典 = State |
| **VRP-TW** | 带时间窗的车辆路径问题，运筹学经典难题（NP-hard）——你的行程问题就是它 |
| **CP-SAT / OR-Tools** | Google 的约束求解器，专解上面这种数学难题，**保证算对、最优** |
| **NP-hard** | 一类「没有已知快速精确算法」的难题，规模一大就要靠求解器+技巧 |
| **约束 / 目标** | 必须满足的硬规则（营业时间）= 约束；想优化的东西（景点尽量多）= 目标 |
| **RAG** | 检索增强生成：先从知识库搜出真资料，再喂给 LLM，防它瞎编 |
| **embedding / 向量** | 把文字变成一串数字，**意思相近的数字也相近**，用来做语义搜索 |
| **pgvector** | 让 PostgreSQL 数据库能存向量、做向量搜索的扩展 |
| **hybrid 检索 / RRF** | 向量搜+关键词搜+结构化搜 三路并用；RRF 是把三路结果融合排序的方法 |
| **幻觉 (hallucination)** | LLM 一本正经地胡说（编造票价、不存在的景点） |
| **SSE** | 服务器单向、实时、一段段往浏览器推消息的长连接（推进度用） |
| **WebSocket** | 双向实时长连接，比 SSE 重；你项目主用 SSE，WS 作备选 |
| **202 / 异步** | HTTP 状态码「已收到，在处理」；先秒回 202，活儿丢后台慢慢干 |
| **FastAPI / async** | Python 异步 Web 框架；异步=等 LLM/数据库时能去服务别的请求，扛并发 |
| **Celery / broker** | Python 后台任务队列，把重活丢给 worker 进程跑；broker=存任务的地方（用 Redis） |
| **checkpoint / 断点续跑** | 把流程状态存进数据库，断了能从上次的地方接着跑 |
| **人在环路 (HITL)** | 流程中途暂停，等人确认/修改后再继续（你的 confirm_gate） |
| **限流 / 熔断** | 限流=防别人狂刷打爆我；熔断=下游挂了就快速失败，别被拖死 |
| **缓存三连** | 穿透/击穿/雪崩，三种缓存失效打垮数据库的经典问题（看 05） |
| **可观测三支柱** | Metrics 指标(Prometheus) / Tracing 链路(OTel) / Logging 日志，定位线上问题 |
| **网关 (gateway)** | 所有请求的「大门保安」，统一做鉴权/限流/熔断（你用 Go 写） |
