# TravelAgent 面试准备 · 05 高并发与可观测

"高并发"标题的兑现。限流/熔断、成本治理、可观测三件套、缓存八股——大厂尤其爱问。

---

## A. 限流与熔断(两道:网关 + 应用)

**限流(Rate Limit)**:防止有人狂刷打垮系统。你是**两层**:
- **主限流在 Go 网关**:所有流量入口统一限,Go 性能高。
- **应用层二次防护**:`RateLimitCostController` 再按用户/IP/配额校验。

📖 **限流算法八股**:
| 算法 | 怎么做 | 特点 |
|---|---|---|
| 固定窗口计数 | 每分钟计数,超了拒 | 简单,但窗口临界点会双倍突发 |
| 滑动窗口 | 窗口平滑移动 | 解决临界问题 |
| 漏桶 | 请求匀速流出 | 平滑流量,不允许突发 |
| **令牌桶** | 按速率发令牌,有令牌才放行 | **允许一定突发**,最常用 |

**熔断(Circuit Breaker)**:下游服务挂了/变慢,**快速失败**而不是干等,给下游喘息、防止雪崩。**三态**:
- **Closed(正常)**:请求通过,统计失败率。
- **Open(断开)**:失败率超阈值,直接快速失败,不打下游。
- **Half-Open(半开)**:隔一段放几个试探请求,成功→恢复 Closed,失败→回 Open。

**SSE 并发限制**:每用户最多 N 条并发 SSE,用 Redis 带 TTL 的 key 计数(网关主控 + 应用 `_track_sse_connection` 二次);重连同一会话刷新 TTL 而非占新槽,避免前端重连被误杀。

> 💡 **追问「限流和熔断区别」**:限流防**自己被打爆**(控入口流量);熔断防**被下游拖死**(下游故障时快速失败)。一个对外、一个对下游。

## B. 成本治理(LLM 应用特有,★ 很加分)

LLM 调用烧 token/GPU,这套是 TravelAgent 的特色,纯后端项目没有:

1. **model_router 模型分层**:简单意图(意图识别、闲聊)路由到**小模型**,复杂规划/写作才用大模型 —— 省钱又省时。
2. **prompt 压缩**:长对话按 `prompt_compress_max_messages/chars` 截断压缩,降 token。
3. **工具结果两级缓存**:**L1 本地内存 + L2 Redis**,命中就不重复调外部 API/LLM,有 `cache_hits/misses` 指标。
4. **成本熔断(cost circuit breaker)**:全局监控**日 Token/API/GPU 成本**,超预算就**强制降级到小模型**,保护账单。
5. **分级配额(user_tier + token_quota)**:游客/免费/会员不同配额,游客强制走小模型。
6. **external_api_tracker**:统计 Tavily 等外部 API 调用次数与成本。

> 💡 **追问「LLM 应用怎么控成本」**(标准答法):「五招:① 模型分层——简单任务走小模型;② prompt 压缩降 token;③ 工具结果两级缓存避免重复调用;④ 全局成本熔断——超日预算强制降级保护账单;⑤ 游客/会员分级配额。前两招降单次成本,后三招控总量。」—— 这套答下来,做过 LLM 应用的面试官立刻有共鸣。

## C. 缓存八股:穿透 / 击穿 / 雪崩(必问)

| 问题 | 是什么 | 解决 |
|---|---|---|
| **穿透** | 查一个**根本不存在**的 key,每次都打到 DB | 布隆过滤器拦截 / 缓存空值 |
| **击穿** | 某个**热 key 过期瞬间**,大量请求同时打 DB | 互斥锁(只放一个去重建)/ 逻辑过期 |
| **雪崩** | **大量 key 同时过期**,DB 被瞬间压垮 | 过期时间加**随机抖动** / 多级缓存 |

**缓存一致性**:更新 DB 后怎么处理缓存?主流 **Cache Aside**:先更 DB,再**删**缓存(不是更新缓存);极端场景用**延迟双删**(删→更DB→延迟再删一次)兜并发。

## D. 可观测三件套(各管一层)

📖 **可观测三大支柱:Metrics(指标)/ Tracing(链路)/ Logging(日志)**。

| 工具 | 类型 | 看什么 |
|---|---|---|
| **Prometheus** | Metrics | 聚合数值:HTTP/LLM 延迟直方图、token 用量、缓存命中率、成本、求解延迟、活跃 SSE 数 → Grafana 看板 |
| **OpenTelemetry** | Tracing | 一个请求跨多个服务的**调用链**,定位慢在哪一跳 |
| **LangSmith** | Agent 链路 | trace 每个 LangGraph 节点的 **LLM 输入输出**,debug prompt |
| **Loki** | Logging | 日志聚合 |

**一句话区分**:Metrics 看「系统跑得好不好」(聚合趋势),Tracing 看「单个请求怎么走的」(调用链),Logging 看「具体发生了什么」(明细)。

> ⚠️ **诚实提醒**:`structlog` 在依赖里但我没在 src 找到实际调用,**别说「结构化日志」**,被追问会露馅。说「Loki 做日志聚合」即可。

> 💡 **追问「线上一个慢请求怎么定位」**:「先看 Prometheus 哪个接口的 P99 高 → 用 OTel trace 看这个请求慢在哪一跳(LLM?DB?求解?)→ 如果是 Agent 内部,用 LangSmith 看是哪个节点的 LLM 调用慢或 prompt 异常 → 最后看 Loki 日志细节。」—— 三支柱串起来定位,标准答案。

## E. 高可用其他:K8s / 探针 / 混沌测试

- **HPA(水平自动扩缩容)**:按 CPU/QPS 自动加减 Pod 副本,流量高自动扩、低自动缩。
- **PDB(Pod 中断预算)**:滚动升级/节点维护时,保证**最少存活实例数**,不会一次全挂。
- **健康/就绪探针(`/health` `/ready`)**:K8s 用它判断 Pod 是否存活、是否能接流量(没就绪不给打流量)。
- **混沌测试(chaos)**:故意注入故障(触发成本熔断、外部 API 挂),验证**降级正确**——比如熔断后是否真降级小模型、游客是否强制小模型。

## F. 必背 + 追问

**必背**:
1. **限流**(令牌桶,网关主+应用二次)防自己被打爆;**熔断**(三态)防被下游拖死。
2. **成本治理五招**:模型分层 + prompt 压缩 + 两级缓存 + 成本熔断 + 分级配额。
3. **缓存三连**:穿透(布隆/空值)、击穿(互斥锁)、雪崩(随机过期)。
4. **可观测三支柱**:Metrics(Prometheus)/ Tracing(OTel)/ Logging(Loki)+ LangSmith 追 Agent。

**高频追问**:
- *限流算法有哪些?* → 固定窗口/滑动窗口/漏桶/令牌桶,你用令牌桶(允许突发)。
- *熔断三态?* → Closed/Open/Half-Open。
- *LLM 怎么控成本?* → 五招(见上)。
- *缓存穿透击穿雪崩?* → 见表。
- *Metrics 和 Tracing 区别?* → 聚合趋势 vs 单请求调用链。

> 📖 **八股底**:令牌桶/漏桶、熔断三态、缓存三连 + 一致性(Cache Aside/延迟双删)、可观测三支柱、HPA/PDB/探针。
