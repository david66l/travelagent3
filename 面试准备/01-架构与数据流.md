## A. 用大白话说清楚:这项目干嘛的

**一句话**:用户用大白话说旅行需求(「我想去上海玩 3 天,预算 2000,喜欢历史景点,带老人」),系统自动生成一份**可执行的多天行程**(每天去哪几个景点、几点到几点、怎么走、吃饭、花多少钱),并实时把规划进度推给用户。

**为什么这事不简单**(这是项目的「价值」,面试要能说清):

1. **听懂模糊需求** —— 用户说话不完整,得追问(「几月去?」「带不带小孩?」),靠 LLM。
2. **排出合理行程是个数学难题** —— 不是「LLM 拍脑袋列几个景点」就行。要同时满足:营业时间、闭馆日、预算、每天走多少路、必去的点、远的景点别和近的挤一天……这是**组合优化问题**,LLM 算不准,所以用了专门的**数学求解器**。
3. **不能瞎编** —— LLM 容易胡说票价、时间。系统加了**事实核验**层,逐字段校验。
4. **要快、要扛并发** —— 生成行程要几十秒,不能让用户干等;很多人同时用也不能崩。这就是「高并发」那套设计的来由。

> 💡 **面试开场模板**:「这是一个 AI 旅行规划 Agent。核心难点不是调 LLM,而是把『行程规划』拆成两半——**理解需求和润色文案用 LLM,但真正排行程用数学求解器(OR-Tools CP-SAT)**,因为多天行程要同时满足十几种约束,LLM 算不可靠。外面再包一套高并发的工程架构保证响应快、能扛量。」

## B. 整体架构:每个零件是什么、为什么需要它

```
用户浏览器 (Next.js 前端)
      │
      ▼
Go + Echo 网关  ← 大门保安:鉴权、限流、熔断
      │
      ▼
FastAPI 后端 (业务大脑)
   │        │            │
   ▼        ▼            ▼
PostgreSQL  Redis     LangGraph 编排
(持久化)  (缓存/队列/  (识别→检索→规划
          会话/状态)   →核验→输出 的流程图)
                          │
                          ▼
                  VRP Solver 微服务
                  (OR-Tools CP-SAT 算行程)

旁挂:Celery worker(后台跑重活)、可观测栈(Prometheus/OTel/LangSmith/Grafana)
```

| 组件 | 是什么 | 为什么要它 |
|------|--------|-----------|
| **Next.js 前端** | React 的全栈框架,做网页界面 | 用户聊天、看行程的界面 |
| **Go + Echo 网关** | Go 语言写的「大门」,Echo 是 Go 的 Web 框架 | 所有请求先过它:**JWT 鉴权**(验你是谁)、**限流**(防狂刷)、**熔断**(后端挂了快速拒绝,不拖死)。用 Go 写是因为性能高、且把「保安」和「业务」解耦 |
| **FastAPI 后端** | Python 的**异步** Web 框架 | 业务大脑,处理聊天、调 LLM、触发规划。「异步」=一个进程能同时处理很多请求不互相阻塞(对高并发关键) |
| **PostgreSQL** | 关系型数据库 | 永久存:用户、会话、消息、行程、规划任务,还有**向量**(靠 pgvector 扩展) |
| **Redis** | 内存数据库(快但断电易失) | **一鱼多吃**:① 缓存 ② Celery 任务队列 ③ 会话热状态 ④ SSE 并发计数 ⑤ 发布订阅(pub/sub)推消息 |
| **Celery + Beat** | Python 的**分布式任务队列**;Beat 是定时器 | 把「生成行程」这种耗时几十秒的重活丢到后台工人去干。**消息中间件用 Redis,不是 RabbitMQ** |
| **VRP Solver** | 独立小服务,内部用 **OR-Tools CP-SAT** | 专门解「行程路线优化」数学问题。拆成独立微服务是因为求解 CPU 密集,和主业务隔离 |
| **LangGraph** | LLM 应用的**编排框架**(LangChain 出的) | 把「理解需求→检索→规划→核验→输出」组织成一张**可控流程图**,而非一坨 if-else |
| **可观测栈** | Prometheus(指标)+ OTel(链路追踪)+ LangSmith(专追 Agent/LLM)+ Grafana(看板) | 线上出问题能定位:系统层看延迟/成本,Agent 层看每步 LLM 输入输出 |

> 💡 **追问:「为什么单独搞个 Go 网关,不在 FastAPI 里做鉴权限流?」**
> ① 职责分离——网关只管流量治理,后端只管业务,各自独立扩缩容;② Go 处理高并发网络 I/O 比 Python 强,放最前面当第一道防线;③ 限流/熔断这种保护逻辑统一在入口做,所有后端服务都受益。

## C. 一个请求从头到尾怎么走(★ 面试必挖)

**关键设计:两个通道。**

- **通道 1(POST)**:用户发消息 `POST /chat/message` —— 后端**立刻返回 202**(「收到了,在处理」),不等结果。
- **通道 2(SSE)**:前端另开一条**长连接** `GET /chat/stream` —— 服务器把规划进度**实时一段段推**过来。

**为什么要两个通道?** 生成行程要几十秒。一个普通请求干等会超时、用户盯着转圈。所以拆开:发消息的请求秒回,结果走另一条流式通道慢慢推。

完整流程(按时间顺序):

**① 前端先开 SSE 长连接** `GET /chat/stream?conversation_id=xxx`
→ 后端注册一个内存消息队列,把连接挂住,每 30 秒发 keepalive 心跳防断,等事件往里塞。

**② 用户发消息** `POST /chat/message`,后端依次:
1. **限流/配额/成本检查** —— 游客和会员配额不同,超了直接拒。
2. **感知层(多模态输入)** —— 用户传了**图片或 PDF**(行程截图、票据),用 **PaddleOCR / PyMuPDF** 抠出文字拼进输入。(加分点:Agent 不只吃文字)
3. **输入安全** —— 检测**提示词注入攻击**(有人想用「忽略前面的指令」骗 LLM),拦截并计数。
4. 把用户消息存进数据库。
5. **关键**:`asyncio.create_task(...)` 把真正处理**丢到后台异步跑**,然后**立刻 `return 202`**。

> 💡 这就是「首响应快」的原因:POST 不干活,只登记任务就返回。`asyncio.create_task` = 「起一个后台协程去干,我不等它」。

**③ 后台异步跑 LangGraph 流程**(真实节点):

```
gathering(理解需求,缺信息就追问)
    │
    ▼
profile_recall(召回用户历史画像)
    │
    ├──────────────┐   ← 并行!两条腿同时跑
    ▼              ▼
retrieve         weather_check
(检索景点POI)    (查天气)
    └──────┬───────┘   ← 汇合
           ▼
        plan(调 VRP Solver,用 CP-SAT 排行程)
           ▼
        output(先出「草稿行程」)
           ▼
     confirm_gate(★ 暂停!等用户点「确认」)  ← 人在环路
           ▼ 用户确认后
        tool_call(查真实票价/酒店/餐厅)
           ▼
       factcheck → hallucination(事实核验 + 幻觉检测)
           ▼
        output(最终行程)
           ▼
        booking(下单)
```

每跑一个节点,就通过队列往 SSE **推一个进度事件**(前端显示「正在检索景点…」「正在规划路线…」)。

**④ 面试官最爱挖的三个亮点**:

- **并行分支**:`retrieve`(检索景点)和 `weather_check`(查天气)互不依赖,LangGraph 让它们**同时跑**再汇合,省时间。
- **人在环路(confirm_gate)**:行程先出**草稿**,流程**暂停**(LangGraph 的 `interrupt` 机制),等用户点「确认/修改」再继续查真实票价、下单。暂停状态**存进 PostgreSQL**(靠 `langgraph-checkpoint-postgres`),所以服务重启、用户关页面再回来也能从暂停处接着走——**断点续跑**。
- **最终产物**:`output` 节点生成可下载的 **PDF(WeasyPrint)/ Excel(openpyxl)/ 地图**,URL 一起推给前端。

**⑤ 前端收到 `final` / `done` 事件** → 渲染完整行程 + 下载链接 → SSE 关闭。

> 💡 **答「讲一下你的数据流」**:照 ①→⑤ 讲,突出三个词:**202 异步**(快)、**SSE 流式**(实时进度)、**confirm_gate 人在环路 + checkpoint 断点续跑**(可控、可恢复)。

## D. 进阶:两种执行模式(真正的「高并发」底牌)

代码里留了**两种跑法**,用配置 `planning_executor` 切换:

1. **进程内模式(embedded)**:规划直接在 FastAPI 进程里用 `asyncio` 协程跑。轻量,适合小规模。
2. **Celery 解耦模式**:把规划任务丢给**独立的 Celery worker** 进程跑。worker 把进度写进数据库 + 用 Redis 发布订阅推给 SSE。一整套**可靠性设计**:
   - `acks_late=True`:任务执行完才确认,**worker 中途崩了任务会重新派发**,不丢。
   - `max_retries=10` + **指数退避重试**:失败了隔越来越久再试。
   - **死信队列(DLQ)**:重试耗尽或不可重试的错误,扔进死信队列人工排查,不阻塞。
   - **强制取消**:用户取消后,worker 若 30 秒没响应,定时任务强杀。

> 💡 **答「为什么用消息队列/Celery」**:「生成行程是耗时重任务,用 Celery 把它和 Web 请求解耦——好处是 ① 不堵塞 API ② worker 可独立水平扩容,加机器就能提吞吐 ③ 配合 acks_late + 重试 + 死信队列,worker 崩了任务不丢,保证可靠交付。」

## E. 必背三连

1. **它干嘛**:自然语言 → 多天行程;难点是用**数学求解器**而非 LLM 排行程。
2. **怎么架**:Go 网关(治理)+ FastAPI(业务)+ Redis(缓存/队列)+ PG(持久化)+ LangGraph(编排)+ CP-SAT(求解)。
3. **怎么流**:POST 秒回 202 → 后台异步跑 LangGraph(并行检索 + 草稿 + 人工确认 + 事实核验)→ SSE 实时推进度 → 出 PDF/Excel。
