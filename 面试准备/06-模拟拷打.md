# TravelAgent 面试准备 · 06 模拟拷打

把这当一次真实面试。**先盖住答案自己说一遍,再对照**。答不出的回去看对应章节。
答案是「口述风格」(简洁、第一人称),不是背书。

## 第一轮:开场(必考)

**Q1:介绍一下你这个项目。**

> **30 秒版**:「这是一个 AI 旅行规划 Agent,用户用大白话说需求,系统自动生成多天行程。核心设计是把规划拆两半——理解需求和润色用 LLM,但真正排行程用 OR-Tools CP-SAT 约束求解,因为多天行程要同时满足十几种约束,LLM 算不可靠。外面包了一套 Go 网关 + FastAPI + Celery + LangGraph 的高并发架构。」

> **2 分钟版**(在 30 秒基础上展开):「技术上分四块——① **编排**用 LangGraph,把理解需求、检索、规划、事实核验、人工确认串成一张状态图;② **规划**把行程建模成带时间窗的车辆路径问题(VRP-TW),用 CP-SAT 求解,配热启动和贪心兜底;③ **数据**用 pgvector 做混合检索找真实景点,再用两道确定性防线防 LLM 篡改事实;④ **工程**上 POST 秒回 202 + SSE 流式推进度,Celery 异步跑规划,还有成本熔断、模型分层、限流熔断、Prometheus/LangSmith 可观测。」

*考点:能不能结构化讲清,而不是流水账。*

## 第二轮:架构与数据流

**Q2:整体架构怎么设计的?**
> Go 网关(JWT/限流/熔断)→ FastAPI(业务)→ Redis(缓存/队列/状态)+ PostgreSQL(持久化,含 pgvector)+ LangGraph(编排)+ CP-SAT 微服务(求解),旁挂 Celery worker 和可观测栈。分层是为了职责分离和各自独立扩缩容。

**Q3:一个请求怎么走的?**
> 前端先开 SSE 长连接。用户发 `POST /chat/message`,后端做限流/感知层 OCR/输入安全检查,存消息后用 `asyncio.create_task` 把处理丢后台,**立刻返 202**。后台跑 LangGraph:理解需求→并行检索景点和天气→CP-SAT 排行程→出草稿→confirm_gate 暂停等用户确认→查真实票价→事实核验→出最终行程和 PDF。每步通过 SSE 实时推进度。

**Q4:为什么 Go 网关 + FastAPI 两层?**
> 职责分离:网关只管流量治理(鉴权/限流/熔断),Go 处理高并发 I/O 强;后端只管业务。保护逻辑统一在入口,所有后端服务受益。

**Q5:为什么用 SSE 不用 WebSocket?**
> 推进度是单向(服务器→用户),SSE 走标准 HTTP、自动重连、实现简单,够用。WebSocket 双向更重,需要双向实时才上。我项目 WS 也支持,作备选。

**Q6:返回 202 后前端怎么拿结果?**
> 走另一条 SSE 长连接。后端把规划进度和最终结果通过 SSE 一段段推过去,带 event_id 支持断线续传。

## 第三轮:求解(硬核,重点)

**Q7:行程怎么排出来的?为什么不用 LLM?**
> 建模成带时间窗的车辆路径问题(VRP-TW),用 OR-Tools CP-SAT 求解。不用 LLM 是因为多天行程要同时满足营业时间、预算、步行、必去点、闭馆日等十几种**硬约束**,LLM 没有硬约束概念,只能给"看起来合理"的结果,不保证可行和最优;求解器保证可行+最优+可复现。

**Q8:具体怎么建模?**
> 决策变量:每天去不去某景点、走哪条路线弧、到达时间。约束:AddCircuit 保证每天是从酒店出发回酒店的闭环、时间窗、时间传播、每天时长/预算/步行上限、必去点、整天景点、餐厅绑饭点不重叠、远郊隔离、闭馆日。目标是加权多目标,景点数权重最高、同类去重权重更高。

**Q9:多个目标冲突怎么平衡?**
> 两种手段结合:目标函数内部**加权求和**(精心设计权重层级,景点数 3000 压过车程,去重 6000 又压过景点数);外部用 **ε-约束法**,把步行差异、预算均衡等转成"不低于底线"的约束。

**Q10:求解超时/算不出来怎么办?**
> 三层兜底:① 热启动——先地理聚类猜个粗略分天作提示,让求解器精修而非从零找;② 收敛早停——跑过 45% 时间后改善小于 0.3% 就停;③ 贪心兜底——超时或无解自动降级贪心,小问题直接走贪心。保证最坏也秒级出可行结果。

**Q11(挖坑):CP-SAT 底层怎么求解的?**
> 诚实+有料:「CP-SAT 是约束规划求解器,底层把问题转成 SAT(布尔可满足)+ 线性规划松弛混合求解,用分支定界和约束传播剪枝。更深的内部算法细节我没研究到源码级,但我清楚它是精确求解器、能证明最优,这也是我选它而非启发式的原因。」

## 第四轮:RAG 与防幻觉

**Q12:你的 RAG 怎么做的?**
> 混合检索:结构化(预算/城市硬过滤)+ 向量(pgvector 语义)+ BM25(关键词)三路并行,用 RRF 倒数排名融合,取 top-k,空了有 fallback。向量模型用 BGE 中文 1024 维,本地跑。

**Q13:为什么 pgvector 不用 Milvus?**
> 本项目景点量不大,pgvector 让向量和结构化字段同库,一条 SQL 同时按相似度和预算过滤、事务一致、少维护组件。我另一个项目 PaperRAG 是 30 万文献规模,才用 Milvus——按场景选型。

**Q14:LLM 会胡说票价时间,怎么防?**
> 两道确定性防线:① fact_guard——求解器算出的时间/票价/坐标是真 facts,LLM 只润色,fact_guard 逐字段比对确保没被篡改;② hallucination_detector——把生成内容和真实工具数据交叉核验(POI 存在性、营业时间、票价偏差比例)。故意不用"LLM 判 LLM",省 token 又不引入新幻觉。

## 第五轮:高并发与成本

**Q15:高并发体现在哪?**
> 异步架构(202 + SSE + Celery 解耦)、Go 网关限流熔断、HPA 自动扩缩容、两级缓存、SSE 并发控制。k6 压测下 SSE 首事件 P99<500ms、单实例并发 SSE≥1000。

**Q16:LLM 很烧钱,怎么控成本?**
> 五招:模型分层(简单任务走小模型)、prompt 压缩、工具结果两级缓存、全局成本熔断(超日预算强制降级)、游客/会员分级配额。

**Q17:缓存穿透/击穿/雪崩?**
> 穿透——查不存在的 key,用布隆过滤器或缓存空值;击穿——热 key 过期瞬间打 DB,用互斥锁只放一个重建;雪崩——大量 key 同时过期,过期时间加随机抖动。

**Q18:线上请求很慢怎么排查?**
> Prometheus 看哪个接口 P99 高 → OTel trace 看慢在哪一跳 → Agent 内部用 LangSmith 看哪个节点 LLM 慢或 prompt 异常 → Loki 看日志细节。

## 第六轮:挖坑 / 压力题(★ 最关键)

**Q19:这项目你一个人做的?哪些是你写的?**
> (★ AI coding 的标准答法,诚实又强)「我个人主导的项目。需求拆解、架构选型、技术方案都是我定的;编码上我用 AI 工具加速实现——这也是现在很普遍的方式。但关键决策都是我把控的:为什么用 CP-SAT 不用 LLM 排行程、为什么 Redis 当 broker、两道事实防线怎么设计,我都能展开;踩的坑比如 big-M 调太小导致求解退化成贪心,也是我调出来的。AI 帮我写得快,但懂不懂是另一回事——任何一个模块您都可以往下深聊。」

**Q20:你这多 Agent 我觉得就是个 workflow,算 Agent 吗?**
> 「您说得有道理,我更愿意叫它**结构化 Agent workflow**:整体流程是我设计的图,可控可解释;但每个节点内部由 LLM 做决策——理解需求、判断是否需要澄清、核验事实。我没做成完全自主的 ReAct 循环,是因为旅行规划要可控可降级,纯自主 Agent 不可靠。所以是『编排可控 + 节点自主』的折中。」

**Q21:k6 压测并发 1000,LLM 是真调的还是 mock 的?**
> 诚实:「压的是网关、SSE、任务链路这套工程链路的并发能力,LLM 调用我用 stub 替代了——因为真调 LLM 受限于上游 API 的速率和成本,压不出系统本身的极限。所以那个 1000 是系统承载能力,不含 LLM 上游延迟。」(★ 千万别吹成真调)

**Q22:Redis 一鱼多吃(缓存+队列+broker),有隐患吗?**
> 「有,主要是单点和资源竞争风险。我做了 DB 隔离(broker、result、缓存用不同 db),生产会上 Redis 主从+哨兵做高可用。如果规模再大,会把队列拆到独立 Redis 实例,避免缓存压力影响任务队列。」

**Q23:成本熔断阈值怎么定的?**
> 「按日预算倒推:设一个日 Token/API 成本上限,接近阈值先告警,超了就强制全局降级小模型。阈值是根据测试期的日均消耗 + 余量定的,可配置。」

**Q24:为什么不直接接现成旅行平台 API,要自己排?**
> 「现成平台给的是搜索和单点预订,没有『把十几个约束放一起求最优多天行程』的能力——这正是我的核心价值。我也确实接了外部数据(搜索、天气、POI)做检索,但排程这步是自研求解器。」

## 诚实兜底模板(不会的题怎么答)

遇到真不会的,**别硬编**,用这个结构:
> 「这块我了解到 [我知道的部分],更深的 [具体方向] 我还没钻到。不过我的思路是 [给个合理推测/我会怎么查]。」

例:「Redis 持久化我知道 RDB 快照 + AOF 日志两种,生产一般结合用;AOF 的 fsync 策略细节我没深究,但我理解是在性能和不丢数据之间权衡。」

**面试官要的是边界清晰 + 有思路,不是全知。装懂被拆穿才是致命的。**

## 红线:这些话别说(会被当场拆穿)

- ❌ 「k6 并发 1000 是真调 LLM 压的」→ 说 stub。
- ❌ 「每一行代码都是我手写的」→ 说 AI 辅助 + 我主导决策。
- ❌ 「用了结构化日志 structlog」→ src 里没实际用,说 Loki 日志聚合。
- ❌ 「recall@5 100% 是生产指标」(这是 Paw 的)→ 说自建 golden set、小样本。
- ❌ 把"设计目标"说成"线上实测"——分清楚。
