# TravelAgent 面试准备 · 07 传统后端转 AI 我避开的坑

> 用来回答这类问题：你这套 AI 后端跟传统 Java/微服务后端有什么不一样？你踩过哪些坑、怎么避的？
> 底稿是《传统后端转 AI 的思维惯性问题》那 9 个坑，逐条对到我项目里。

那篇文章是 Java/Spring 视角列的坑。我的后端是 Python FastAPI 全异步，有些坑的机制在我这儿不一样，比如 JVM 的 Full GC、Tomcat 那 200 个线程的固定线程池，我根本没有。但底层道理是一样的。我把这些坑分三类讲：一类是我设计时当红线主动避开的，一类是靠选型直接绕过去的，还有一类是这套架构压根不会触发的。讲清楚哪条属于哪类，比每条都硬说"我解决了"更可信。

## 1. 长耗时 Agent 把分布式锁撑爆

传统惯性是用 Redis 的 `setNx` 加个 30 秒定时锁防并发冲突。问题是 Agent 跑一轮，带多步 Tool Calling 和反思，可能要 15 到 60 秒。网络稍微一抖，锁到期自动释放了，另一个节点以为前一个任务挂了又起一个，同一个会话里两个大模型同时写状态，数据库或者图状态就乱了。

我避的方式有两层。第一层，长任务的状态我不靠定时锁去扛，用 LangGraph 的 PostgresSaver 做检查点（`graph/graph.py` 里 `compile(checkpointer=...)`），每个节点跑完状态就落库，断了能从断点续跑，再配合 `interrupt` 节点做"等用户确认"的暂停和恢复。等于把这种有状态、长耗时、要可恢复的流程交给状态机引擎，而不是拿锁硬抗延迟。第二层，我确实也用了分布式锁，但锁只圈住"写状态"这一下（`core/memory.py` 的 `acquire_lock`），大模型生成那十几秒是在锁外面的，不会出现攥着锁等大模型的情况。

可以被追问的点：锁带了个后台续租，TTL 过一半续一次，但因为锁范围本来就短，续租更多是兜底。如果被问"为什么不上 Redlock 硬扛延迟"，我会答：用锁扛长延迟是治标，根因是这流程有状态、要能恢复，所以该上 checkpoint，不是把锁加得更重。

## 2. 把大模型调用塞进数据库事务里

这是最容易讲具体的一个。Java 里习惯在 Service 方法上随手挂 `@Transactional`。要是事务中间调了个 15 秒的大模型，Spring 会一直攥着那条数据库连接不放，二十来个并发就能把 HikariCP 连接池占满，然后整个系统其他不相干的业务，登录、查商品，全因为抢不到连接一起卡死。

Python 里对应的就是别让一个数据库 session 跨过 LLM 调用。我的 Celery 规划任务是"快进快出"：开一个短 session 写任务状态、commit、关掉，再到事务外面去跑求解和大模型，跑完之后另开一个新 session 把结果写回去。`worker/planning_worker.py` 整个就是一段段这样的短块：

```python
async with async_session_maker() as db:   # 开
    repo = PlanningJobRepository(db)
    await repo.mark_running(job_id)
    await db.commit()                      # 提交、连接还回池子
ai_result = await run_agent(job)           # 慢活在事务外面，不占连接
async with async_session_maker() as db:    # 写回时再开一个新的
    ...
```

连接被占用的时间就是几毫秒的写库，不是十几秒的大模型。这跟 Java 那边说的 `REQUIRES_NEW`、用 `TransactionTemplate` 显式控制事务边界是一个思路，只是 Python 异步里更直接，session 的生命周期我自己用 `with` 管。

## 3. 流式被统一拦截器或网关缓冲吞掉

传统后端一定有一层全局拦截器，把结果包成 `Result<T>`，有的还会在 Filter 里把完整 response 攒齐了再返回。流式接口碰上它就废了：大模型一个个吐出来的 chunk 会被在内存里攒到全部传完，再一次性发给前端，打字机效果没了，用户盯着空屏卡二十秒再啪一下全蹦出来。

我把流式路由单独拎出来，不套统一包装。FastAPI 用 `StreamingResponse`，`media_type` 是 `text/event-stream`，async generator 直接 `yield` 每个 delta（`api/v1/chat.py`、`agent_chat.py`）。更关键的是网关那层我把缓冲关了，`gateway/nginx.conf` 里这条路由配了 `proxy_buffering off`。很多人应用层写对了，结果栽在网关默认开缓冲上，症状跟没做流式一模一样，这一句一定要主动点出来。

追问方向通常是 SSE 和 WebSocket 怎么取舍，以及为什么 token 计费要放在流式的 finally 里，后面第 10 条会讲。

## 4. 超时时间和线程模型

微服务习惯配 3 到 5 秒超时，防下游拖死上游。套到大模型上，光首字延迟就一两秒，复杂 Agent 要三十秒。结果要么熔断器判超时直接误杀报 504，要么你把超时放大到 60 秒，Tomcat 那 200 个线程被这些慢请求占满，新进来的普通请求连线程都抢不到，服务假死。

FastAPI 全异步，没有那个固定线程池被占满的问题，大模型在等的时候事件循环就去服务别的请求了。超时我也分开配：大模型专用 60 秒（`llm_timeout`），工具调用 3 秒（`tool_timeout`），两条线互不干扰，不会拿微服务的短超时去卡大模型。

诚实的追问钩子：异步不是银弹。CPU 密集的活，比如 BGE 向量化、OR-Tools 求解，我是用 `asyncio.to_thread` 丢到线程里跑的。要是直接在事件循环里跑同步阻塞调用，照样会把整个服务卡住，异步反而更危险。

## 5. 盲目重试烧账单，还可能重复执行

传统 `@Retryable` 失败自动重 3 次，接口又便宜又快，用户基本无感。大模型不一样，一次调用可能几毛钱、十几秒，盲目重 3 次直接账单翻倍、用户多等一分钟。更麻烦的是非幂等：要是第一次其实已经成功了，比如已经通过 Tool Calling 下发了一条指令，只是回传文本时超时，你一重试它就再下发一次。

我对云端大模型默认不自动重试，`core/llm_client.py` 里非 vLLM 路径就是只调一次，只有自托管 vLLM 的 503 才重试几次。结构化输出解析失败也只补一次"修复 prompt"，不是无脑重跑整个方法。任务级的重试按异常类型分类（`core/task_retry.py`），参数错、权限错这种重一百次也没用的直接不重，只有限流和 5xx 才重。

主动交代的边界：我现在的工具都是只读查询，POI、天气、价格，所以进重试循环是安全的。如果以后加"下单、预订"这种写操作工具，得单独上幂等键、不能直接套重试。这点自己说出来，比被面试官挖出来好。

## 6. 记忆无限膨胀

传统请求里 new 出来的对象朝生夕死，用完就被回收。但 Agent 的多轮上下文要常驻，每聊一句 message 列表就变长，RAG 还会把几万字文档塞进去，几千个会话一起聊，这些"超长记忆"就把内存撑爆，JVM 那边表现就是频繁 Full GC 卡顿。

我做了三层。最近的对话只在会话里留 10 条原文，滑动窗口，超了就滚掉。真正的长期偏好不靠聊天历史扛，是结构化抽取进 `profile` 的，不吃辣、喜欢慢节奏这些存成字段，跨行程也还在。每次调大模型之前再过一道压缩（`core/prompt_compress.py`）：近窗原文保留，更早的折成一条摘要而不是直接丢掉，单条超长的留头尾、挖中间，避免把结论或者 JSON 的闭合括号切断，system prompt 永远不动。

这里有个能体现判断力的取舍：我刻意没上 LLM 滚动摘要那套重方案。因为长期记忆已经被 profile 抽取兜住了，再加一层摘要会给每次调用增加延迟和成本，属于该省的地方。我留了个可注入的 summarizer 口子，真碰到超长多轮场景，插一个 LLM 摘要进去就行。知道什么时候不该加，和知道怎么加一样重要。

## 7. 向量库的"伪更新"

Milvus、Pinecone 这类专用向量库为了搜索快，底层是读写分离、异步建索引的。你 `upsert` 完数据不一定立刻生效，下一微秒拿着同一个 id 去查，可能查出来还是旧向量，Agent 就会基于过期数据做出错误的二次决策，甚至卡进循环更新。

这个坑我是靠选型绕过去的。我用的是 pgvector，它就是 Postgres 的一个扩展，写完即时可读、强一致，没有异步索引滞后那回事。而且那篇文章建议的"向量库只当只读搜索引擎、真值放 Redis 或 MySQL"，在我这儿天然成立，因为召回和真值本来就在同一个 Postgres 里，不存在两套存储对不上。

要讲就讲清代价：pgvector 的召回性能和水平扩展不如专用向量库，数据量到千万级、QPS 很高的时候得换 Milvus，那时候才需要认真处理最终一致性。我选 pgvector，是因为我这个量级下强一致加上少维护一套组件更划算。这是带着取舍做的选型，不是不知道有专用向量库。

## 8. GPU 批处理，这个坑老实说不在我场景里

自己本地部署 Embedding 或者大模型时，GPU 是按批处理算的。你在应用层开 100 个线程并发怼显卡，显存会瞬间爆，直接 CUDA OOM 把进程带崩。控制点得从线程池挪到 GPU 队列，做动态批处理，把 0.1 秒内进来的请求打包成一个矩阵一次喂进去。

我的情况是没有自己扛高 QPS 的推理。向量化用 BGE，是把整个文本列表一次交给 sentence-transformers，它内部自己 batch，再用 `to_thread` 卸到线程，不在应用层开一堆线程硬并发。大模型主力走云端 DeepSeek，批处理是云那边的事。如果要自托管，我用 vLLM，它的 continuous batching（`Dockerfile.vllm` 里 `--max-num-seqs 256`）本身就是文章说的那套动态批处理，在引擎层撮合请求成批喂显卡。

所以这条我不会硬说"我解决了 GPU OOM"，而是说"我的架构没把这个压力放在应用层，真要自托管我会用 vLLM 的连续批处理来接"。诚实，而且正好踩在点子上。

## 9. 可观测性盲区

传统的 SkyWalking、ELK，按 TraceId 把 Controller 到 Service 到 DAO 串起来就够了。但 Agent 一次请求在后台是自己套娃：先思考，调工具，看结果，不满意再调一个，再反思，最后才返回。你只看传统日志，这一秒里就打了一条入参一条出参，中间它为什么走偏、为什么调错工具、为什么死循环，全抓不到。

我在普通日志之外单独上了 Prompt 级的链路追踪。LangSmith 记每一步的 prompt、返回、token 数；我自己还有个 `thought_logger` 把每个节点的思考、工具回调、耗时、token 结构化落盘，存成 JSON 加 Markdown 可以回放；再加 OpenTelemetry。出了问题能像看录像回放一样，看 Agent 每一步在想什么、在哪一步脑抽了。

这块我做得偏厚，三套有重叠，真要精简可以合并。但从面试角度，能讲清"为什么 Agent 的可观测性要做到 prompt 粒度、而不是接口粒度"，本身就是加分项。

## 10. 限流降级和 token 的实时计费、断线扣费

文章目录里还点了两个架构师级的死结：大模型流式输出的时候怎么限流降级，以及用户中途断线了，这部分已经产生的 token 怎么算钱。

成本侧我有个全局成本熔断（`core/cost_circuit_breaker.py`），按天统计 token、外部 API、GPU 花费，超阈值就降级，比如回退小模型或者拦住新请求。用户侧有 token 配额（`core/token_quota.py`）。断线扣费这点，我是把 token 统计放在流式的 `finally` 块里（`llm_client.py` 的 `stream_chat`），不管前端是正常收完还是中途断开，只要这次调用在服务端跑过，已经产生的 token 都会被记账，不会因为断线就漏算。

实现上的钩子：流式的用量是靠 `stream_options` 的 `include_usage` 在最后一个 chunk 里拿到的，所以哪怕连接断了，`finally` 也能兜住把它记下来。

## 还能更好的地方，以及我的取舍

主动交代几个没做满的点，比被问出来强：

记忆压缩现在是窗口加摘要折叠，没上 LLM 滚动摘要，是因为 profile 抽取已经兜住了长期记忆，属于刻意不做，不是没想到。

可观测性三套工具有重叠，能合并精简，现在偏重。

工具重试是安全的，但这个安全建立在"工具都是只读查询"这个前提上，一旦加写操作就要重新设计幂等。

把这套讲清楚，传达的不是"我堆了多少组件"，而是"我知道 AI 后端和传统后端的边界在哪、每个决定为什么这么做、什么地方该省"。这才是面试官真正想听的。
