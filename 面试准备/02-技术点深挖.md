## 1. SSE vs WebSocket vs 轮询

**SSE 是什么**:Server-Sent Events,服务器主动单向推送给浏览器。本质是一条**不关闭的 HTTP 响应**,服务器源源不断往里写文本,格式 `event: xxx\ndata: {...}\n\n`。浏览器用 `EventSource` 接收。

| 方式 | 怎么工作 | 缺点 |
|------|---------|------|
| **短轮询** | 前端每隔几秒问一次「好了吗」 | 浪费请求、延迟高 |
| **长轮询** | 问一次,服务器 hold 住到有数据才回 | 每条消息一次连接,开销大 |
| **SSE** | 一条长连接,服务器持续单向推 | 只能服务器→客户端、只能文本 |
| **WebSocket** | 一条长连接,双向全双工 | 要协议升级握手、比 SSE 重、代理有时不友好 |

**为什么用 SSE 推进度**:规划进度是**单向**的(服务器→用户),不需要用户过程中频繁回话。SSE 比 WebSocket 简单、走标准 HTTP(网关/CDN/代理都支持)、断了**浏览器自动重连**。

> 注:项目其实 **WebSocket 也支持**(`api/websocket.py`),ConnectionManager 同时管 WS 和 SSE。可说「主推 SSE,WS 作双向场景备选」。

**项目里的 SSE 细节(讲出这些就很深)**:
- **断线重连续传**:每事件带 `id:`(event_id),前端重连带 `Last-Event-ID`,服务器从该 id 之后继续推,不丢。
- **keepalive 心跳**:30 秒没数据发一行 `: keepalive`,防连接被代理掐断。
- **pending 缓冲**:事件在前端还没连上时就产生了,先缓存内存,等 register 回放,不丢早期 token。
- `X-Accel-Buffering: no`:告诉 Nginx 别缓冲,立即转发(否则进度一坨一坨而非实时)。

> 💡 **追问「SSE 和 WebSocket 区别 / 为什么不用 WS」**:SSE 单向、基于 HTTP、自动重连、实现简单;WS 双向全双工但更重。推进度是单向场景,SSE 够用且更稳。需要双向实时(协同编辑)才上 WS。

📖 **八股底**:SSE 基于 HTTP/1.1 长连接;HTTP/1.1 下同域名浏览器并发连接 ~6 条,大量 SSE 要注意(HTTP/2 多路复用可缓解)。

## 2. FastAPI + asyncio(为什么不用 Flask)

**FastAPI 是什么**:Python 现代 **异步** Web 框架,底层 Starlette(ASGI)+ Pydantic(数据校验)。

**asyncio / async-await(大白话)**:处理请求时大量时间在「等」——等 LLM、等 DB、等外部 API。同步代码(Flask)等的时候**整个线程干等**。异步代码用 `async/await`,等 A 时切去处理 B,**一个线程内并发处理成百上千个「等待中」的请求**。背后一个 **事件循环(event loop)** 在调度协程。

**为什么选 FastAPI 不选 Flask**:
1. **原生 async** —— 业务全是 I/O 等待,async 能在等待时处理别的请求,**高并发吞吐高得多**。Flask 同步 WSGI,一个请求占一个 worker。
2. **Pydantic 数据校验** —— 请求/响应自动按类型校验。
3. **自动 OpenAPI 文档**(Swagger)。

**项目里**:全链路 async —— `asyncpg`、async SQLAlchemy、async Redis,配 `asyncio.create_task` 起后台任务。

> 💡 **追问「async 一定比同步快吗 / 什么时候不该用」**:async 只对 **I/O 密集** 有用。**CPU 密集**任务(CP-SAT 求解、OCR)会**阻塞事件循环**,拖垮所有请求——所以项目把求解拆成**独立微服务/Celery**,不卡 FastAPI。这就是 VRP solver 单独成服务的原因。

📖 **八股底**:
- Python 有 **GIL**,同一时刻只一个线程执行字节码,多线程救不了 CPU 密集;async 是**单线程协程并发**,救 I/O 等待。
- 阻塞事件循环的坑:async 函数里调同步重计算 / `time.sleep` 卡死整个 loop。正解:丢线程池(`run_in_executor`)或独立进程/服务。

## 3. Redis(为什么一鱼多吃 + 持久化 + 为什么快)

**Redis 是什么**:基于内存的键值数据库,数据在内存所以**极快**。支持 string/hash/list/set/zset/stream 多种结构。

**项目里一鱼多吃**:
1. **缓存** —— 工具结果、热数据,减少重复调用。
2. **Celery 队列** —— list/stream 存待执行任务(db1),结果存 db2。
3. **会话热状态** —— 当前对话状态(hot 层),读写快。
4. **SSE 并发计数** —— 带 TTL 的 key 记每用户活跃 SSE 数,限流用。
5. **pub/sub** —— Celery worker 把进度 `publish` 到频道,SSE 连接 `subscribe` 转发前端。

**为什么快**:① 数据在内存;② **单线程**执行命令(避免锁开销和竞争);③ I/O 多路复用(epoll)高效处理大量连接。

**内存数据库怎么持久化(怕断电丢)**:
- **RDB**:定时把内存**快照**dump 磁盘。小、恢复快;宕机丢最后一段。
- **AOF**:把每条**写命令**追加日志,恢复时重放。更不易丢,但文件大、恢复慢。
- 生产常**两者结合**。

> 💡 **追问「pub/sub 和队列(list)区别」**:pub/sub **发完即忘**——没订阅者在线就丢,不持久化;队列消息留着等消费。项目里:**进度推送用 pub/sub**(实时、丢了无所谓,还有 DB 轮询兜底),**任务派发用队列**(不能丢)。

📖 **八股底**:Redis 单线程指「命令执行」(Redis 6 后网络 I/O 多线程);TTL 过期 + 内存淘汰(LRU/LFU);缓存三连(穿透/击穿/雪崩)——第 5 块细讲。

## 4. Celery + 消息队列(任务队列八股)

**Celery 是什么**:Python **分布式任务队列**框架。把耗时活从主流程剥离,丢后台 worker 异步执行。

**核心角色**:
- **Broker(消息中间件)**:存「待执行任务」。你用 **Redis**(db1)。
- **Result Backend**:存「任务结果」。也用 Redis(db2)。
- **Worker**:干活进程,从 broker 取任务执行。
- **Beat**:定时调度器,按时往队列塞周期任务。

**一次任务生命周期**:API 调 `execute_planning_job.apply_async(job_id)` → 进 Redis 队列 → worker 取出执行 → 进度写 DB + Redis pub/sub → 结果存 backend。

**项目的可靠性设计(重点背)**:
- `acks_late=True`:**执行成功后才确认**。worker 半路崩了,任务**没确认会重投**别的 worker —— 保证「至少执行一次」。
- `max_retries=10` + **指数退避**:失败重试,间隔越来越长,避免雪崩重试。
- **死信队列(DLQ)**:重试耗尽 / 不可重试错误,推 DLQ 单独存,人工排查,不阻塞正常队列。
- **强制取消**:用户取消后 worker 30 秒不响应,定时任务 `enforce_cancel_deadline` 强杀。

> 💡 **追问「acks_late 的代价 / 为什么要幂等」**:`acks_late` 不丢任务,但代价是**可能重复执行**(崩在确认前被重投)。所以任务必须**幂等**——执行两次效果同一次。你代码里 `execute_job_by_id` 先「认领」job(claim),已在跑/已完成的不重复跑,就是为幂等。

> 💡 **追问「为什么 Redis 当 broker 不用 RabbitMQ」**:Redis 当 broker 够用且少维护一个组件(项目已重度用 Redis);RabbitMQ 在复杂路由、严格可靠投递上更强,但本项目任务模型简单,Redis + acks_late + DLQ 已满足可靠性。

📖 **八股底**:投递语义 at-most-once / at-least-once / exactly-once;at-least-once + 幂等 ≈ 工程 exactly-once;死信队列;可见性超时。

## 5. LangGraph(到底是什么,和直接调 LLM 的区别)

**LangGraph 是什么**:LangChain 团队的 **Agent 编排框架**,把复杂 LLM 流程建模成**状态图(StateGraph)**:
- **节点(node)**:一步操作(理解需求、检索、规划、核验……),读写共享 **State**(状态字典)。
- **边(edge)**:节点怎么走。**条件边**按 State 决定下一步(分支)。
- 支持 **并行**(多节点同 superstep)、**循环**(回退)、**中断 interrupt**(暂停等人)、**checkpoint**(存档续跑)。

**和「直接写代码调 LLM」的区别(关键)**:

| 直接 if-else 调 LLM | LangGraph |
|---|---|
| 逻辑散在一堆代码,难维护 | 流程是**显式的图**,清晰 |
| 自己管状态传递 | 统一 **State** 贯穿全程 |
| 暂停/续跑/回退自己造轮子 | 内置 **interrupt + checkpoint** |
| 并行/分支自己写调度 | 内置条件边、并行 |

**为什么 Agent 适合用图**:Agent 流程**不是直线**——要按 LLM 输出决定下一步(分支)、要能暂停等确认(中断)、要能核验失败回去重做(循环)。这些用图表达最自然。

**项目里**:`build_graph()` 注册 gathering、profile_recall、retrieve、weather_check、plan、confirm_gate、tool_call、factcheck、hallucination、output、booking 等节点;retrieve∥weather_check 并行;confirm_gate 用 interrupt 暂停;checkpoint 存进 PostgreSQL。

> 💡 **追问「LangGraph 和 LangChain 区别」**:LangChain 偏「**链**」——线性串组件,适合固定流程;LangGraph 是「**图**」——支持循环、分支、状态、中断,适合**有状态、要决策、要人机交互**的 Agent。简单 RAG 用 LangChain 够,复杂 Agent 用 LangGraph。

> 💡 **追问「你这算真 Agent 吗,还是 workflow」**(诚实且有水平):「更偏**结构化的 Agent workflow**:整体流程是我设计的图(可控、可解释),但每个节点内部由 LLM 决策(理解需求、判断是否澄清、核验事实)。没做成完全自主的 ReAct 循环,是因为旅行规划要可控、可降级,纯自主 Agent 不可靠。」——「知道边界」面试官很吃这套。

📖 **八股底**:superstep(类 Pregel 图执行模型)、State reducer(多节点写同字段怎么合并)、checkpointer(MemorySaver / PostgresSaver)。

## 本块必背

1. **SSE**:单向、HTTP、自动重连——推进度最优解;WS 双向更重。
2. **FastAPI/async**:救 I/O 等待,不救 CPU(GIL);CPU 密集(求解/OCR)要拆出去。
3. **Redis**:内存所以快(单线程+epoll);一鱼多吃;RDB+AOF 持久化;pub/sub 发完即忘 vs 队列不丢。
4. **Celery**:broker(Redis)放任务、backend 放结果;acks_late 不丢任务但要幂等;DLQ 兜底。
5. **LangGraph**:把 Agent 流程建成有状态的图,内置分支/并行/中断/续跑;比 if-else 调 LLM 可控可维护。
