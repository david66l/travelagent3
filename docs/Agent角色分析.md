# TravelAgent2 Agent 角色与职责分析

## 一、当前架构中的「Agent」现状

项目名为 TravelAgent，但严格来说，当前架构**不是真正的 AI Agent**，而是**确定性管线 + LLM 点缀**。

```
用户输入 → IntentRecognitionAgent(LLM)
         → RealtimeQueryAgent(并行工具调用)
         → PlanningPipeline(纯算法, 无LLM)
         → RuleValidator(规则引擎)
         → EnrichWriter(LLM润色)
         → 输出
```

当前有两个"Agent"类：

| 组件 | 职责 | Agent 程度 |
|---|---|---|
| `IntentRecognitionAgent` | LLM 理解用户意图 + 实体抽取 | ⭐⭐⭐ 真正的 Agent 推理 |
| `RealtimeQueryAgent` | 编排并行 POI/天气/价格查询 | ⭐⭐ 工具编排，但无决策 |
| `PlanningPipeline` | 确定性算法排程 | ⭐ 不是 Agent，是管道 |

## 二、旅游 Agent 应该做什么

一个真正的旅游 AI Agent 不是"生成行程的工具"，而是**用户的私人旅行顾问**。核心能力：

### 🎯 角色一：需求分析师（Conversation Designer）

**做什么**：像旅行社顾问一样，通过多轮对话挖掘用户真实需求。

```
❌ 现在: 「杭州3日游」→ 直接生成行程
✅ 应该: 「杭州3日游」
        → 「几月去？杭州春天有龙井茶季，秋天满城桂花」
        → 「喜欢爬山还是闲逛？灵隐寺要爬台阶哦」
        → 「有老人小孩吗？我可以调整节奏」
        → 生成个性化行程
```

**需要的能力**：
- 感知信息缺口（destination 有了，但缺 travel_dates、pace）
- 主动追问（不是等用户说，而是引导用户说）
- 根据上下文推荐（"既然你喜欢美食，杭州的知味观必去"）

### 🎯 角色二：行程规划师（Itinerary Planner）

**做什么**：基于需求生成合理、可执行的行程。

```
当前已做到 ✅（确定性算法 + 修复引擎）
待加强 🟡：加入 LLM 做「软决策」—— 比如「西湖和灵隐寺谁先谁后」由 LLM 根据天气/人流量/用户体力判断
```

### 🎯 角色三：知识顾问（Travel Knowledge Base）

**做什么**：回答旅行相关问题，提供深度建议。

```
❌ 现在: 「推荐游览西湖」（无信息量）
✅ 应该: 「西湖十景中最推荐断桥残雪和苏堤春晓，春天桃花盛开时最美。
        建议早上8点前到，避开旅行团。步行一圈约3小时，可以在楼外楼吃午饭。」
```

**需要的能力**：
- 景点深度知识库（历史/季节/最佳时间/注意事项）
- 本地生活 tips（排队时间/性价比/隐藏玩法）

### 🎯 角色四：执行协调器（Task Orchestrator）

**做什么**：根据当前状态决定下一步做什么。

```
当前架构是硬编码的 pipeline: intent → data → plan → validate → write
真正的 Agent 应该根据上下文动态决策:

if 用户第一次用 and 没说目的地:
    → 推荐热门目的地，等待选择
elif 用户说了目的地但没时间:
    → 追问日期
elif 信息齐全:
    → 生成行程
elif 用户说「第三天换一个」:
    → 不需要重新走完整 pipeline，只修改第三天
```

### 🎯 角色五：记忆管理者（Memory Manager）

**做什么**：记住用户偏好，跨会话复用。

```
❌ 现在: 每次都是新对话，不知道用户喜欢什么
✅ 应该: 
  - 上次你说喜欢自然风光，这次推荐了杭州西溪湿地
  - 你之前去过西湖了，这次不重复安排
  - 饮食偏好「不吃辣」已保存，所有目的地都会避辣
```

**需要的能力**：
- 短期记忆（本次对话上下文）
- 长期记忆（历史行程/偏好/feedback）
- 偏好推理（从行为中学习，如"3次生成都删了购物环节→不喜欢购物"）

### 🎯 角色六：异常处理者（Graceful Degradation）

**做什么**：外部服务挂了也能优雅降级。

```
当前已做到 ✅（POI 查询失败→内置数据 fallback）
待加强 🟡：降级时主动告知用户
  → 「实时天气暂时获取失败，生成了基于历史气候的建议行程」
```

## 三、当前差距分析

| Agent 角色 | 完成度 | 差距 |
|---|---|---|
| 需求分析师 | 🔴 20% | 不会主动追问，不会引导，「去杭州3天」直接生成 |
| 行程规划师 | 🟢 80% | 规划核心很好，缺 LLM 软决策和天气/人流量感知 |
| 知识顾问 | 🔴 10% | 描述全是模板/LLM 通用输出，无真正的景点知识 |
| 执行协调器 | 🔴 15% | 硬编码 pipeline，无法动态调整流程 |
| 记忆管理者 | 🟡 50% | 有双层记忆架构，但未在对话中真正利用偏好 |
| 异常处理者 | 🟢 70% | fallback 机制完善，但用户无感知 |

## 四、改造路线图

### 短期（让 Agent 真正「对话」起来）

1. **主动追问引擎**：在 IntentRecognitionAgent 后增加「信息完整性检查」，缺口 > 2 时不进入规划，先追问
2. **上下文感知推荐**：根据已收集的偏好（interests/food_preferences）在追问中推荐具体 POI
3. **知识库注入**：将 P0 的模板描述作为 Agent 的知识来源，追问和回答时引用

### 中期（让 Agent 学会「思考」）

4. **动态流程控制**：用 LLM 决策下一步做什么，而不是硬编码 pipeline
   ```
   while not done:
       state = analyze(user_input, conversation, profile)
       action = llm.decide(state)  # "追问" / "生成行程" / "回答知识" / "修改行程"
       execute(action)
   ```
5. **偏好学习**：从用户行为中推理偏好（删了某个景点→不喜欢这类，加了某类→喜欢）

### 长期（让 Agent 成为「顾问」）

6. **多模态交互**：支持图片（"帮我看看这个景点值得去吗"）
7. **实时数据接入**：天气/人流量/排队时间，影响行程推荐
8. **行程对比**：生成 A/B 两套方案让用户选
