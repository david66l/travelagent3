## 1. 你现在在训练什么

不是让小模型背更多旅游知识，而是让它在每一步都能作出更好的选择：

> 我现在知道什么 → 还缺什么 → 用哪个工具 → 用什么参数 → 结果能不能信 → 下一步继续、调整、追问还是结束。

知识和实时事实由工具提供，时间和预算由求解器、校验器检查。小模型学习如何组织这些能力完成任务。

架构详见 `AGENT_HARNESS_ARCHITECTURE.md`（交付目录中的文件名为《Agent Loop + Harness 架构说明》）。目前只有一个 loop，在线与训练复用；旧阶段、控制器代答与专用训练环境已移除。

## 4. 怎样判断问题属于模型还是系统

看完整的“状态—动作—执行结果”记录，不只看最终答案。

- 模型选错工具、日期或关键词：模型决策错误。
- 模型选对了，但 provider 返回错误或工具吞掉参数：工具/执行错误。
- 模型拿到了充分证据，状态里却没展示：状态投影错误。
- 模型没提交或未通过校验，奖励却给成功：评测/奖励错误。
- 模型被拒绝后无法从错误中知道哪里有问题：harness 反馈问题。

先修系统错误，再拿模型错误做训练数据。否则训练会让模型迁就系统缺陷，效果也解释不清。

## 5. 数据怎么做才有价值

同时保留两种样本：完整任务轨迹，以及来自真实失败点的局部纠错样本。

完整轨迹让模型学习连续决策。局部纠错帮助它区分“重复同一无效查询”和“根据证据改参数”。教师提出的动作必须通过同一个 harness 实际执行，不能仅凭流畅解释就当作正确标签。

训练只优化模型应输出的动作与参数。工具响应、系统注入的城市/实体、真实约束、校验结果不应成为让模型编造的目标。当前轨迹保存原始模型参数和实际执行参数，便于审核。

按任务来源、城市组合、场景模板和事件实体分组拆分 train/dev/test。相同案例改写措辞不应跨集合。最终测试锁住，只用于验收；本次的 24 个诊断案例属于开发用途，不把这些案例及其同源变体的正确答案直接加入训练目标；示范从另造的任务中采集。

数据规模先做小批人工审核，再扩大。不要一开始生成几万条而没有逐条执行和质量门槛。

## 6. SFT 怎么做

SFT 可以理解为“照着正确示范学习”。这次基模已能稳定生成合法调用，第一批训练重点改为读证据、纠正无进展操作、处理不可行约束，以及从求解走到校验和提交；格式保留为回归指标。

使用完整轨迹时，只对助手输出的决策计算训练损失，工具返回与用户消息不参与目标损失。保留正确的 tool-call ID、角色顺序和模型原生模板。离线局部样本不能被包装成“模型自己从头完成了任务”。

每次实验登记基础模型与 tokenizer、模板、数据版本、代码版本、超参数、随机种子、训练时间和 checkpoint。用相同任务、工具预算和解码设置比较训练前后。

如果只提高格式合法率，却没有提高完整任务成功率，就不能宣称决策能力已提升。分别报告两者。

## 7. 为什么还要自主运行后纠偏

模型看着教师写好的前半段容易答对，但自己从第一步开始可能选另一条路径。让学生从真实起点运行，收集它实际到达的失败状态，再由教师示范可执行的修正。

例如：学生第一次查询已经错了，后面的问题不是“怎样润色答案”，而是“是否能根据错的观察改查询”。这类样本比不断重复教师顺畅轨迹更接近你的目标。

## 8. GRPO 什么时候值得做

GRPO 可以理解为“同一任务尝试多次，依据可验证结果比较哪些尝试更好”。它不是 SFT 的必选装饰。

先满足：模型能稳定调用工具；部分任务有成功也有失败；工具快照稳定；奖励已审计；预算允许完整多步 rollout。全部失败的组常常学不到方向，应该先补接口或示范；全部轻松成功的组需要提高难度。

当前只保留完整 episode 的 `travel` 环境。旧 controller_first、policy_driven、专门从某一步开始的教师前缀环境不再运行。`grpo_decision_state` 旧语料需要重新生成。

奖励首先看硬约束和任务结果，其次才是效率。未完成任务不能因为调用少而拿高效率奖励。模型必须明确提交通过校验的草案，才能获得“有效行程”结果；正确澄清、正确拒绝需要独立统计，不能与旅行规划完成率混为一谈。

用户确认不由模型伪造。需要多轮用户回复的任务，应显式回放预设回复并继续同一会话，而非自动替用户作答。

## 9. 最终至少报告这些数字

| 指标 | 要回答的问题 |
|---|---|
| 完整任务成功率 | 从原始请求开始，是否得到满足要求的提交结果 |
| 硬约束通过率 / 越权率 | 是否偷偷改预算、日期、必去项或约束 |
| 参数合法率与语义正确率 | 格式正确之外，参数是否真的适合任务 |
| 证据识别与恢复成功率 | 遇到不相关、过期和失败结果能否恢复 |
| 不必要提问 / 过早结束率 | 是否把问题推给用户或提前提交 |
| 工具调用、token、延迟与成本 | 改善需要付出多少代价 |
| 重复运行波动 | 成绩是否依赖一次好运气 |

先报告样本量和原始计数，再给百分比。规模足够时提供区间估计和分场景结果。安排一组证据变化案例：改变关键工具结果，看模型是否相应改变动作，排查背固定顺序。

## 11. 目标调整：面向 Agent 后训练相关岗位（2026-09-05）

你的目标由 AI 应用开发进一步明确为后训练相关岗位。建议以 Agent 后训练 / 应用算法为项目主线：研究在同一 Agent Loop 与工具环境中，小模型能否通过训练改善证据使用、工具选择、失败恢复和终止决策。项目验收需要包括训练原理、训练实现、数据与奖励设计、独立评测和对照实验。

当前新架构主线的 Qwen 3/6、教师 6/6 是新 train 任务抽样；24 条任务属于小批管线验证，4 条示范通过初审、2 条待查。这些都不是后训练提升或独立测试成绩。历史其他训练实验按各自版本报告。

### 接下来的执行顺序

1. **先完成数据与评测验收。** 解决 2 条待查项，核实多实体证据新鲜度是否逐实体覆盖；补齐 18 条教师轨迹。另建分组隔离的 dev 和锁定 test，不把同源改写拆到不同集合。增加“单个场馆证据过期但另一个新鲜”“省略证据引用”“重复查询”“提前停止”等评测反例。
2. **验证 SFT 训练管线。** 逐 token 查看输入与 labels，确保只训练模型动作和参数；系统消息、工具返回、用户消息不参与目标损失。检查原生工具模板、截断、结束 token、梯度和可训练参数。用少量样本做过拟合检查只用于验证实现，然后在独立 dev 上验证从起点自主运行。沿用真实 4B 基模和当前同一 Harness。
3. **扩大有效数据并建立可信 SFT 基线。** 24 条只负责打通管线。初步可按 200–500 条不同任务组合规划扩展，实际数量根据审核通过率、学习曲线和计算成本调整；不是岗位门槛或保证有效的数量。全程记录来源、场景组、难度、失败类型、数据版本与采样成本。
4. **做针对性的学生失败纠错。** 让 SFT 学生从任务起点自主运行，收集实际失败状态；教师提出可执行的修正。对比等训练 token 的普通新增示范和定向纠错，验证收益来自纠错内容，而不只是多训练了一些数据。
5. **进行 GRPO / 可验证奖励强化学习对照。** 前提是 SFT 能产生部分成功且奖励经过审计。同题采样多条完整轨迹，工具执行结果提供可验证信号；只优化模型输出，记录行为策略和采样参数、组内奖励方差、优势、KL、熵、长度、梯度、实际工具成本与越权率。具体 KL 或 clipping 设置以选定实现为准，不把某一种配置误当作所有 GRPO 的定义。若组内全对或全错，分析难度与奖励可学习性，不靠增加无意义奖励制造分差。
6. **做消融、复现与最终验收。** 固定模型、Harness、任务、推理配置和预算，在 dev 上进行主要实验；资源允许时对主要训练配置做至少 3 个种子复现，清楚区分训练种子和仅重复推理。方法冻结后才运行锁定 test；若根据 test 调整方法，该集合就转为 dev，需要新的 test。

### 必须交付的实验对照

| 对照 | 要解释的问题 |
|---|---|
| 基模 vs SFT | 示范学习是否改善完整任务决策 |
| SFT + 普通增量数据 vs SFT + 定向纠错 | 纠错策略的额外价值，尽量匹配训练 token |
| 同一 SFT 起点 vs SFT + GRPO | 在线执行反馈是否带来额外收益 |
| 终局可验证奖励 vs 加过程/效率奖励 | 奖励塑形是否有帮助，是否导致投机 |

DPO 可以作为选做的偏好优化对照；先完成一条可信的 SFT → GRPO 主线，不以堆算法数量作为成果。若 RL 没有稳定收益，保留失败结论和诊断，不为简历强行宣布成功。

### 面试时需要自己掌握的内容

- SFT：交叉熵、shift labels、assistant-only mask、工具模板、截断与 packing、LoRA 的更新形式，以及学习率、batch、过拟合和显存问题。
- RL：policy gradient、优势估计、PPO clipping、GRPO 组内相对优势、KL 约束、采样分布与策略更新、奖励投机和长轨迹信用分配。
- 工程：PyTorch/autograd、混合精度、梯度累积、检查点恢复、生成与训练的 logprob 一致性。分布式训练需要理解基本原理；没有实际多卡实验时不把它写成实践经验。
- 实验：数据泄漏、同源分组、任务级验收、反事实证据测试、等成本比较，以及如何解释训练失败。

每完成一个阶段，应能解释相关代码、图表和失败案例；仅有自动生成的脚本与报告不足以证明掌握。优先把单卡 4B 实验做扎实，不为了展示模型规模而放弃对照和复现。
