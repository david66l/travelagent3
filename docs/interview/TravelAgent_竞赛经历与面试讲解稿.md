## 一、先把项目讲对

### 推荐项目名

**TravelAgent：基于多教师蒸馏与可验证规划的低成本旅行智能体**

备选：

- 偏算法：**Verifier-Guided Travel Agent：面向工具决策的教师—学生后训练系统**
- 偏工程：**TravelAgent：可恢复、可评测、可灰度的复杂约束旅行 Agent**

### 一句话定位

我做的不是一个“让大模型自动写攻略”的聊天机器人，而是一套解决复杂旅行约束的 Agent 系统：策略模型在任务 DAG 和动作白名单约束下逐步选择天气、搜索、详情、路线、求解与验证等动作，工具负责真实执行，CP-SAT 和 Verifier 负责确定性计算与验收；再通过多教师蒸馏、SFT、DPO/GRPO、大小模型路由和 Shadow 门禁，把高频决策训练成更便宜、更稳定、可审计的策略能力。

### 30 秒版本

传统旅行大模型最大的问题不是不会写，而是经常把“看起来合理”当成“真的可执行”，例如预算超限、景点闭馆、路线不可达，或者工具调用重复。我把系统拆成模型决策层和确定性执行层：1.7B 学生负责高频工具决策，8B 负责课程外复杂问题和失败回退；工具负责查事实，CP-SAT 负责排路线，验证器负责最终验收。在后训练上，我完成了多教师行为蒸馏、QLoRA SFT、DPO 故障修复和边界加权 SFT。最终 1.7B 学生在 150 条冻结难例上达到生产契约 150/150，并把重复工具调用降到 0；但该结果仍是合成冻结评测和 5% Shadow 候选，不冒充真实线上效果。

## 二、面试官能看懂的架构

```text
用户自然语言需求
       │
       ▼
LangGraph：收集日期/预算/偏好，维护多轮状态和人工确认
       │
       ▼
Controller：根据当前状态收窄模型可选动作
       │
       ├── 高频、有边界动作 ──> 1.7B 学生
       └── 课程外复杂决策/学生失败 ──> 8B 教师（最多回退一次）
       │
       ▼
搜索 / 天气 / POI / 详情等工具，只返回可追溯事实
       │
       ▼
CP-SAT 行程求解器：处理时间窗、天数、距离和容量约束
       │
       ▼
Verifier：检查硬约束、工具合同、事实来源和终止条件
       │
       ├── 不通过：澄清、恢复、重新规划或安全终止
       └── 通过：生成行程，交给用户确认或局部修改
```

系统工程链路：

```text
POST 消息
  → PostgreSQL 持久化消息和 PlanningJob
  → Celery/Redis 异步派发
  → Worker 执行 LangGraph/Agent Loop
  → PlanningJobEvent 持久化事件
  → SSE 按 job_id + last_event_id 实时推送或断线重放
```

这套架构最关键的边界是：

- **模型决定下一步做什么，不直接伪造事实。**
- **工具提供事实，求解器负责组合，验证器决定能不能交付。**
- **PostgreSQL 是任务和事件的事实源，Redis 只负责队列、热状态和实时唤醒。**
- **训练、离线评测和线上 Agent 共用工具参数合同，避免“训练时学到的动作线上不能执行”。**

## 三、我在项目中做了什么

> 暂按个人项目/核心开发者口径组织。若实际为多人组队，需要把下列模块按真实分工删改；未确认前不使用“独立主导全部系统”。

### 1. Agent 运行时与安全边界

- 把开放式文本规划改成有界 Agent Loop，设计 `Agent Ledger` 保存目标版本、任务图、事实、产物、失败记录和预算。
- 用 Controller 根据状态动态收窄动作空间，模型只选择 `search_pois`、`ask_user`、`propose_tradeoff`、`abort` 等合法动作。
- 接入工具执行、CP-SAT 路线求解、Verifier、完成门禁与人工确认，支持澄清、失败恢复、局部修改和安全终止。

### 2. 后训练数据与实验体系

- 建立训练快照环境和可回放轨迹，使 Teacher、SFT/DPO 数据生成、GRPO rollout 和生产工具使用同一参数合同。
- 使用 4B 与 8B 生成候选，由 Verifier 按任务成功、硬约束、工具合法性和效率裁决，保留模型来源、选择原因与内容哈希。
- 构建 1,443 条 SFT 数据和 1,091 对偏好数据；按任务/场景分组切分，并对冻结评测做精确与近重复泄漏审计。

### 3. SFT、DPO 与 GRPO

- 使用 NF4 double quantization + LoRA 完成 QLoRA SFT，把高频工具决策压缩到 Qwen3-1.7B。
- 定位 DPO reference 配置错误：旧实现实际使用 Base 而非冻结 SFT 作为 reference，导致模型退化和 HTTP 流中断；改为显式只读 `ref` adapter 后恢复行为。
- 在前一代 Qwen2.5-3B 上完成 trajectory-level GRPO-B0，用真实环境 rollout、分层 Reward 与 checkpoint 晋升门做同协议对照。
- 面对“DPO 离线偏好准确率 100%，生成却仍重复调用工具”的问题，没有继续盲目扩数据，而是定位到首次工具调用后的终止边界，设计 EOS 边界加权 SFT 修复。

### 4. 推理路由与效率

- 先完成 4B 学生/8B 教师的动作族路由：高频动作走学生，复杂权衡或学生失败走教师，并记录 requested/executed target、路由原因、Token、延迟和回退。
- 再把工具决策继续蒸馏到 1.7B，8B 只保留课程外复杂决策与单次 fallback。
- 对 Prefix Cache、CUDA Graph、LoRA 静态合并和并发做实测消融；拒绝没有实际收益的 Prefix Cache，保留预热后有效的 CUDA Graph。

### 5. 服务可靠性与可观察性

- 将异步规划改为 `PlanningJob → Celery Worker → PlanningJobEvent → SSE replay` 的持久链路。
- 用数据库租约处理重复派发，用定时扫描补偿“数据库提交成功但 Broker 首次发布失败”的任务。
- 前端按 `job_id + last_event_id` 重连，不再依赖某个 FastAPI 进程内存或不可重放的 Redis Pub/Sub。

## 四、最值得讲的四个难点

### 难点 1：大模型答案流畅，但不一定可执行

**问题**

旅行规划有预算、营业时间、地理距离、每日容量等硬约束。让 LLM 直接生成最终行程，语言可能合理，但缺少可执行性保证。

**解决**

我采用 Controller-first 架构：模型只做有界动作选择；搜索/天气/POI 工具提供事实；CP-SAT 求解器组合路线；Verifier 检查硬约束、事实引用和完成条件。模型输出不通过就进入澄清、恢复或重新规划。

**结果**

在 300 个生产格式的模拟授权回放中，Agent 硬通过率为 99.33%，确定性基线为 98.33%；兜底率由 38.33% 降到 0.67%。该批次不是 300 名真实用户，软评分还低于基线 0.0379，因此只能证明系统硬约束与恢复链路，不能证明主观体验全面更优。

### 难点 2：训练正确，不等于线上能执行

**问题**

早期训练快照按调用顺序返回工具结果。一旦候选筛选顺序变化，就可能把 A 景点的 observation 错配给 B 景点；另外，离线标签可能要求一个线上 Controller 根本不允许的动作。

**解决**

我把线上工具、Teacher 轨迹、SFT/DPO 数据和评测环境统一到同一参数模型；快照按 `tool_name + normalized arguments` 匹配响应，并增加标签—运行时合同冲突审计。训练集按场景分组切分，冻结集重叠为 0。

**结果**

后训练收益和 Controller 收益可以分开评估：1.7B 模型裸能力由 Base 106/150 提升到 SFT 135/150，而最新生产合同下 Base/SFT 都可被约束到 148/149。这避免把系统约束带来的收益错误归功于模型训练。

### 难点 3：DPO 指标很好，模型反而变差

**问题**

第一版 DPO 的偏好准确率看起来正常，但冻结评测从 SFT 的 135/150 降到 104/150，还出现 37 次 HTTP 流中断。

**定位**

排查 TRL 1.9.2 与 PEFT 行为后发现，`ref_model=None` 并不等于“冻结当前 SFT”；没有 `ref` adapter 时，实际 reference 是禁用 adapter 后的 Base。

**解决与结果**

显式加载同一 SFT checkpoint 为只读 `ref` adapter，只训练 policy adapter。修正版达到 137/150、0 HTTP 错误。由于相对 SFT 只增加 2 题且 McNemar `p=0.5`，我只让它进入 Shadow，没有虚构显著收益。

这个案例体现的不是“DPO 一定有效”，而是：训练 loss 和偏好准确率不能替代独立生成评测、协议一致性与线上门禁。

### 难点 4：动作选对了，模型却不知道什么时候停

**问题**

Stage35 的三组 DPO smoke 都达到离线偏好准确率 100%，但同一个难例仍连续输出两次 `abort`。动作语义正确，失败发生在生成序列的终止边界。

**解决**

从审计回放构建 240 条单动作数据，在保留工具名和参数普通 SFT loss 的同时，把第一次 `</tool_call>` 后的 EOS token 权重提高 16 倍；训练前强制每条样本恰好有一个合法终止边界。

**结果**

Stage36 在冻结 150 条难例上取得原始标签 149/150、生产合同 150/150、多动作输出 0/150，目标重复案例连续 5/5 通过，并晋级 5% Shadow 候选。

## 六、3 分钟竞赛答辩稿

这个项目的出发点是：旅行规划看起来像文本生成，但真正困难的是可执行性。用户可能同时给出预算、日期、兴趣、开放时间和交通距离等约束，通用大模型很容易生成一个“读起来不错、实际走不了”的方案。

所以我没有让模型直接生成最终行程，而是把系统设计成“模型逐步选择工具 + 确定性执行与验收”。LangGraph 负责多轮状态和人工确认，Controller 根据当前任务限制模型可选动作；模型逐步选择天气、搜索、详情、路线、求解与验证动作，真实事实由工具返回，路线由 CP-SAT/Greedy 计算，最后由 Verifier 检查硬约束。这样既保留 Agent 的多步决策，也把模型的不确定性限制在可验证边界内。

第二个重点是后训练。我先用 4B 和 8B 多教师生成候选，再让 Verifier 根据任务成功、硬约束和工具合法性裁决，形成 1,443 条 SFT 数据和 1,091 对偏好数据，最终将高频策略蒸馏到 Qwen3-1.7B。冻结外部模型评测中，1.7B 从 Base 的 106/150 提升到 SFT 的 135/150。

过程中最有价值的不是最高分，而是两个失败复盘。第一版 DPO 虽然训练指标正常，却跌到 104/150并出现 37 次流中断。我定位到 TRL/PEFT 的 reference 实际回到了 Base，改成显式冻结 SFT adapter 后恢复到 137/150、0 HTTP 错误，但因为比 SFT 只多 2 题且不显著，所以只进入 Shadow。之后又遇到重复 `abort`：三组 DPO 的离线偏好准确率都是 100%，生成仍然重复。说明问题不是“喜欢哪个动作”，而是“不知道什么时候停”。我给首次工具调用后的 EOS 增加 16 倍 token 权重，最终在 150 条冻结难例上做到生产合同 150/150、多动作 0/150。

在工程上，我把规划任务改成 PostgreSQL 持久化、Celery 异步执行、事件日志和 SSE 断线重放，避免服务重启或 Redis 通知丢失后任务消失。最终成果是一套有训练数据谱系、独立评测、失败晋升门、大小模型路由和可恢复服务链路的旅行 Agent。当前最诚实的边界是：核心数字来自冻结工程评测和模拟授权回放，最新模型只晋级 5% Shadow，还不能宣称已经被真实用户验证。

## 九、面试追问准备

### 为什么不用一个大模型全部完成？

因为规划、事实查询和约束求解是不同类型的问题。大模型擅长理解意图和选择下一步，但不擅长稳定满足时间窗、距离和预算等硬约束；把这些交给工具、求解器和验证器，既更可靠，也更容易定位问题。大小模型路由则是为了让高频简单动作不必每次调用 8B。

### 这算蒸馏吗？

算行为蒸馏，不是 logits 蒸馏。4B 和 8B 在同一任务上生成候选轨迹，Verifier 根据真实环境执行结果选择 chosen，并记录教师来源，学生通过 SFT 学习这些被验证的动作，再用偏好数据做 DPO。

### 为什么 8B 有时还不如小模型？

这个任务不是开放式知识问答，而是严格结构化的有界动作选择。参数更大不等于更遵守特定工具合同；8B 如果未经专门后训练，可能输出多个动作或选择控制器不允许的动作。生产系统必须看同协议评测，而不能按参数量猜能力。

### DPO 为什么会比 SFT 差？

项目里有两个原因。第一是工程配置：reference 实际退回 Base，导致策略相对错误参考优化。第二是目标错位：偏好数据能区分 chosen/rejected，却不一定教会模型在第一个工具调用后停止。所以要同时检查 reference、数据分布、生成门禁和外部行为，而不是只看 DPO accuracy。

### 为什么最后用边界加权 SFT，不继续做 DPO？

因为失败点已经被定位为 EOS 终止 token，而不是动作偏好。用直接监督提高正确终止边界的梯度信号，比继续优化整段 chosen/rejected 更对症。20-step smoke 先验证目标难例，完整 150 条回归通过后才训练正式模型。

### Controller 已经把动作空间限制得很窄，后训练还有意义吗？

有，但要拆开评估。Controller 提供安全下限，后训练提升模型在开放动作空间中的裸能力、减少错误参数和无效回退。项目中 Base 106/150 到 SFT 135/150 是模型收益，而生产合同下都接近 148/149 是系统约束收益。两者不能混为一个数字。

### 这个项目目前最大的不足是什么？

一是关键评测仍以合成冻结集和模拟授权回放为主，缺少 outcome-observed 的真实 Shadow；二是 8B 对课程外复杂规划的优势还缺专门的分布外多轮 benchmark；三是最新持久任务链路需要在真实 PostgreSQL/Redis 环境补一轮全链路故障注入。回答不足时要同时给出下一步验证方案，而不是回避。

## 十、收获怎么讲

- **模型能力和系统能力要拆开。** 模型分数变高不代表系统一定更好，Controller 兜底也不能冒充后训练收益。
- **后训练首先是数据与评测工程。** 工具合同、同上下文偏好对、泄漏审计、reference 策略和冻结门禁，比单次 loss 更决定结果可信度。
- **负结果是研发资产。** Prefix Cache 没有收益、DPO 增益不显著、8B 在有界动作上未必更强，都应被保留并影响决策。
- **Agent 的核心是可恢复的状态机。** 模型只是一环；任务持久化、事件重放、失败分类、人工确认和回滚决定它能否成为产品。
- **上线不是一个开关。** 离线评测、Shadow、Canary、放量和回滚是不同证据等级，不能用模拟数据跳级。
