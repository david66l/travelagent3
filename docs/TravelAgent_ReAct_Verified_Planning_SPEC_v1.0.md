# TravelAgent ReAct + 可验证规划架构 SPEC v1.0

## 1. 改造目标

将现有“模型沿固定任务 DAG 逐项执行”的 Agent 主链，改为“意图驱动的 ReAct 研究循环 + 确定性规划门禁”。模型负责根据当前信息缺口动态选择工具、观察结果、补充证据和决定何时尝试收口；代码负责权限、预算、证据新鲜度、CP-SAT 求解、硬约束验证、持久化和人工确认。

旧 `controller_first` / `policy_driven` DAG 保留为离线对照基线，不再作为目标生产架构。

## 2. 用户可见流程

1. 由结构化意图模型识别用户意图和约束，并区分：
   - 只有用户能回答的信息，例如目的地、希望玩几天、接受什么取舍；
   - 可以通过工具查到的信息，例如演唱会时间地点、天气、开放时间和车次。
2. 只有缺少第一类信息时才追问用户；不得让用户提供本可搜索得到的事实。
3. 先从本地知识库取得城市和 POI 的稳定信息。
4. ReAct 根据证据缺口动态调用实时工具：天气、POI、统一网页搜索和航班/火车等。演唱会、展览、比赛、节庆、市集等开放集合全部进入同一个搜索工具，由 `query + info_type` 表达需求，禁止按活动品类新增工具。
5. 模型提出“研究完成”后，由 `ResearchSufficiencyVerifier` 检查证据覆盖、来源和新鲜度；不通过时把缺口作为 Observation 退回 ReAct。
6. 证据充足后构建路线矩阵，交给 CP-SAT 排程；演出、预约等固定事件作为日期/时间窗硬约束。
7. `ItineraryValidator` 检查硬约束。失败时把违规码返回 ReAct，由它选择补证据、换候选、重求解、向用户提出取舍或安全停止。
8. 仅允许从已验证的结构化行程生成自然语言，润色器不得改变 POI、时间、价格和路线顺序。
9. 用户接受则完成；用户拒绝但没说明原因则追问；用户给出原因后，由模型生成带字段白名单的 `RevisionOperation`，Controller 校验类型与边界并形成新约束，再重新进入研究/求解。不得用关键词或正则直接改写 Ledger。

## 3. 控制权边界

### LLM 决定

- 当前缺的是什么证据；
- 下一步使用哪个只读工具以及安全参数；
- 搜索结果不足时如何改写查询或换工具；
- 何时提出结束研究；
- Verifier 失败后采用哪一种修复策略；
- 如何解释经过验证的结果。

### Controller 决定

- 当前允许调用哪些工具；
- 用户字段是否真的缺失；
- 工具参数是否越权或未被用户约束支撑；
- 调用次数、Token、时延和求解次数预算；
- 证据是否覆盖必需项、是否过期；
- CP-SAT 与 Verifier 的真实结果；
- 是否允许向用户展示或最终完成。

## 4. ReAct 状态

运行状态独立于聊天文本，至少包含：

- `goal`：意图、硬约束、软偏好、用户锁定项；
- `evidence_requirements`：当前意图对应的必需证据和时效要求；
- `facts/artifacts`：带来源、置信度、版本和有效期的证据；
- `decision_history`：动作、参数、结果签名和是否取得新进展；
- `failures`：工具错误和 Verifier 违规码；
- `plan_version`：每次约束修改或全局重规划递增；
- `budget`：模型轮次、工具、求解、Token 和总时延；
- `user_feedback`：接受、拒绝原因及由其形成的约束变更。

生产日志保存简短的决策理由和可审计动作，不保存或展示模型私有思维链。

## 5. 意图与证据需求示例

意图模型通过一个 Pydantic 契约同时输出 `intent/slots/intent_kind/event_query/transport_modes_requested/information_needs/current_info_queries`。后续 ReAct 只读这些结构化字段；关键词解析仅允许存在于模型完全不可用时的基础槽位降级路径，且不得据此猜测活动、实时取证或用户修改语义。

| 意图 | 用户必填 | 工具可发现 | 规划前证据 |
|---|---|---|---|
| 普通多日行程 | 目的地、天数 | 城市知识、POI、开放时间、路线；近期出发时天气 | 城市知识、足量 POI、POI 详情、路线矩阵 |
| 演唱会旅行 | 目的地/可定位的演出名、天数 | 场馆、日期、开始结束时间、官方来源 | 普通行程证据 + 完整活动证据 |
| 航班/火车需求 | 出发地、目的地 | 班次、时间、来源链接 | 交通搜索证据；价格/余票标注查询时间 |
| 餐厅/季节活动 | 城市和用户偏好 | 营业时间、临时闭店、当季活动 | 对应实时网页证据和查询时间 |

统一搜索在 `info_type=event` 时额外抽取日期、开始/结束时间、场馆、城市和来源链接，并将场馆交给地图服务做实体与坐标落地。新增活动类型只需要更换查询内容，不改变 Agent 动作空间。航班和火车因具有明确的出发地、目的地、日期、班次等结构化供应商契约，继续使用独立交通工具。

搜索证据必须经过“来源结果 → 实体对齐 → 结构化规划约束”适配层后才算完成取证：活动形成固定预约；临时营业时间和闭馆形成 POI 的按日期可用性；进城到达时间加接驳缓冲后形成首日开始边界，返程出发时间减值机/候车缓冲后形成末日结束边界。CP-SAT 与 Verifier 必须读取同一组字段，无法结构化或没有匹配到候选实体的结果不得满足证据门禁。

## 6. 后训练门禁

在下列条件满足前不开始新一轮 SFT/GRPO：

1. 至少覆盖普通行程、演出、交通、餐厅时效、工具失败、Verifier 修复和用户拒绝修改七类真实全链路；
2. 每条轨迹确实包含模型多轮决策与真实 Observation，而非预生成固定动作；
3. CP-SAT 输入、硬验证报告和最终回复能够按 `trajectory_id/plan_version` 对齐；
4. 建立旧 DAG、纯 ReAct、ReAct+CP-SAT+Verifier 三套同协议基线；
5. 训练样本只接收工具合法、证据充分、硬验证通过或正确安全停止的轨迹。

SFT 学习“怎样在该环境中采取正确动作”；GRPO 优化真实生产环境中的证据覆盖、硬通过、失败恢复、用户修改成功率和效率。不得把模拟工具结果与真实在线结果混入同一个指标。

## 7. 验收指标

- 意图/补槽：仅追问用户拥有的信息，字段发现类问题不误问用户；
- 工具选择：不同场景出现不同动作序列，且重复无进展动作会被终止；
- 证据：所有时效事实有来源、查询时间和有效期；
- 规划：固定活动日期和时间不得被 CP-SAT 移动；
- 验证：最终展示的每份行程均 `hard_pass=true`；
- 交互：拒绝无原因必追问，带原因拒绝必产生新 `plan_version`；
- 工程：检查点恢复后不重复副作用，轨迹可重放，预算可审计；
- 后训练：在冻结评测集上分别报告 SFT 与 GRPO 的增量，不用训练集或模拟集数字代替。
