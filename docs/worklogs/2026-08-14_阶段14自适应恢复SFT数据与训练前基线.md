# 阶段 14：自适应恢复 SFT 数据与训练前基线

日期：2026-08-14  
状态：已完成（数据、生产链路修复、训练前基线均已验收）

## 本阶段目标

把旧的“工具超时后原参数重试”数据升级为真正的长任务恢复数据：模型必须读取工具失败反馈，根据可见证据修改检索参数，并由真实 Agent Loop 验证修改后的动作可以继续完成整条行程规划。

## 发现的核心问题

### 1. 旧 Recovery SFT 只学习重试，没有学习策略调整

旧数据的第一轮和第二轮 `search_pois` 参数相同，只能证明模型对 `UPSTREAM_TIMEOUT` 有重试容忍度，不能证明模型会理解失败原因、改变策略。因此旧数据不能作为“自适应恢复能力”的证据。

### 2. 生产执行器会覆盖模型的恢复决策

首次真实 Agent Loop 测试中，策略已经把两个兴趣关键词缩小为失败反馈指定的一个关键词，但 `TravelActionExecutor._hydrate_arguments` 又把全部用户兴趣合并回请求，最终触发 `SNAPSHOT_ARGUMENT_MISMATCH`。这意味着在修复前，App 中的自适应查询恢复在结构上不可能成功。

修复原则：

- 模型没有提供关键词时，控制器用受信用户偏好补全；
- 模型提供了经过策略参数校验的关键词时，执行器尊重该选择；
- 城市、类别、约束、候选集等受保护字段仍由控制器注入，模型不能越权写入。

这将“受信事实注入”和“策略选择”分开，既没有放宽安全边界，也恢复了 Agent 调整搜索策略的能力。

### 3. Python 运行时与脚本入口问题

- 默认 PowerShell Python 指向 Miniconda，缺少项目测试依赖；改用 `backend/.venv/Scripts/python.exe`，未修改依赖规避问题。
- 新脚本在 pytest 中可导入，但直接执行时找不到 `scripts` 包。原因是测试配置自动加入仓库根目录，而脚本只加入了 `backend/src`。已显式加入仓库根目录，并用真实 CLI 烟测验证。
- 从仓库根目录直接执行裸 `pytest` 时不会自动读取 `backend/pyproject.toml`，因此会误收集一份导入即 `sys.exit()` 的遗留 e2e 诊断脚本。正式回归改用明确的 `backend/tests/unit backend/tests/integration`；后续仓库收口阶段将补统一根目录测试入口。

### 4. 正式构建超过工具首次 30 秒返回窗口

正式 640 条轨迹构建没有在首次命令窗口内返回，而且输出目录一度尚未出现。没有把工具等待超时当作成功；随后确认进程完成、五个产物全部落盘，再执行 manifest、数量和训练预检。

### 5. AutoDL 使用了错误的系统 Python

同步后首次调用系统 `python` 报缺少 `pydantic`。检查发现既有训练环境位于项目 `.venv`，其 CUDA 和训练依赖完整，因此没有重复安装或污染环境，后续统一使用 `.venv/bin/python`。

## 实现内容

### 可见证据驱动的 Teacher

新增 `AdaptiveRecoveryTeacherPolicy`：

- 首次搜索使用两个已落地兴趣关键词；
- 只有看到 `failure_summary` 中 retryable 的 `QUERY_TOO_BROAD` 才进入恢复；
- 只允许从失败消息与用户兴趣的交集中选择唯一关键词；
- Teacher 看不到 `hidden_test_facts`，与线上模型使用相同 `PolicyContext`。

### 自适应恢复数据构建器

新增 `scripts/build_adaptive_recovery_sft_dataset.py`。每条自适应样本必须同时通过以下硬门槛：

1. 第一轮在真实 Agent Loop 中以 `QUERY_TOO_BROAD` 失败；
2. 失败消息出现在模型可见的 `policy_state.failure_summary`；
3. 第二轮参数必须与第一轮不同；
4. 新参数只能使用失败反馈中点名且原请求已经提供的兴趣；
5. 第二轮由不可变快照环境验证成功；
6. 序列化消息不得包含 `hidden_test_facts` 或 `target_keywords`；
7. 完整 episode 必须通过 replay 与 reward gate。

### 数据隔离

- Recovery SFT 的所有样本只来自官方 GRPO `train`；
- 官方 GRPO `validation` 完全不参与训练或内部验证；
- SFT train / validation / test 按稳定哈希后的不同 source task 切分；
- 三个内部 split 的 source task 无交集；
- 每个 split 使用 1:1 的自适应恢复样本与旧能力回放样本，降低灾难性遗忘风险。

## 验证结果

### 代码级验证

- 执行器与恢复专项测试：16 passed
- Ruff：all checks passed
- 后端完整 unit + integration：972 passed，439 warnings，72.32 秒

### 当前最佳模型训练前基线

Checkpoint：`artifacts/grpo-qwen25-3b-aligned-learnable-step1`  
协议：12 个独立留出任务，每题 4 次随机 rollout，temperature 0.7，共 48 条。

- 成功 rollout：4 / 48
- 成功率：8.33%
- 进入 `grpo_update` 的任务：2 / 12
- 路由到 `sft_repair` 的任务：10 / 12
- 典型成功奖励：0.9570～0.9605
- 典型失败奖励：-0.6925

结论：当前恢复任务对 3B 模型大部分仍然过难，直接 GRPO 会产生大量全负奖励、组内零方差，无法形成有效优势信号。正确顺序是先做 Recovery SFT，把大多数任务移入可学习区间，再运行带有效性门控的 GRPO。

## 训练后追加记录：R1 被拒绝

R1 配置：从当前最佳 GRPO adapter 续训，2 epoch，学习率 `5e-5`，adaptive:replay = 1:1。训练耗时 369 秒，train loss 0.011996，内部 eval loss 0.000304。

相同 12 任务 × 4 rollout 行为评测结果：成功 0/48，低于训练前的 4/48，因此 R1 明确拒绝，不进入 GRPO。

定位证据：

- R1 的 48 条轨迹都在首次模型决策前截断，`actions=[]`；
- 原始生成仍有合法 `<tool_call>` 外壳，但参数包含 schema 禁止的 `trusted_city` 和 `max_results`；
- 基础 checkpoint 在同输入、同 seed 下只输出合法的 `keywords`；
- 训练集全文不包含 `trusted_city` 或 `max_results`，排除标签泄漏；
- 512 条训练样本中 446 条最终动作是 `search_pois`，且 2 epoch 很快达到训练 token accuracy 1.0。

判断：窄任务更新强度过大且动作分布偏斜，造成参数 schema 能力回退。修复方向是降低学习率与 epoch、提高多能力回放比例，并把未知/受保护参数率纳入 checkpoint 硬门槛；不会放宽线上参数校验来迁就模型。
