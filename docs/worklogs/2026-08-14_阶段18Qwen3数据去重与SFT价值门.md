# 阶段 18：Qwen3 数据去重与 SFT 价值门

日期：2026-08-14

## 1. 目标

阶段 17 确认 Qwen3-8B 训练链路兼容，但均衡数据的 train split 只有 1024 条。本阶段尝试构建 train≥3000 的正式候选数据，并用小步训练回答“Qwen3 zero-shot 已满分时，SFT 是否仍有增益”。

正式 SFT 和 GRPO 在本阶段默认关闭，只有数据与配对行为门同时通过才可能开启。

## 2. 源容量审计

原 4500 个课程任务只有 3804 个 train source，无法在四类完全均衡、source task 全局唯一的条件下构建 3072/384/384 SFT split。

因此使用同一真实 Agent Loop、reward gate 与 replay verifier 生成 12000 个确定性课程任务：

- executed episodes：12000；
- GRPO train：10129；
- GRPO validation：1871；
- reward 范围：0.889125–0.97425。

目标配比为 adaptive / clarification / tradeoff / search 四类各 960。容量审计：

| source family | 可用 | 需要 |
|---|---:|---:|
| adaptive | 993 | 960 |
| clarification replay | 1024 | 960 |
| tradeoff replay | 1014 | 960 |
| search replay | 7098 | 960 |

## 3. 第一版扩容被拒绝

第一版使用 `travel-curriculum.v1` 生成 3840 个 ID 唯一、split 无 overlap 的 examples。表面 manifest 全部通过，但独立计算模型实际看到的 `messages + tools` 哈希后发现：

- examples：3840；
- unique model-visible payloads：946；
- 重复 payload：2894；
- example/scenario ID overlap：0。

根因是 v1 的日期、预算、城市、偏好和 scenario kind 在约 1200 个 index 后循环。该数据集只保留在 AutoDL 作为拒绝证据，不进入训练，也不回收到仓库。

## 4. 数据唯一性硬门

新增两层保护：

1. `build_adaptive_recovery_sft_dataset.py` 在写 manifest 前对全 split 的 `messages + tools` 做 SHA-256；任意重复直接抛出 `MODEL_VISIBLE_PAYLOAD_DUPLICATE`；
2. 通用 `preflight_sft_dataset` 再次独立计算相同指标，报告 `unique_model_visible_payloads`，并以 `MODEL_VISIBLE_PAYLOAD_DUPLICATES` 阻止训练入口。

这避免未来用唯一 ID 包装重复模板来满足 3000 条数量门。

## 5. Curriculum v2 与正式候选数据

课程契约升级为 `travel-curriculum.v2`：

- 日期窗口从 300 天扩展到 1095 天；
- 预算从 5 档扩展到 37 档；
- 保持日期在 2027–2029 的现实范围；
- 不修改旧 v1 语料或历史评估集。

## 6. 16-step SFT 价值门

配置：Qwen3-8B、NF4、LoRA r16/alpha32、all-linear、256 个 action-stratified train rows、64 eval rows、16 optimizer steps、gradient accumulation 8。

训练结果：

| 指标 | 结果 |
|---|---:|
| train runtime | 89.2239 s |
| train loss | 0.353023 |
| eval loss | 0.000932 |
| eval token accuracy | 1.0 |
| training GPU memory | 约 11.4 GiB |

仅 16 steps 后 held-out template loss 已接近 0，说明标签规则很快饱和，继续训练有明显模板过拟合风险。

## 7. 与 zero-shot 的配对 rollout

所有评估沿用阶段 16 的 task、seed、temperature、NF4 和 `qwen_tool_envelope`。

| 门 | Qwen3 zero-shot | smoke16 | 延迟变化 |
|---|---:|---:|---:|
| adaptive success | 48 / 48 | 48 / 48 | 无新增成功 |
| adaptive mean | 2180.139 ms | 3656.124 ms | +67.70% |
| adaptive P95 | 2196.979 ms | 4292.452 ms | +95.38% |
| fixed success | 128 / 128 | 128 / 128 | 无新增成功 |
| fixed mean | 1602.554 ms | 2333.335 ms | +45.60% |
| fixed P95 | 2229.020 ms | 3387.498 ms | +51.97% |

两个门的 policy output、argument、unknown argument 和 protected argument errors 均为 0。行为没有退化，但没有产生任何新增成功，延迟显著增加。

## 8. 决策

`qwen3-stage18-sft-smoke16` 状态为 rejected：

- 不启动正式 Qwen3 SFT；
- 不启动 GRPO；
- Qwen3-8B zero-shot 继续作为当前最强 Agent Policy 候选；
- v2 唯一数据保留用于未来混入真实 shadow/人工难例后的实验，不把纯模板低 loss 当能力提升。

下一项真正有价值的工作是 Qwen3 vLLM HTTP canary 和真实/对抗 holdout，而不是继续增加 synthetic epoch。
