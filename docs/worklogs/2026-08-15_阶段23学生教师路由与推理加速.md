# 阶段 23：学生/教师路由与推理加速

日期：2026-08-15

状态：阶段 23 核心目标完成。已实现 4B 学生/8B 教师路由、学生失败单次教师回退、能力状态下的工具权限收紧、独立模型服务地址，以及单步/多轮组合评测。CUDA Graph 稳定态获得进一步加速；前缀缓存未带来收益，明确拒绝。当前实验为单卡顺序模型重放，生产双模型在线仍需要双 GPU、独立教师服务或统一模型网关。

## 1. 路由契约

新增 `RoutedAgentPolicy` 与 `PolicyRouteDecision`：

- clarification、search、recovery → Qwen3-4B DPO 学生；
- tradeoff 与未覆盖复杂动作 → Qwen3-8B 教师；
- 学生推理失败、输出非法或多工具调用时，只允许一次教师 fallback；
- 教师失败继续向上抛出，不被静默吞掉；
- `ContextVar` 保存当前请求路由结果，避免并发请求串线。

配置新增：

- `AGENTIC_POLICY_ROUTING_ENABLED`；
- `AGENTIC_STUDENT_POLICY_MODEL` / `AGENTIC_TEACHER_POLICY_MODEL`；
- `AGENTIC_STUDENT_BASE_URL` / `AGENTIC_TEACHER_BASE_URL`；
- 学生与教师独立 max tokens。

两种部署均支持：

1. 一个模型网关同时暴露两个 served model name；
2. 学生和教师使用不同 OpenAI-compatible 地址，适合双 GPU 或远程教师。

## 2. 单动作权限收紧

Qwen3-8B Base 在原冻结单步集为 168/172，4 个 tradeoff 全部错误选择 `capability_check`。问题不是 8B 不会 tradeoff，而是控制器在 `capability.status=infeasible` 时仍把已经非法的 `capability_check`、`ask_user` 暴露给模型。

新增 `constrain_policy_context`，只在真实模型适配器入口生效：

- needs_user 或 missing_information 非空时，只暴露 `ask_user`；
- infeasible、unsafe、missing_tool 时，只暴露 `propose_tradeoff` 与 `abort`；
- 离线扰动策略继续看到原始动作集，从而仍能构造真实 rejected，避免污染偏好数据审计。

首次把约束放在通用 `ControllerFirstPolicy` 时，3 个负样本测试失败；全量回归及时发现后，将约束下移到 API/native/local 模型适配器，旧的环境执行式负样本语义恢复。

权限收紧后，8B 在 4 道 tradeoff × 3 次重复共 12 次请求上 12/12 正确。

## 5. 前缀缓存 A/B

在同一 4B 静态模型、相同 516 请求、并发 4 下开启 vLLM prefix caching：

- 缓存查询 tokens 369589；
- 命中 tokens 333376，token 命中率约 90.2%；
- 但平均延迟从 335.841 ms 上升到 348.835 ms；
- 吞吐从 11.873 降到 11.433 req/s；
- P95 从 493.369 上升到 511.175 ms。

结论：该模型和请求长度下缓存管理开销没有转化为端到端收益，阶段 23 拒绝默认开启 prefix caching。OpenAI-compatible usage 字段未上报 cached tokens，但服务端 Prometheus counter 已提供真实命中证据。

## 6. CUDA Graph A/B

vLLM 官方文档说明 `--enforce-eager` 会禁用 CUDA Graph 和异步输出。移除该参数后：

- 首次 engine 初始化约 83.87 秒；
- 其中 torch.compile 约 41.62 秒；
- CUDA Graph 捕获约 20 秒，占用额外约 0.60 GiB；
- 因此只适合常驻服务。

第一次评测仍受形状热身长尾影响；同服务不重启的稳定态结果：

| 模式 | 平均延迟 | P50 | P95 | 吞吐 |
|---|---:|---:|---:|---:|
| eager，并发 4 | 335.841 ms | 295.950 ms | 493.369 ms | 11.873 req/s |
| CUDA Graph 稳定态，并发 4 | 310.596 ms | 278.626 ms | 445.456 ms | 12.835 req/s |

稳定态平均延迟降低约 7.5%，P95 降低约 9.7%，吞吐提高约 8.1%。因此常驻服务采用 CUDA Graph，开发调试和频繁启停可继续使用 eager。

官方依据：

- <https://docs.vllm.ai/en/v0.9.0/performance/optimization.html>；
- <https://docs.vllm.ai/en/v0.9.2/api/vllm/platforms/cuda.html>。

## 7. 并发吞吐

同一 CUDA Graph 稳定服务，516 请求、3 次重复：

| 并发 | 平均延迟 | P95 | 吞吐 | 相对并发 4 吞吐 |
|---:|---:|---:|---:|---:|
| 4 | 310.596 ms | 445.456 ms | 12.835 req/s | 1.00× |
| 8 | 346.846 ms | 503.874 ms | 22.904 req/s | 1.78× |
| 16 | 398.403 ms | 572.700 ms | 38.716 req/s | 3.02× |

建议：在线默认并发 8，在延迟与吞吐间平衡；离线批处理或高峰吞吐优先时使用 16；低延迟单请求场景使用 4。

## 8. vLLM 单工具调用版本边界

当前远端 vLLM 0.9.2 会忽略 `parallel_tool_calls=false`，服务日志也明确打印该选项被忽略，因此同一响应可能包含连续两个工具调用。生产 `LLMClient` 已严格要求恰好一个调用，多调用会触发学生到教师的单次 fallback。

当前 vLLM 官方实现已增加：当 `parallel_tool_calls` 显式为 false 时只保留第一个工具调用。该能力属于后续版本，升级前仍必须保留客户端严格门禁。官方实现：<https://docs.vllm.ai/en/latest/api/vllm/entrypoints/serve/utils/tool_calls_utils/>。

## 9. 资源与部署边界

- Qwen3-4B 静态 FP16 权重约 7.6 GiB；
- Qwen3-8B FP16 权重约 16 GiB；
- 两者加 KV cache 和 CUDA Graph 后无法在当前单张 RTX 4090 24 GiB 上稳定同驻；
- 因此本阶段 4B/8B 组合指标来自同硬件、同协议、顺序切换模型后的冻结重放；
- 它证明路由决策和组合质量，不证明单卡双服务已经上线；
- 真正在线部署需要双 GPU、远程 8B 教师、量化教师或统一网关。
