# 阶段 17：Qwen3-8B 训练与服务迁移准备

日期：2026-08-14

## 1. 本阶段目标

在阶段 16 已确认 Qwen3-8B zero-shot 明显优于 Qwen2.5-3B 的前提下，验证三件事：

1. Qwen3-8B 是否与现有 SFT 数据、官方 chat template、QLoRA target modules 和训练栈兼容；
2. 现有 preflight 是否真的能阻止模型协议不兼容和序列截断；
3. vLLM/OpenAI-compatible 服务配置是否满足后端原生工具调用契约。

本阶段不授权正式 SFT、GRPO 或生产 Qwen3 晋升。所有训练验证均为新目录中的有界 smoke。

## 2. 初始审计发现

### 2.1 原 preflight 存在“假通过”窗口

`train_sft.py --preflight-only` 原先只检查 manifest、split、样本数量和 Python 依赖。即使传入 `--model`，它也不会加载 tokenizer，不检查：

- 模型是否有原生 chat template；
- template 是否接受 `tools` 和历史 tool messages；
- assistant tool call 是否保留 Qwen `<tool_call>` 外壳；
- prompt token 是否为 full sequence 的严格前缀；
- completion 是否为空；
- 序列是否超过 `max_length`。

因此旧命令不能作为 Qwen3 迁移保护门。

### 2.2 数据规模不足正式训练门

均衡数据集 `sft-adaptive-recovery-balanced-zh-v1` 的 split 为：

| split | 数量 |
|---|---:|
| train | 1024 |
| validation | 128 |
| test | 128 |
| 合计 | 1280 |

代码的正式训练下限是 3000 个 train examples。默认 preflight 正确返回：

`TRAIN_EXAMPLES_BELOW_MINIMUM:1024<3000`

因此当前数据只允许 `--allow-small-dataset` 的 smoke，不允许把结果声明为 formal SFT。

## 3. Qwen3 tokenizer / template 全量审计

远端模型：`/root/autodl-tmp/models/Qwen3-8B`。模型权重只保留在 AutoDL 数据盘，没有复制到仓库。

模型配置：

- `model_type=qwen3`；
- architecture：`Qwen3ForCausalLM`；
- 官方 chat template 存在；
- template 包含 `<tool_call>`；
- pad token 为 `<|endoftext|>`。

以 `enable_thinking=False` 对 train/validation/test 全部 1280 条执行 prompt 和 full conversation 双编码：

| 指标 | 结果 |
|---|---:|
| 成功编码 | 1280 / 1280 |
| template errors | 0 |
| tool envelope rows | 1280 / 1280 |
| 最大完整序列 | 1055 tokens |
| P95 完整序列 | 1048 tokens |
| 超过 2048 | 0 |
| completion tokens | 23–43 |

结论：现有数据协议与 Qwen3-8B 官方 Hermes 风格 JSON tool-call template 兼容，2048 上限有足够余量。

## 7. vLLM / OpenAI 工具调用契约审计

后端 `LLMClient.tool_call` 固定发送：

- `tool_choice="required"`；
- `parallel_tool_calls=False`；
- 恰好一个工具调用。

审计发现原部署存在以下确定性冲突：

1. `vllm/vllm-openai:v0.6.3.post1` 早于 required tool choice 支持；
2. 服务未配置 tool parser；
3. Compose 使用 Llama-3.2-3B，却挂载 Qwen LoRA 占位目录；
4. K8s 的 vLLM 只加载 Qwen，却让后端请求未注册的 `deepseek-v4-flash`；
5. 三个 LoRA 目录没有 `adapter_model.safetensors`，不能注册为真实 adapter。

安全修复：

- vLLM 固定到 `v0.9.2`，高于 required tool choice 的最低支持版本；
- Qwen2.5 现有服务使用 `--tool-call-parser hermes`；
- 启用 auto tool choice 入口，并保留 required 模式；
- 无真实权重时不再注册占位 LoRA；
- K8s served model 与后端 model name 统一为 `Qwen2.5-14B-Instruct`；
- vLLM Agent Policy 请求显式传 `chat_template_kwargs.enable_thinking=false`；
- 新增独立 `docker-compose.vllm.qwen3-canary.yml`，Qwen3 只作为 `travel-policy-qwen3-8b-base` canary，不覆盖生产 Qwen2.5。

Compose 合并配置已由 `docker compose ... config` 成功解析；四份 YAML 均通过解析。当前 AutoDL 没有 Docker 和 vLLM 包，且数据盘只剩约 12 GiB，因此没有在训练节点临时安装另一套大型 serving runtime。真实 HTTP `required` tool-call canary 仍是生产晋升前的独立门。

官方依据：

- [vLLM Tool Calling](https://docs.vllm.ai/en/latest/features/tool_calling/)：`required` 自 v0.8.3 支持，并说明 Qwen2.5 使用 Hermes parser；
- [Qwen3 Concepts](https://github.com/QwenLM/Qwen3/blob/main/docs/source/getting_started/concepts.md)：Qwen3 使用 Hermes-like JSON in `<tool_call>` 协议；
- [vLLM Reasoning Outputs](https://docs.vllm.ai/en/v0.10.1/features/reasoning_outputs.html)：Qwen3 可通过 `chat_template_kwargs.enable_thinking=false` 关闭 thinking。

## 9. 阶段结论

Qwen3-8B 的模型架构、tokenizer、tool template、序列预算和 QLoRA 训练链路已经确认兼容。模型升级本身不是当前阻塞项。

当前不启动正式微调，原因是训练数据门未通过：`1024 < 3000`。下一阶段应先扩充/重采样为至少 3000 条、保持 action 与 recovery family 平衡并重跑 overlap/audit，然后才启动 Qwen3 SFT。GRPO 继续保持关闭，直到新 SFT checkpoint 通过固定、adaptive 和真实 vLLM canary 三类门。
