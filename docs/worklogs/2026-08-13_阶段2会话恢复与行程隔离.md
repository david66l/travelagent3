# 2026-08-13 阶段 2：会话恢复、多行程隔离与局部重规划一致性

## 本阶段目标

在真实 API 和真实浏览器环境中，闭合以下容易被演示流程掩盖的状态链路：

1. 刷新页面后恢复已确认行程；
2. 刷新页面后恢复待确认草案，并能继续原检查点；
3. 多个历史行程分别绑定自己的 LangGraph 会话；
4. 局部删除或替换后，行程费用与预算同步重算；
5. 旧版本本地数据可以平滑迁移。

## 完成的工作

### 1. 统一恢复服务端会话

- `restore_session_state` 改为通过 `ChatSessionManager.load_state()` 恢复状态，统一覆盖内存、Redis、LangGraph 检查点和规划任务冷存储。
- 恢复事件现在携带 profile、phase、revision、最近消息、结构化 itinerary、预算和导出地址。
- 兼容旧检查点：如果顶层没有 itinerary，会从最近一条带 itinerary 的消息中恢复。

### 2. 前端持久化和刷新恢复

- 持久化 sessionId、待确认状态、当前视图、行程列表、当前行程和对话快照。
- `state_restored` 会恢复用户画像、最近消息、结构化行程、确认状态、运行阶段、预算和导出信息。
- 草案刷新后仍停留在确认门，而不是生成一个只有页面缓存、无法继续的假草案。

### 3. 建立行程和后端检查点的所有权关系

- `TripRecord` 增加 `conversationId`。
- 点击历史行程时，同时切换展示状态和对应 SSE/LangGraph 会话。
- 只有当前展示行程属于当前会话时，才开放删除、替换和约束调整。
- 同一目的地和日期再次确认时原位更新 TripRecord，避免产生重复历史行程。
- 旧 TripRecord 通过匹配对话快照迁移 conversationId。

### 4. 修正局部重规划的派生数据

- 局部修改使用深拷贝，不再存在嵌套 activity 列表意外污染旧检查点的风险。
- 删除、替换、增加或重排后，由后端统一重算：
  - `day.total_cost`
  - `day.transport_cost`
- 固定的每日餐饮预留继续保留；景点票价、餐饮明细和交通明细按修改后的活动重新汇总。
- 行程一旦修改，旧的预订总预算立即失效；用户确认新版行程后由 booking 节点重新计算。
- 前端在草案阶段从结构化行程投影预算，在最终事件到达时再以服务端完整预算覆盖。

### 5. 兼容旧预算数据

- 旧版本 TripRecord 如果预算面板全为 0，但行程本身带有每日费用，会自动重建预算面板。
- 不直接修改用户浏览器中的历史数据，迁移在 Zustand hydration 时完成。

## 发现的问题与根因

### 问题 1：刷新后只有页面缓存，未必能继续原任务

根因是恢复接口只读取异步规划任务数据库，没有读取交互式 LangGraph 检查点。

解决：恢复入口统一收敛到会话管理器，由它决定 hot/warm/cold/checkpoint 的读取顺序。

### 问题 2：切换历史行程后可能修改另一个会话

根因是 TripRecord 只保存行程内容，没有保存生成它的 conversationId。UI 切了页面，但发送修改动作的 SSE 连接仍属于旧会话。

解决：把 conversationId 作为行程领域对象的一部分，切换行程必须切换会话；修改按钮还增加所有权保护。

### 问题 3：删除景点后费用不变

根因是局部变更只修改 activities，`total_cost` 仍沿用求解器最初的派生值；前端预算又继续沿用确认时的预订预算。

解决：在变更领域层重算每日派生费用，并让旧 booking budget 失效。前端仅做结构化数据的展示投影。

### 问题 4：宿主 Python 无法直接运行测试

宿主 Conda 环境缺少 `pytest-asyncio` 和 Ruff，生产容器又只安装运行依赖。最终通过项目的 `uv run --project backend --extra dev` 创建一致的开发环境完成验证。运行过程中也补全了此前 agentic-training extra 未写入的 `uv.lock`。

## 验证结果

### 自动化验证

- Ruff：通过。
- 针对性后端测试：44 passed。
- 新增测试覆盖：
  - 交互式草案恢复投影；
  - 删除活动后的费用重算；
  - 替换活动后的费用差额；
  - 旧 booking budget 失效；
  - 输入状态不被原地修改。
- backend + frontend 生产镜像构建：通过。
- 扩大 graph/API 回归运行到 68% 无失败，随后停在一个真实流式 API 等待用例，人工终止；该长测不作为本阶段通过条件。

### 真实浏览器验证

1. 已确认的北京行程刷新后恢复成功，预算由旧的 ¥0 迁移为 ¥5,000 / ¥416.61。
2. 西安待确认草案刷新后恢复成功，点击确认能从原 LangGraph 检查点继续完成。
3. 北京和西安来回切换时，各自目的地、日期、活动和预算保持独立。
4. 在北京删除票价 ¥60 的“故宫”后：
   - 第 1 天费用：¥171 → ¥111；
   - 行程费用：¥416.61 → ¥356.61；
   - 预算余额：¥4,583.39 → ¥4,643.39；
   - 页面重新进入待确认状态。
5. 确认北京修订并切回西安后，西安仍显示陕西历史博物馆、预算 ¥4,000 / ¥626，不含故宫，证明没有跨会话污染。

浏览器工具自身的 Statsig 遥测请求偶尔超时，但 TravelAgent 页面交互和接口结果均正常，不属于项目故障。
