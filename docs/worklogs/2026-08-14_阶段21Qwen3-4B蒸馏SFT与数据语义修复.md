## 4. 训练转换缺陷修复

`to_conversational_prompt_completion` 原使用 `exclude_defaults=True`。它会把零参数工具的 `arguments: {}` 删除，Qwen3 原生工具模板随后拿到 Undefined 并在 JSON 序列化时报错，共影响 120 条样本。

已改为 `exclude_none=True`，既去掉无意义的 null，又保留空参数对象，并补充回归测试。旧数据在真实 Qwen3-4B tokenizer 上完成 2726/2726 模板编码，证明该问题已修复。

## 5. 关键语义审计：原澄清标签有误

旧 SFT v3 的失败分布集中在：

- `capability_check`：17 个动作错误；
- `propose_tradeoff`：8 个自由文本参数不完全相等；
- `ask_user`：2 个自由文本参数不完全相等；
- 搜索类全部正确。

进一步审计发现，SFT 中 120 条 `capability_check` 的可见上下文全部是：

- `capability.status = needs_user`；
- `missing_information` 非空；
- 正确行为应是直接 `ask_user`。

原强偏好 v4 的 120 条 clarification chosen 也同样是旧的 `capability_check`。因此问题不是“4B 模型太弱”，而是教师历史轨迹和奖励门存在语义漏洞。旧 SFT v3、旧强偏好 v4 以及归档 `stage20-final-sft-preferences-v1.tgz` 均已标记为被新版本取代，不能再用于正式训练或正式结论。

## 6. 澄清动作的新硬门禁

奖励引擎新增 `needs_user_action_mismatch`：

- 当 `capability.status = needs_user`；
- 且 `missing_information` 非空；
- Policy 却先调用 `capability_check`；
- 即使后面又成功追问并以 `awaiting_user` 结束，整条 episode 仍判为 `task_failed`；
- `gate_reasons` 记录 `NEEDS_USER_CAPABILITY_CHECK_MISMATCH`。

生产工具提示也新增明确规则：缺信息时立即调用 `ask_user`，不得先做 `capability_check`。

相关 Reward 与 Policy 定向测试：22 passed；其中 Reward 文件单独复跑为 12 passed。

## 16. 全量不均衡 SFT 的负结果

首次正式全量训练 `qwen3-4b-stage21-sft-formal-v1` 使用 aligned v4 全部 2144 条 train 样本训练一轮。训练指标很好：train loss 0.0221119、eval loss 0.000522549、eval token accuracy 0.999839，但实际 Agent 行为明显退化：

- 单步困难集仅 459/516，出现 57 个参数错误；
- 冻结多轮集仅 123/172；
- recovery 仅 1/50，49 条轨迹被 `TEACHER_GROUPS_WITHOUT_VERIFIED_SUCCESS` 拒绝；
- 平均验证奖励降至 0.493394。

根因是搜索样本占比过高，模型在恢复场景中学会重复宽泛兴趣，而不是缩窄为一个关键词。该实验证明“训练 loss 很低”不等于 Agent 能力更强。此 checkpoint 已明确拒绝，不能用于后续偏好优化的起点。

## 18. 静态合并部署实验

为去除动态 LoRA 服务开销，新增 `merge_lora_into_base.py`，包含成功训练报告检查、拒绝覆盖、适配器与训练报告哈希、FP16/BF16 合并选项，以及原始 Base tokenizer 字节复制。后者避免 Transformers 5 训练配置被旧版 vLLM tokenizer 解析器拒绝。

静态合并权重经数值抽查确认 LoRA 缩放正确：抽查首层 q_proj 的实际缩放比为 1.9994，理论值为 2.0。但静态写盘和动态低秩计算路径仍在动作边界上产生不同结果：

| 服务方式 | 单步结果 | 平均延迟 | 结论 |
|---|---:|---:|---|
| 动态 LoRA，同配置复测 | 172/172 | 1308.858 ms | 正确率门通过 |
| BF16 静态合并，3 次重复 | 492/516 | 339.419 ms | 快但 24 次动作回退，拒绝 |
| FP16 静态合并 | 159/172 | 474.152 ms | 快但 13 次动作回退，拒绝 |

失败集中在 clarification/tradeoff 边界，错误动作主要回退为 `capability_check`。因此静态服务没有晋级；两个可重建的 7.6 GiB 临时模型目录已删除以释放系统盘，merge report、分片哈希和评测逐请求记录均保留在 `ml/agentic/reports/stage21-*merged*` 与 `stage21-static-merge-fp16-v1`。

该负结果将直接转化为阶段 22 的验收门：偏好优化不仅要保持 172/172 多轮成功，还要扩大 clarification/tradeoff 的 chosen/rejected margin，并在重新静态合并后保持动作不掉点。
