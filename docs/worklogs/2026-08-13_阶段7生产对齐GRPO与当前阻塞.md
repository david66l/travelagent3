# 阶段 7：生产对齐的 Agentic GRPO 与当前阻塞

日期：2026-08-13

## 阶段目标

让 GRPO 优化的策略、环境状态转换、工具权限和 Reward 与线上生产 Agent Loop 完全一致，并验证 3B 模型在 24GB GPU 上能够进行真实的有状态 Agentic GRPO。

## 已完成的 GRPO 基础能力

1. 使用 TRL `environment_factory` 接入有状态环境，不把 Agent Loop 简化成一次文本问答。
2. 每次 rollout 从不可变任务及工具快照重置，训练时不访问线上 API。
3. Reward 使用生产的 `hierarchical-b0.v1`，包含 task、constraint、format、tool、grounding、efficiency 六类程序化分量。
4. 安全和硬约束作为上层 Gate，过程分不能掩盖硬失败。
5. 使用 DAPO 风格 token 聚合、group reward scaling、左侧 padding、截断 completion mask。
6. 支持从 SFT PEFT adapter 继续训练，而不是错误地从 Base 重新开始。
7. 训练报告明确标记 smoke/formal，当前只做 smoke。
8. 已实现 GRPO group 审计、零方差检测、标准化相对优势、model-aware curriculum 路由和 return-to-go 研究对照信号。

## 发现的架构错位

最初的 GRPO 环境把天气、POI 详情、路线矩阵、求解、校验和文案组装等所有动作都暴露给模型。但生产主链采用 Controller-first：

- 模型负责搜索策略、必要澄清、冲突取舍和极端情况下的安全终止；
- Controller 负责能力检查、天气、详情、矩阵、确定性求解、程序校验、文案投影和最终确认状态。

如果直接训练，GRPO 会优化一套线上根本不会让模型执行的动作，离线 Reward 再高也无法证明生产效果。

## 对齐改造

### 1. 共享 Controller 决策

从生产 `ControllerFirstPolicy` 中抽出统一 `controller_policy_action`。线上推理和 RL 交互环境调用同一个函数，避免维护第二套“哪些步骤属于 Controller”的规则。

### 2. 自动推进确定性步骤

`InteractiveAgentSession` 支持自动动作提供器。环境启动后会在同一个生产 `BoundedAgentLoop` 中自动执行 Controller 步骤，只在真实策略决策点暂停并请求模型动作。

普通规划人工验证结果：

- 模型决策：仅 `search_pois`；
- Controller 动作：capability、weather、detail、matrix、solve、validate、compose、finish；
- 终止：等待用户确认；
- Reward：0.97425。

### 3. 按任务类型隔离工具面

TRL 会根据环境公开方法生成工具 schema。为使训练工具面与生产当前状态一致，拆分为三个环境：

- `TRLSearchEnvironment`：仅公开 `search_pois`；
- `TRLClarificationEnvironment`：仅公开 `ask_user`；
- `TRLTradeoffEnvironment`：仅公开 `propose_tradeoff` 和 `abort`。

GRPO 数据行根据 `missing_slots` 和 feasibility report 路由到对应环境。确定性工具不再出现在模型 prompt 中。

### 4. 同步工具门面

生产 Agent Loop 保持异步运行，但对 TRL 暴露同步工具方法，内部通过每个 rollout 独立的事件循环线程串行提交动作。这消除了 TRL 异步工具线程与 Agent Loop 状态线程之间的双重事件循环桥接。

### 5. 工具 schema 对齐

删除了 RL `search_pois` 中生产策略 contract 不支持的 `category` 参数，使 SFT 时看到的 schema、线上本地模型 schema 和 GRPO schema 保持一致。

## 3B GRPO 烟雾试验记录

以下试验都从 20 步 SFT 适配器继续，`num_generations=4`，均为工程 smoke，不是正式效果结果。

### 试验 A：生产自动推进，但仍暴露全部环境工具

- 单步训练：15.44 秒；
- 峰值显存：约 6.3GB；
- 平均 Reward：-0.83375；
- Reward 标准差：0.19224；
- 工具调用频率：1.5；
- 工具失败率：50%；
- 适配器保存、评测和重载成功。

意义：证明 3B Agentic GRPO 可以在 4090 上运行且存在非零组方差；失败主要来自过宽工具面。

### 试验 B：只暴露四类策略工具

- 平均 Reward：-0.68；
- Reward 标准差：0；
- 工具失败率：50%。

意义：固定普通规划任务对当前策略容易产生相同动作，组内没有有效学习信号；仍需进一步按状态缩窄工具。

### 试验 C：按任务路由环境，但 schema 尚未一致

- 平均 Reward：-0.655；
- Reward 标准差：0；
- 工具失败率：100%。

根因：RL 搜索工具多出 `category` 参数，与生产策略参数校验器不一致。

### 试验 D：环境路由、同步门面和 schema 完全一致

- 工具调用频率：1.0；
- 工具失败率：0%；
- completion 平均长度：25 tokens；
- 平均 Reward：-0.68；
- Reward 标准差：0；
- 单步训练约 11.84 秒。

意义：工具协议问题已经消除，但 TRL 批量 rollout 的 Reward 仍与手工执行同一环境得到的 0.97425 不一致。这是当前尚未解决的问题。

## 当前阻塞的准确描述

当前不是“GRPO 跑不起来”，而是以下一致性问题尚未闭环：

- 手工对 `TRLSearchEnvironment` 执行正确 `search_pois`，生产 Agent Loop 自动完成后 Reward 为 0.97425；
- TRL 批量采样已经显示工具调用成功、工具失败率 0%，但该组 Reward 仍全部为 -0.68；
- 由于四个 rollout 同分，GRPO 正确地不给出有效相对优势，训练 loss 为 0；
- 在查明 episode 最终状态或 reward 收集时机的差异前，不应扩大步数或启动正式训练。

下一步应捕获 TRL 每个 environment instance 的完整 episode、终止原因、最后动作和六类 Reward 分量，与手工 episode 做字段级对比。重点检查 `get_reward` 调用时机、环境实例复用及 rollout 是否在工具调用后又生成了未执行的尾部文本。不能通过硬改 Reward 或忽略零方差来绕过问题。

## Model-aware curriculum 的后续要求

协议一致后，先对候选任务进行多采样审计：

- 全成功且零方差：作为评测锚点，不消耗 GRPO 更新；
- 有成功有失败且 Reward 非零方差：进入 GRPO；
- 全失败：返回 SFT repair 集，而不是让 GRPO反复采样；
- 环境或指纹不一致：拒绝。

当前普通搜索任务可能对 3B 过于简单或呈现一致错误，不能直接把 3804 个训练任务全部送入正式 GRPO。
