# 2026-08-16 阶段36：工具调用终止边界 SFT

## 背景

Stage35 的三组 DPO 小实验都把离线偏好准确率推到 100%，但固定难例
`ext-v1-stage29-ds-065` 仍连续输出两次相同的 `abort`。这说明动作选择本身已经正确，
失败点是生成序列在第一次 `</tool_call>` 后没有可靠停止，普通偏好分数无法替代真实生成门禁。

## 本阶段实现

1. 在 SFT 训练入口增加 termination-boundary 预检，要求每条监督完成：
   - 恰好包含一个模型 EOS；
   - EOS 紧跟在 `</tool_call>` 后；
   - EOS 后只允许模板空白。
2. 增加 boundary-weighted SFT：保留工具名和参数的普通 completion loss，同时把闭合后的
   `<|im_end|>` 权重提高到 16。
3. 从 Stage35 已审计的单动作训练回放打包 240 条样本：
   - `abort`、`ask_user`、`propose_tradeoff`、`search_pois` 各 60 条；
   - train/validation/test = 192/24/24；
   - 240 个唯一模型可见 payload；
   - 跨 split 场景重叠 0；
   - 与冻结 150 条难例重叠 0。
4. 先做 20-step smoke，生成门禁通过后，再从 Stage32 SFT adapter 固定训练 2 epoch，
   产出正式 adapter。

## 真实生成门禁

### 固定重复调用难例

- smoke：5/5 成功
- formal：5/5 成功
- 单次完成长度：从 Stage32 SFT 的 76 token 降为 39 token
- 输出：一次 `abort`，不再重复

### 冻结 150 条难例

| 指标 | Stage32 SFT | Stage36 正式模型 |
|---|---:|---:|
| 原始标签正确 | 148/150 | 149/150 |
| 生产契约正确 | 149/150 | 150/150 |
| 多动作输出 | 1 | 0 |
| HTTP 错误 | 0 | 0 |

四类动作的生产契约结果全部通过：abort 30/30、ask_user 35/35、
propose_tradeoff 40/40、search_pois 45/45。

唯一原始标签失败是已知冲突 `ext-v1-stage29-ds-002`：冻结标签要求 `abort`，但当前控制器
只允许 `ask_user`。模型执行了 `ask_user`，因此生产契约口径为成功。

## 决策

Stage36 正式模型通过晋级门禁，已通过独立 overlay 应用到本地 5% Shadow 灰度，不直接全量发布。
部署后 backend 为 healthy，Shadow worker 已连接 Redis 并进入 ready；实际注入的 student model 和
deployment ID 均为 Stage36。Stage33 历史配置保持不变。下一阶段需要观察真实流量中的单调用率、
契约成功率、教师升级率、超时率和回退率，再决定是否提高暴露比例。
