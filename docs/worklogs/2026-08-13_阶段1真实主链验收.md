# 2026-08-13 工作日志：阶段 1 真实 API 主链验收（第一步）

## 本步目标

在不切换 Agent Policy、不调整模型参数的前提下，先验证当前 DeepSeek API + LangGraph 主链是否能从真实前端完成一条行程，并建立不会随日期过期的自动验收基线。

- 启动方式：`docker compose up -d --build`
- 服务：PostgreSQL、Redis、VRP Solver、Backend、Frontend、Gateway、Celery Worker、Celery Beat
- LLM：项目 `.env` 中配置的 DeepSeek OpenAI-compatible API
- Policy 模式：未显式设置，使用默认 `shadow`

- 预订：明确为 mock/sandbox 数据，不代表真实下单

## 发现的问题与根因

### 1. 旧冒烟输入已经失效

原脚本写死“3 月 15 日到 3 月 18 日”，运行时已经是 2026-08，且“15 日到 18 日”和“玩 3 天”互相矛盾，同时缺少出发地、人数、老人/儿童信息。系统正确进入澄清，但旧脚本把“没有 `job_created`”误判为系统故障。

处理：完整场景改为动态生成 30 天后的未来日期，并一次给齐八类必填槽位；另保留独立的不完整需求场景，明确断言必须进入澄清。

### 2. 冒烟脚本仍按旧异步 Job 协议验收

当前浏览器主链直接运行持久化 LangGraph：先生成草案，在 `confirm_gate` 暂停；用户确认后从同一 checkpoint 恢复并完成。旧脚本只等待 `job_created -> planning job completed`，因此把实际已经生成草案的链路报成失败。

处理：冒烟测试现在同时识别两种运行模式：

- 交互式图：`draft -> awaiting_confirm -> confirm -> final -> done`
- 队列式任务：`job_created -> planning job completed`

这不是降低断言，而是让测试匹配真实状态机。

### 3. 确认成功后，前端没有形成“当前行程”

后端确认成功并返回最终行程后，前端只更新 `itinerary`，从未调用 `confirmCurrentItinerary()`。因此聊天中已经有最终方案，但侧栏仍显示“暂无行程”；点击“当前行程”只会弹出原生 alert，历史行程、行程页和导出入口与主链割裂。

处理：把“提交行程”放在服务端最终成功事件的消费端执行，而不是用户点击确认按钮时乐观保存。只有收到最终 `message` / `final` / `completed` 后才写入 `trips`，后端失败时不会留下假行程。

### 4. 日期范围没有形成前端领域字段

后端返回 `travel_dates=2026-10-10|2026-10-12`，前端保存了原字符串，却没有设置 `startDate/endDate`。而最近行程排序、状态计算和去重都依赖这两个字段。

处理：在服务端 profile 转换边界统一提取 ISO 日期，保留原始 `travel_dates` 展示值，同时生成 `startDate/endDate` 供领域逻辑使用。

### 5. 行程页预算显示为全 0

某些最终事件没有结构化 `budget_breakdown`，旧前端便给已确认行程写入全 0 预算。实际页面出现“当日花费 ¥171”，右侧却显示预算总额 ¥0、已使用 ¥0。

处理：预算来源采用明确优先级：后端结构化预算优先；缺失时用各日 `total_cost` 汇总支出；总预算来自已确认的用户需求，并据此计算余额和是否超支。

## 架构判断

当前 API 主链不是 Celery Job 流程，而是“持久化 LangGraph + human-in-the-loop confirm interrupt”。Celery planning job 仍是兼容执行路径。测试必须覆盖产品实际状态机，同时保留对队列执行器的兼容，而不能强迫业务回退到旧测试模型。

确认动作目前还会再次执行一次较长的行程文案生成，真实测得约 9 秒。这会造成重复 token 和等待时间，已列入阶段 4 性能根因清单；当前步骤不混入性能改造。

后端生产镜像还包含 OCR、三套 OpenCV、Pandas 等重依赖，首次构建耗时和镜像体积偏大。它属于部署架构债务，将在主链功能稳定后单独拆分，不在本步用临时依赖删除冒险处理。
