# 阶段 4：真实 Shadow 双跑与成对评测

日期：2026-08-13

## 阶段目标

把原来仅设置 `policy_mode=shadow`、实际仍只走确定性工作流的伪 Shadow，改造成真实且可审计的双轨执行：用户结果继续由稳定工作流负责，Agent 使用隔离输入在后台独立运行，两者以同一个场景 ID 形成评测对。

## 完成的架构

1. `profile_recall` 在 Shadow 模式下生成一次稳定的 `trajectory_id/scenario_id`。
2. 只投影规划所需字段到 Agent 副本，排除 `session_id`、`job_id`、消息历史、输出推流、确认、预订和记忆写回字段。
3. 投影执行 PII 脱敏和 JSON round-trip，避免把活动连接、客户端或不可序列化对象送入后台。
4. Agent 副本通过 Celery `shadow` 独立队列执行，用户主链不等待副本。
5. PostgreSQL `agentic_evaluation_records` 按 `(scenario_id, mode)` 唯一约束持久化两侧指标和 Agent episode。
6. 使用 pending -> running -> completed/failed 状态机和原子 claim，Celery 重投不会重复执行同一轨迹。
7. 确定性侧在首次生成可确认草稿时记录指标；确认、修改等后续轮次不会覆盖原始样本。
8. 管理员评测接口只读取完整成对数据，使用确定性硬门禁计算是否允许 Agent 晋级。

## 真实测试暴露并解决的问题

### 1. Celery 子进程未初始化 Redis

现象：天气和 POI 详情工具全部返回 `Redis client not connected`，Agent 提前失败。

根因：规划任务会显式调用 worker Redis 初始化，而新 Shadow task 没复用同一生命周期入口。

解决：Shadow task 在访问工具栈前调用统一 `_ensure_redis()`；仍保留任务级失败隔离。

### 2. 失败轨迹被丢弃

现象：Agent 到达 `unsolvable_constraints` 后，集成层只返回 fallback patch，没有 `agent_episode`，失败案例无法进入评测、SFT 清洗或 GRPO 分析。

解决：所有已进入 bounded loop 的终态，包括求解/校验失败，都保留带完整性哈希的 replayable episode；评测将其记为低质量样本，而不是基础设施错误。

### 3. 午餐与晚餐被误判为连续就餐

现象：列表中午餐、晚餐之间没有显式景点，即使相隔四小时也被判硬违规。

根因：规则只比较相邻 category，没有比较时间。

解决：改成按时间判断，仅重叠或间隔不足 60 分钟的餐饮块视为异常。新增求解器/校验器联合回归测试。

### 4. 高德嵌套类型错误分类

现象：`餐饮服务;中餐厅` 等细分类型没有被精确字典命中，默认落成 attraction，或反向导致供给集中在餐饮。

解决：分类器支持父类/细分类包含匹配；求解前加入“验证候选集中必须存在景点”的不变量，拒绝污染事实进入求解器。

### 5. 中英文城市名进入不同事实源

现象：`Shanghai` 查不到只以 `上海` 建库的内置与 PostgreSQL POI，过度依赖外部 API。

解决：新增共享城市规范化模块，统一 English alias、中文“市”后缀和规范名称；ToolExecutor 与 POI fallback 共用。

### 6. Shadow 评测不能影响用户结果

处理：持久化、入队和评测记录均 fail-open；异常只记录日志/Shadow 状态，不改变确定性路由或输出。
