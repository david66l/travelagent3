# 2026-08-29 ReAct 可验证规划架构改造

## 本轮目标

把生产主链从“模型沿固定任务 DAG 逐项执行”改为“意图识别与按需补槽 → ReAct 动态取证 → 证据门禁 → CP-SAT 排程 → Verifier 硬校验 → 用户确认/带原因修改”，并在该链路验收前暂停新一轮后训练。

## 已完成

- 新增 `ReactTaskGraphPlanner`：任务图只保留研究、求解、验证、审查、成稿和确认等阶段边界；`research_evidence` 内的工具顺序由模型根据 Observation 动态决定。
- 新增 `ResearchSufficiencyVerifier`：按意图检查城市知识、可排程 POI、POI 详情、路线矩阵，以及按需天气、活动、交通和时效信息；检查查询时间、网页来源、矩阵维度和演出场馆坐标。
- Controller 每轮把当前意图仍缺的 Evidence 映射成动态动作子集。存在多个缺口时由模型决定先补哪个；只剩一个确定缺口时由 Controller 直接执行，避免模型在唯一答案上浪费 Token。这一动作空间由实时 Evidence 计算，不是预写的固定工具顺序。
- 新增城市知识、统一时效搜索和交通工具契约与执行器；稳定事实优先本地知识库，实时事实才访问外部搜索。演唱会、展览、比赛、节庆等统一使用 `search_current_info(info_type=event)`，不为活动品类新增独立工具；搜索结果再结构化为日期、时间、场馆、来源和坐标证据。
- 模型只能提出 `finalize_research`；是否真的研究充分由程序判定，失败码作为下一轮 Observation 返回模型。
- 演出/预约被转换为 CP-SAT 的固定日期和时间窗；Validator 再校验日期、开始时间和结束时间，防止求解器或润色层移动固定活动。
- 用户拒绝无原因时追问具体问题；给出原因后保留同一 `trajectory_id`，递增 `goal_version/plan_version` 并重开受影响子图。
- `react` 生产模式采用 Controller-owned gates：LLM 只负责有选择空间的研究和修复，唯一的 CP-SAT、验证、成稿和确认动作不再浪费模型调用。
- 补齐意图链路断点：`DemandParser` 的结构化模型输出新增活动类型、活动查询、城际交通方式和实时事实需求；`GoalLedger`、研究证据门禁和搜索参数直接使用这些字段，移除 ReAct 主路径的关键词二次分类。
- 用户自然语言修改改为模型输出 `RevisionOperation(set/add/remove/clear)`；Controller 对字段白名单、数值范围、布尔值和枚举做校验后才写入新版本。模型不可用时只保留反馈，不再用正则猜天数、预算或节奏。
- 缓存锁降级：Redis 缓存不可用时核心工具仍可执行，缓存不再成为规划硬依赖。
- 实时 Evidence 保存来源、置信度和 fallback 标记；估算天气等 fallback 不得满足实时证据门禁。修复 Open-Meteo 同时发送日期范围和 `forecast_days` 的冲突参数，以及小数风速与整数模型的类型冲突。
- 打通搜索证据到排程的约束适配：活动继续形成固定预约；候选 POI 的官方营业/闭馆结果形成 `date_opening_hours/closed_dates`；高铁/航班搜索抽取来源可追溯的往返班次，进城到达时间加 60 分钟接驳缓冲后限制首日开始，返程出发时间减 90 分钟候车/值机缓冲后限制末日结束。CP-SAT 和 Validator 共用这些字段，无法形成约束的链接会被 Evidence Verifier 拒绝。
- 新增可重复的真实 checkpoint smoke 脚本，并在执行前校验端点实际提供的模型，防止 SSH 隧道串到其他本地服务污染结果。

## 真实模型证据

使用云端原始 `Qwen3-4B` 作为策略模型，本地执行真实知识、POI、路线矩阵、求解和验证链路。普通上海两日游得到：

- 5 次真实策略决策：`retrieve_city_knowledge → search_pois → get_poi_detail → get_route_matrix → finalize_research`；
- 研究、Solver、Validator、审查、成稿均成功，最终停在等待用户确认；随后审计发现旧 `auto` 策略在两日小实例中实际选择贪心，因此该次 smoke 只证明 Solver/Verifier 全链可达，不能作为 CP-SAT 参与证据；
- 1 次求解，13 次工具调用（含批量 POI 详情），总计 10 个 Agent step；
- 模型累计 11,015 Token，记录的端到端 Agent latency 为 7,809 ms；
- 无工具失败、无策略重试、无 Verifier 硬违规。

这是一条真实 smoke 轨迹，不作为总体准确率或正式性能结论。新 ReAct 主链随后已改为默认强制 `strategy=cpsat`，必须以修复后的复测结果作为 CP-SAT 全链证据。

修复后使用同一 `Qwen3-4B` 再次执行同一请求：动作序列和资源计数保持一致，`solver_status=optimal`、`validation_hard_pass=true`，端到端记录延迟为 9,674 ms，无失败记录。这一条才是“真实模型动态取证 + 真实 CP-SAT + 真实 Validator”的普通行程 smoke 证据。

近期户外天气场景最初暴露出 4B 会忽略 Verifier 缺口、调用非必需实时搜索，以及天气 API fallback 被误当作实时证据三个问题。完成动态动作收窄、来源门禁和天气适配修复后，同一场景最终按 `city knowledge → weather → POI → POI detail → route matrix → finalize` 完成取证，`solver_status=optimal`、`validation_hard_pass=true`，累计 7,397 Token、8,907 ms，无失败记录。普通场景与天气场景产生不同工具轨迹，证明研究段不是固定动作回放。

## 完整 Agent Loop 在线验收（full-agent-loop.v2）

- 新增 10 条冻结全链用例和可恢复评测脚本，覆盖普通行程、老人约束、天气、营业时间、餐厅、季节活动、城际高铁、周末活动、首次澄清，以及用户拒绝首版后的二次规划。
- 每条规划用例从原始自然语言开始，真实经过意图模型、ReAct 多轮工具决策、Evidence 门禁、CP-SAT、Verifier 和成稿；用户修改用例还要求 `goal_version/plan_version` 同时递增，修改后再次求解并硬通过。
- 修复 ReAct 在研究证据已齐时继续重复检索的问题：Controller 现在直接关闭研究阶段；真实普通场景由 7 次策略调用、19,559 Token 降至 3 次策略调用、5,786 Agent Token，预检延迟由 15.1 秒降至 7.89 秒。
- 修复外部工具失败后耗尽整段预算的问题：每种研究动作最多尝试两次，仍无可靠来源时只允许模型向用户提出降级方案；不再用 14 次全局重试烧掉两三万 Token。
- Tavily 当前返回 432，DuckDuckGo 在本机网络不可用。新增中文查询优先的 360 Search 无密钥降级通道，并把搜索超时收紧；同一营业时间查询由约 26.8 秒降至约 1.39 秒。实时来源仍必须带 URL，fallback 不得绕过 Evidence Verifier。
- 本地城市知识库未覆盖某城市时现在记录 `availability=not_indexed`，表示“查询成功但无覆盖”，随后允许 AMap/POI 工具继续取证；不再把知识库空结果误当成整个规划系统宕机。
- 修复显式高铁需求漏问出发地的问题：条件必填规则要求 `origin`，且在不完整收集轮增加一次模型语义复核；该复核不使用关键词分类，完整普通请求也不会多付第二次调用成本。
- 修复 CP-SAT 状态误报：内部 `UNKNOWN` 后走 greedy 时，对外状态明确为 `fallback` 并记录 `cpsat_status`，不能再把降级结果写成 `optimal`。
- 最终在线报告 `artifacts/full-agent-loop-v2/formal-10-final-measured.json`：10/10 场景按各自安全契约通过；5 个稳定草案场景 Verifier 硬通过率 100%，CP-SAT 真成功 4/5（80%），另 1/5 为明确记录的 greedy fallback；用户修改场景首版与修改版均硬通过；3 个外部事实无法充分确认的场景安全停在 `awaiting_information`，没有编造车次、餐厅营业或活动场馆；澄清场景一次问齐出发地和天数。
- 最终计量包含意图模型 Token，不再把异步解析上下文误报为 0：10 条总计 107,473 Token，平均 10,747.3 Token/条；平均端到端延迟 11.04 秒，p95 16.19 秒。稳定草案场景平均 3.6 次策略调用、13.6 次工具调用。
- 回归验证：本轮相关 Agent、意图、工具、搜索、评测与 Solver 单元测试共 `607 passed`；本轮文件 Ruff 通过。仍有 3 条既有依赖弃用/asyncpg 清理 warning，不影响测试通过。

## 完整 Agent Loop 扩展困难集（full-agent-loop.v3）

- 修复意图结构化 schema 与提示词，避免默认值覆盖用户显式约束；补齐 Memory Conflict Resolver 的字段保留；把无障碍、禁去、最长步行、忌口等投影为硬约束，把疲劳与避开拥挤投影为软偏好。
- 搜索阶段将必去地点加入查询词，并在有限的 POI 详情预算前优先保留必去候选；禁去地点在候选入库前过滤，同时在 Solver 和 Verifier 再做防御性校验。新增 `MUST_NOT_VISIT_PRESENT` 硬违规，避免模型成稿时把用户明确排除的地点加回来。
- 对预算不足或客观事实无法证实时，不再盲目生成行程，也不把安全降级误判为失败：系统必须给出基于能力检查或 Verifier 结果的取舍方案，且不能输出未经验证的行程。

## 云端训练模型接入新 ReAct 全链路

## 新 ReAct 故障恢复配对评测

- 新增 full-agent-loop-recovery.v1：从原始用户请求开始，在第一次 search_pois 时注入一次可恢复故障，随后恢复真实 POI 工具、CP-SAT 和 Verifier。8 个冻结案例覆盖 change_arguments/retry_same_arguments × explicit_instruction/diagnostic_evidence 四个语义分层。
- 每条轨迹同时要求：故障确实注入；下一模型回合直接采取正确恢复；不依赖 Self-Repair 二次纠错；恢复后完整规划通过原安全契约。QUERY_TOO_BROAD 接受“历史文化”与 ["历史","文化"] 这类检索等价分词，但 TOOL_TIMEOUT 必须完整复用原参数。
- OpenAI-compatible vLLM 请求增加固定 seed，按 sha256(case_id, sample_index) 为 SFT/GRPO 生成 checkpoint 无关的成对随机种子。比较报告检查 benchmark hash、温度、group size、seed 协议和意图结果一致性，并输出 McNemar 精确检验及按任务聚类 bootstrap 区间。
- 8 条预检结果：SFT 与 GRPO 都是 6/8；两者只在诊断式改参场景失败。
- 扩大为 8 个案例 × 4 个种子，共 32 对完整轨迹后，SFT 与 GRPO 仍均为 24/32 = 75%；共同成功 24、共同失败 8、任一模型单独成功 0，绝对增益 0pp，McNemar p=1.0，意图不一致 0。两者的三类简单分层均为 100%，change_arguments/diagnostic_evidence 均为 0%。
- 失败簇表明两模型都能从诊断证据得到正确窄查询，但 SFT/GRPO 的原始首答仍先重复宽参数，再由 SelfRepairingAgentPolicy 根据 REPEATED_NO_PROGRESS_ACTION 纠正；因此完整链路通常能继续，但不能把修复器功劳记成 RL 首答能力。另有少量轨迹在恢复动作前耗尽任务尝试。
- 根因是训练/服务协议错位：Stage3 SFT/GRPO 的模型可见状态为 task_id=search_candidates 且 allowed_actions=["search_pois"]；新 ReAct 服务状态为 task_id=research_evidence，并曾同时暴露多个研究与终止动作。旧独立盲测证明的 +5.47pp 不能直接迁移为新 ReAct 全链路增益。
- 新增一次性、时序有效的搜索恢复动作掩码：仅当“最近一次决策就是失败的 search_pois”、错误可重试且预算尚存时，下一回合移除不能修复该失败的工具；一旦搜索成功，历史故障不再继续触发掩码。该改动保留模型对恢复参数的决策权，并修复了首次实现因历史 failure 长期驻留而重复搜索的状态污染问题。
- 对最难的 2 个诊断案例 × 4 种子重新配对后，动作掩码没有恢复旧 GRPO 增益：SFT/GRPO 仍均为 0/8 首答恢复。说明剩余主要问题不是动作空间宽度，而是 Stage3 数据中的旧任务语义和新 ReAct 生产上下文本身未对齐。

结论：当前可以严谨保留“Stage3 独立恢复子策略盲测由 86.72% 提升至 92.19%”的既有 RL 结果，但不能声称该增益已经迁移到新 ReAct 全链路。下一训练阶段必须从 research_evidence 的真实生产 PolicyContext 采集/生成数据，在相同工具 schema、failure summary、decision history 和 Controller 掩码下进行 Stage4 SFT warm-up 与 GRPO；最终仍用本冻结全链路集验收，禁止继续用旧 search_candidates 指标代替。
