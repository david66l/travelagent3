# 阶段 5：性能预算与全链路回归

日期：2026-08-13

## 目标

把“感觉快不快”变成可量化、可回归的阶段预算，同时确认优化没有破坏真实 API、SSE、确认和保存链路。

## 完成内容

1. Agent episode 的每一步新增 `policy_latency_ms` 与 `action_latency_ms`，指标随轨迹持久化，不依赖临时日志。
2. 新增确定性性能门禁：总时延、单次策略调用、最慢工具批次、求解器时延和策略调用次数。
3. 默认草稿性能预算：总时延 10 秒、策略调用 3 秒、工具批次 5 秒、求解 3 秒、最多 1 次策略 LLM。
4. Benchmark 输出逐阶段耗时和性能门禁结果，方便本地/API/本地模型使用同一口径比较。
5. 城市别名归一化后，英文 `Shanghai` 会复用 `上海` 的 PostgreSQL/内置事实源，减少无意义外部检索和失败重试。
6. 保留 Controller-first：天气、详情、矩阵、求解、校验、文案组装和确认不调用策略模型；只有候选搜索策略由 LLM 决定。

## 实测拆分

代表性 Agent 草稿：5.27 秒，硬约束通过。

- 唯一策略 LLM：约 1061ms。
- 天气与候选搜索并行批次：约 1386ms。
- POI 详情与路线矩阵并行批次：约 124ms。
- 求解：约 978ms。
- 校验：约 5ms。
- 其余 Controller 状态转换：接近 0ms。

连续三次同场景 Agent 草稿实测为 3.63s、5.47s、6.20s，均生成有效草稿并停在等待确认。

## 完整 App 回归

Playwright 单 worker 顺序执行三类浏览器测试：

1. 新建对话并发隔离：消息只发往新会话一次。
2. 主输入/发送链路。
3. 真实 API + SSE 生成三日行程、人工确认、深度补全、保存当前行程和预算展示。

结果：3 项全部通过，总耗时 26.8 秒；真实完整场景单测 26.9 秒。

## 结论

当前草稿阶段已经从早期约 15 秒的需求理解和多次 LLM 串行调用，收敛为一次约 1 秒策略调用加可并行工具链；完整含确认、补全、保存的 App 链路保持约 27 秒。性能指标已进入轨迹和自动门禁，后续切换本地模型时可以直接比较，而不需要靠主观体验判断。
