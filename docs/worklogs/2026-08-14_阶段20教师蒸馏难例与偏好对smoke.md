# 阶段 20：教师蒸馏难例与偏好对 smoke

日期：2026-08-14

状态：已完成。最终保留 5340 条按当前门禁复验成功的教师轨迹、2726 条输入唯一的 SFT 样本和 1724 对 verifier-grounded 强偏好数据，核心动作家族均已覆盖。

## 1. 本轮目标

建立 Qwen3-8B 教师多候选生成、确定性验证、最优轨迹选择和偏好对导出的完整闭环。教师身份本身不作为正确标签，所有候选必须经过 Agent 环境、Replay、Reward、硬约束和数据泄漏门禁。

## 2. 新增数据契约

新增 `teacher-distillation.v1`：

- 保存每个教师候选的完整可回放 `EnvironmentRollout`；
- 显式记录 success、hard pass、Reward、Policy 步数、工具次数、completion Token、重复调用、非法动作和请求延迟；
- 排序优先级为：验证成功 → 硬约束通过 → 无非法/重复动作 → 更少 Policy 步数、工具调用和 Token → 更高 Reward；
- 墙钟延迟只作审计，不作为偏好训练标签；
- 偏好对只从“模型可见上下文和工具 Schema 完全相同，但响应不同”的步骤中提取；
- 只有存在验证成功、硬约束、步骤、工具、Token 或 Reward 的可解释差异时才保留 pair；
- 原始候选全部保留用于审计，训练偏好载荷按 `pair_id` 去重。

生成脚本 `generate_teacher_distillation.py` 同时导出原始候选、chosen episode、selection 摘要、失败组、偏好对和经现有 `SFTDatasetBuilder` 清洗后的训练分片，并检查冻结 holdout 的 task ID 与模型输入哈希重叠。

## 3. 普通 curriculum smoke

### 4 个任务 × 4 候选

- 4 个核心家族各 1 个任务；
- 16 / 16 候选通过；
- 4 / 4 chosen episode 被 SFT 清洗器接受；
- 6 / 6 模型输入唯一；
- 冻结 holdout task/payload overlap 均为 0；
- 3 个原始偏好候选去重后保留 2 对。

两对均来自澄清场景，chosen 和 rejected 都正确，但 chosen 更短。例如：

- chosen：`您的预算是850元吗？`
- rejected：`您提到的预算范围是850元，是否需要进一步确认这个预算范围？`

这类 pair 可以用于长度偏好优化，但 Reward margin 为 0，不能冒充能力差异。

### 16 个新任务 × 4 候选

- clarification / recovery / search / tradeoff 各 4 个任务；
- 64 / 64 候选通过，16 / 16 chosen episode 接受；
- 22 / 22 模型输入唯一；
- 14 个原始偏好候选去重后保留 6 对；
- 冻结 holdout overlap 为 0。

结论：普通 curriculum 对 8B 教师过于容易，只适合作为能力 replay 和长度偏好来源，不能作为阶段 20 主训练分布。

## 4. L3 自适应恢复 smoke

从 official train/validation 派生 `travel-adaptive-recovery.v1`：首轮宽泛搜索确定性返回 `QUERY_TOO_BROAD`，错误反馈只点名一个来自用户偏好的合法关键词，第二轮响应要求模型精确使用该关键词重试。

- 派生 train 128、validation 32，task ID overlap 为 0；
- 教师 smoke 使用 16 个 train 任务，每任务 4 候选；
- 64 / 64 候选成功，16 / 16 chosen episode 接受；
- 16 / 16 导出的 SFT 模型输入唯一；
- 首轮 16 个失败动作全部被 SFT 清洗器排除，只保留 16 个验证成功的恢复动作；
- 四次教师采样动作一致，因此偏好对为 0，没有为了凑数量制造虚假 DPO 数据；
- 冻结 holdout overlap 为 0。

## 5. 当前判断与下一步

数据生成闭环已经通过真实 vLLM 教师服务验证，但阶段 20 尚未完成。下一步必须：

1. 扩展搜索参数错误、重复搜索、过早 finish、多约束 tradeoff 和长链路失忆等难例族；

## 12. 不可行请求奖励漏洞与真实 tradeoff 覆盖

正式审计发现旧奖励存在语义漏洞：任务 capability 已是 `infeasible`，模型仍可选择 `capability_check` 并继续生成一个通过行程硬约束的计划，旧 Reward 会把它判成成功。修复后增加 `capability_termination_mismatch` 硬门禁：`infeasible`、`unsafe` 或 `missing_tool` 请求若没有以安全终止结束，一律 `task_failed`，不能被后续行程验证分抵消。

该修复反向审计旧正式教师数据时，准确拒绝了原来 379 条没有执行 `propose_tradeoff` 的伪 tradeoff 轨迹，旧数据不再进入最终 SFT。

新增 `travel-tradeoff-decision.v1` 专用环境与策略提示：当 capability 不可行时不得继续规划；有可执行替代项时调用 `propose_tradeoff`，否则 `abort`。正式结果：

- 专用 tradeoff 任务 379；
- Qwen3-8B 教师 379 / 379 成功执行 `propose_tradeoff`；
- 对照策略 379 / 379 故意错误执行 `capability_check` 并继续规划；
- 379 / 379 对照 rollout 被新的 capability 终止门禁判失败；
- 原始 tradeoff 偏好 379 对；
- 删除 139 个精确重复上下文，隔离 52 个同上下文不同教师回答的冲突组、172 条冲突 pair；
- 最终保留 68 对输入唯一、标签唯一的 tradeoff 强偏好，holdout overlap 为 0。

教师生成器同时补上失败组门禁：只要存在没有 verifier-success 候选的 task group，manifest 现在必须为 `rejected`，不能再出现 failed group 大于 0 但总状态仍为 passed。
