# 阶段 24：统一后训练消融与最终评估

## 本阶段目标

把此前分散在不同 schema、不同运行时和不同训练阶段中的实验结果，整理成一份可复现、可审计、不过度包装的总报告。报告同时覆盖：

- Qwen3-4B Base；
- 8B 教师蒸馏后的 Qwen3-4B SFT；
- Qwen3-4B SFT + DPO；
- DPO adapter 的静态合并与校准；
- Qwen3-8B 教师；
- 4B 学生 / 8B 教师路由；
- 前一代 Qwen2.5-3B 的真实多轮 GRPO-B0 证据。

## 统一口径

原始实验存在三种不同含义的指标，不能混成一张表后直接比较：

1. 严格单步工具决策：测动作和参数是否正确，延迟只包含模型 HTTP 请求；
2. 完整多轮轨迹：测冻结任务在真实 Agent Loop 中是否完成，延迟是每条轨迹内模型请求延迟之和；
3. 学生/教师路由回放：在不能让 4B 和 8B 同时常驻 24GB GPU 的条件下，分别实测后按固定路由规则做顺序合成。

新增 `scripts/build_stage24_final_report.py` 负责读取这些不同 schema，验证任务集合、聚合指标，并为每个源文件记录 SHA-256。最终生成：

- `ml/agentic/reports/stage24-final-evaluation-v1/report.json`；
- `ml/agentic/reports/stage24-final-evaluation-v1/REPORT.md`。

## 最终结果

### Qwen3 最终部署候选

最终方案为：Qwen3-4B SFT+DPO 静态学生模型负责澄清、搜索和恢复；Qwen3-8B 教师负责复杂权衡；动作空间按状态收紧，学生异常时只升级一次教师。

| 指标 | 结果 |
|---|---:|
| 严格工具决策 | 516 / 516 |
| 完整多轮任务 | 172 / 172 |
| 平均轨迹 Reward | 0.965842 |
| 8B 教师任务占比 | 2.33% |
| 相比全量 8B 的生成 Token | -28.52% |
| 相比全量 8B 的模型请求延迟 | -47.87% |

这里的路由延迟来自顺序模型回放，不是同一张 4090 上双模型同时常驻的在线结果。该边界已经写入 JSON 和 Markdown 报告。

### 蒸馏 SFT 与 DPO

- SFT：1202 条序列通过训练前预检；train loss 0.116687；eval loss 0.034903；训练 382.53 秒。
- DPO：1011 个唯一偏好对，train / validation / test 为 667 / 172 / 172；train loss 0.074456；eval loss 0.127135；eval preference accuracy 100%；训练 631.88 秒。
- 在完全相同的 172 个模型输入和 chosen/rejected 对上，SFT 与 DPO 的 preference accuracy 都是 100%，但平均 log-prob margin 从 0.672975 增加到 0.825050，提升 22.60%。
- 这说明 DPO 的可辨识收益是偏好置信间隔，而不是在已经饱和的小测试集上虚构准确率增长。

### GRPO 能力证据

项目此前已在 Qwen2.5-3B 上完成生产状态机对齐的多轮 trajectory-level GRPO-B0，并保留固定配对结果：

| 模型 | 32 题 × 4 rollout 成功率 | 平均 Reward |
|---|---:|---:|
| Base 3B | 60.16% | 0.2301 |
| SFT 3B | 80.47% | 0.5934 |
| SFT+GRPO 3B | 82.81% | 0.6373 |

GRPO 相比同协议 SFT 提升 2.34 个百分点。该结果证明项目具有真实环境 rollout、分层 Reward、非零方差任务选择、训练和 checkpoint 晋升门能力；但它是 B0 工程基线，不宣称解决了逐轮信用分配，也不与后续 Qwen3 结果跨协议排名。

## 推理消融

### 静态 LoRA 合并

- 1.25× validation：165 / 172；
- 1.50× validation：172 / 172；
- 只依据 validation 选择 1.50×，再在冻结 test 上评估，避免用 test 调参。

### Prefix cache

- eager 平均延迟：335.841 ms；
- prefix cache 平均延迟：348.835 ms；
- 变化：+3.87%，本 workload 下拒绝启用。

虽然服务端记录到较高的共享前缀命中率，但短输出和当前调度开销没有转化成端到端收益。因此没有按“理论上应该更快”强行保留配置。

### CUDA Graph

- eager 平均 / P95：335.841 / 493.369 ms；
- 预热后 CUDA Graph 平均 / P95：310.596 / 445.456 ms；
- 平均延迟 -7.52%，P95 -9.71%，吞吐 +8.10%；
- 结论：常驻服务预热后启用，冷启动和显存开销单独计算。

### 并发

| 并发 | 吞吐 | 平均延迟 | P95 |
|---:|---:|---:|---:|
| 4 | 12.835 req/s | 310.596 ms | 445.456 ms |
| 8 | 22.904 req/s | 346.846 ms | 503.874 ms |
| 16 | 38.716 req/s | 398.403 ms | 572.700 ms |

在线默认建议并发 8，吞吐约为并发 4 的 1.78 倍，同时尾延迟仍比并发 16 更可控。批处理离线任务可以使用并发 16。

## 文献核对

- [QLoRA](https://arxiv.org/abs/2305.14314) 支持本项目采用 NF4、double quantization 和 LoRA 在单卡上完成参数高效后训练的技术选择。
- [Direct Preference Optimization](https://arxiv.org/abs/2305.18290) 支持在 SFT 后直接用 chosen/rejected 优化策略而不单独训练 Reward Model 的路线。
- [RouteLLM](https://arxiv.org/abs/2406.18665) 证明强弱模型路由可以用于质量与成本折中。本项目当前采用可审计的确定性任务族路由，而不是把它包装成 learned router。
- [vLLM engine arguments](https://docs.vllm.ai/en/v0.10.0/configuration/engine_args.html) 明确 `enforce-eager` 会禁用 CUDA Graph；本项目通过预热后 A/B 实测决定常驻配置。

论文只用于校验方法选择，所有具体提升数字均来自 TravelAgent 自己的冻结任务和真实服务压测，没有外推论文结果。
