# TravelAgent2：Agent Loop + Harness 架构说明

版本：agent-harness-v1，执行修订 evidence-progress-retry-v9，2026-09-05。架构重构验证见《架构重构交付报告》；证据/预算修复见《Harness 修复与基模复测报告》；终止契约修复见 `TERMINAL_CONTRACT_FIX_20260905.md`。

v7/v8 重试恢复记录见 `HARNESS_RETRY_COMPARE_20260905.md`。v9 在完整 ledger 上重新检查历史失败动作的当前前置条件：条件已满足时允许模型再次提出该动作；不选动作、不调用工具、不改写失败历史。内部判定不进入模型提示或训练上下文。不同实体的证据不能互相替代。最新云端验证及学生纠错数据见 `STUDENT_CORRECTION_REPORT_20260905.md`。

## 1. 先用一句话理解

**模型决定下一步做什么；harness 负责让这一步可靠地执行，并把结果交回模型。**

例如：用户要从济南去上海玩两天，其中一天看演出。模型可以先查演出，也可以先查交通；发现时间冲突后，可以调整搜索、重新求解、询问用户或停止。系统不再预先安排“查完 A 自动做 B”。

代码仍需要负责参数、状态、预算、工具、证据和确认。把这些都交给模型，会使错误无法定位，也无法证明后训练学到了什么。

## 2. 现在只有这一条规划路径

```text
用户需求 / 用户补充 / 用户修改
              │
       输入理解与用户事实更新
              │
              ▼
      模型读取当前状态并选择一个动作 ◄────────────────┐
              │                                       │
              ▼                                       │
      Harness：权限、参数、预算与前置证据检查             │
              │                                       │
       执行工具或返回明确的拒绝原因                       │
              │                                       │
       记录结果、失败、证据版本与实际参数 ────────────────┘
              │
       模型选择 ask_user / propose_tradeoff → 等用户补充后继续
       模型选择 finish → 校验通过 → 展示草案 → 等用户确认
       模型选择 abort，或预算耗尽 → 停止并记录原因
```

`finish` 是模型提交草案，用户确认才是产品流程完成。提交未通过校验的草案会被拒绝，拒绝原因返回同一个模型。

外层 LangGraph 仅保留 `gathering → profile_recall → agent_loop` 与 `output / confirm_gate / booking` 等对话、存储、展示节点。它不再包含另一条规划工作流。用户修改、拒绝及旅途中的新情况都回到同一 agent loop。

## 3. 谁负责什么

| 问题 | 负责人 | 当前行为 |
|---|---|---|
| 先查什么、选哪个工具 | 模型 | 每轮选一个动作 |
| 查什么关键词、事件、日期和交通方式 | 模型 | 保留模型提出的语义参数；冲突时拒绝并反馈 |
| 结果不相关或工具失败，下一步怎么办 | 模型 | 可以换查询、继续研究、重新求解、追问或停止 |
| 什么时候求解、校验、提交 | 模型 | 不再自动推进阶段 |
| 城市、约束、候选实体等可信数据的传递 | Harness | 从用户事实和工具记录装配，同时记录来源 |
| 参数格式、调用额度、超时 | Harness | 明确拒绝或停止，不替模型选策略 |
| 证据过期、输入更新后旧校验是否失效 | Harness | 失效处理后，模型自己决定如何补齐 |
| 时间、预算、必去景点等硬约束 | 求解器与校验器 | 程序化计算；模型不能自报通过 |
| 当前事实能否证明任务不可行 | Harness 的证据校验 | 从明确闭馆日期和必付成本下界生成证据；不选择后续动作 |
| 改预算、取消必去项、确认草案 | 用户 | 系统保留权限边界和确认凭证 |

为了保留已有持久化协议，状态对象仍叫 `task_graph`，但里面只有一个 `travel_agent` 会话任务，没有阶段依赖。`TaskGraphController` 在这里仅维护 ready/running/blocked/succeeded 等生命周期，不安排工具策略。

## 4. 模型能用的动作

| 类别 | 动作 |
|---|---|
| 查资料与景点 | `retrieve_city_knowledge`、`search_pois`、`get_poi_detail` |
| 查实时信息 | `get_weather`、`search_current_info`、`search_transport` |
| 路线与行程 | `get_route_matrix`、`solve_itinerary`、`validate_itinerary` |
| 交互与结束 | `ask_user`、`propose_tradeoff`、`abort`、`finish` |

共 13 个动作。`propose_tradeoff` 受当前权限约束：只能展示已获准提出的折中选项，不允许借此自动修改用户约束。没有权限时仍可以通过 `ask_user` 询问用户。

`get_poi_detail`、矩阵和求解器接收的是系统保存的候选集合，模型选择调用时机；这些工具内部的数据装配不是另一个 planner。当前接口尚不提供任意逐个 POI 的编辑动作，这属于今后需要用失败案例判断是否扩展的工具能力。

不再要求先调用 RAG，也不再要求固定的候选数量。求解仍需要非空的候选、详情和可用矩阵，因为求解器实际消费这些数据。天气、演出、交通等证据按任务要求检查。

## 5. 一个完整例子

1. 模型看到“去上海看演出”，发现缺出发地，选择 `ask_user`。
2. 用户回答“济南”。输入理解结合模型刚才的问题提取出发地；无法可靠理解时保留原话，不把答案硬塞进第一个空字段。
3. 模型选择 `search_current_info` 查询演出。查到结果不匹配，它决定改关键词继续查。
4. 模型自己选择景点、详情、交通、矩阵等研究动作。此处顺序取决于任务和已有证据。
5. 模型选择 `solve_itinerary`。如果证据不足，系统返回缺口；如果求解失败，模型得到失败结果。
6. 模型决定继续搜索或换求解策略，然后选择 `validate_itinerary`。
7. 校验通过后，模型可以继续完善，也可以选择 `finish` 提交草案。
8. 用户修改行程后，目标版本更新，旧版本证据不能冒充新证据；仍由这个模型继续处理。

本次测试用可控工具结果验证了这些关键分支。这个例子不是新模型成绩，也不是已完成的线上旅行订单。

## 6. 在线、离线评测、训练如何共用

- 在线：`integration.py → BoundedAgentLoop → TravelActionExecutor`。
- 离线快照评测：相同 loop 和工具动作，工具响应来自冻结快照。
- TRL/GRPO：唯一 `TRLAgentEnvironment` 经交互适配器驱动相同 loop，每一步都等待模型，没有控制器自动跑完前几步。
- 同一份动作规范、状态投影、前置检查、执行器和轨迹格式。API 模型、本地 checkpoint、JSON 与 native tool calling 是模型接入方式，不是不同规划架构。
- 轨迹格式升级为 v4，区分 `model_arguments`、`executed_arguments` 与 `argument_sources`，可以检查“模型实际提出了什么，系统补了什么”。旧轨迹哈希仍可用于历史审计。
- GRPO 从原始用户任务开始；旧 `grpo_decision_state` 教师前缀语料明确拒绝。原来的单步专项环境不能继续参与当前基线。

当前训练 episode 到模型提问时会暂停/结束本轮，并不自动模拟用户替它补槽。因此完整多轮对话的评测需要显式的用户回复脚本，不能把“一次正确提问”当成整段旅行规划完成。

## 7. 删了什么，为什么

删除了旧 DAG/legacy 环境、ControllerFirstPolicy、specialist/student-teacher/challenger 决策包装、shadow 第二条执行路径、旧阶段动作、旧外层规划节点，以及仅依赖它们的数据生成器、启动脚本和专属测试。旧的 RAG 节点包装及幻觉检查节点包装也已移除；工具内的检索和硬约束校验保留。

旧阶段动作包括 `capability_check`、`accept_candidates`、`accept_itinerary`、`finalize_research`、`compose_draft`、`retry_solve`。重试通过模型再次选择 `solve_itinerary` 表达。

历史数据、权重、报告仍是实验资产，不属于可运行的第二套架构。本次没有删除它们。改动前的源码已备份在项目外；详细删除清单随交付报告提供。

## 8. 后面先做什么

先冻结这版架构，做 24 个开发诊断案例：六类能力各 4 个，覆盖工具选择、参数、证据判断、失败恢复、约束冲突、停止/追问。这是用来找问题的开发集。

让未经本轮新训练的小模型、现有候选模型和教师模型在同一环境跑这些任务。看完整轨迹后，再决定数据和训练。架构测试通过，只能证明框架按预期运行，不能证明小模型已经会做决策。


## 本次基模实测后的 harness 修订

- 模型能看到有上限的搜索正文、来源、开放时间、闭馆日期、票价和候选行程摘要；外部文字仍是不可信数据。
- 模型看到当前参考时间和剩余资源预算。前置拒绝消耗决策步数与模型 tokens；工具/求解额度在接受执行后扣除。
- 同类重复快照不会挤掉关键行程。相同有效内容保持成果；候选、详情或证据有效性改变时，相关求解/校验结果失效。
- 同一基模、同一 24 个开发任务中，有效行程提交 1/17 → 8/17。没有训练模型；没有引入固定工具编排。


## 终止契约补充（2026-09-05）

一次求解遗漏必去景点，只说明当前方案失败，不能证明任务无解。现在校验结果将“行程是否合格”与“事实能否证明不可行”分开：后者只有明确证据才标记 `infeasible`，否则是 `undetermined`。这不是一个新的规划流程。

拿到当前候选详情后，Harness 自动检查两种充分条件：必去场馆在全部旅行日期明确闭馆；必去项的已知门票合计下界已经超过硬预算。不使用推测的每周闭馆规律证明无解，也不把检索不到当成不存在。它生成包含日期、费用和证据 ID 的 `constraint_evidence`，不会调用求解器或替模型输出停止动作。

模型可以在这时选择 `abort` 并引用 `capability.evidence_ids`，也可以继续取证。停止前不再隐含要求走“矩阵 → 求解 → 校验”。若模型主动选择 `validate_itinerary`，没有行程但已有详情时可以检查约束事实；空行程仍不可能通过行程验收。

事实发生变化或证据过期后，旧引用不能授权停止。折中选项只能来自用户已声明的可放宽范围。证据引用核验支持停止的事实，不能自动证明回复里任意一句自然语言都正确；示范数据仍需要审核文字解释。

保留对历史轨迹的兼容判分，但新的运行使用 `travel-validator.v2`、`terminal-contract-v3`。两者是版本标识，不是第二套 Agent 架构。没有改变用户约束、代选下一工具或增加教师前缀控制器。


## 停止提案被拒绝后的恢复

`abort` 提案若证据引用缺失或无效，任务保持可继续，错误反馈给同一个模型；只有被接受的 `POLICY_ABORT` 才结束会话。Harness 不自动补齐引用。详见 `RESEARCH_DATA_PILOT_20260905.md`。
