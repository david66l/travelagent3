## 实测速度

- 本批 1,000 条净采集 **18.82 分钟**，平均 53.13 条/分钟；模型初始化 30.00 秒。只加载一份模型，16 路会话并发，任务内部按顺序调用工具。
- 相同 20 个先导场景、相同权重与提示契约、同一个 Transformers 4.57.6 环境：旧 Transformers batch4 净采集 150.17 秒，vLLM 并发16为 28.21 秒，实测 **5.32 倍**。含启动/加载/文件哈希的命令分别 180.86/76.07 秒，约 2.38 倍。
- 20 条对照两边均 19 条通过任务判据、14 条通过候选筛选、1 次原始参数错误；首轮输入 token 哈希全部相同，任务通过结果逐例一致。采样规模小，未证明所有轨迹逐 token 等价；5.32 倍是该对照的结果，不是对新 1,000 条做了双引擎完整重复实验。
- 优化来自已安装 vLLM 0.8.5.post1 的持续动态批处理、前缀缓存、分块预填充与共享 LoRA。使用现有原生模板生成 token ID，保留原参数校验和原始输出审计，超长请求拒绝截断。为了适配该旧版 vLLM，推理使用云端原有全局 Python/Transformers 4.57.6；没有修改或升级全局安装。
- 1,000 条实测峰值 allocated GPU 内存 20.48 GiB。vLLM 记录的是完成请求事件，**不把这些事件数当作实际 GPU batch 数**。

## 数据规模的实际含义

1,000 个唯一需求与上一批 100 条没有完全相同请求。它们来自 **20 个父模板、40 个基础/组合约束组，每组 25 个相关变体**，共享场馆类型目录。城市、日期变化不能增加独立结构组数量；这些数据不等于 1,000 个独立真实旅行任务。

本批改变了合成场馆票价与空间分布，并加入双必去项、门票合计超过预算、可选场馆闭馆、提前闭馆和故障与约束组合。provenance、父组及 train 标记均保留；未来拆分必须按父组和来源关系执行，不能随机按行拆分验证集或测试集。本次没有运行独立 dev/locked test。

具名餐厅实际入路线数仍为 0，午晚餐仍有通用占位；意图槽位预先填写，澄清任务在提问后结束。新增规模没有消除这些产品缺口，不能凭当前任务通过率宣称完整旅游规划能力已达标。
